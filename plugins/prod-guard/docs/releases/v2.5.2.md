Patch release, and the first cut from `karlkfi/claude-bouncer`: a production deny on a pinned target now tells you about the session-scoped override, and the friction report stops counting two things as one.

> [!IMPORTANT]
> **This plugin now ships from the `claude-bouncer` marketplace, and the old one stops at v2.5.1.** `karlkfi/claude-prod-guard` still serves 2.5.1 and will not move again, so an install pinned to `prod-guard@prod-guard` gets no further updates and no notice that it is behind. The two commands that move it are under [Upgrading](#upgrading). No config key changed name, default, or meaning, and no verdict moved — see [Decision surface](#decision-surface).

## Highlights

**[A pinned-target deny names the override that covers a whole batch](https://github.com/karlkfi/claude-bouncer/blob/prod-guard/v2.5.2/plugins/prod-guard/README.md#session-scoped-override).** `PROD_GUARD_SESSION_OVERRIDE` has existed since before the move, and the denials that it can actually lift were not mentioning it — so the way out of a ten-command production task was a per-command prefix typed ten times, and the one-off confirmation was discoverable only by reading the README. Denies on an explicitly pinned production target now offer both forms.

The two classes that do **not** gain it are the point of the change rather than an omission. An ambient-context deny and a shared-state switch are not session-grantable: the target is whatever the context says at the moment the command runs, so a confirmation given once cannot speak for a later command whose target has moved underneath it. Those denies still offer `PROD_GUARD_OVERRIDE` alone, and the table below shows both classes holding.

**The friction report counts the two overrides apart.** One line labelled `PROD_GUARD_OVERRIDE` was tallying both variables, so a per-command figure read high wherever session overrides were in use — and it read high in exactly the situation the session override exists to improve, which is the reading most likely to send you looking for friction that had already been dealt with. They are separate lines now.

**And it stops proposing patterns for things that are not targets.** An unresolved variable name — `$CTX`, `$CLUSTER` — was listed as a pattern-gap candidate, inviting a `nonprod` pattern that could never match it, because the text is a variable rather than the target it expands to. Those entries stay under "Top targets", where the friction they cause is still counted; they are simply no longer offered as something a pattern would fix.

## Decision surface

Measured by running the hook as it stood at the subtree boundary and the one shipping here as subprocesses over the same payloads, and diffing both the emitted `permissionDecision` and the reason text.

| command | 2.5.1 | 2.5.2 | reason names the session override |
|---|---|---|---|
| `kubectl delete ns app --context prod-cluster` | deny | deny | no → **yes** |
| `helm upgrade app --kube-context prod-cluster` | deny | deny | no → **yes** |
| `bash <<EOF` … `kubectl delete ns app --context prod-cluster` … `EOF` | deny | deny | no → **yes** |
| `cat <<EOF` … `$(kubectl delete ns app --context prod-cluster)` … `EOF` | deny | deny | no → **yes** |
| `kubectl delete ns app` *(ambient context)* | deny | deny | no |
| `kubectl config use-context prod-cluster` | deny | deny | no |
| `terraform apply` *(ambient backend)* | deny | deny | no |
| `kubectl delete ns app --context kind-local` | defer | defer | no |
| `kubectl get pods --context prod-cluster` | defer | defer | no |
| `ansible --version` | defer | defer | no |
| `git status` | defer | defer | no |

**Zero verdicts moved.** Not one row differs between the first two columns, which is what a patch claims here: the same decisions, better. The only column that changes is the third, and it is text a reader sees rather than a command that runs or does not.

## Upgrading

An install from the old marketplace cannot reach this version, because the marketplace it points at is a different repository. Remove it and add the new one:

```
/plugin marketplace remove prod-guard
/plugin marketplace add karlkfi/claude-bouncer
/plugin install prod-guard@claude-bouncer
```

Already on `claude-bouncer`:

```
claude plugin marketplace update claude-bouncer
claude plugin update prod-guard@claude-bouncer
```

Either way a restart is needed — the hook is registered at startup, so a running session stays on the version it loaded.

**Nothing was removed and no configuration changed meaning.** `PROD_GUARD_OVERRIDE` and `PROD_GUARD_SESSION_OVERRIDE` keep their names, their scopes, and their behaviour; the second is only mentioned in more places.

**Your friction numbers will move, and the movement is the fix.** If you use session overrides, the old report folded them into the `PROD_GUARD_OVERRIDE` line, so that count drops and a new line appears beside it. The same window read by 2.5.1 and by 2.5.2 gives different numbers, so compare 2.5.2 output only against 2.5.2 output. Pattern-gap candidates will also shrink where variable-named targets were being listed.

**The move**

The five guards now live in one repository with one marketplace manifest, one test workflow, and one backlog. The part that could have reached this plugin's behaviour is the shell parser: all five carried their own lexer and the copies had drifted, so merging them took the superset rather than a favourite. This guard's `tokenize` was rewritten in the process — it gave up a stripper that removed only quoted heredoc bodies for the shared `strip_heredoc_bodies`, with the bodies bash would expand and the ones whose terminator never appeared handed back through out-parameters and re-lexed as their own segments. It needed that `unterminated` out-parameter added to keep its posture: bash hands an unterminated body over as data, and a guard that can deny a production mutation would rather judge malformed text than take the friendlier reading.

That is a real rewrite of how the command is read, so it was measured rather than assumed. Eighteen shapes built to hit the changed path — production commands inside expanded, quoted, tab-stripped and unterminated heredocs, inside substitutions, behind pipes, and the non-production controls beside them — returned the same verdict on all eighteen, before any of the changes above. Four of those shapes are in the table above.

Documentation, images, backlog and release tooling round out the rest and change nothing the hook decides.

## Validation

**427 tests green** on the release tree, alongside the 140 shared-parser tests that cover `lib/bouncer_parse.py` directly and the four sibling suites `make check` runs beside them. The count is from the release branch rather than quoted from an earlier run.

**What this does not assert.** No live Claude Code session runs in the suite — hook behaviour is asserted against synthetic payloads, and the table above against real subprocess invocations rather than a real session. Classification depends on your own kubeconfig, cloud profiles and backend configuration, so no test can tell you whether *your* production targets are recognised; the [friction report](https://github.com/karlkfi/claude-bouncer/blob/prod-guard/v2.5.2/plugins/prod-guard/README.md#measuring-friction) is the tool for that, and the two fixes here are about making its output mean what it says.

**This is a guard, not a control.** It reads the command string Claude is about to run, so it governs Claude's own tools and nothing else. Anything that must hold unconditionally belongs in your cluster's RBAC or your cloud provider's policy engine.
