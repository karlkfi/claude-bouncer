Minor release: wrappers, comments, quoting and shell keywords that hid a production command from the guard are now read through, and a kubeconfig the command names counts as a pinned target. Thirteen of the shapes measured below passed with no prompt at all on v2.6.0 and now deny or ask. Four move the other way: an override that now arms, a wrapper's `--help` that runs nothing, and two non-production targets the old hook could not read.

## Highlights

**[More wrappers stop hiding the command behind them](https://github.com/karlkfi/claude-bouncer/blob/prod-guard/v2.7.0/plugins/prod-guard/README.md#covered-tools).** `nice`, `ionice`, `setsid`, `chrt` and `taskset` are peeled like `sudo` and `timeout`. Wrapper options are now one table shared across the guards, so a value-taking flag is skipped with its value however it is spelled: bundled (`sudo -nu root`, `env -iu FOO`, `timeout -vk 5 10`), abbreviated (`timeout --kill 5`, `sudo --us root`), or newly listed (`sudo -r`/`-t`/`-a`/`-c`, GNU `env -a`). `sudo FOO=1 kubectl …`, an `env` operand that is not a shell identifier (`env 'a b=c'`), and a split string behind a bundled `env -iS` are read through too. Every one of these let a mutating command against a production target run unprompted.

**Shell syntax stops hiding the command.** A command inside `{ …; }`, an `if`/`then` or loop body, behind `!`, or in a function body is judged as the bare command is. So is a command substitution inside double quotes (`echo "$(kubectl … delete ns x)"`) or inside an unquoted heredoc body. A `#` comment ends at its own newline and no longer swallows the lines after it, including when the comment holds a `$(`, a backtick or an apostrophe. A `#` inside backticks or `${…}`, an ANSI-C string such as `$'\''`, an escape-spelled name such as `$'\x6bubectl'`, and a subscripted prefix such as `FOO[0]=x` no longer hide what follows them.

**[A kubeconfig the command names is a pinned target](https://github.com/karlkfi/claude-bouncer/blob/prod-guard/v2.7.0/plugins/prod-guard/README.md#covered-tools).** `kubectl`, `oc`, `helm` and `flux` now read `--kubeconfig <absolute path>`, or a `KUBECONFIG` the command exports or prefixes, and take that file's current-context as the target. A non-production context stops drawing the pin-`--context` deny. A production one is still denied, and the reason now names the context instead of asking you to pin one.

**Variables resolve the way bash runs them.** A variable an `eval` body sets carries to the commands after it, so `eval 'C=<prod context>'; kubectl --context $C …` denies instead of asking. A single-quoted `bash -c` body sees what `env` or `sudo` hands it, and loses what `env -i` or `env -u` takes away. A prefix append such as `AWS_PROFILE=$P AWS_PROFILE+=x` expands `$P` before joining, where v2.6.0 read a different variable named `Px`. An unquoted `--context=$(…)` now asks as an unresolved target instead of passing.

**[The override arms from an `env` or `sudo` operand](https://github.com/karlkfi/claude-bouncer/blob/prod-guard/v2.7.0/plugins/prod-guard/README.md#the-override-escape-hatch).** `env PROD_GUARD_OVERRIDE=<reason> kubectl …` and `sudo PROD_GUARD_OVERRIDE=<reason> kubectl …` downgrade a deny to a prompt, the same as the bare prefix, and so does `PROD_GUARD_SESSION_OVERRIDE`. An exported override still does nothing. Written as `PROD_GUARD_OVERRIDE[0]=<reason>` it does not arm, because bash never sets the variable.

**A wrapper's own `--help` or `--version` runs nothing, so it is not judged.** `sudo --help kubectl delete ns foo`, `sudo -V …` and `env --version …` print and exit, and now defer instead of denying. `sudo -h HOST` is read as a host, as sudo before 1.9.17p1 ran it, and the command behind it is judged; `sudo -h -n …` is help.

**A deny names the writes it discarded.** A deny refuses the whole call, so a `>` redirect, `tee`, `sed -i`, `cp`/`mv` or heredoc script in the same command never happened. The reason now ends by listing them.

**[The hook launches through `run-python-hook.cmd`](https://github.com/karlkfi/claude-bouncer/blob/prod-guard/v2.7.0/plugins/prod-guard/README.md#install).** On Windows machines where `python3` is only the Microsoft Store stub, the guard now finds a working Python and enforces. Before, it let every command through without a word. If no working Python exists, it says so on stderr.

## Decision surface

Measured by running the v2.6.0 hook and this one over the same payloads and recording the emitted `permissionDecision`. Each hook was launched the way its own `hooks.json` launches it, `python3` for v2.6.0 and `run-python-hook.cmd` for v2.7.0, with an empty `$HOME`, no `PROD_GUARD_*` variables and no config file. `defer` means the guard expressed no opinion and your own permission settings decided. `acme-production` matches a built-in production pattern and `kind-ci` a built-in non-production one. A *kind-ci kubeconfig* is a throwaway file, named by absolute path, whose current-context is `kind-ci`, and a *production kubeconfig* the same with `acme-production`.

| command | v2.6.0 | v2.7.0 |
|---|---|---|
| `nice kubectl --context acme-production delete ns x` | defer | **deny** |
| `timeout --kill 5 10 kubectl --context acme-production delete ns x` | defer | **deny** |
| `sudo -nu root kubectl --context acme-production delete ns x` | defer | **deny** |
| `sudo FOO=1 kubectl --context acme-production delete ns x` | defer | **deny** |
| `env -iS 'kubectl --context acme-production delete ns x'` | defer | **deny** |
| `echo "$(kubectl --context acme-production delete ns x)"` | defer | **deny** |
| `# note` ⏎ `kubectl --context acme-production delete ns x` | defer | **deny** |
| `{ kubectl --context acme-production delete ns x; }` | defer | **deny** |
| `$'\x6bubectl' --context acme-production delete ns x` | defer | **deny** |
| `FOO[0]=x kubectl --context acme-production delete ns x` | defer | **deny** |
| `P=acme-; Pproduction=kind-ci; AWS_PROFILE=$P AWS_PROFILE+=production aws s3 rm s3://b/k` | defer | **deny** |
| `kubectl --context=$(cat ctx) delete ns x` | defer | **ask** |
| `sudo PROD_GUARD_OVERRIDE=why kubectl --context acme-production delete ns x` | defer | **ask** |
| `eval 'C=acme-production'; kubectl --context $C delete ns x` | ask | **deny** |
| `env C=acme-production bash -c 'kubectl --context "$C" delete ns x'` | ask | **deny** |
| `env PROD_GUARD_OVERRIDE=why kubectl --context acme-production delete ns x` | deny | **ask** |
| `env C=kind-ci bash -c 'kubectl --context "$C" delete ns x'` | ask | **defer** |
| `kubectl --kubeconfig <kind-ci kubeconfig> delete ns x` | deny | **defer** |
| `sudo --help kubectl --context acme-production delete ns x` | deny | **defer** |
| `kubectl --kubeconfig <production kubeconfig> delete ns x` | deny | deny |
| `kubectl --context acme-production delete ns x` | deny | deny |
| `kubectl --context kind-ci delete ns x` | defer | defer |

Fifteen rows gain scrutiny and four lose it. Thirteen of the fifteen were silent on v2.6.0, and twelve of those thirteen are a mutating command against a production target that ran with no prompt. One of the twelve is the `sudo PROD_GUARD_OVERRIDE` row, which now prompts the way the bare prefix does. Of the four that lose scrutiny, `env PROD_GUARD_OVERRIDE` is the break-glass arming as intended, and it still prompts. The other three run nothing, or name a non-production target the old hook could not read. The production-kubeconfig row keeps its deny, but the reason moves from "pin `--context`" to naming `acme-production`.

## Upgrading

```
claude plugin marketplace update claude-bouncer
claude plugin update prod-guard@claude-bouncer
```

A restart is needed. The hook is registered at startup, so a running session stays on the version it loaded.

**Nothing was removed, and no configuration key changed name or default.** `PROD_GUARD_OVERRIDE`, `PROD_GUARD_SESSION_OVERRIDE`, `PROD_GUARD_PROD_PATTERNS`, `PROD_GUARD_NONPROD_PATTERNS` and `.claude/prod-guard.json` behave as they did. The environment-variable surface is identical to v2.6.0's. Python 3 is still the only requirement, now under any of the names the launcher tries.

**Expect denials where you were getting silence, and they are the release.** If one is routine for you against a cluster the heuristic is calling production wrongly, add it to `PROD_GUARD_NONPROD_PATTERNS` or to `.claude/prod-guard.json` rather than reaching for the override each time.

**A kubeconfig you name by absolute path is now how you pin.** If you wrote `--context` only to satisfy the pin-`--context` deny while also passing `--kubeconfig`, the context in that file is enough. `KUBECONFIG=<path>; kubectl …` with no `export` still denies, because bash never hands that value to `kubectl`.

## Validation

**574 tests green** on the release tree, alongside the 304 tests at the repository root, 148 of them on the shared modules under `lib/`, and the four sibling suites `make check` runs beside them. The counts are from the release branch rather than quoted from an earlier run.

The decision surface above is the check a test suite cannot make: both hooks run as subprocesses over the same payloads, each through its own launcher, so a row records what a session would actually have seen.

**What this does not assert.** No live Claude Code session runs in the suite, and the launcher's Windows path was not exercised for this release: the table was measured on macOS, where the launcher takes its POSIX branch. Hook behaviour is asserted against synthetic payloads, and no fixture uses a real cluster, context name, or credentials path. Classification is a heuristic over target names, so whether *your* production cluster is recognised is a question for `PROD_GUARD_PROD_PATTERNS` and the config file, not for the suite. The guard reads the command string Claude is about to run, so it governs Claude's own tools and nothing else. Anything that must hold unconditionally belongs in RBAC.
