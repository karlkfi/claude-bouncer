Minor release: six command shapes that hid a production command from the guard are now read, and three that run nothing stop being denied. The boundary moved outward on every one of the six — each was a mutating command against a production target that previously ran with no prompt at all.

## Highlights

**[Six wrappers stop hiding the command behind them](https://github.com/karlkfi/claude-bouncer/blob/prod-guard/v2.6.0/plugins/prod-guard/README.md#what-it-does).** `stdbuf` and `unbuffer` are now peeled like any other wrapper. `env -S` / `--split-string` has its command string parsed rather than treated as one opaque argument. And a wrapper flag that takes a *separate* value — `exec -a`, `/usr/bin/time -o`, `sudo -C`/`-D`/`-R`/`-T`, BSD `env -P`, GNU `time -f`/`--format`/`--output` — no longer leaves the guard reading the value as the command. In every case a mutating command against a production target was deferring silently.

**Two shell bodies now resolve variables the way bash does.** A `bash -c "…"` body written in double quotes picks up what the parent expanded, so a production target reached through `$VAR` denies instead of merely prompting — and a non-production one stops prompting. An `eval` body does the same, under single and double quotes alike. A `bash -c` started *inside* an `eval` body still sees only exported variables, so nothing newly denies on a value that never reaches it.

**A quoted operator word no longer splits the command.** `kubectl ';' --context acme-production delete ns x` was split at the `';'` by the lexer but not by bash, which hid the flags naming the target and left the guard with nothing to judge. Same class as the `X+=1` prefix, which made the guard stand aside entirely and now arms as an assignment — including `PROD_GUARD_OVERRIDE+=<reason>`, which arms the break-glass.

**Three modes that run nothing stop being denied.** `sudo -l`, `-v`, `-e`, `-K` and `-U` run no command, so there was never a command to guard; the words after them were being classified anyway. `command -v kubectl helm` and `command -V kubectl` are lookups, not invocations, so a multi-binary lookup is no longer denied against the ambient context.

**A quoted prefix is a program, not an assignment.** `'X=1' kubectl …` makes bash look for a program named `X=1`; it never reaches `kubectl`, so the guard stops judging a command that will not run. The same holds for `'PROD_GUARD_OVERRIDE=why' kubectl …`, which never armed the break-glass in bash and no longer appears to here. Written unquoted, both behave exactly as before.

## Decision surface

Eleven rows gain scrutiny and six lose it. Every one of the eleven is a mutating command against a production target, and eight of them were saying nothing at all. The six withdrawals are commands that run nothing, or that bash would never run the way the old lexer read them.

## Upgrading

```
claude plugin marketplace update claude-bouncer
claude plugin update prod-guard@claude-bouncer
```

A restart is needed — the hook is registered at startup, so a running session stays on the version it loaded.

**Nothing was removed, nothing was added, and no configuration changed meaning.** `PROD_GUARD_OVERRIDE`, `PROD_GUARD_PROD_PATTERNS`, `PROD_GUARD_NONPROD_PATTERNS` and `.claude/prod-guard.json` keep their names and their defaults. The environment-variable surface is identical to v2.5.2's.

**Expect denials where you were getting silence, and they are the release.** Eight of the shapes above used to pass unremarked. If one is routine for you against a cluster the heuristic is calling production wrongly, add it to `PROD_GUARD_NONPROD_PATTERNS` or to `.claude/prod-guard.json` rather than reaching for the override each time.

**If you scripted `'PROD_GUARD_OVERRIDE=…' kubectl …`, it never worked.** Quoted, bash runs it as a program and the assignment never happens. Write the prefix unquoted; quoting the *value* — `PROD_GUARD_OVERRIDE='incident 42' kubectl …` — is unaffected, and the append spelling now arms too.

## Validation

**493 tests green** on the release tree, alongside the 207 shared-parser tests that cover `lib/bouncer_parse.py` directly and the four sibling suites `make check` runs beside them. The count is from the release branch rather than quoted from an earlier run.

The decision surface above is the check a test suite cannot make: both hooks run as subprocesses over the same payloads, so a row records what a session would actually have seen.

**What this does not assert.** No live Claude Code session runs in the suite — hook behaviour is asserted against synthetic payloads, and no fixture uses a real cluster, context name, or credentials path. Classification is a heuristic over target names, so whether *your* production cluster is recognised is a question for `PROD_GUARD_PROD_PATTERNS` and the config file, not for the suite. The guard reads the command string Claude is about to run, so it governs Claude's own tools and nothing else. Anything that must hold unconditionally belongs in RBAC.
