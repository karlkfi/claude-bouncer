Minor release: the guard reads a prefix's command words and a single-quoted `$NAME` the way bash expands them, keeps a production target that a `source` sits beside, and asks about nesting it cannot read instead of deferring on it. Twenty-one of the shapes measured below moved toward a prompt or a deny, and none moved away from one.

## Highlights

**A prefix assignment does not change the command's own words.** bash expands a command's words before it applies the prefix, so in `CTX=kind-ci kubectl --context=$CTX delete …` the `$CTX` is the shell's value, not `kind-ci`. The guard used to read the prefix's value. It now judges the shell's value as well: an unknown shell `CTX` prompts, and a production one denies. The same holds inside a double-quoted `bash -c`, `eval` or `env -S` string.

**A `$` the parent shell leaves alone is judged as the child's.** In a double-quoted `bash -c` body, `\$X` and `"$"X` reach the child as `$X`, so the child expands them. The guard used to read the parent's `X`. So `X=kind-ci; bash -c "\$X kubectl --context=<prod> delete …"` now denies where it passed.

**A `$NAME` written in single quotes is kept as text.** `B='$C'` stores the four characters `$C`, and a child shell may expand them later. The guard used to read the parent's `C` through it. `C=<nonprod>; B='$C'; bash -c "kubectl --context=$B delete …"` and `bash -c "kubectl --context=$(echo '$C') delete …"` now prompt, and so does `kubectl --context=$B` at top level. A production `C` still denies.

**A production target held across a `source` still denies.** A sourced file may define functions, so any command after `source`, `.`, or inside a `bash -c` that a `BASH_ENV` file runs first, may change a name. The guard now forgets a nonprod value after such a command and prompts, as in `source x.sh; C=kind-ci; f; kubectl --context $C delete …`. It keeps a production value, so `C=<prod>; source x.sh; kubectl --context $C delete …` denies where it asked. A value copied through `export`, `declare` or `readonly` (`export D=$C`) keeps the same protection, which also makes `C=<prod>; x && C=kind-ci; export D=$C; kubectl --context $D delete …` deny where it passed.

**Nesting too deep for the guard to read now asks.** Past roughly 500 levels of command substitution, the guard used to exhaust Python's stack and defer. A production target inside a substitution nested more than 25 levels deep now denies, as it did before, and reaches 545 levels down. Past 545 levels it asks, and so does a target that is not production past 25. A `sh -c` body nested four or more levels deep also asks, where it passed whatever the innermost body ran.

**The shared parser reads more of what bash reads.** A production command after `time -- -p` in a subscript, after a thousand nested `${…}`, inside a double-quoted `$((…) ; …)` that bash runs as a command substitution, in bash 5.3's `${ …; }` substitution, or in a `case` after `!` inside `$( … )` is now judged.

## Upgrading

```
claude plugin marketplace update claude-bouncer
claude plugin update prod-guard@claude-bouncer
```

A restart is needed. The hook is registered at startup, so a running session stays on the version it loaded.

**Nothing was removed and no configuration changed meaning.** `PROD_GUARD_OVERRIDE`, `PROD_GUARD_SESSION_OVERRIDE`, the pattern variables and `.claude/prod-guard.json` behave as they did, and existing grant files are read as before.

**A script that sources a file and then sets a nonprod target will now prompt.** The guard cannot see what a function from that file changes, so it asks after any command that follows the `source`. Pass the target as a literal (`--context acme-staging`) where you want the command judged on its own.

## Validation

**611 tests green** on the release tree, up from 588 at v2.8.0, run with `python3 -m unittest discover tests` in `plugins/prod-guard`, alongside the 355 tests at the repository root and the four sibling suites `make check` runs beside them.

The decision surface above is the check a test suite cannot make: both hooks run as subprocesses over the same payloads, so a row records what a session would actually have seen.

**What this does not assert.** No live Claude Code session runs in the suite. Classification is a heuristic over target names, so whether *your* production cluster is recognised is a question for `PROD_GUARD_PROD_PATTERNS` and the config file, not for the suite. The guard reads the command string Claude is about to run, so it governs Claude's own tools and nothing else. Anything that must hold unconditionally belongs in RBAC.
