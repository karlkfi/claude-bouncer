Minor release: the guard now tracks a variable the way bash does — through a subshell, a builtin that reassigns it, a function called with it, and an assignment that may or may not run — and reads a production command behind an empty expansion, an escaped substitution in a heredoc or a double-quoted `bash -c` body, `time` with an assignment, or `sudo --login`. Eighteen of the shapes measured below moved toward a prompt or a deny, and one that bash never runs stopped being denied.

## Highlights

**A target is followed through the shell's own scoping.** An assignment inside `( … )` or `$( … )` stays in that subshell, as in bash. So `x=$(C=kind-ci); kubectl --context $C delete …` now asks as an unknown target instead of passing as `kind-ci`, and `(C=<prod>; kubectl --context $C delete …)` denies where it asked.

**A variable another command may have changed is no longer trusted.** When `read`, `printf -v`, `mapfile`, `getopts`, `unset`, a `for` loop, `source` or a `BASH_ENV` file sets a variable, the guard used to keep judging the value it had before, and now asks. A function's body is judged again where it is called, so `C=<prod> f` denies. An assignment after `&&` or `||` may or may not run, so the command after it is judged under both values: `C=<prod>; <check> && C=<nonprod>; kubectl --context $C delete …` denies where it used to pass.

**A word that may expand to nothing no longer hides the command behind it.** bash drops an unquoted `$X` or `${X}` that is unset or empty, so `$X kubectl --context <prod> delete …` runs `kubectl`. The guard now judges it, bare and behind `sudo`, `env` or `nohup`. Other expansions in that position, such as `${X:-}`, `$1` or `$(…)`, still defer.

**An unquoted heredoc body is read with bash's escapes removed.** In a body under `<<EOF` that is piped to a shell, `` \` `` and `\$` become the substitutions that shell runs. The guard now judges them as substitutions, inside double quotes too.

**A double-quoted `bash -c` or `eval` body is read as the child shell gets it.** Inside double quotes bash drops the backslash before `$` and a backtick, so `bash -c "\$X kubectl …"` hands the child `$X kubectl …`, and an escaped backtick becomes a live substitution. The guard used to keep the backslash and defer. It now judges the command the child runs. One shape moves the other way: in ``bash -c "echo \\\`…\\\`"`` the child receives escaped backticks and prints them as text, so the guard no longer denies it.

**The shared parser reads more of what bash reads.** A production command behind `time FOO=x`, behind `sudo --login`, or after a `#` that bash treats as text (inside an extglob group, a `(( … ))`, a `[[ … =~ … ]]` operand, or after an escaped blank) is now judged. So is one inside a quoted `$( )` that holds `${…}`, a backtick, or a nested quoted `$( )`.

## Decision surface

Measured by running the v2.7.1 hook and this one through their launchers with an empty `$HOME`, no `PROD_GUARD_*` variable and no config file. `acme-production` matches a built-in production pattern and `kind-ci` matches none. `defer` means the guard expressed no opinion and your own permission settings decided.

Eighteen rows gain scrutiny and one loses it. Two of the eighteen moved from ask to deny, where the guard now knows the target is production rather than unknown. The one that lost its deny prints the command as text in the child shell rather than running it, which bash 5.3.15 confirmed when the change was written. The rows under them are the neighbours that keep their verdict: an expansion form that still defers, a subshell assignment that correctly does not leak out, the single-quoted control, and the plain production and non-production commands.

## Upgrading

```
claude plugin marketplace update claude-bouncer
claude plugin update prod-guard@claude-bouncer
```

A restart is needed. The hook is registered at startup, so a running session stays on the version it loaded.

**Nothing was removed and no configuration changed meaning.** `PROD_GUARD_OVERRIDE`, `PROD_GUARD_SESSION_OVERRIDE`, the pattern variables and `.claude/prod-guard.json` behave as they did, and existing grant files are read as before.

**A script that sets its target with `read`, a loop or `source` will now prompt.** The guard cannot know what value such a command leaves behind, so it asks. Pass the target as a literal (`--context acme-staging`) where you want the command judged on its own.

## Validation

**588 tests green** on the release tree, alongside the 334 tests at the repository root and the four sibling suites `make check` runs beside them. The counts are from the release branch rather than quoted from an earlier run.

The decision surface above is the check a test suite cannot make: both hooks run as subprocesses over the same payloads, so a row records what a session would actually have seen.

**What this does not assert.** No live Claude Code session runs in the suite. Classification is a heuristic over target names, so whether *your* production cluster is recognised is a question for `PROD_GUARD_PROD_PATTERNS` and the config file, not for the suite. The guard reads the command string Claude is about to run, so it governs Claude's own tools and nothing else. Anything that must hold unconditionally belongs in RBAC.
