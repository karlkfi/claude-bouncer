Patch release: a `PROD_GUARD_SESSION_OVERRIDE` grant re-approved after its 8-hour cap now renews, so a long batch goes back to one prompt instead of one per command.

## Highlights

**[A re-approved session grant renews](https://github.com/karlkfi/claude-bouncer/blob/prod-guard/v2.7.1/plugins/prod-guard/README.md#session-scoped-override).** A session grant covers one production target for 8 hours, and an expired grant asks again, as the README says. Answering that prompt is meant to start a new grant. It recorded nothing instead, because the store skipped any target already on file, expired or not, so every later command against that target asked for the rest of the session. The approval now replaces the expired entry with a fresh timestamp and reason. A live grant still keeps its first timestamp, so the cap never slides.

## Decision surface

Measured by running the v2.7.0 hook and this one through their launchers with an empty `$HOME`, no other `PROD_GUARD_*` variable and no config file. Each step is a `PreToolUse` call, and an approval is the `PostToolUse` call Claude Code makes once the command has run. Every command carries the prefix `PROD_GUARD_SESSION_OVERRIDE=rebuild`, and `acme-production` matches a built-in production pattern. The nine-hour gap is simulated by moving the stored grant's timestamp back. `defer` means the guard expressed no opinion and your own permission settings decided.

| step | v2.7.0 | v2.7.1 |
|---|---|---|
| `kubectl --context acme-production delete node old-1` *(first use)* | ask | ask |
| `kubectl --context acme-production cordon old-2` *(after approval)* | defer | defer |
| `kubectl --context acme-production cordon old-2` *(nine hours later)* | ask | ask |
| `kubectl --context acme-production cordon old-3` *(after re-approval)* | ask | **defer** |

**One verdict moved, and it is the one the README already described.** A patch here means the same decisions, better: the expiry was always meant to cost one prompt, and v2.7.0 charged one per command after it.

## Upgrading

```
claude plugin marketplace update claude-bouncer
claude plugin update prod-guard@claude-bouncer
```

A restart is needed. The hook is registered at startup, so a running session stays on the version it loaded.

**Nothing was removed and no configuration changed meaning.** `PROD_GUARD_OVERRIDE`, `PROD_GUARD_SESSION_OVERRIDE`, the pattern variables and `.claude/prod-guard.json` behave as they did. Existing grant files are read as before, so an upgrade mid-session keeps every live grant.

## Validation

**574 tests green** on the release tree, alongside the 319 tests at the repository root and the four sibling suites `make check` runs beside them. The counts are from the release branch rather than quoted from an earlier run.

**What this does not assert.** No live Claude Code session runs in the suite, and the nine-hour gap in the table was simulated by editing the stored timestamp rather than waited out. Classification is a heuristic over target names, so whether *your* production cluster is recognised is a question for `PROD_GUARD_PROD_PATTERNS` and the config file, not for the suite. The guard reads the command string Claude is about to run, so it governs Claude's own tools and nothing else. Anything that must hold unconditionally belongs in RBAC.
