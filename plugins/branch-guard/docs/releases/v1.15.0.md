Minor release: a git command inside `sh -c '…'` or `bash -c '…'` is now judged, and a command hidden in a subscript after a second `time` option is read.

## Highlights

**[A git command inside a shell's `-c` string is judged](https://github.com/karlkfi/claude-bouncer/blob/branch-guard/v1.15.0/plugins/branch-guard/README.md#how-it-works).** branch-guard never read the string a shell runs, so `sh -c 'git commit -m x'` on `main` got no decision at all while the bare commit asked. In a session that allowlists `git commit`, that commit landed on a protected branch with no prompt. The body is now judged by the same rules as a bare command, and its ask or deny stands. Its allow approves nothing, because the shell around it can change what git sees, so `sh -c 'git status'` still falls back to your permission settings.

The body runs from where the shell starts, so `env -C ../repo sh -c 'git commit -m x'` from a feature branch asks when `../repo` is on `main`, and so does a body that `cd`s there first. Variables set for the shell are read as if set for git. The break-glass does not reach into a body: `BRANCH_GUARD_OVERRIDE=why sh -c 'git reset --hard'` asks. The shells read are `sh`, `bash`, `dash`, `zsh`, `ksh`, `mksh` and `ash`, with options bundled (`-lc`) or split (`bash -e -c`), and a shell inside a body is read too.

**A command after a second `time` option is read.** In `time -- -p FOO[a;git push --force origin main;b]=x true`, bash runs the push. The shared parser misread the assignment position after `time -- -p` and `time -p -p`, and the guard deferred. Both now ask, as `time -p git push --force origin main` already did.

## Decision surface

Measured by running the v1.14.0 hook and this one through their launchers over identical payloads, against a fresh repository with a bare `origin`. The primary checkout, `repo`, is on `main`. The session's linked worktree sits beside it on `claude/x`, so `../repo` from the worktree is the primary checkout. The default `strict` policy applies, and no `BRANCH_GUARD_*` variable is set unless the row says so. `defer` means the guard expressed no opinion and your own permission settings decided.

|---|---|---|---|
| `sh -c 'git commit -m x'` | `main` | defer | **ask** |

| `bash -lc 'git commit -m x'` | `main` | defer | **ask** |
| `bash -e -c 'git commit -m x'` | `main` | defer | **ask** |
| `sh -c 'git commit -m x' argv0 a b` | `main` | defer | **ask** |
| `sh -c "sh -c 'git commit -m x'"` | `main` | defer | **ask** |
| `sh -c 'git reset --hard'` | `main` | defer | **ask** |
| `BRANCH_GUARD_OVERRIDE=why sh -c 'git reset --hard'` | `main` | defer | **ask** |
| `sh -c 'git push --force origin main'` | `claude/x` | defer | **ask** |

| `git checkout -b feat/y` | `claude/x` | allow | allow |
| `git log` | `claude/x` | allow | allow |

Fourteen rows gain scrutiny and none lose it. Twelve are a `-c` body, and their controls are the bare commit on `main` and the push from `claude/x`, which asked before and still do. A body whose own verdict is allow still defers rather than allowing, as the `git status` and feature-branch commit rows show. A script on stdin (`sh -s`), a script file, and a body that runs its own arguments (`sh -c '"$@"' _ git commit`) are not read and defer, as before.

## Upgrading

```
claude plugin marketplace update claude-bouncer
claude plugin update branch-guard@claude-bouncer
```

A restart is needed. The hook is registered at startup, so a running session stays on the version it loaded.

**Nothing was removed and no configuration changed meaning.** `BRANCH_GUARD_OVERRIDE` and the rest keep their names and their defaults. The break-glass lifts nothing inside a `-c` body, so a destructive command written there asks even with the override set. Run it bare to use the override.
