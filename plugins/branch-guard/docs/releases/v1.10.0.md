Minor release, and the first cut from `karlkfi/claude-bouncer`: the two asks whose answer the guard could work out for itself become denies that carry the fix, and the break-glass reaches the push form for the first time.

> [!IMPORTANT]
> **This plugin now ships from the `claude-bouncer` marketplace, and the old one stops at v1.9.0.** `karlkfi/claude-branch-guard` still serves 1.9.0 and will not move again, so an install pinned to `branch-guard@branch-guard` gets no further updates and no notice that it is behind. The two commands that move it are under [Upgrading](#upgrading). The protected-branch set, the push policies, the classifier and `BRANCH_GUARD_OVERRIDE` all keep their names and their defaults.

## Highlights

**A prompt is the wrong place to settle a question the model can answer.** Both verdict changes here come from the same test: if the missing input is a fact about the world rather than a judgement about intent, asking spends the one reviewer that does not scale, and the answer teaches the session nothing — Claude Code delivers an `ask` reason to the permission prompt and nowhere else, while a `deny` reason reaches the model. So where the fix fits in the reason, the verdict is now `deny` and the reason carries the fix.

**[`git reset --hard` on a tip nothing else reaches now denies](https://github.com/karlkfi/claude-bouncer/blob/branch-guard/v1.10.0/plugins/branch-guard/README.md#behavior).** The trigger for this is squash merges, which is what made the old prompt expensive: a squash-merged branch's tip is unreachable by construction while its content sits on `main` under another object name, so the check fired on the most routine end-of-work cleanup there is. The denial names the `gh pr view <n> --json state,mergeCommit` that settles whether the content survived, and routes the no-pull-request case as well as the squash case. A tip the guard cannot check still prompts.

**[An overlap push denies, and the break-glass lifts it](https://github.com/karlkfi/claude-bouncer/blob/branch-guard/v1.10.0/plugins/branch-guard/README.md#push-guard).** v1.8.0 added the check — when `origin/main` has moved into the same lines your branch edits, the auto-approve is withdrawn — and v1.9.0 delivered the rebase to the model as `additionalContext` while leaving the verdict an ask. The ask was the remaining problem: approving it pushes onto the stale base the reason just told the session to rebase onto, and the merge queue spends the cycle the check existed to save. The verdict is now `deny-rebase`, and it denies in every permission mode.

That makes the override load-bearing rather than decorative, which is the second half of the change: `BRANCH_GUARD_OVERRIDE=<reason> git push` now lifts the overlap deny. It is the one push form the break-glass reaches — a protected-branch push, a cross-name push and a tag publish are all still outside it, and the release ships fixtures that fail if any of them starts to lift.

**A reproducible merge stops blocking a reset.** A `git reset --hard` on a scratch branch whose only unshared commit is a merge git can reproduce is auto-approved rather than denied, matching what `git branch -D` already did to the same branch. Nothing is lost that git cannot reconstruct, which is the condition the second chance tests for.

## Decision surface

Measured by running the v1.9.0 hook and this one over the same throwaway repositories and diffing the emitted `permissionDecision`. `origin/main` moved after `claude/x` forked, with both sides editing line 5 of `file.txt` where a row says *base moved*, under the default `strict` policy.

| command | v1.9.0 | v1.10.0 |
|---|---|---|
| `git reset --hard` *(tip unreachable from anything else)* | ask | **deny** |
| `git push` *(base moved into the same line)* | ask | **deny** |
| `git push --force` *(same)* | ask | **deny** |
| `BRANCH_GUARD_OVERRIDE=rebased-by-hand git push` *(same)* | ask | **allow** |
| `git push` *(base has not moved)* | allow | allow |
| `git push origin main` *(protected target)* | ask | ask |
| `git commit -m x` *(feature branch)* | allow | allow |
| `git branch -D scratch` | ask | ask |
| `git clean -fd` | ask | ask |
| `gh repo delete o/r` | ask | ask |
| `git status` | allow | allow |

Three rows harden and one opens, and the one that opens only does so behind a break-glass somebody has to type. **No command that was auto-approved at v1.9.0 stopped being auto-approved**, and none that prompted at v1.9.0 became silent: every movement is out of the `ask` column, which is the column this release is about.

## Upgrading

An install from the old marketplace cannot reach this version, because the marketplace it points at is a different repository. Remove it and add the new one:

```
/plugin marketplace remove branch-guard
/plugin marketplace add karlkfi/claude-bouncer
/plugin install branch-guard@claude-bouncer
```

Already on `claude-bouncer`:

```
claude plugin marketplace update claude-bouncer
claude plugin update branch-guard@claude-bouncer
```

Either way a restart is needed — the hook is registered at startup, so a running session stays on the version it loaded.

**Nothing was removed and no configuration changed meaning.** `BRANCH_GUARD_PUSH_OVERLAP_ENABLED=false` still switches the overlap check off entirely, deny included.

**Changes that need no action, but will be visible.**

* **A push you would have approved now fails, and the session rebases instead.** That is the point of the release. If you meant to push onto the stale base, re-run it as `BRANCH_GUARD_OVERRIDE=<reason> git push` — the reason is yours to write and it is recorded in the command.
* **An end-of-work `git reset --hard` after a squash merge now fails rather than prompting.** The denial tells the session how to establish that the content is on `main`. Where you know it is not, the same override applies.
* **Neither denial is liftable by answering a prompt any more**, because there is no prompt. In `dontAsk` and `bypassPermissions` this changes nothing: an ask was already converted to a refusal there.

## Everything since v1.9.0

**Verdicts**

* feat(branch-guard): deny the unreachable-tip reset instead of asking by @karlkfi in https://github.com/karlkfi/claude-bouncer/pull/33
* feat(branch-guard): deny the push-overlap ask, and give it an override by @karlkfi in https://github.com/karlkfi/claude-bouncer/pull/36
* fix(branch-guard): give a reset the reproducible-merge second chance by @karlkfi in https://github.com/karlkfi/claude-bouncer/pull/41

**The move**

The five guards now live in one repository with one marketplace manifest, one test workflow, and one backlog. The part that could have reached this plugin's behaviour is the shell parser: all five carried their own lexer and the copies had drifted, so merging them took the superset rather than a favourite. branch-guard's share of that was mechanical — its `tokenize` now calls the shared `lex` in place of an identical inline construction, and it keeps its own `SEPARATORS` and `REDIR`, which fold the duplicating operators in a shape the shared split does not carry. The three later parser fixes in this window all landed in the substitution scanner, which this guard does not call. That is why none of them appears above, and why the table's controls are the check rather than a formality.

Documentation, images, backlog and release tooling round out the rest and change nothing the hook decides.

## Validation

**494 specs green** on the release tree, alongside the 140 shared-parser tests and the four sibling suites `make check` runs beside them. The count is from the release branch rather than quoted from an earlier run.

The decision surface above is the check a suite cannot make: both hooks run as subprocesses against real git repositories built for the case, so a row records what a session would actually have seen. The override rows matter most — a break-glass that is asserted only by unit test is a break-glass nobody has watched lift anything.

**What this does not assert.** No live Claude Code session runs in the suite. The overlap detection reads `git diff` against the fetched base, so a base that has moved without a fetch looks unmoved — the check is only as fresh as your last fetch, unchanged from v1.8.0. And the hook parses the Bash command Claude runs, so it governs Claude's Bash tool and nothing else; anything that must hold unconditionally belongs in a git `pre-push` hook or server-side branch protection.
