Minor release: cleanup after a rebase you already pushed stops being refused, a branch reset spelled `switch -C` stops being auto-approved, and the guard now reads a `git` command behind a wrapper, inside a group or loop, or after `|&`, where before it said nothing at all.

## Highlights

**[A rebase you already pushed no longer blocks the cleanup](https://github.com/karlkfi/claude-bouncer/blob/branch-guard/v1.12.0/plugins/branch-guard/README.md#git-branch-what-the-session-owns-not-how-the-verb-looks).** Rebasing a branch and pushing the result under another name gives every commit a new object name, so the old tip is reachable from nothing and `git reset --hard` off it was denied. The guard now matches each commit the move would orphan by patch-id against the newest 200 commits on your remotes, and a full match is auto-approved. `git branch -D` and the force overwrites (`-f`, `-M`, `-C`) take the same check. A match must also keep the commit's message, so a reword made locally after publishing, or during the rebase itself, still denies: the move would discard a message that exists nowhere else. A base that moved inside the lines around your change still denies too, and the denial now names `git cherry <remote-branch> <branch>` to show which commits have no match.

**`git switch -C main …` was auto-approved, and now asks.** `git switch -C`, `git checkout -B` and `git worktree add -B` reset an existing branch, and v1.11.0 read them as the harmless branch-creating forms. They are judged like `git branch -f` now: resetting a protected branch asks (denies under `dontAsk`), and resetting a private one asks when it would orphan commits nothing else reaches.

**[A `git` command behind a wrapper is judged](https://github.com/karlkfi/claude-bouncer/blob/branch-guard/v1.12.0/plugins/branch-guard/README.md#how-it-works).** `env`, `sudo`, `timeout`, `nice`, `nohup`, `command`, `stdbuf`, `setsid`, `time` and `exec` used to hide the command from the guard entirely, so `timeout 60 git push origin main` ran with no prompt. It now gets every `ask` and `deny` the bare command would. A wrapped command is still never auto-approved, because the wrapper can change the user or the environment, and the guard reads neither. The break-glass does reach it: `BRANCH_GUARD_OVERRIDE=<reason>` written before the wrapper, or as an `env` or `sudo` operand (`env BRANCH_GUARD_OVERRIDE=<reason> git reset --hard …`), lifts a deny the way the bare prefix does. A wrapper that changes directory (`env -C`, `sudo -D`, `sudo -i`) keeps the deny, as `git -C` does. `env -C <dir>` and `sudo -D <dir>` are followed into a literal directory the way `git -C <dir>` is, so a commit into a checkout on a protected branch asks. The wrapper options that take a value come from a table shared with the other guards, which covers `sudo -r`, `env -a`, abbreviated long options such as `sudo --us root`, and `sudo -h HOST`.

**[Groups, conditionals, loops and `|&` no longer hide a command](https://github.com/karlkfi/claude-bouncer/blob/branch-guard/v1.12.0/plugins/branch-guard/README.md#how-it-works).** A `git` command inside `{ … }`, an `if`, `while` or `for` body, after `!`, or in a function body is judged as it would be typed bare, so `{ git push --force origin main; } 2>&1` asks. The same goes for a command after `|&`, and for one written straight after a `)` and an operator, as in `x=$(…); git commit`. All of these used to return no decision. In the other direction, a read-only command piped with `|&` into a filter is auto-approved as `|` already was, and a `cd` inside `( … )`, a pipeline stage or a backgrounded list no longer moves the branch later commands are judged against.

**Shared-parser fixes stop five spellings from hiding a command.** A prefix that assigns an array element (`FOO[0]=x git …`, `FOO[a;b]=x git …`), an ANSI-C quoted string earlier in the line (`echo $'\'' ; git …`), an escape-spelled command name (`$'\x67it' push …`), and a double-quoted substitution holding a quote (`echo "$(printf '%s"' x)" ; git …`) each made the guard defer, and each is now judged. Every deny also ends by naming the file writes in the refused command, since a deny discards the whole call and those writes never happened.

## Decision surface

Measured by running the v1.11.0 hook and this one through their launchers over identical `PreToolUse` payloads and recording the emitted `permissionDecision`. `defer` means the guard expressed no opinion and your own permission settings decided. The session checkout is on `claude/x`, and a linked worktree has the protected `main`. Rows marked *republished* use a repository where `claude/dup` holds two commits that were replayed onto a moved base and published as `origin/claude/republished`. *Base moved in context* means the base edited line 12 of the file `claude/dup` edits at line 10.

| command | v1.11.0 | v1.12.0 |
|---|---|---|
| `git reset --hard origin/main` *(republished)* | deny | **allow** |
| `git branch -D claude/dup` *(republished)* | ask | **allow** |
| `git branch -f claude/dup origin/main` *(republished)* | ask | **allow** |
| `git log \|& head` *(on `main`)* | defer | **allow** |
| `(cd <worktree on main>) && git commit -m x` | ask | **defer** |
| `git switch -C main origin/main` | allow | **ask** |
| `git switch -C scratch main` *(`scratch` holds unique work)* | allow | **ask** |
| `timeout 60 git push origin main` | defer | **ask** |
| `sudo --us root git push origin main` | defer | **ask** |
| `{ git push --force origin main; } 2>&1` | defer | **ask** |
| `x=$(true); git commit -m x` *(on `main`)* | defer | **ask** |
| `true \|& git commit -m x` *(on `main`)* | defer | **ask** |
| `env -C <worktree on main> git commit -m x` | defer | **ask** |
| `FOO[0]=x git commit -m x` *(on `main`)* | defer | **ask** |
| `timeout 60 git reset --hard origin/main` *(base moved in context)* | defer | **deny** |
| `BRANCH_GUARD_OVERRIDE=why timeout 60 git reset --hard origin/main` *(same)* | defer | **allow** |
| `env BRANCH_GUARD_OVERRIDE=why git reset --hard origin/main` *(same)* | defer | **allow** |
| `git reset --hard origin/main` *(republished, then reworded locally)* | deny | deny |
| `git reset --hard origin/main` *(base moved in context)* | deny | deny |
| `git commit -m x` *(on `main`)* | ask | ask |
| `timeout 60 git status` | defer | defer |
| `git status` | allow | allow |

Seven rows open and ten harden. Of the seven, three are the republish check, one is a read-only `|&` pipe, and two are the break-glass written before a wrapper or as an `env` operand, on a command v1.11.0 never saw. The seventh is a prompt about the wrong branch, which is now left to your permission settings. Of the ten, two were auto-approved resets of a branch, `main` included. The other eight were commands the guard never saw: seven now ask where nothing prompted, and the eighth is a wrapped `reset --hard` that denies exactly where the bare command does.

## Upgrading

```
claude plugin marketplace update claude-bouncer
claude plugin update branch-guard@claude-bouncer
```

A restart is needed. The hook is registered at startup, so a running session stays on the version it loaded.

**Nothing was removed and no configuration changed meaning.** `BRANCH_GUARD_OVERRIDE` and the rest keep their names and their defaults.

**Changes that need no action, but will be visible.**

* **A wrapped `git` command can prompt or deny where it passed in silence.** That is the point of the wrapper change. A destructive wrapped command such as `timeout 60 git reset --hard …` now denies exactly where the bare one does.
* **The break-glass works behind a wrapper, except one that changes directory.** Behind `env -C`, `sudo -D` or `sudo -i` the deny stands, as it does for `git -C`. Drop that wrapper and write the override as a bare prefix if you mean to proceed.

## Validation

**847 fixtures green** on the release tree, alongside the 304 tests at the repository root, 148 of them on the shared modules under `lib/`, and the four sibling suites `make check` runs beside them. The counts are from the release branch rather than quoted from an earlier run. Every fixture goes through the launcher named in `hooks/hooks.json`, so the path under test is the path Claude Code executes.

The decision surface above is the check a fixture suite cannot make: both hooks run as subprocesses over the same repositories, so a row records what a session would actually have seen. The shared-parser rows were also run through the v1.11.0 hook with this release's `lib/` swapped in, which is how the list above separates the parser fixes that reach this guard from the ones that do not.

**What this does not assert.** No live Claude Code session runs in the suite. The republish check is a property of the commit graph and of what your remote-tracking branches hold, so it is only as fresh as your last fetch, and a republish older than the newest 200 remote commits still denies. The guard reads the command string Claude is about to run, so it governs Claude's own tools and nothing else; a branch that must not move belongs behind a server-side protection rule.
