Minor release: a commit or push into a repository named by `--git-dir` or `GIT_DIR` now asks, a prefix variable that can make git run a program withholds the auto-approve, a forced `git checkout -b` asks as a forced `git switch -c` already did, an abbreviated git long option gets the verdict of its full spelling, and a `GIT_DIR` or `GIT_CONFIG*` variable is read the way its option form is.

## Highlights

**A commit or push into another repository asks.** A commit, merge, rebase, pull or push that names its repository with `--git-dir`, `GIT_DIR`, `GIT_COMMON_DIR`, or a `git -C` path only the shell can compute was judged against the session's own branch. From a feature branch it was allowed, even when the repository it named sat on `main`. The guard cannot tell which branch that repository is on, so these now ask. `--work-tree` and `GIT_WORK_TREE` alone still allow, since git still reads HEAD from the session's directory, and a read such as `git --git-dir=… log` still allows.

**A prefix variable outside a short list of data withholds the auto-approve.** `GIT_EXTERNAL_DIFF='echo ran' git diff` was approved, and git ran the program. So were `GIT_SSH_COMMAND`, `GIT_ASKPASS`, `PATH`, `HOME`, `GIT_EXEC_PATH`, `LD_PRELOAD` and every other variable that names a program or names config that does. That list has no end, so the guard now names the safe side instead: the repository variables, author and committer identity and dates, `TZ`, `LANG`, `LC_*`, gh's host, repo and token variables, and the guards' own `*_OVERRIDE` names. Any other prefix variable falls back to your normal permissions rather than being approved. An editor or pager set to exactly `true`, `:` or `cat` keeps the approval, so `GIT_EDITOR=true git commit --amend` still allows. The same variables now also stop the break-glass from lifting a denial.

**A forced `git checkout -b` asks.** `git checkout -f -b <name>` discards uncommitted changes before it creates the branch, and the guard allowed it, while `git switch -f -c <name>` already asked. Every spelling now asks: `-fb`, `--force -b`, an abbreviated `--forc`, and `-f -B`. A plain `git checkout -b` still allows.

**An abbreviated long option is read as the option git reads.** git accepts any unambiguous prefix of a long option, so `git push --mir` is `git push --mirror`. The guard compared spellings exactly, so `git branch --forc`, `git switch --discard` and `git push --mir` were allowed as commands with no option at all. Each now gets the verdict of its full spelling.

**[`GIT_DIR` and `GIT_CONFIG*` are read like `--git-dir` and `-c`](https://github.com/karlkfi/claude-bouncer/blob/branch-guard/v1.14.0/plugins/branch-guard/README.md#break-glass-branch_guard_override).** The break-glass lifts a loss only in the checkout the session owns, and already refused `git --git-dir=… clean -fd`. It lifted `GIT_DIR=… git clean -fd`, and the same command behind `GIT_WORK_TREE`, `GIT_INDEX_FILE` or any `GIT_CONFIG*` variable, bare or as an `env` or `sudo` operand. Those now ask. A config variable can also make git run a program, as `git -c core.pager=x log` can, so `GIT_CONFIG_PARAMETERS='core.pager=x' git log` now defers where it was allowed.

**`sudo --login` in front of a git command is read as `sudo -i`.** The guard used to read `--login` as the start of `--login-class`, which takes a value, and so missed the command behind it.

Twenty-four rows gain scrutiny and none lose it. Twelve of them take the verdict a neighbour below already had: the full spelling of the option, `git switch -f -c`, the `--git-dir` or `-c` form, or `sudo -i`. Five are writes into a repository the guard cannot place, and their controls are the `--work-tree` commit and the `--git-dir` read, which still allow. The last seven carry a prefix variable outside the safe list. `FOO=1` runs nothing, and it defers anyway: that is the price of naming the safe side rather than the dangerous one. Their controls are the no-op editor and pager and `TZ=UTC`, which keep the allow and leave the break-glass alone.

## Upgrading

```
claude plugin marketplace update claude-bouncer
claude plugin update branch-guard@claude-bouncer
```

A restart is needed. The hook is registered at startup, so a running session stays on the version it loaded.

**Nothing was removed and no configuration changed meaning.** `BRANCH_GUARD_OVERRIDE` and the rest keep their names and their defaults. The break-glass covers fewer commands than before: one carrying a repository or config variable, or any prefix variable outside the safe list, is no longer lifted, as one carrying `--git-dir` or `-c` never was.

**A command that sets an editor to a real program now prompts.** `GIT_SEQUENCE_EDITOR="sed -i …" git rebase -i` was auto-approved and now falls back to your permission settings. Set the editor to `true`, `:` or `cat` where you want the approval kept.

## Validation

**1061 fixtures green** on the release tree, alongside the 334 tests at the repository root and the four sibling suites `make check` runs beside them. The counts are from the release branch rather than quoted from an earlier run. Every fixture goes through the launcher named in `hooks/hooks.json`, so the path under test is the path Claude Code executes.

The decision surface above is the check a fixture suite cannot make: both hooks run as subprocesses over the same repository, so a row records what a session would actually have seen.

**What this does not assert.** No live Claude Code session runs in the suite. That git honours the `GIT_CONFIG*` and `GIT_DIR` variables was measured on git 2.55 when that change was written, not again for this release. The guard reads the command string Claude is about to run, so it governs Claude's own tools and nothing else; a branch that must not move belongs behind a server-side protection rule.
