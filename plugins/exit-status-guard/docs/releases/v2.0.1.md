Patch release, and the first cut from `karlkfi/claude-bouncer`: the guard stops denying the rewrite its own denial recommends, and a gate written inside a `case` clause is finally seen.

> [!IMPORTANT]
> **This plugin now ships from the `claude-bouncer` marketplace, and the old one stops at v2.0.0.** `karlkfi/claude-exit-status-guard` still serves 2.0.0 and will not move again, so an install pinned to `exit-status-guard@exit-status-guard` gets no further updates and no notice that it is behind. The two commands that move it are under [Upgrading](#upgrading). This is a marketplace move, not a second rename: the plugin name, the registry file, the `EXIT_STATUS_GUARD_OVERRIDE` prefix and the 1.x compatibility aliases are all unchanged from v2.0.0.

## Highlights

**[The capture form no longer denies](https://github.com/karlkfi/claude-bouncer/blob/exit-status-guard/v2.0.1/plugins/exit-status-guard/README.md#3-sequenced-before-a-state-change-with-).** A gate sequenced before a *restore* with `;` was denied along with every other `;` sequence, including when the status was captured and re-checked around it — so `make check > log 2>&1; rc=$?; git reset --hard; [ "$rc" -ne 0 ] || exit 1` was refused, and that is one of the two rewrites the denial reason itself offers. A guard that rejects the fix it recommends leaves nowhere to go but the override. It now runs as written.

The condition is narrow and deliberately so. The status has to be captured into a variable and re-checked after the sequence, and the command in between has to be a *restore* rather than a publish. A gate sequenced before `git push` still denies, because there the status is read correctly and then ignored, which is the whole shape the rule exists for.

**A `case` clause no longer hides a gate.** A substitution holding a `case` clause used to end at the pattern's `)`, so a `make check | tail -1` written in a clause body was never scanned and the whole command string passed. It denies now. Two sibling fixes in the same shared parser cover a heredoc body inside a substitution and an apostrophe in an earlier top-level heredoc body; neither moved a verdict for this guard in the shapes measured below, and both are asserted directly against `lib/bouncer_parse.py`.

**A sequencing denial names both rewrites.** The reason offered `&&` alone, which is right for a gate whose success should gate the next step and wrong for one whose failure *is* the assertion and whose restore has to run either way. It now names the capture form — `cmd > log 2>&1; rc=$?; restore; [ "$rc" -ne 0 ] || exit 1` — beside it, which is the form the fix above made runnable.

## Decision surface

Measured by running the v2.0.0 hook and this one over the same payloads, each with its own bundled registry, and diffing the emitted `permissionDecision`.

| command | v2.0.0 | v2.0.1 |
|---|---|---|
| `make check > log 2>&1; rc=$?; git reset --hard; [ "$rc" -ne 0 ] \|\| exit 1` | deny | **defer** |
| `echo "$(case $x in a) make check \| tail -1;; esac)"` | defer | **deny** |
| `make check > log 2>&1; rc=$?; git push; [ "$rc" -ne 0 ] \|\| exit 1` | deny | deny |
| `make check \| tail -30` | deny | deny |
| `make check; git push` | deny | deny |
| `x=$(make check \| tail -1)` | deny | deny |
| `make check && git push` | defer | defer |
| `EXIT_STATUS_GUARD_OVERRIDE=reading-the-log make check \| tail -30` | defer | defer |
| `git status` | defer | defer |

One denial lifts and one lands, and the two are the release. The rest of the rows are there because a patch has to be able to say what did *not* move: the three headline shapes, the publish case that separates a restore from an announcement, the substitution capture, and the override.

## Upgrading

An install from the old marketplace cannot reach this version, because the marketplace it points at is a different repository. Remove it and add the new one:

```
/plugin marketplace remove exit-status-guard
/plugin marketplace add karlkfi/claude-bouncer
/plugin install exit-status-guard@claude-bouncer
```

Already on `claude-bouncer`:

```
claude plugin marketplace update claude-bouncer
claude plugin update exit-status-guard@claude-bouncer
```

Either way a restart is needed — the hook is registered at startup, so a running session stays on the version it loaded.

**Nothing was removed and no configuration changed meaning.** A project registry named `pipe-guard.json` still loads, and `PIPE_GUARD_REGISTRY` still resolves, alongside their `exit-status-guard` counterparts.

**If you added an override to get the capture form past the guard, you can drop it.** The rewrite runs unprefixed now, and an override left in place still works — it just no longer records a reason for something the guard has stopped objecting to.

**The move**

The five guards now live in one repository with one marketplace manifest, one test workflow, and one backlog. The part that reaches this plugin's behaviour is the shell parser: all five carried their own lexer, the copies had drifted, and this guard's copy was the reason the drift was worth measuring — on 2026-08-20 it and workspace-guard fixed the same heredoc bug on the same day with different mechanisms, and each fix left a gap the other had closed. Merging them took the superset. This guard gave up its own `strip_heredoc_bodies`, whose pre-scan for the closing `)` tracked quotes and so read an unbalanced quote in a body as an unterminated substitution, leaving the body to reach the lexer; a commit message containing a `"` is the shape that produced it. It kept its `strip_comments`, which folds backslash-newline continuations, and its `|&` separator, both of which the other four now have. Each plugin carries a vendored copy of `lib/bouncer_parse.py` that `make sync-check` verifies, because a plugin installed into Claude Code's cache cannot read a path outside its own root.

Documentation, images, backlog and release tooling round out the rest and change nothing the hook decides.

## Validation

**59 tests green** on the release tree, alongside the 140 shared-parser tests that cover `lib/bouncer_parse.py` directly and the four sibling suites `make check` runs beside them. The count is from the release branch rather than quoted from an earlier run. The parser this guard hands its hardest cases to is now tested where it lives rather than five times over in five copies, which is most of why this suite is the smallest of the five.

**What this does not assert.** No live Claude Code session runs in the suite. The registry is the guard's model of which commands are gates and which are state changes, and no test can tell you whether *yours* are registered — only that a registered one behaves. A command absent from it defers, which is the fail-open the guard is built on: `frobnicate | tail -5` says nothing, at v2.0.0 and here alike.

**Every verdict is a `deny`, never an `ask`.** A deny's reason reaches the model, so the fix lands where the command gets rewritten; an ask goes to you and the model never sees it. That is why the reason text in the second highlight is a behaviour change rather than a documentation one.
