Minor release: a gate hidden behind a wrapper's options, a process substitution or a `(…)` subshell is now denied, `set -o pipefail` counts only where bash keeps it on for the pipe, and the override arms behind `env` or `sudo`.

## Highlights

**A gate behind a wrapper's options or operands is judged.** The guard used to peel a wrapper's name and stop, so `sudo -n make check | tail -5` and `stdbuf -oL make check | tail -5` passed with no verdict. It now reads through the options the way the wrapper does, using one shared table of which options take a value: `sudo -r`/`-t`/`-a`/`-c`, GNU `env -a`, an abbreviated long option like `sudo --us root`, `sudo -h HOST`, a `sudo` option written after a `NAME=value` operand, and an `env` operand that is not a shell identifier (`env 'a b=c'`, `env 1=x`). `env -S 'make check' | tail -5` is split and judged too. A wrapper mode that runs nothing still says nothing: `command -v make | head` and `sudo -l make check | tail -5` defer as before, and `sudo -- A=1 make check` runs a program named `A=1`, as sudo does.

**[`set -o pipefail` counts only where bash keeps it on for the pipe](https://github.com/karlkfi/claude-bouncer/blob/exit-status-guard/v2.2.0/plugins/exit-status-guard/README.md#1-piped-into-a-filter).** Any `set -o pipefail` anywhere in the command used to lift the denial on a piped gate. It no longer does when the setting comes after the pipe, sits inside a subshell that has ended, is turned off again with `set +o pipefail`, or is written as `set -e pipefail`. A `set` that bash runs in a process of its own does not count either: a pipeline stage (`set -o pipefail | true`), a backgrounded list, a piped or backgrounded `{ …; }`, `if`, `case` or loop, or a function nobody called. Two shapes go the other way and lose a denial: a pipe inside a later `$(…)`, which inherits the option (`set -o pipefail; out=$(make check | tail -5)`), and a function that sets it and is then called (`function f { set -o pipefail; }; f`).

**[A gate inside a process substitution is denied](https://github.com/karlkfi/claude-bouncer/blob/exit-status-guard/v2.2.0/plugins/exit-status-guard/README.md#4-inside-a-process-substitution).** The shell reports a `<(…)` body's status nowhere, so `tail <(make check)` turned a failing check into a 0. That is a fourth rule, with its own README section. A gate or state change written in a `(…)` subshell around a `;` is also seen now, so `(make check); git push` denies like the unwrapped form.

**[The override arms behind `env` or `sudo`](https://github.com/karlkfi/claude-bouncer/blob/exit-status-guard/v2.2.0/plugins/exit-status-guard/README.md#the-override-escape-hatch).** `env EXIT_STATUS_GUARD_OVERRIDE=why make check | tail -5` was denied, because the guard only looked for the variable as a leading assignment. Both programs set the variables their operands name, so the override now counts there, as it already did in foreground-guard.

**Quoting and comments no longer hide the command after them.** Several shared-parser fixes close shapes where a command written after some quoting passed unjudged: a subscripted prefix (`FOO[0]=x`, `FOO[a;b]=x`), an ANSI-C string such as `$'\''`, a `#` inside backticks or `${...}`, a `#` straight after a substitution's close, and a substitution in double quotes that holds a quote character (`echo "$(printf '%s"' x)" ; make check | tail -5`). Each of those now reaches the piped-gate rule.

**`git apply` counts as a restore.** The capture-and-recheck form the sequencing denial recommends now runs as written with `git apply` as the restore step.

**Denials say more about what did not happen.** When a `;` sequence starts with `set -e`, the reason now explains that the Bash tool ignores errexit, because it runs the command inside an `eval` in an `&&` list, so `set -e` does not stop the second command. Every denial also ends by naming the file writes in the refused command, such as a `>` redirect or a `tee`, because a deny discards the whole call and those writes never happened.

## Decision surface

Measured by running the v2.1.0 hook and this one over the same payloads and diffing the emitted `permissionDecision`. `defer` means the guard expressed no opinion and your own permission settings decided. All rows are foreground calls.

| command | v2.1.0 | v2.2.0 |
|---|---|---|
| `sudo -n make check \| tail -5` | defer | **deny** |
| `sudo --us root make check \| tail -5` | defer | **deny** |
| `sudo -h host make check \| tail -5` | defer | **deny** |
| `sudo A=1 -u root make check \| tail -5` | defer | **deny** |
| `env 'a b=c' make check \| tail -5` | defer | **deny** |
| `env -S 'make check' \| tail -5` | defer | **deny** |
| `make check \| tail -5; set -o pipefail` | defer | **deny** |
| `set -o pipefail \| true; make check \| tail -5` | defer | **deny** |
| `tail <(make check)` | defer | **deny** |
| `(make check); git push` | defer | **deny** |
| `FOO[0]=x make check \| tail -5` | defer | **deny** |
| `echo ${x:- #} ; make check \| tail -5` | defer | **deny** |
| `set -o pipefail; out=$(make check \| tail -5)` | deny | **defer** |
| `function f { set -o pipefail; }; f; make check \| tail -5` | deny | **defer** |
| `env EXIT_STATUS_GUARD_OVERRIDE=why make check \| tail -5` | deny | **defer** |
| `make check > log 2>&1; rc=$?; git apply p.diff; [ "$rc" -ne 0 ] \|\| exit 1` | deny | **defer** |
| `make check \| tail -5` | deny | deny |
| `make check > log 2>&1; rc=$?; git push; [ "$rc" -ne 0 ] \|\| exit 1` | deny | deny |
| `set -o pipefail; make check \| tail -5` | defer | defer |
| `sudo -l make check \| tail -5` | defer | defer |

Twelve rows gain a denial and four lose one. Every addition is a piped or sequenced gate that v2.1.0 failed to see, because a wrapper, a misplaced `pipefail`, a process substitution or a stretch of quoting hid it. The four withdrawals are commands that keep the status: `pipefail` really is on for the pipe, the override was armed, or the restore runs inside the capture-and-recheck form.

## Upgrading

```
claude plugin marketplace update claude-bouncer
claude plugin update exit-status-guard@claude-bouncer
```

A restart is needed — the hook is registered at startup, so a running session stays on the version it loaded.

**Nothing was removed and no configuration changed meaning.** `EXIT_STATUS_GUARD_OVERRIDE`, `EXIT_STATUS_GUARD_REGISTRY` and `.claude/exit-status-guard.json` keep their names and their defaults, and the environment-variable surface is identical to v2.1.0's. The 1.x spellings — `PIPE_GUARD_OVERRIDE=`, `.claude/pipe-guard.json`, `PIPE_GUARD_REGISTRY` — still work and are not going away. Where both config files exist the current one wins outright and they are never merged, so a file left under the old name goes unread the moment anyone adds the new one. The bundled registry gains one entry, `git apply` under `restores`.

**If a `set -o pipefail` was satisfying the guard from the wrong place, move it.** Put it before the pipe, at the top level of the command, in a statement of its own. A setting after the pipe, inside an ended subshell, or in a pipeline stage never reached the pipe in bash, so the gate's failure was being lost all along.

## Validation

**75 tests green** on the release tree, alongside the 304 tests at the repository root, 148 of them on the shared modules under `lib/`, and the four sibling suites `make check` runs beside them. The counts are from the release branch rather than quoted from an earlier run. Python 3.9 is this plugin's floor: this suite and the parser and wrapper tests were run again under Python 3.9.6 with the same result, and CI runs the shared parser against it.

The decision surface above is the check a test suite cannot make: both hooks run as subprocesses over the same payloads, so a row records what a session would actually have seen.

**What this does not assert.** No live Claude Code session runs in the suite — hook behaviour is asserted against synthetic payloads. The registry covers commands whose exit status *is* the answer, so whether *your* gates are registered is a question for `.claude/exit-status-guard.json`, not for the suite. Wanting a pipeline's output rather than its status is legitimate and indistinguishable from the bug, which is why the override exists rather than a narrower rule.
