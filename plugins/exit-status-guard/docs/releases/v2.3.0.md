Minor release: a `gh api` read piped into a filter is no longer denied, a gate tested by `if`, `while` or `until` is no longer denied as sequenced, and one shape that slipped past the sequencing rule inside a subshell is now caught.

## Highlights

**A `gh api` read piped into a filter passes.** `gh api` was registered as a gate whole, so `gh api repos/o/r/pulls | jq length` was denied as if its exit status were the answer. Only a write is a gate now: `-X` or `--method` naming anything but `GET`, or, with no method named, a field flag (`-f`, `-F`, `--field`, `--raw-field`) or `--input`, which switch gh to `POST`. An explicit `-X GET` with fields is a read, since gh sends them as a query string. A `gh api graphql -f query=…` call still counts as a write, because the field flag makes it a `POST`. A denied `gh api` write now names `--jq` (`-q`) as the rewrite, which keeps gh's exit status and needs no pipe, and falls back to the log-file form where the call passes `--slurp`, which gh refuses beside `--jq`.

**[A gate tested by a condition is not sequenced](https://github.com/karlkfi/claude-bouncer/blob/exit-status-guard/v2.3.0/plugins/exit-status-guard/README.md#3-sequenced-before-a-state-change-with-).** The `;` before `then` or `do` hands the gate's status to the condition, so nothing after it runs regardless of the result. `if git merge x; then …; else git merge --abort; fi`, `until make check; do sleep 5; done; git push` and `if make check; then git push; fi` now pass. An `if` whose failure path falls through to the next command, such as `if make check; then :; fi; git push`, still denies, and wrapping it in a subshell, `(if make check; then :; fi); git push`, now denies too.

## Decision surface

Measured by running the v2.2.0 hook and this one through their launchers over the same payloads and recording the emitted `permissionDecision`. `defer` means the guard expressed no opinion and your own permission settings decided. All rows are foreground calls.

| command | v2.2.0 | v2.3.0 |
|---|---|---|
| `gh api repos/o/r/pulls \| jq length` | deny | **defer** |
| `gh api repos/o/r/pulls --paginate \| jq length` | deny | **defer** |
| `gh api -X GET repos/o/r/pulls -f state=open \| jq length` | deny | **defer** |
| `gh api -X get repos/o/r/pulls \| jq length` | deny | **defer** |
| `if git merge x; then echo ok; else git merge --abort; fi` | deny | **defer** |
| `until make check; do sleep 5; done; git push` | deny | **defer** |
| `while ! make check; do sleep 5; done; git push` | deny | **defer** |
| `if make check; then git push; fi` | deny | **defer** |
| `(if make check; then :; fi); git push` | defer | **deny** |
| `gh api -X POST repos/o/r/issues -f title=x \| jq .number` | deny | deny |
| `gh api repos/o/r/issues -f title=x \| jq .number` | deny | deny |
| `gh api --method PATCH repos/o/r/issues/1 --input body.json \| head` | deny | deny |
| `gh api graphql -f query='{viewer{login}}' \| jq .` | deny | deny |
| `gh api -X POST repos/o/r/issues --jq .number` | defer | defer |
| `if make check; then :; fi; git push` | deny | deny |
| `if x; then make check; fi; git push` | deny | deny |
| `for x in a; do make check; done; git push` | deny | deny |
| `make check; git push` | deny | deny |
| `make check \| tail -5` | deny | deny |

Eight rows lose a denial and one gains one. The eight are reads, or gates whose status a condition consumes, and none of them lost a status. The one gained is the fall-through `if` from the row below it, now also seen inside a subshell. The `gh api` write rows keep their verdict, but the reason now leads with `--jq`.

## Upgrading

```
claude plugin marketplace update claude-bouncer
claude plugin update exit-status-guard@claude-bouncer
```

A restart is needed. The hook is registered at startup, so a running session stays on the version it loaded.

**Nothing was removed and no configuration changed meaning.** `EXIT_STATUS_GUARD_OVERRIDE`, `EXIT_STATUS_GUARD_REGISTRY` and `.claude/exit-status-guard.json` keep their names and defaults, as do the 1.x spellings. The bundled registry's `gh` gate loses `api`, and two new entries cover the `gh api` write forms.

**A registry of your own can keep every `gh api` call a gate.** If `.claude/exit-status-guard.json` or `EXIT_STATUS_GUARD_REGISTRY` carries a copy of the old `gh` pattern, the one ending in `|api)`, it still matches every `gh api` call, whether that registry extends the bundled one or sets `replace: true`. Drop `|api` from your copy, and under `replace: true` add the two new `gh api` patterns from the bundled `exit-status-guard.json`.

## Validation

**77 tests green** on the release tree, alongside the 319 tests at the repository root and the four sibling suites `make check` runs beside them. The counts are from the release branch rather than quoted from an earlier run. Python 3.9 is this plugin's floor, and CI runs the shared parser against it.

The decision surface above is the check a test suite cannot make: both hooks run as subprocesses over the same payloads, so a row records what a session would actually have seen.

**What this does not assert.** No live Claude Code session runs in the suite. The `gh api` method rules were measured with `--verbose` on gh 2.101.0 when the change was written, not again for this release, so a gh that picks its method differently would need its own patterns. Wanting a pipeline's output rather than its status is legitimate and indistinguishable from the bug, which is why the override exists rather than a narrower rule.
