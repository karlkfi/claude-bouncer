Minor release: a pipeline whose status was being read through a zsh array no longer escapes the piped-gate rule, and three denials that were reading a correct command as a broken one are withdrawn.

## Highlights

**Reading `$pipestatus` no longer suppresses the denial.** `make check | tail -5; echo $pipestatus` was treated as a command that recovers its own status, so the piped gate went unremarked. `$pipestatus` is zsh's array and the Bash tool runs bash, where it expands to empty — so the recovery was not happening and the gate's failure was still being lost. Redirect and read `$?` instead, or set `EXIT_STATUS_GUARD_OVERRIDE=<reason>` for a deliberate pipe.

**A quoted operator word no longer hides the pipe.** `make check ';' | tail -5` was split at the `';'` by the lexer but not by bash, so the pipeline the guard was meant to judge fell out of view. An `X+=1` prefix did the same thing by another route, reading as a command name rather than an assignment.

**A status test joined to the mutation with `&&` is credited.** `make check > log 2>&1; rc=$?; [ "$rc" -eq 0 ] && git push` captures the status, tests it, and publishes only on success — which is the shape the rule exists to produce. It was being denied under the sequencing rule anyway. The `[`, `[[` and `test` spellings are all credited; the `;`-joined and `||`-joined forms still deny, because neither gates the publish on the result.

**A backgrounded call may combine two statuses arithmetically.** `… ; exit $((rc|rc2))` is a status that reaches the completion notification, but `$((…))` was being read as several words and the `exit` as bare. It is no longer denied as a lost status.

**A newline is named as the separator it is.** A gate sequenced before a state change by a newline — the shape a heredoc leaves behind — still denies, and the reason now says so, and says to put the `&&` on the line carrying `<<` rather than after the body.

**A quoted prefix is a program, not an assignment.** `'X=1' make check | tail -5` makes bash look for a program named `X=1`, so the gate never runs and there is no status to lose. The denial is gone. Written unquoted it behaves exactly as before, and `'EXIT_STATUS_GUARD_OVERRIDE=…'` quoted no longer appears to arm a break-glass bash never set.

## Decision surface

Measured by running the v2.0.1 hook and this one over the same payloads and diffing the emitted `permissionDecision`. `defer` means the guard expressed no opinion and your own permission settings decided. The *background* row carries `run_in_background: true`; the rest are foreground calls.

| command | v2.0.1 | v2.1.0 |
|---|---|---|
| `make check \| tail -5; echo $pipestatus` | defer | **deny** |
| `make check ';' \| tail -5` | defer | **deny** |
| `X+=1 make check \| tail -5` | defer | **deny** |
| `make check > log 2>&1; rc=$?; [ "$rc" -eq 0 ] && git push` | deny | **defer** |
| `… rc=$?; … rc2=$?; exit $((rc\|rc2))` *(background)* | deny | **defer** |
| `'X=1' make check \| tail -5` | deny | **defer** |
| `make check \| tail -5` | deny | deny |
| `make check > log 2>&1; rc=$?; [ "$rc" -eq 0 ] \|\| git push` | deny | deny |
| `make check` newline `git push` | deny | deny |
| `make check > log 2>&1; echo EXIT=$?` *(background)* | deny | deny |
| `EXIT_STATUS_GUARD_OVERRIDE=why make check \| tail -5` | defer | defer |
| `make check && git push` | defer | defer |
| `ls -la` | defer | defer |

Three rows gain a denial and three lose one. The three additions are pipelines whose status was being lost while the guard said nothing; the three withdrawals are commands that either handle the status correctly or never run the gate at all.

## Upgrading

```
claude plugin marketplace update claude-bouncer
claude plugin update exit-status-guard@claude-bouncer
```

A restart is needed — the hook is registered at startup, so a running session stays on the version it loaded.

**Nothing was removed and no configuration changed meaning.** `EXIT_STATUS_GUARD_OVERRIDE`, `EXIT_STATUS_GUARD_REGISTRY` and `.claude/exit-status-guard.json` keep their names and their defaults, and the environment-variable surface is identical to v2.0.1's. The 1.x spellings — `PIPE_GUARD_OVERRIDE=`, `.claude/pipe-guard.json`, `PIPE_GUARD_REGISTRY` — still work and are not going away. Where both config files exist the current one wins outright and they are never merged, so a file left under the old name goes unread the moment anyone adds the new one.

**Every denial names `.claude/exit-status-guard.json`**, so a project can exempt its own report targets once instead of overriding them on every call. This repository exempts `make backlog` and `make backlog-next`.

**If you were relying on `$pipestatus` to satisfy the guard, it never satisfied bash.** Redirect the gate to a log, capture `$?` in the next statement, and read the log as its own step.

## Validation

**70 tests green** on the release tree, alongside the 207 shared-parser tests that cover `lib/bouncer_parse.py` directly and the four sibling suites `make check` runs beside them. The count is from the release branch rather than quoted from an earlier run. Python 3.9 is this plugin's floor, and CI runs the shared parser against it.

The decision surface above is the check a test suite cannot make: both hooks run as subprocesses over the same payloads, so a row records what a session would actually have seen.

**What this does not assert.** No live Claude Code session runs in the suite — hook behaviour is asserted against synthetic payloads. The registry covers commands whose exit status *is* the answer, so whether *your* gates are registered is a question for `.claude/exit-status-guard.json`, not for the suite. Wanting a pipeline's output rather than its status is legitimate and indistinguishable from the bug, which is why the override exists rather than a narrower rule.
