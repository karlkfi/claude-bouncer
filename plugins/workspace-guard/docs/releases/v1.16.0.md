Minor release: the guard reads the files an `awk` program opens and a `sed` script built from an expansion, and a relative path after a command that can `cd` now denies with the rewrite. A script the same call writes no longer runs under the guard's allow. A file after a substitution is judged, a `cd` inside a substitution stays where bash keeps it, and shell shapes that hid a guarded command from the parser are now read.

## Highlights

**An `awk` program's own files are judged.** `print > "FILE"`, `getline < "FILE"` and gawk's `@include` are judged like any other operand, and a target the guard cannot name, such as a variable, a field or a write to `ARGV`, asks. `system()`, the pipe forms and gawk's `@load` withhold the allow, as sed's `e` command does.

**A `sed` script built from an expansion is read as bash builds it.** A literal that the same command assigns is substituted, so a `w` command it adds asks for its file. A `$(…)`, a backtick, a `${…}` operator, `$1` or `$_` in a script now denies, as does a name the command binds in a form the guard cannot read (`declare`, a subshell, a copy, a glued `-e"$p"`). The deny carries a rewrite that writes the script literally.

**`sed -l` and `gsed` are read correctly.** On macOS, `sed -l SCRIPT FILE` now asks when `FILE` is outside the workspace. BSD sed's `-l` takes no argument, and the guard had been reading `FILE` as the script. `gsed`, GNU sed under its Homebrew name, is now checked as `sed` is, so `gsed -i 's/a/b/' /outside/y` asks instead of passing to your own permission rules.

**A relative path after a command that can `cd` denies.** `eval`, `source`, `.`, a trap that can fire before exit, and a `mapfile -C` callback can each change the directory, so the guard can no longer say where a later relative path lands. It denies and tells the agent to give the path absolutely. A trap set only on `EXIT` keeps the directory, and so does a trap whose action is literal text that cannot move it, so the cleanup idiom `trap 'rm -f ./tmp/key.pem' EXIT INT TERM` is unaffected. A trap whose action changes directory, or is built from an expansion the guard cannot read, denies.

**A script the same call writes is no longer vouched for.** The guard trusts a script inside the workspace as repo-resident code, so `cat in.txt; bash s.sh` is allowed. That trust used to reach a script the call had just written: `cat > t.sh <<'EOF'` … `EOF` followed by `bash t.sh` was allowed, whatever the heredoc held, which skipped your own permission rules entirely. A script that a redirect, heredoc, `cp`, `tee` or similar writes earlier in the same call now loses the exemption, so the call falls to your permission settings. A script that already existed keeps it.

**A file named after an unquoted substitution is judged.** `cat <(echo a) /outside/f` and `head -n $(echo 1) /outside/f` ask where they used to get `allow`. So do `grep`, `awk` and `sed` reading a file after a process substitution that stands as their pattern or program, as in `grep -v <(echo x) /outside/f`, and the same behind a wrapper that names its command, as in `env grep -v <(echo x) /outside/f`. Words after a substitution are no longer read as a command, which ends a false prompt on `echo $(date) cat /outside/f`. `ssh $(host) cat /outside/f` and `watch $(x) cat /outside/f` now defer, as they do with no substitution.

**A `cd` stays where bash keeps it.** A `cd` inside a process substitution stays inside it: after `x=<(cd sub)`, a relative read outside the workspace now asks instead of being allowed, and `cat <(cd sub; cat ../in.txt)` no longer prompts. bash 5.3's `${ …; }` and `${| …; }` substitutions run in the current shell, so a `cd` in one now moves the commands after it, and a command in one is judged.

**The shared parser reads more of what bash reads.** An outside read used to pass unjudged in each of these shapes, and is now judged:

- a `case` that follows `!`, `}`, `fi`, `done` or `esac` inside a `$( … )` substitution
- a subscript after a second `time` option, as in `time -- -p FOO[a;cat /x;b]=x true`
- a `$((…) ; …)` that bash runs as a command substitution, inside double quotes
- the line after a `[[ … =~ … ]]` test whose operand opens with a quote or an expansion, or after a `[[` used as a plain word, when a comment holding an apostrophe follows it

A thousand nested `${…}` expansions, alone or alternating with `$( )`, no longer crash the hook, so the command after them is judged.

**A quoted name before a `$(` no longer arms the override.** In `'WORKSPACE_GUARD_OVERRIDE'=$(echo x)` bash runs the word as a command rather than assigning it, so the guard keeps its deny where it used to downgrade it to a prompt.

Thirty-three rows gain scrutiny and four lose it. Eight of the thirty-three trade an allow or a prompt for a deny that carries the rewrite, so the agent gets the fix and nobody is asked. Three withdraw the allow from a script the call writes, which hands the call to your own permission settings. Of the four that lose it, two are reads that really stay inside the workspace, now that a `cd` is placed where bash runs it. `echo $(date) cat …` only prints. `ssh $(host) cat …` reads a file on another machine, and now defers as `ssh host cat …` already did.

The unquoted forms of the `case` and `$((…) ; …)` shapes already asked at v1.15.0, so only the double-quoted forms appear above.

## Upgrading

```
claude plugin marketplace update claude-bouncer
claude plugin update workspace-guard@claude-bouncer
```

A restart is needed. The hook is registered at startup, so a running session stays on the version it loaded.

**Nothing was removed and no configuration changed meaning.** No variable is new or renamed. `WORKSPACE_GUARD_OVERRIDE` still downgrades a deny to a prompt when it is a real assignment. A quoted name that bash runs as a command never was one.

**Expect two new denies.** A relative path after `eval`, `source`, `.`, a trap or a `mapfile -C` callback now denies, and so does a `sed` script the guard cannot read literally. Each deny names the rewrite, an absolute path or a literal script, and the agent retries with it.

**Expect a write-then-run call to reach your own permission rules.** A call that writes a script and runs it no longer gets the guard's allow. Replaying 4,000 commands sampled from one machine's last 30 days of sessions, 10 moved from allow to defer: 9 wrote a script and ran it, and 1 ran a repo script through a `$(…)` after a `cd`. 8 of the 10 ran in `auto`, where the classifier decides, and 2 in `default`, where they prompt unless a rule of yours allows them. Writing the script in one call and running it in the next keeps the exemption for an in-workspace script.
