Patch release: the `auto`-mode prompt about a shell `-c` body the hook "could not reach" stops firing on bodies it did in fact read.

## What changed

**A readable `-c` body no longer prompts.** 1.12.0 set the suppression off a loose scan — some token is a shell, a later short-option cluster carries `c` — and never asked whether the body had actually been extracted. Where it had been, the hook was checking that body's own paths a few lines later, so the prompt's reason was false for the shape behind most of the prompts measured in local session transcripts (Q211): the watcher idiom `timeout 240 bash -c 'until grep -q DONE tmp/w.log; do sleep 5; done'` sharing a string with a `tail` or `grep` of the same log. A body behind a container runtime or a remote shell is still out of reach and still prompts, and the body's own paths are checked either way.

The `allow` is still withheld for a readable body, so `default` mode is unchanged — your own permission rules decide there, exactly as before.

## Decision surface

Measured by running the v1.12.0 hook and this one as subprocesses over the same throwaway project, macOS, `WORKSPACE_GUARD_ESCALATE` unset. `defer` means the guard expressed no opinion and your own permission settings decided.

| command | mode | v1.12.0 | v1.12.1 |
|---|---|---|---|
| `cat f; timeout 5 bash -c 'grep -q DONE f'` | `auto` | ask | **defer** |
| `cat f; timeout 5 bash -c 'grep -q DONE f'` | `acceptEdits` | ask | **defer** |
| `cat f; timeout 5 bash -c 'grep -q DONE f'` | `bypassPermissions` | deny | **defer** |
| `cat f && bash -c 'echo hi'` | `auto` | ask | **defer** |
| `cat f; docker exec c sh -c 'cat /x'` | `auto` | ask | ask |
| `cat f; ssh host sh -c 'cat /x'` | `auto` | ask | ask |
| `cat f; bash -c 'cat /etc/passwd'` | `auto` | ask | ask |
| `cat f; bash -c 'kill -9 -1'` | `auto` | ask | ask |
| `cat f; bash -c 'kill -9 -1'` | `bypassPermissions` | deny | deny |
| `cat f && bash -c 'echo hi'` *(`ESCALATE=all`)* | `auto` | ask | ask |
| `cat f; timeout 5 bash -c 'grep -q DONE f'` | `default` | defer | defer |
| `cat /etc/passwd` | `default` | ask | ask |
| `cat ./f` | `default` | allow | allow |

Four rows lose a prompt and none gains one. Every row that keeps its prompt keeps it for a reason the prompt states correctly: a body on another filesystem, a path outside the root, or an unscoped kill.

The kill rows are there because they nearly moved. Reading the body changes which label the group carries, and the label is what the escalation acts on — an unscoped `kill` written inside a readable body was masked by it for the length of one commit on `main`. It never reached a release; the rows are pinned by tests now.

## Upgrading

```
claude plugin marketplace update claude-bouncer
claude plugin update workspace-guard@claude-bouncer
```

A restart is needed — the hook is registered at startup, so a running session stays on the version it loaded.

Nothing was removed and no configuration changed meaning. To keep prompting on these, `WORKSPACE_GUARD_ESCALATE=all` escalates the interpreter suppression, which covers every readable `-c` body — and inline interpreter code besides, so it is broader than what 1.12.0 did.

## Validation

**1567 tests green** on the release tree, alongside the 207 shared-parser tests and the four sibling suites `make check` runs beside them. The count is from the release branch rather than quoted from an earlier run.

The decision surface above is the check a test suite cannot make: both hooks run as subprocesses over the same project, so a row records what a session would actually have seen.

**What this does not assert.** No live Claude Code session runs in the suite — hook behaviour is asserted against synthetic payloads. The table was measured on macOS. And the guard reads the command string Claude is about to run, so it governs Claude's own tools and nothing else.
