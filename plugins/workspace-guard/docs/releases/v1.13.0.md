Minor release: the guard now reads through command wrappers such as `env`, `sudo` and `xargs`, judges the commands a `find` runs, and tracks a `cd` the way bash scopes it, so a guarded command behind any of them gets the decision it would get typed bare. Eight shell shapes that hid a command from the guard no longer do.

## Highlights

**[A guarded command behind a wrapper is judged as if typed bare](https://github.com/karlkfi/claude-bouncer/blob/workspace-guard/v1.13.0/plugins/workspace-guard/README.md#limitations).** The guard now peels `env`, `nice`, `nohup`, `timeout`, `stdbuf`, `setsid`, `ionice`, `time`, `xargs`, `exec`, `command`, `builtin`, `sudo`, `doas`, `caffeinate`, `chrt`, `taskset` and `flock` by their own option tables. `env cat /outside/f` and `sudo cat /outside/f` used to defer, and now ask. `command cd /outside && cat f` tracks the `cd` and asks where it was allowed. Files a wrapper opens itself are checked too: `sudo -e` writes its operands and `flock` creates its lock file, so `flock /tmp/lock make` now denies the way any host-wide temp write does. Put the lock under the project or the session scratchpad instead.

**[A wrapper the guard cannot read past escalates in the pre-approving modes](https://github.com/karlkfi/claude-bouncer/blob/workspace-guard/v1.13.0/plugins/workspace-guard/README.md#suppression-escalation-in-pre-approving-modes).** A wrapper flag the guard does not know, or an `xargs` that takes its operands on stdin, withholds `allow`. Where the command behind it is one the guard judges, that now asks in `auto` and `acceptEdits` and denies in `bypassPermissions`, the same as an unreadable `sh -c` body. `git ls-files | xargs grep foo` is one of those. `ls | xargs echo` is not, because `echo` is not a guarded command. `WORKSPACE_GUARD_ESCALATE=off` restores the silence.

**[`find -exec` is judged with `{}` standing for each start point](https://github.com/karlkfi/claude-bouncer/blob/workspace-guard/v1.13.0/plugins/workspace-guard/README.md#how-it-works).** The command behind `-exec`, `-execdir`, `-ok` or `-okdir` gets the decision it would get run against the start points, so `find /outside -name hosts -exec cat {} \;` asks where it used to defer. `find /outside -delete` and `-fprint /outside/f` ask too.

**A `cd` moves the tracked directory only where bash would move it.** A `cd` inside `( … )`, a bare `$( … )`, a function body, or a `{ … }` group, loop or `if` that is piped or backgrounded no longer moves the directory for the commands after it. Each of these used to place a later relative path in the wrong directory. `(cd sub) && cat ../secret` was allowed, and it now asks. A call to a function that runs a `cd` denies a later relative path with the literal-`cd` rewrite, because the guard cannot see where the call left the shell. A `case` pattern's `x)` no longer closes the subshell around it. A substitution inside a here-string is checked from the directory its command runs in. On the PowerShell tool, a `$(…)` after a `Set-Location` is checked in the directory it moved to.

**Eight shell shapes stop hiding a command from the guard.** Each of these shapes used to make the guard misread where a command started or ended, and so defer or allow the command after it. They are: an array-element prefix such as `FOO[0]=x`, an ANSI-C string such as `$'\''`, a `#` inside backticks or `${...}`, a `#` straight after a substitution's close, a nested backtick, and a quote inside a double-quoted substitution. A command inside a process substitution, `true >(rm -rf ../x)`, is now judged like the same command written plainly. A file operand that holds a backtick substitution, ``cat `cat list.txt` ``, denies as the `$(…)` spelling already did.

**Three prompts stop firing.** Two were about files the command never opens. After `(cd ..)`, `cat in.txt` reads the project's own file, because the subshell's `cd` never reached the outer shell. `cd sub && cat <<<"$(cat ../in.txt)"` reads inside the project too. The third was a false deny: BSD sed's in-place form, `sed -i '' "s/old/$new/" in.txt`, read the empty suffix as the script and denied the variable in it as an unexpandable path. It is allowed now.

**A deny names the writes it discarded.** A deny refuses the whole call, so every file write in it never happened. The reason now lists them: a `>` redirect, `tee`, `sed -i`, `cp`, `mv`, or a heredoc script fed to an interpreter.

## Decision surface

Measured by running the v1.12.1 hook and this one as subprocesses over the same throwaway project, holding `in.txt`, `list.txt` and an empty `sub/`, with no `WORKSPACE_GUARD_*` variable set unless the row says so. macOS. `defer` means the guard expressed no opinion and your own permission settings decided.

| command | mode | v1.12.1 | v1.13.0 |
|---|---|---|---|
| `env cat /outside/f` | `default` | defer | **ask** |
| `sudo cat /outside/f` | `default` | defer | **ask** |
| `command cd /outside && cat f` | `default` | allow | **ask** |
| `git ls-files \| xargs grep foo` | `auto` | defer | **ask** |
| `git ls-files \| xargs grep foo` | `bypassPermissions` | defer | **deny** |
| `flock /tmp/lock make` | `default` | defer | **deny** |
| `find /outside -name hosts -exec cat {} \;` | `default` | defer | **ask** |
| `(cd sub) && cat ../secret` | `default` | allow | **ask** |
| `f() { cd sub; }; f; cat in.txt` | `default` | allow | **deny** |
| ``cat `cat list.txt` `` | `default` | allow | **deny** |
| `true >(rm -rf ../x)` | `default` | defer | **ask** |
| `echo ${x:- #} ; cat /outside/f` | `default` | defer | **ask** |
| `sudo cat in.txt` | `default` | defer | **allow** |
| `(cd ..) && cat in.txt` | `default` | ask | **allow** |
| `cd sub && cat <<<"$(cat ../in.txt)"` | `default` | ask | **allow** |
| `sed -i '' "s/old/$new/" in.txt` | `default` | deny | **allow** |
| `git ls-files \| xargs grep foo` *(`ESCALATE=off`)* | `auto` | defer | defer |
| `ls \| xargs echo` | `auto` | defer | defer |
| `cat /outside/f` | `default` | ask | ask |
| `echo x > /var/tmp/f` | `default` | deny | deny |

Twelve rows gain scrutiny and four lose it. Three of the four are the withdrawn prompts above, about files the command never opens or a path that was never unexpandable. The fourth, `sudo cat in.txt`, used to defer because the guard could not see past `sudo`; reading through it, the guard finds a read inside the project and allows it, the same as `cat in.txt` typed bare.

## Upgrading

```
claude plugin marketplace update claude-bouncer
claude plugin update workspace-guard@claude-bouncer
```

A restart is needed. The hook is registered at startup, so a running session stays on the version it loaded.

**Nothing was removed and no configuration changed meaning.** No variable is new or renamed. `WORKSPACE_GUARD_ESCALATE` now also covers the wrapper and `xargs` suppressions, and `=off` turns them off with the rest.

**Expect new prompts on commands behind a wrapper, and on relative paths after a scoped `cd`.** Both are reads the guard used to miss. If you work in `auto` or `acceptEdits`, an `xargs` feeding a guarded command now asks. Where that is routine for you, `WORKSPACE_GUARD_ESCALATE=off` puts it back without turning the guard off. If a script takes a `flock` under `/tmp`, move the lock file into the project or the session scratchpad.

**1680 tests green, 19 skipped,** on the release tree, alongside the 304 tests at the repository root, 148 of them on the shared modules under `lib/`, and the four sibling suites `make check` runs beside them. The counts are from the release branch rather than quoted from an earlier run.

The decision surface above is the check a test suite cannot make: both hooks run as subprocesses over the same project, so a row records what a session would actually have seen rather than what a fixture asserts.

**What this does not assert.** No live Claude Code session runs in the suite. Hook behaviour is asserted against synthetic payloads. The table was measured on macOS; the PowerShell paths are asserted by fixtures on every platform rather than by a Windows session. And the guard reads the command string Claude is about to run, so it governs Claude's own tools and nothing else.
