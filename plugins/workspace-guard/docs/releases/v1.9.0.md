Minor release: the workspace boundary now covers process kills. A path is the main way out of a workspace but not the only one — `pkill -f ginkgo` reaches every checkout on the host — so an unanchored kill is denied, on both shells and inside a `sh -c` body. Shell `-c` bodies are analyzed as their own command string, plus parsing and performance fixes.

> [!IMPORTANT]
> **Kills that used to run untouched now deny.** `pkill -f ginkgo`, `killall node`, `Stop-Process -Name node`, `taskkill /IM node.exe`, and `pgrep -f ginkgo | xargs kill` all signal by pattern or by name, which reaches sibling worktrees and unrelated repos alike. Each is denied unless an operand anchors the pattern to this project root. The two rewrites cost nothing in the normal case: run `pgrep -fl <pattern>` and kill the pid(s) you meant, or put the workspace path in the pattern. For a deliberate cross-workspace kill, `WORKSPACE_GUARD_OVERRIDE=<reason>` downgrades the deny to `ask`.

Killing by pid is untouched: `kill 1234`, `Stop-Process -Id 1234` and `taskkill /PID 1234` all defer, as does a `kill -0` liveness probe whatever fed its pids. An *anchored* kill defers too rather than emitting `allow` — a destructive command is not this hook's to green-light. See [Unanchored process-kill deny](https://github.com/karlkfi/claude-workspace-guard/blob/v1.9.0/README.md#unanchored-process-kill-deny) for the anchoring rule, the pid-source rules, and the full case list.

**Shell `-c` bodies**

* feat(shell-c): analyze the body of a shell `-c` command (Q61) by @karlkfi in https://github.com/karlkfi/claude-workspace-guard/pull/139

`sh -c 'cat /etc/hosts'` now gets the same answer it would written unwrapped, under the wrappers that actually appear (`timeout`, `xargs -I{}`, `find -exec`, `env`, `nohup`, `nice`, `stdbuf`). A body that doesn't run on this host is left alone — `docker exec c sh -c …` and `ssh host sh -c …` defer, because a path inside a container is not a path on this disk. Either way a `-c` body never earns the string an `allow`.
