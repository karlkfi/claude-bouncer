Minor release: the files a `sed` script names are now judged, a relative `ln -s` target is read from where the link lands, and two prompts become denies that carry the rewrite. One sibling-checkout deny becomes a prompt, and shell shapes that hid a guarded command from the parser are now read.

## Highlights

**A `sed` script's own files are judged.** `sed '/x/w /outside/f' in.txt` writes `/outside/f`, and the guard used to allow it, because it judged `in.txt` and read the script as text. The `w`, `W`, `r` and `R` commands and the `s///w` flag now name a file the guard judges like any other argument. GNU sed's `e` command runs a shell command, so a script holding it no longer earns an `allow`.

**`sed -i '' SCRIPT FILE` denies with the `-e` rewrite.** On macOS, `sed -i '' '/re/d' in.txt` takes `/re/d` as the script, while GNU sed takes it as a file, so the guard cannot tell which it is. It used to ask about the script as an absolute path. It now denies and names `sed -i '' -e SCRIPT FILE`, which is the same edit on macOS sed and which the guard can read. A script that writes, reads or runs something still asks.

**A relative `ln -s` target resolves from the link's directory.** The kernel reads a relative link target from the directory the link sits in, and the guard read it from the working directory. So `cd a/b && ln -s ../main/f ../../rel`, with `main` another checkout beside the workspace, was allowed: the guard judged a path inside the workspace while the link pointed into a sibling checkout. It now judges the path the link really reaches. A hard link's source is still a path from the working directory.

**[A link installed outside the workspace may point into a sibling checkout](https://github.com/karlkfi/claude-bouncer/blob/workspace-guard/v1.15.0/plugins/workspace-guard/README.md#worktree-aware-sibling-checkout-deny).** `ln -s TARGET LINK` writes only at `LINK`, and `TARGET` is a string stored in the link. The guard judged both as writes, so installing a link outside the workspace that points into another checkout of the same repository was denied as a sibling-checkout write. It now asks on the link. A link landing inside the workspace or into a directory, a hard link, and a later write through the link in the same command still deny. On the PowerShell tool, a `New-Item -ItemType SymbolicLink` that is the whole command gets the same treatment.

**[A guarded command beside an unreachable `sh -c` body denies in `auto` and `acceptEdits`](https://github.com/karlkfi/claude-bouncer/blob/workspace-guard/v1.15.0/plugins/workspace-guard/README.md#suppression-escalation-in-pre-approving-modes).** `cat in.txt; docker exec c sh -c '…'` used to ask, because the guard cannot read inside a container or remote shell and so would not vouch for the whole string. The deny tells the agent to run the wrapper call on its own, where the guard has nothing to judge. `WORKSPACE_GUARD_OVERRIDE=<reason>` as a prefix turns the deny back into a prompt for one command.

**A PowerShell-tool deny names the operator's override.** It used to tell the agent to re-issue the command through the Bash tool with `WORKSPACE_GUARD_OVERRIDE`, a route that ran the command with no prompt at all. It now names the override as an environment setting the operator makes.

**The shared parser reads more of what bash reads.** A guarded command written behind `time -p` or `time --`, or after a `#` that bash reads as text — inside an extglob group, a `(( … ))`, a `[[ … =~ … ]]` operand, after an escaped blank — used to pass unread. So did one inside a quoted `$( )` holding `${…}`, a backtick or a nested quoted `$( )`, and one after a `[[ … ]]` holding a comment with an apostrophe. Each is now judged.

## Decision surface

Measured by running the v1.14.0 hook and this one through their launchers over the same throwaway repository, where the session runs in a linked worktree holding `in.txt` and an empty `a/b/`, and `<sibling>` is the repository's main checkout. No `WORKSPACE_GUARD_*` variable is set unless the row says so. macOS. `defer` means the guard expressed no opinion and your own permission settings decided.

| command | mode | v1.14.0 | v1.15.0 |
|---|---|---|---|
| `sed '/x/w /opt/q8-fake-target/f' in.txt` | `default` | allow | **ask** |
| `sed 's/x/y/w /opt/q8-fake-target/f' in.txt` | `default` | allow | **ask** |
| `sed '/x/r /opt/q8-fake-target/f' in.txt` | `default` | allow | **ask** |
| `sed -i '' '/re/d' in.txt` | `default` | ask | **deny** |
| `cd a/b && ln -s ../repo/in.txt ../../rel` *(target in `<sibling>`)* | `default` | allow | **deny** |
| `cd a/b && ln -s ../outside ../../link` | `default` | allow | **ask** |
| `ln -s <sibling>/in.txt /opt/q8-fake-target/link` | `default` | deny | **ask** |
| `cat in.txt; docker exec c sh -c 'cat /opt/q8-fake-target/c'` | `auto` | ask | **deny** |
| `time -p cat /opt/q8-fake-target/c` | `default` | defer | **ask** |
| `[[ $x == @(a\|#b) ]]; cat /opt/q8-fake-target/c` | `default` | defer | **ask** |
| `echo a\ #b ; cat /opt/q8-fake-target/c` | `default` | defer | **ask** |
| `echo "$(echo ${y:- #}; cat /opt/q8-fake-target/c)"` | `default` | defer | **ask** |
| `echo "$(echo "$(true ")" x)"; cat /opt/q8-fake-target/c)"` | `default` | defer | **ask** |
| `[[ -n x #it's` newline `]] && echo "$(cat /opt/q8-fake-target/c)"` | `default` | defer | **ask** |
| `sed 's/x/y/' in.txt` | `default` | allow | allow |
| `sed -i '' -e '/re/d' in.txt` | `default` | allow | allow |
| `sed -i '' '/re/w /opt/q8-fake-target/f' in.txt` | `default` | ask | ask |
| `cd a/b && ln -s ../in.txt ../link` | `default` | allow | allow |
| `ln -s <sibling>/in.txt link` | `default` | deny | deny |
| `ln <sibling>/in.txt /opt/q8-fake-target/link` | `default` | deny | deny |
| `WORKSPACE_GUARD_OVERRIDE=why cat in.txt; docker exec c sh -c 'cat /opt/q8-fake-target/c'` | `auto` | ask | ask |
| `cat in.txt; docker exec c sh -c 'cat /opt/q8-fake-target/c'` | `default` | defer | defer |
| `cat /opt/q8-fake-target/c` | `default` | ask | ask |
| `cat in.txt` | `default` | allow | allow |

Thirteen rows gain scrutiny and one loses it. Two of the thirteen trade a prompt for a deny that carries the rewrite, so the agent gets the fix and nobody is asked. The one that loses scrutiny is a link installed outside the workspace, which now asks instead of denying. The `<sibling>` rows deny only because the guard knows that path is another checkout: from a main checkout the same commands ask as outside-workspace paths.

## Upgrading

```
claude plugin marketplace update claude-bouncer
claude plugin update workspace-guard@claude-bouncer
```

A restart is needed. The hook is registered at startup, so a running session stays on the version it loaded.

**Nothing was removed and no configuration changed meaning.** No variable is new or renamed. `WORKSPACE_GUARD_OVERRIDE` now also downgrades the unreachable-`sh -c` deny to a prompt, and `WORKSPACE_GUARD_ESCALATE=off` still turns escalation off altogether.

**If you edit files with `sed -i ''` on macOS, expect a deny where it used to prompt.** The agent reads the `-e` rewrite and retries, and the retried command is allowed.

## Validation

**WG_COUNT** on the release tree, alongside the ROOT_COUNT tests at the repository root and the four sibling suites `make check` runs beside them. The counts are from the release branch rather than quoted from an earlier run.

The decision surface above is the check a test suite cannot make: both hooks run as subprocesses over the same repository and home directory, so a row records what a session would actually have seen.

**What this does not assert.** No live Claude Code session runs in the suite. The table was measured on macOS, and the PowerShell rows of the symlink change were not re-driven for this release. The guard reads the command string Claude is about to run, so it governs Claude's own tools and nothing else.
