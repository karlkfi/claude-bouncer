Minor release, and the first cut from `karlkfi/claude-bouncer`: four commands join the workspace boundary on the Bash tool and three on the PowerShell tool, a write into another session's scratchpad now denies instead of prompting, and a substitution hiding a guarded read behind a `case` clause or a heredoc is finally read in full.

> [!IMPORTANT]
> **This plugin now ships from the `claude-bouncer` marketplace, and the old one stops at v1.10.0.** `karlkfi/claude-workspace-guard` still serves 1.10.0 and will not move again, so an install pinned to `workspace-guard@workspace-guard` gets no further updates and no notice that it is behind. The two commands that move it are under [Upgrading](#upgrading). Nothing else about the plugin changed identity — same hook, same environment variables, same config file, same `WORKSPACE_GUARD_OVERRIDE`.

## Highlights

**[Four more commands read and write files, so four more are guarded](https://github.com/karlkfi/claude-bouncer/blob/workspace-guard/v1.11.0/plugins/workspace-guard/README.md#what-it-does).** `cut`, `base64` and `unlink` join the guarded set, and `ln` is now judged by its own operands rather than only by a later read through the link. An `ln` naming a path outside the project root prompts on the link command itself, where it used to pass and surface only when something read through the link afterwards. BSD `base64 -o` is treated as a write, so it is checked against the write boundary rather than the read one.

**PowerShell catches up with Bash on three counts.** `New-Item` is guarded, and for `SymbolicLink`, `HardLink` and `Junction` the `-Target`/`-Value` path is checked as well as `-Path`. `mkdir` and `md` are guarded too — they are functions over `New-Item` rather than aliases of it, which is why they needed their own entry, and `-Value` and `-Name` are named-only content parameters, so `mkdir x -Value C:\out\y` does not prompt. And the PowerShell tool no longer lets a clean cmdlet vouch for interpreter code sharing its command string: `Get-Content .\README.md; python3 -c '...'` falls through to your own permission settings instead of returning `allow`, matching the Bash tool since v1.10.0.

**A write into another session's scratchpad denies.** Claude Code hands every session a scratchpad under `/tmp/claude-<uid>/<project-slug>/<session-id>/`, and the guard exempts your own for reads and writes both. A sibling session's tree under the same project slug stays readable and is no longer writable — the refusal names your own scratchpad, and `WORKSPACE_GUARD_OVERRIDE=<reason>` covers a deliberate cross-session write.

**Two rules stop firing where they should not.** A loop variable used inside a command substitution — `for f in docs/*.md; do echo "$(wc -l < "$f")"; done` — is resolved now instead of blocked as unreadable. On the PowerShell side, `Remove-Item`, `Move-Item` and `Rename-Item` judge a symlink by the link rather than by what it points at, so removing a link whose target sits outside the workspace no longer prompts; `-Recurse` over a directory link joins them, because it unlinks the entry without reaching the target. Reading, writing or copying *through* a link still follows it and is checked as before.

**A `case` clause and a heredoc body no longer end a substitution early.** Four parser fixes land here, and they point the same way: a guarded command written inside `"$(…)"` used to escape the scan when the substitution held a `case` clause whose pattern `)` looked like the terminator, when a heredoc body inside it contained an apostrophe, or when an apostrophe in an *earlier* top-level heredoc body opened a quoted run that swallowed the rest of the raw scan. Each of those returned `allow` for the whole command string on the strength of a leading guarded command reading stdin. They now prompt.

## Decision surface

Measured by running the v1.10.0 hook and this one over the same throwaway project and diffing the emitted `permissionDecision`. `~/other/` is outside the project root; `defer` means the guard expressed no opinion and your own permission settings decided.

| command | v1.10.0 | v1.11.0 |
|---|---|---|
| `cut -d: -f1 ~/other/f.txt` | defer | **ask** |
| `base64 ~/other/f.txt` | defer | **ask** |
| `base64 -o ~/other/out.b64 ./docs/a.md` | defer | **ask** |
| `unlink ~/other/f.txt` | defer | **ask** |
| `ln -s ~/other/f.txt ./link` | defer | **ask** |
| `echo "$(case $x in a) cat ~/other/f.txt;; esac)"` | defer | **ask** |
| `echo "$(cat <<E` … `E` `cat ~/other/f.txt)"` | defer | **ask** |
| `for f in docs/*.md; do echo "$(wc -l < "$f")"; done` | deny | **defer** |
| `cat ~/other/f.txt` | ask | ask |
| `cat ./docs/a.md` | allow | allow |
| `grep -r x .` | allow | allow |

Seven rows gain a prompt and one loses a denial. Every one of the seven is a command that reads or writes outside the project root and used to say nothing about it, which is the whole of what a minor means here: the boundary moved, and it moved outward.

## Upgrading

An install from the old marketplace cannot reach this version, because the marketplace it points at is a different repository. Remove it and add the new one:

```
/plugin marketplace remove workspace-guard
/plugin marketplace add karlkfi/claude-bouncer
/plugin install workspace-guard@claude-bouncer
```

Already on `claude-bouncer`:

```
claude plugin marketplace update claude-bouncer
claude plugin update workspace-guard@claude-bouncer
```

Either way a restart is needed — the hook is registered at startup, so a running session stays on the version it loaded.

**Nothing was removed and no configuration changed meaning.** `WORKSPACE_GUARD_OVERRIDE`, `WORKSPACE_GUARD_READ_ALLOW_PREFIXES` and the rest keep their names and their defaults.

**Expect more prompts, and they are the release.** Seven of the shapes in the table above used to pass unremarked and now reach you. If one of them is routine in your workflow, the fix is a read-allow prefix or an in-root path rather than turning the guard off — see [Allowed read prefixes](https://github.com/karlkfi/claude-bouncer/blob/workspace-guard/v1.11.0/plugins/workspace-guard/README.md#allowed-read-prefixes) and [Avoiding workspace-guard permission prompts](https://github.com/karlkfi/claude-bouncer/blob/workspace-guard/v1.11.0/plugins/workspace-guard/README.md#avoiding-workspace-guard-permission-prompts).

**The move**

The five guards now live in one repository with one marketplace manifest, one test workflow, and one backlog. The part that reaches this plugin's behaviour is the shell parser: all five carried their own lexer, the copies had drifted, and merging them took the superset rather than a favourite. workspace-guard picked up exit-status-guard's backslash-newline folding in `strip_comments` and its `|&` separator. Neither moved a verdict in the shapes measured above, which is the expected result for a merge that was checked in both directions before it landed — `tests/test_bouncer_parse.py` asserts each guard's gap so a later edit cannot quietly reintroduce it. Each plugin carries a vendored copy of `lib/bouncer_parse.py` that `make sync-check` verifies, because a plugin installed into Claude Code's cache cannot read a path outside its own root.

Documentation, images, backlog and release tooling round out the rest and change nothing the hook decides.

## Validation

**1420 tests green** on the release tree, alongside the 140 shared-parser tests that cover `lib/bouncer_parse.py` directly and the four sibling suites `make check` runs beside them. The count is from the release branch rather than quoted from an earlier run.

The decision surface above is the check that a test suite cannot make: both hooks run as subprocesses over the same project, so a row records what a session would actually have seen rather than what a fixture asserts.

**What this does not assert.** No live Claude Code session runs in the suite — hook behaviour is asserted against synthetic payloads. The PowerShell changes are asserted the same way on every platform; the Windows job runs the suite under both pwsh and Git Bash, but `Remove-Item -Recurse` over a directory link rests on a measurement of what the cmdlet does rather than on a Windows fixture exercising it. And the guard reads the command string Claude is about to run, so it governs Claude's own tools and nothing else. Anything that must hold unconditionally belongs in the filesystem's permissions.
