Minor release, and the first cut from `karlkfi/claude-bouncer`: a repo that configured `"action": "ask"` gets the prompt it asked for in `auto` mode, instead of a refusal.

> [!IMPORTANT]
> **This plugin now ships from the `claude-bouncer` marketplace, and the old one stops at v0.5.1.** `karlkfi/claude-foreground-guard` still serves 0.5.1 and will not move again, so an install pinned to `foreground-guard@foreground-guard` gets no further updates and no notice that it is behind. The two commands that move it are under [Upgrading](#upgrading). No config key changed name, default, or meaning.

## Highlights

**[`auto` is not an unattended mode](https://github.com/karlkfi/claude-bouncer/blob/foreground-guard/v0.6.0/plugins/foreground-guard/README.md#unattended-permission-modes).** `UNATTENDED_MODES` converts a would-be `ask` into a `deny`, on the reasoning that a prompt nobody answers blocks the session forever. In `auto` that reasoning does not hold: the prompt is delivered and somebody answers it. So the conversion was removing the human rather than protecting them, and `auto` is out of the set.

The change is narrow by construction. Both classes deny by default, so nothing converts unless a `deny` has already been de-escalated — the set only ever fired on a repo that wrote `"action": "ask"` into `.claude/foreground-guard.json` and asked to be prompted. A default install sees no difference at all. `dontAsk` and `bypassPermissions` still convert, because there the prompt genuinely reaches nobody.

This is the last of the three guards to drop it. branch-guard removed `auto` from its own `NON_INTERACTIVE_MODES` in v1.7.0 for the same reason, and workspace-guard has always treated `bypassPermissions` alone as human-free.

## Decision surface

Measured by running the v0.5.1 hook and this one over the same payloads and diffing the emitted `permissionDecision`. The *config* rows carry `{"poll": {"action": "ask"}, "slow": {"action": "ask"}}`; the *default config* rows carry no config file.

| command | v0.5.1 | v0.6.0 |
|---|---|---|
| `gh run watch` *(config `"action": "ask"`, `auto`)* | deny | **ask** |
| `tail -f log` *(config `"action": "ask"`, `auto`)* | deny | **ask** |
| `gh run watch` *(config `"action": "ask"`, `manual`)* | ask | ask |
| `gh run watch` *(config `"action": "ask"`, `dontAsk`)* | deny | deny |
| `gh run watch` *(config `"action": "ask"`, `bypassPermissions`)* | deny | deny |
| `gh run watch` *(default config, `auto`)* | deny | deny |
| `gh run watch` *(default config, `manual`)* | deny | deny |
| `ls -la` | defer | defer |

Two rows move and both move the same way, out of `deny` and into the prompt the config asked for. The two unattended modes and every default row are unchanged, which is what makes this a de-escalation of a de-escalation rather than a weakening of the guard.

## Upgrading

An install from the old marketplace cannot reach this version, because the marketplace it points at is a different repository. Remove it and add the new one:

```
/plugin marketplace remove foreground-guard
/plugin marketplace add karlkfi/claude-bouncer
/plugin install foreground-guard@claude-bouncer
```

Already on `claude-bouncer`:

```
claude plugin marketplace update claude-bouncer
claude plugin update foreground-guard@claude-bouncer
```

Either way a restart is needed — the hook is registered at startup, so a running session stays on the version it loaded.

**Nothing was removed and no configuration changed meaning.** The eight config keys are the same eight, with the same defaults.

**If you configured `"action": "ask"` and worked in `auto`, expect prompts where you were getting refusals.** That is the release. The guard is still doing the same detection and reaching the same conclusion; the difference is that you now get to answer it.

**This plugin is pre-1.0 and its surface is unstable by design.** Nothing breaks in this release, but a break here rides in a minor rather than waiting for a major, and it will be stated in the notes when it happens.

## Everything since v0.5.1

* feat(foreground-guard): honour a configured ask in auto mode by @karlkfi in https://github.com/karlkfi/claude-bouncer/pull/23

**The move**

The five guards now live in one repository with one marketplace manifest, one test workflow, and one backlog. The part that could have reached this plugin's behaviour is the shell parser: all five carried their own lexer and the copies had drifted, so merging them took the superset rather than a favourite. This guard's share was an import swap — it keeps its own tokenizer and segmenter, because it has to know which segment was *backgrounded* and the shared operator-preserving lexer does not answer that. Its heredoc stripper was checked against the copy it replaced over thirteen shapes crossing quoted and expanded bodies, tab-stripped forms, unterminated bodies, arithmetic `<<`, and multiple heredocs on one line: identical output on all thirteen. The three later parser fixes in this window landed in the substitution scanner, which this guard does not call.

Documentation, images, backlog and release tooling round out the rest and change nothing the hook decides.

## Validation

**200 tests green** on the release tree, alongside the 140 shared-parser tests and the four sibling suites `make check` runs beside them. The count is from the release branch rather than quoted from an earlier run.

The **never-`allow`** invariant is asserted on every end-to-end call: the hook returns `ask`, `deny`, or nothing. An `allow` would bypass your permission settings and override the sibling guards evaluating the same command.

**What this does not assert.** No live Claude Code session runs in the suite — hook behaviour is asserted against synthetic payloads, and the table above against real subprocess invocations rather than a real session. Class B's registry is per-repo by design, so no test can tell you whether *your* slow commands are registered, only that a registered one behaves; the [friction report](https://github.com/karlkfi/claude-bouncer/blob/foreground-guard/v0.6.0/plugins/foreground-guard/README.md#friction-report) is the tool for that.

**This is a productivity guard, not a security boundary.** Parsing uncertainty defers, and infrastructure errors fail open to a silent defer, because a guard that breaks the session is worse than a missed prompt. Do not deploy it as a control that something must not run.
