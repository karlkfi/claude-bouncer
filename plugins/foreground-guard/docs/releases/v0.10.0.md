Minor release: a loop that waits through `$( )`, `bash -c` or `eval` now denies, and a `sleep` after a loop's `done` no longer counts as polling. A `Monitor` until-loop stops being denied on Claude Code 2.1.321 and later. Shared-parser fixes expose blocking commands that bash 5.3's `${ …; }`, a quoted `$((…) ; …)`, a `case` after `!`, and a `[[ … =~ … ]]` followed by a comment used to hide.

## Highlights

**A `Monitor` until-loop is no longer denied.** From Claude Code 2.1.321, a hook matched on `Bash` also runs for a `Monitor` call, and receives it with `tool_name` set to `Bash`. So `until curl -sf localhost:8080/health; do sleep 2; done`, armed as a Monitor the way the poll-loop deny advises, was denied by that same deny. The matcher now names `Monitor`, which Claude Code delivers as itself, and the hook lets any tool but `Bash` through.

**A loop that sleeps through a substitution, `bash -c` or `eval` denies.** `while true; do x=$(sleep 5); done` polls as surely as a bare `sleep` in the body, and the guard used to defer on it. The body of a `$( )`, a `bash -c` string or an `eval` string now counts toward the loop around it. A `for` loop's word list is the exception: bash expands it once, so `for i in $(sleep 1; echo a b c); do :; done` still defers.

**A `sleep` after a loop's `done` is judged on its own.** `for c in a b; do true; done; sleep 1; ls` runs the sleep once, and the guard denied it as a poll. A sleep now counts toward the loop finding only while a `while`, `until` or `for` is open. A long sleep after the loop is still denied by the sleep floor.

**The shared parser reads more of what bash runs.** bash 5.3's `${ …; }` substitution runs its body, so `echo ${ sleep 600; }` now denies. A substitution body holding a heredoc is judged, where the guard deferred. bash runs a double-quoted `"$((echo x) ; gh run watch 1)"` as a command substitution, and the guard let the watch inside it through, though it already denied the unquoted form. A `case` after `!` in a `$( )` body, a subscript after `time -- -p`, and a line after `[[ x =~ "a" ]];#it's` or `echo [[ =~ x;#it's` all used to hide the command in them. A thousand nested `${…}` expansions, alone or alternating with `$( )`, used to end the hook with no decision. Each of these now gets judged.

## Decision surface

Measured by running the v0.9.0 hook and this one through their launchers over the same payloads, with no config file, and recording the emitted `permissionDecision`. `defer` means the guard expressed no opinion and your own permission settings decided. A row with a newline in it is one command written over two lines.

| command | v0.9.0 | v0.10.0 |
|---|---|---|
| `while true; do x=$(sleep 5); done` | defer | **deny** |
| `while true; do bash -c 'sleep 5'; done` | defer | **deny** |
| `while true; do eval 'sleep 5'; done` | defer | **deny** |
| `for c in a b; do true; done; sleep 1; ls` | deny | **defer** |
| `echo ${ sleep 600; }` | defer | **deny** |
| `echo "$(cat <<E` newline `x` newline `E` newline `gh run watch 1)"` | defer | **deny** |
| `echo "$((echo x) ; gh run watch 1)"` | defer | **deny** |
| `echo $(! case a in a) gh run watch 1;; esac)` | defer | **deny** |
| `time -- -p FOO[a;gh run watch 1;b]=x true` | defer | **deny** |
| `[[ x =~ "a" ]];#it's` newline `gh run watch 1` | defer | **deny** |
| `echo [[ =~ x;#it's` newline `gh run watch 1` | defer | **deny** |
| `echo ${x:-` …1000 nested… `}; gh run watch 1` | defer | **deny** |
| `echo ${x:-$(` …500 alternating… `)}; gh run watch 1` | defer | **deny** |
| `for i in $(sleep 1; echo a b c); do :; done` | defer | defer |
| `for c in a b; do true; done; sleep 300` | deny | deny |
| `while true; do sleep 5; done` | deny | deny |
| `echo $((echo x) ; gh run watch 1)` | deny | deny |
| `echo ${\| sleep 600; }` | deny | deny |
| `[[ x =~ a ]];#it's` newline `gh run watch 1` | deny | deny |
| `sleep 300` | deny | deny |
| `sleep 1` | defer | defer |
| `ls -la` | defer | defer |

Twelve rows gain a denial and one loses one, all on a default install with no config file. The one that lost its deny runs a one-second sleep once, after the loop has finished.

The `Monitor` change is not in the table, because it moves which payload Claude Code sends rather than what the hook does with one. Both versions of the hook deny the curl until-loop when it arrives as `Bash` and defer when it arrives as `Monitor`. That Claude Code 2.1.321 sends a `Monitor` call as `Bash` under the old matcher is from the transcripts behind the fix, not re-measured for this release.

## Upgrading

```
claude plugin marketplace update claude-bouncer
claude plugin update foreground-guard@claude-bouncer
```

A restart is needed. The hook and its matcher are registered at startup, so a running session stays on the version it loaded.

**Nothing was removed and no configuration changed meaning.** The configuration keys and the environment-variable surface are identical to v0.9.0's. The hook's matcher widens from `Bash` to `Bash|Monitor`, and the hook defers on every `Monitor` call it receives.

**This plugin is pre-1.0 and its surface is unstable by design.** Nothing breaks in this release, but a break here would ride in a minor rather than waiting for a major, and it would be stated in these notes when it happens.

## Validation

**275 tests green**, up from 269 at v0.9.0, on the release tree, alongside the 355 tests at the repository root and the four sibling suites `make check` runs beside them. The counts are from the release branch rather than quoted from an earlier run.

The **never-`allow`** invariant is asserted on every end-to-end call: the hook returns `ask`, `deny`, or nothing. An `allow` would bypass your permission settings and override the sibling guards evaluating the same command.

**What this does not assert.** No live Claude Code session runs in the suite. Hook behaviour is asserted against synthetic payloads, and the table above against real subprocess invocations rather than a real session. Class B's registry is per-repo by design, so no test can tell you whether *your* slow commands are registered, only that a registered one behaves.

**This is a productivity guard, not a security boundary.** Parsing uncertainty defers, and infrastructure errors fail open to a silent defer, because a guard that breaks the session is worse than a missed prompt. Do not deploy it as a control that something must not run.
