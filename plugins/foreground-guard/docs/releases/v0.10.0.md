Minor release: a `Monitor` whose script is an until-loop is no longer denied, and neither is a `sleep` after a loop's `done`. A loop that waits through `$( )`, `bash -c` or `eval` now denies, and so do several commands the shared parser used to hide.

## Highlights

**A `Monitor` until-loop runs, as the poll-loop deny tells you to.** That deny recommends arming a `Monitor` whose script exits when the condition flips, and since Claude Code 2.1.321 the guard denied exactly that. Claude Code now runs a hook whose matcher is `Bash` for a `Monitor` call too, and hands it a payload rewritten as `tool_name: "Bash"` with the `timeout_ms` dropped, so the guard could not tell the script from a foreground loop. The matcher is now `Bash|Monitor`, which receives the real `Monitor` payload, and the guard defers on it. A foreground Bash until-loop is still denied.

**A `sleep` after a loop's `done` is judged on its own.** `for c in a b; do true; done; sleep 1; ls` used to deny as a polling loop, because the loop finding fired on any loop plus any `sleep` in the same command. A `sleep` now counts toward a loop only while a `while`, `until` or `for` is open, so a short settle wait after a loop passes and a long one is still denied by the sleep floor.

**A loop that sleeps through a nested command denies.** `while true; do x=$(sleep 5); done`, and the same loop with `bash -c 'sleep 1'` or `eval 'sleep 1'`, used to defer: the nested body was judged on its own, and the loop around it never learned that it slept. Each now denies as a polling loop, whatever the sleep's duration. A `for` word list such as `for i in $(sleep 1; echo a b c)` expands once, so it still defers.

**Commands the shared parser used to hide are judged.** bash 5.3's `${ …; }` substitution is read like a `$( )`, so `echo ${ sleep 600; }` denies, and so does a substitution body that holds a heredoc. A `$((…) ; …)` that bash runs as a command substitution is judged inside double quotes. A comment with an apostrophe after a `[[ … =~ "…" ]]` test no longer hides the next line, and a subscript after `time -- -p` no longer hides the command inside it.

## Decision surface

Measured by running the v0.9.0 hook script from the plugin cache and this one over the same payloads, with no config file, and recording the emitted `permissionDecision`. `defer` means the guard expressed no opinion and your own permission settings decided. The *Monitor* row is the hook wiring rather than the script: on Claude Code 2.1.321, v0.9.0's `Bash` matcher receives the rewritten Bash payload, which its script denies, and this release's matcher receives the `Monitor` payload, which it defers. That wiring was measured end to end in https://github.com/karlkfi/claude-bouncer/pull/326, not re-run for these notes.

| `while true; do x=$(sleep 5); done` | defer | **deny** |
| `while true; do bash -c 'sleep 1'; done` | defer | **deny** |
| `while true; do eval 'sleep 1'; done` | defer | **deny** |

Eight rows gain a denial and two lose one, all on a default install with no config file.

## Upgrading

```
claude plugin marketplace update claude-bouncer
claude plugin update foreground-guard@claude-bouncer
```

A restart is needed. The hook is registered at startup, so a running session stays on the version it loaded.

**Nothing was removed and no configuration changed meaning.** The configuration keys and the environment-variable surface are identical to v0.9.0's. The hook matcher in `hooks/hooks.json` widened from `Bash` to `Bash|Monitor`; the guard defers on every tool other than `Bash`, so the `Monitor` calls it now receives are passed through.

**This plugin is pre-1.0 and its surface is unstable by design.** Nothing breaks in this release, but a break here would ride in a minor rather than waiting for a major, and it would be stated in these notes when it happens.

## Validation

**275 tests green**, up from 269 at v0.9.0, on the release tree, alongside the 355 tests at the repository root and the four sibling suites `make check` runs beside them. The counts are from the release branch rather than quoted from an earlier run.

The **never-`allow`** invariant is asserted on every end-to-end call: the hook returns `ask`, `deny`, or nothing. An `allow` would bypass your permission settings and override the sibling guards evaluating the same command.

**What this does not assert.** No live Claude Code session runs in the suite. Hook behaviour is asserted against synthetic payloads, and the table above against real subprocess invocations rather than a real session. The `Monitor` matcher's effect depends on Claude Code's payload rewrite, which only an end-to-end run reproduces; the suite pins the matcher string and the defer on a `Monitor` payload. Class B's registry is per-repo by design, so no test can tell you whether *your* slow commands are registered, only that a registered one behaves.

**This is a productivity guard, not a security boundary.** Parsing uncertainty defers, and infrastructure errors fail open to a silent defer, because a guard that breaks the session is worse than a missed prompt. Do not deploy it as a control that something must not run.
