# A bare exit is credited with carrying the status it drops

Backgrounded, `make check > log 2>&1; echo EXIT=$?; exit` is silent.
A bare `exit` exits with the last command's status, which here is `echo`'s 0: `bash -c 'false; echo x; exit'` exits 0 on bash 5.3.15.
So the task notification reports success for a failed gate, the false green rule 2 exists to catch.

**Why.** `_seg_carries` counts any statement headed by `exit` as carrying the gate's status (`plugins/exit-status-guard/scripts/bash-exit-status-guard.py:1046:    if words[0] == 'exit':`).
That is right for `exit $rc`, the documented fix, and for a literal `exit 0`, which is the deliberate discard its comment names.
A bare `exit` is neither.
It hands on whatever ran last, so it carries the gate's status only where the gate itself ran last.

Found while answering the review of #379 (Q400), at its head `6b323c5`.
It is reached through a double-quoted `bash -c` too, where the caller expands `exit $rc` to a bare `exit` (Q417).

**Which way it gets built.** Credit an `exit` with an operand, and treat a bare one as whatever statement precedes it in the list.
Pin the shape above as a deny, and keep `make check > log 2>&1; rc=$?; echo "EXIT=$rc"; exit $rc` and a literal `exit 0` silent.
