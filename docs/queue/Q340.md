# A command nested past the depth limit in sh -c bodies passes unread

`evaluate_command_string` stops reading at its depth limit and returns no
findings, so a `bash -c` body four levels down is never judged and the command
defers:

| command | guard on `main` |
|---|---|
| `bash -c 'bash -c "bash -c \"kubectl --context gke_acme_prod-us delete pod x\""'` | deny |
| `bash -c 'bash -c "bash -c \"bash -c \\\"kubectl --context gke_acme_prod-us delete pod x\\\"\""'` | **defer** |

Measured 2026-11-01 on `main` at `f4f9857`, fixture `$HOME` whose current
context is `gke_acme_prod-us`. bash 5.3.15 runs the four-level form: with
`/bin/echo RAN` in place of kubectl under `env -i
/opt/homebrew/bin/bash --norc --noprofile` it prints `RAN`.

The limit itself, on the Q299 branch:

`plugins/prod-guard/scripts/bash-prod-guard.py:3120:    if depth > 3:`

## Which way it gets built

Q299 made a function call or `eval` at the limit ask instead of passing
unread, with a reason naming the nesting. Do the same for a shell's `-c` body
at the limit, so the cut-off fails closed. Raising the limit only moves the
cut-off.

## If it is never built

A production mutation four `sh -c` levels down runs without a prompt. Nobody
writes that by accident, so the risk is a deliberate bypass.
