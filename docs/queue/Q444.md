# prod-guard forgets a name assigned inside an if, loop or case body

A variable assigned inside an `if`, `while`, `for` or `case` body is unknown to prod-guard even for a later command in the same body, so a production command held in it runs with no prompt.
Found by the prod-guard reviewer on Q423's pull request, against `main` at `7724d13`, and re-measured 2026-11-27 through the hook on Q424's branch, with `~/.kube/config` on `kind-ci`:

| command | prod-guard |
|---|---|
| `if true; then kubectl --context gke_acme_prod-us delete ns x; fi` (control) | deny |
| `X="kubectl --context gke_acme_prod-us delete ns x"; if true; then $X; fi` (control) | deny |
| `if true; then X="kubectl --context gke_acme_prod-us delete ns x"; $X; fi` | **defer** |
| `for i in 1; do X="kubectl --context gke_acme_prod-us delete ns x"; $X; done` | **defer** |

bash runs it: `if true; then X="/bin/echo RAN"; $X; fi` printed `RAN`.
The controls show the body is judged and the value reaches it from outside, so what is lost is an assignment made inside the body.
The site in the walk that drops it was not traced.

The same loss makes an IFS assigned in a body, or in a function, unknown, which is two of Q441's rows.

## Which way it gets built

Inside a body, an assignment holds for the commands after it in that body, as it does at the top level.
After the body, a name it assigned keeps the value as one reading beside the prior one, the way Q301 handles an assignment after `&&`, so a production value on either side still denies.
The fix is unmeasured; find the site first, and check the Q377 cap on readings still holds for a loop that assigns many names.

## If it is never built

A production mutation runs with no prompt when a session assigns a command to a variable and runs it inside the same `if` or loop body, an ordinary way to write a script.
