# prod-guard reads an empty --kubeconfig as ~/.kube/config, not KUBECONFIG

kubectl reads an empty `--kubeconfig=` as no flag and loads the file the `KUBECONFIG` variable names, but prod-guard reads it as a flag naming no file and falls back to `~/.kube/config`.
Where the two files disagree about a context, the guard judges the wrong one.
Measured 2026-11-27 with kubectl v1.36.3: `KUBECONFIG=<kind file> kubectl --kubeconfig= config current-context` printed `kind-ci`, the context of the file `KUBECONFIG` named.

Through the hook at `9931af8` (Q433's head), with `~/.kube/config` on `kind-ci` and a file `A` whose `blue-2` context has a production server:

| command | prod-guard |
|---|---|
| `KUBECONFIG=A kubectl --context=blue-2 delete pod x` (control) | deny |
| `KUBECONFIG=A kubectl --kubeconfig= --context=blue-2 delete pod x` | **ask** |
| `KUBECONFIG=A kubectl delete pod x` | deny |
| `KUBECONFIG=A kubectl --kubeconfig= delete pod x` | deny |

The ask comes from resolving `blue-2`'s server in `~/.kube/config`, which has no such context.
Found by the prod-guard reviewer on Q433's pull request.
The site is `plugins/prod-guard/scripts/bash-prod-guard.py:2759:        env, named = {**seg_env, 'KUBECONFIG': flag}, '--kubeconfig'`, taken whenever the flag value is not None, empty included.

## Which way it gets built

Judge an empty `--kubeconfig` as absent, as Q433 did for an empty `--context`, so the `KUBECONFIG` variable decides.
That turns some denies into defers as well as this ask into a deny — a nonprod file in `KUBECONFIG` currently denies on the ambient rule because the guard reads `~/.kube/config` — so re-run the table above and the named-kubeconfig suite in both directions before shipping.

## If it is never built

A mutation against a production server named only in `$KUBECONFIG` prompts instead of denying when the command also carries an empty `--kubeconfig`, and an approved prompt runs it.
