# `switch -C` and `checkout -B` reset any branch unchecked, `main` too

`git switch -C <name> <rev>`, `git switch --force-create`, `git checkout -B`
and `git worktree add -B` all reset a branch that already exists. That is the
same overwrite as `git branch -f <name> <rev>`, which branch-guard checks
twice: a protected name asks, and a private one is allowed only when what it
would orphan is recoverable. These four spellings skip both checks and are
always allowed.

Measured 2026-10-04 on git 2.55.0, against `origin/main` at `a3c9052` and
#173's head `bf31961`, which give the same answers. The repo is on a feature
branch, with a local commit on `main` that `origin` does not have:

| command | default | `dontAsk` |
|---|---|---|
| `git branch -f main origin/main` (control) | ask | deny |
| `git switch -C main origin/main` | **allow** | **allow** |
| `git checkout -B main origin/main` | **allow** | **allow** |
| `git worktree add -B main ../w origin/main` | — | **allow** |

Running the `switch -C` moved local `main` off its unpublished commit. With
a private branch `claude/dup` holding one unpublished commit, `git branch -f
claude/dup origin/main` asks, while `switch -C`, `switch --force-create` and
`checkout -B` with the same arguments allow. Running `switch -C` left that
commit reachable from no ref. A `switch -C` onto a name that does not exist
yet is a plain create, and allowing it is correct.

The independent review of #178 (Q216) found the private-branch half. The
`main` rows and `worktree add -B` were measured here.

## Why the arms allow

The `switch` arm returns allow for everything except `-f`/`--discard-changes`,
and its comment says git refuses whatever is unsafe
(`plugins/branch-guard/hooks/branch-guard.py:# create (-c) or plain switch; git refuses if unsafe`).
That holds for `-c`, which fails on an existing name, and not for `-C`, which
exists to reset one. The `checkout` arm allows any `b` or `B` as an
"unambiguous branch create"
(`plugins/branch-guard/hooks/branch-guard.py:return ('allow', None)        # unambiguous branch create`).
The `worktree add -B` path was not read. Its verdict is the only evidence
here.

## Which way it gets built

When the force-create name already exists, route it through the checks
`git branch -f` takes. That means `protected_targets` for the shared question,
and `overwrite_verdict` for the orphan question, which also gives these
spellings Q216's republish check once #178 merges. When the name is new, keep
the allow. Cross the fixtures over protected × private × recoverable ×
not-yet-existing for each of the four spellings, and add the `dontAsk` row the
table above failed. The `switch` arm also reads `-f` from a bundle: check that
`-fC` keeps asking.

**Who is worse off:** an unattended session. Under `dontAsk`, the guard denies
one spelling of resetting `main` and allows the other three, so the protected
set holds only against `git branch`.
