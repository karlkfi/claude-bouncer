# A gate tested by `if` or `while` is denied as sequenced

exit-status-guard's rule 3 denies `make check; git push`, because the push
runs whatever the check returned. It also denies the forms where the `;` closes
a condition rather than a statement, and the push runs only when the check
passed. Driven 2026-10-05 through the hook at `origin/main` `26962b0`:

| command | guard | bash runs the push on a failed check |
|---|---|---|
| `if make check; then git push; fi` | deny | no |
| `if ! make check; then exit 1; fi; git push` | deny | no |
| `while make check; do git push; break; done` | deny | no |
| `if make check; then :; fi; git push` (control) | deny | yes |

The rule reads the separator after the gate (`next_op`) and never asks what the
`;` closes. After an `if`, `elif`, `while` or `until` condition, the next
keyword is `then` or `do`, and the status is consumed there. The README already
says the `[ "$rc" -eq 0 ]` form inside `if` is not recognised; this is the
same gap with the gate itself as the condition. Found while working Q277.

## Which way it gets built

In `sequenced_mutation`, skip a gate whose segment is a condition: the words
before it in that list open with `if`, `elif`, `while` or `until`, and the
segment after the `;` opens with `then` or `do`. The `if ! make check; then
exit 1; fi` form needs the `!` read as negation of the same condition. Keep the
control denying.

## Who it is for, and what happens if it is never built

A session writing the gated form as an `if` is denied and has to rewrite a
correct command into `&&`. This is the safe direction. How often the shape
appears has not been measured. The cost of delay is flat.
