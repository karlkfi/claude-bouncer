# Citation drift is under-gated, and the obvious tightening misfires

A citation names a file, a line, and the text on that line. The line rots when
the file moves under it, and `make backlog-lint` reports that in no way that
fails.

`Makefile:85:--strict blocked-opener --strict deferred-trigger --strict empty-store`
is the whole gate. It passes neither `--strict stale-citation` nor
`--citation-window`, so measured 2026-08-23 against a synthetic store with a
**unique** fragment placed 8 and 19 lines off:

    default (window 10)                 8-line: SILENT     19-line: note, exit 0
    --citation-window 0                  8-line: note, 0    19-line: note, exit 0
    --citation-window 0 --strict …       8-line: FAIL, 1    19-line: FAIL, exit 1

Two separate failures wearing the same clothes, which is why one knob does not
close both. `--strict stale-citation` promotes a note's severity and cannot
reach a note that was never emitted; `--citation-window` decides what counts as
a note and not what it costs.

**This row demonstrated its own subject while being written.** The citation
above was first written as `Makefile:83`, two lines off. `make backlog-lint`
returned `30 item(s) OK` at exit 0 and said nothing, because two is inside the
window. Two lines is what writing a citation from a nearby line number costs —
the modal error, not an extreme one.

**The obvious fix misfires — though not in the direction this row was filed
claiming.** `--citation-window 0` is not simply a stricter version of the same
check: the linter reports the *first* line matching the fragment, so where a
fragment occurs more than once, an exact window can name an occurrence the row
never meant. That hazard is real. The worked example this row was built on was
not an instance of it, and the 2026-08-23 groom inverted the reading:

- **Q110 was recorded here as a false alarm and was a genuine mis-point.** It
  cited
  `exhibit:plugins/branch-guard/test/run.sh:1362:git branch -D a scratch test-merge -> allow`,
  and that fragment occurred at both **1350** and **1366**. This row read 1366
  as the referent and 1350 as "a different test case". It is the other way
  round: 1350 is the plain `-D` fixture, sitting directly under the block that
  creates `testmerge` at line 1321, which is what Q110's own sentence names —
  "built on the `testmerge` branch the block above it sets up". 1366 is the
  `[dontAsk]` mode variant of the same case, and the cited 1362 is a line of
  the `[configured]` check between the two. So the citation sat twelve lines
  off its referent, the default window silently rescued it against the *wrong*
  occurrence, and the exact window's "now at line 1350" was correct. The groom
  re-pointed it to 1350.
- **Q98 was genuine and invisible.** It cited
  `exhibit:plugins/workspace-guard/scripts/friction-report.py:428:def coverage_note`
  for a fragment that sat at **429** — one line, unique, silent under the
  default window. The groom re-pointed it to 429.

Both are quoted here as exhibits, because a citation quoted as a row's subject
is still a citation to the checker — which is itself worth noting, since the
copy of `queue.py` vendored at `scripts/queue.py` honours the `exhibit:`
prefix. It rejected `--show-exhibits` and disclosed no count when this was
written, which is the gap Q97 was filed for and confirmed here rather than
inferred; the re-vendor has since landed, so a run over this store now ends
`(2 marked exhibit(s) held back)` and `--show-exhibits` names both.

So both notes the exact window produced on this store were genuine, and the
duplicate fragment manufactured no false alarm — it hid a real one. That is the
opposite of the evidence this row was filed carrying, and it moves the decision
rather than settling it: the store's one known non-unique fragment turned out to
be an argument *for* the exact window. Both citations are repaired, so the
window-0 run is silent today and the next session cannot re-derive either
reading from the store — which is why they are written above in the past tense.

**What to decide, in order:**

1. Whether fragments in this store are unique enough for an exact window. The
   skill's rule is "pick words that occur once", and a test-name fragment in a
   table-driven suite is the shape that recurs by construction — Q110's did.
   What the re-check changed is the consequence of a recurrence: not a false
   alarm, but a silent pass against whichever occurrence happens to land inside
   the window.
2. Whether the answer is a window between 0 and 10, which buys range back and
   picks an arbitrary number, or making fragments unique first and then going
   exact. Weigh it knowing the only measured recurrence favoured going exact.
3. Whether `--strict stale-citation` rides along. It changes nothing about
   which notes exist, only whether they fail the build.

The `exhibit:` prefix is the escape for a pointer a row is *about* rather than
relies on, and the skill's position is that a store can afford an exact gate
once deliberate exhibits carry it. Check whether this store uses the prefix at
all before assuming that path is open.

Worth knowing while deciding: `session-orchestrator`'s merged-set lint already
adds `--strict stale-citation` where it finds this store, so a batch run
through it is checked more strictly than `make check` checks the same tree.
Nobody reading a green `make check` would know that the weaker reading is the
repo's own.

## A whole batch measured, 2026-09-01: eighteen drifts, one visible

The readings above are single citations on a quiet store. A seven-item parallel
batch merged on 2026-09-01 (#73-#80) supplies the population figure, and it is
the argument this row was missing.

Swept the merged trunk by fragment — does the cited line *carry* the quoted
text — rather than by whether the line resolves:

    41 exact, 18 drifted, 0 unresolvable, 2 exhibit-exempt

    Q135 x5, Q145 x5, Q146 x6   +7/+8   one branch-guard PR moved them
    Q151 x1                     +24     one prod-guard PR landing after another
    Q111 x1                     +2      a workspace-guard PR moved a README

Against the same tree, the repo's own gate and the exact form disagree by
seventeen:

    make backlog-lint                            -> exit 0, ONE note (Q151's +24)
    lint --strict stale-citation --window 0      -> exit 1, EIGHTEEN notes

**No pull request could have caught any of them.** Every drift was produced by
a *merge*, not by the branch that carried the citation — no PR moved another
PR's citations, so each was clean on its own branch and each review was correct.
The class is invisible to review by construction, which is what makes it a gate
question rather than a diligence one.

**The +2 is the one to read twice.** `Q111` was re-pointed to 1822 in #79 that
same morning and was stale again inside ninety minutes, moved by a sibling PR in
the same batch. Re-pointing without changing the gate is not durable.

### This answers decision 1, and it answers it *for* the exact window

The groom that followed re-pointed all eighteen, and then:

    lint --strict stale-citation --citation-window 0   -> exit 0, 59 exact

Zero false alarms at window 0 over the whole store, where the same command
exited 1 minutes earlier — so the check is discriminating rather than agreeing,
and this store's fragments are in fact unique enough for an exact window today.
That is the empirical answer decision 1 asked for, on 59 citations rather than
on the single recurrence Q110 supplied.

It does not retire decision 2. Going exact means every future batch reddens the
gate until its drifts are re-pointed, which is the cost to weigh — 18 re-points
took one mechanical pass here, and the pass only exists because somebody went
looking.
