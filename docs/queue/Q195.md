# A wrapper test that cannot fail for the change it guards

`test_read_only_verb_behind_either_wrapper_still_defers` asserts that
`stdbuf -oL kubectl get pods` and two siblings still defer. It reads as the
false-positive control for Q161's wrapper change — the direction that proves a
strip did not shift the tokens — and it is not one. No mutation of the wrapper
path can redden it.

It shipped in [#117](https://github.com/karlkfi/claude-bouncer/pull/117) with a
comment saying so, which is the honest form but the wrong home: a comment is
read by whoever opens the file, and the reason it cannot fail is a fact about
the *suite* that a reader of one test has no way to check.

## Measured

2026-09-09. Two of the three mutations are the ones its own pull request drove;
the third was run for this row.

| mutation | this test | anything else |
|---|---|---|
| `stdbuf`/`unbuffer` out of `PLAIN_WRAPPERS` | **passes** | 15 failures in the two sibling tests |
| `stdbuf`'s `WRAPPER_VALUE_FLAGS` entry removed | **passes** | 5 failures, the detached-value spellings |
| `'get'` out of `KUBECTL_READONLY` | **fails**, 3 subtests | **6 other tests fail with it** |

So it is not unfalsifiable in the absolute sense, and calling it that — as the
#117 body and its comment both do — overstates it. The accurate claim is
narrower and worse: it is **non-discriminating**. Every mutation that reddens it
lies in the read-only verb table, which the wrapper code does not touch, and
each one reddens six sibling tests that say the same thing more directly.

The mechanism is that a mis-strip cannot produce this failure. Shifting the
argument vector in either direction carries the tool name with it, so
`kubectl` stops being the tool before `get` stops being the verb — the segment
goes uncovered and defers, which is the outcome the test asserts. There is no
token alignment under which `kubectl get pods` behind a wrapper denies.

What actually pins alignment for Q161 is the `assertIn("kubectl delete", reason)`
in `test_stdbuf_and_unbuffer_do_not_hide_the_tool`, which did go red under the
second mutation.

## Which way it gets built

Decide between two, and the choice is about what the suite claims rather than
about this test:

- **Delete it.** The alignment property is already covered by the reason
  assertion, and the read-only path by the six tests that fail alongside it. It
  costs three subprocess calls per run and adds no signal.
- **Keep it and say what it is.** Rename toward regression coverage and move the
  reason it cannot fail out of the inline comment into whatever the repository
  uses for suite-level notes, so it is not re-read as a control by the next
  person to add a wrapper.

Do not "fix" it by finding a mutation that reddens it. There is no false-deny
reachable through wrapper stripping here, so a test constructed to have one
would be asserting something the code cannot do.

## Why it is worth a row rather than a note

The class, not the instance. This run produced several tests and probes that
could not fail — a control whose `PATH` mutation silently did not land, a
baseline lint that crashed and read as a verdict, a grep whose count was wrong
in the safe-looking direction. Each was caught by re-deriving rather than by any
gate. This one was caught, described accurately in a pull request body, and
merged anyway, which is the failure mode a row exists for: nothing walks merged
pull request bodies, so the note is now invisible to everyone who did not read
#117 while it was open.

## If it is never built

A test that looks like a control and is not stays on the trunk. The next person
to touch `strip_wrappers` sees it pass and reads that as evidence their change
did not over-deny, which it is not — and the sibling test that would have told
them is the one they were not looking at.
