# A `$(` or backtick in a comment opens a substitution prod-guard reads

bash ignores everything in a comment, a `$(` or backtick included.
`command_substitutions` does not know top-level comments, so on a raw string
it opens a substitution at a `$(` or backtick that sits inside one. The body
runs to the next `)` or backtick, which can be lines later, so the lines in
between read as substitution text. On `origin/main` at `777c6ef`:

```
command_substitutions('echo hi # $(\nP\necho )')   -> ['\nP\necho ']
command_substitutions(strip_comments(<same>))       -> []
```

prod-guard scans the raw string, and P goes unjudged. workspace-guard and
exit-status-guard strip comments before the commands are judged, and both
still judge P. workspace-guard also calls `command_substitutions` on raw text,
a path nothing here exercises.

Found by the independent review of the Q224 pull request. That review
measured prod-guard on `main` and on that pull request's head. The guard columns
below were re-driven 2026-10-04 on `origin/main` at `777c6ef`, with bash under
`env -i /opt/homebrew/bin/bash --norc --noprofile -c`, which prints
`5.3.15(1)-release`. The fixture `$HOME` set the current context to
`gke_acme_prod-us`. Payloads were `kubectl delete ns payments` for prod-guard,
`rm /etc/probe-target` for workspace-guard, and `make check | tail` for
exit-status-guard:

| command | bash runs P | prod / ws / exit |
|---|---|---|
| `echo hi # $(` newline `P` newline `# )` | yes | **defer** / ask / deny |
| `echo hi # $(` newline `P` newline `echo )` | yes, then a syntax error on line 3 | **defer** / ask / deny |
| ``echo hi # ` `` newline `P` newline ``# ` `` | yes | **defer** / ask / deny |
| ``true # ` `` newline `P` newline ``echo ` `` | yes, then a syntax error on line 3 | **defer** / ask / deny |

`bash -c` runs each line before it parses the next, so a syntax error on
line 3 does not stop P on line 2.

There is also a quoting half. An apostrophe in a top-level comment opens a
quote that the scanner never closes, so it finds no substitution after the
comment at all. Measured 2026-10-04 on `origin/main` at `67ee2a6`:

```
command_substitutions("# don't\necho \"$(P)\"")   -> []
command_substitutions("# don't\necho $(P)")       -> []
```

prod-guard no longer meets this, because Q224 strips comments before the scan.
workspace-guard's raw-text call may still meet it. That was not driven.

That review listed a fourth shape: an escaped backtick holding a comment in
an unquoted `bash <<EOF` body. It is not this mechanism. prod-guard denies
the same body without the `#`, so it is Q254's comment-in-backticks
mechanism, met in a script body.

## Which way it gets built

Teach `command_substitutions` that an unquoted `#` at a word start begins a
comment running to the newline, the rule `strip_comments` already follows,
and open nothing inside one. Q230 is the opposite case, a comment inside
`$( )`, in the `$( )` scanner. Check the two together: a fix for one must not
undo the other.

## If it is never built

One comment that mentions `$(` or a backtick, with a matching closer on a
later line, hides every line between them from prod-guard.
