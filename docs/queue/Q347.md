# A git command after an unfollowed cd reads the session's branch

`cd "$X" && git commit -m x`, a `git` command after a `cd` the hook can't follow, is judged as if the commit ran in the session's own checkout, so the branch it lands on is never read. From a feature branch the command defers today (the `cd` is a non-git segment); from `main` it asks, because the fallback reads the session's own branch. Either way a commit there in a session that has allowlisted `git commit` lands wherever `$X` points, including another checkout's `main`.
Q331 closed the same fallback for a repository named on the git command itself (`--git-dir`, `GIT_DIR`, a non-literal `-C`) and left this half alone on purpose: `plugins/branch-guard/hooks/branch-guard.py:3795:head_cwd = inv_cwd or invocation_cwd(seg_cwd or base, inv, True)` starts the HEAD walk from the session's directory when a `cd` left it unknown.

A variable exported earlier in the command reaches the same fallback: `export GIT_DIR=../other/.git && git commit`, its `;` form and `declare -x` all defer on Q331's head, and in git 2.55 each commit landed on the sibling's `main` (measured by Q331's reviewer; frequency unmeasured).
A `sh -c` body falls back the same way, to the directory the shell started in (`sh -c 'cd "$X" && git commit -m x'`).

The first step is done: `cd_substitution` now computes a `cd` to a double-quoted `$(git rev-parse --show-toplevel)` or `$(pwd)`, the forms that made asking here too expensive.
Replayed 2026-11-27 from this machine's transcripts, 310,998 Bash calls gave 8,210 distinct commands carrying a `cd`, `pushd`, `git -C`, `--git-dir` or `GIT_DIR=` and a `commit`, `push`, `merge`, `rebase`, `pull`, `cherry-pick`, `revert` or `am`; 4,348 of them were replayed, the other 3,862 recording a cwd that no longer exists.
Asking on every `cd` the hook can't follow moves 732 of the 4,348 from no decision to an ask on `main` at `9a7c128b`, 576 of them opening with `cd "$(git rev-parse --show-toplevel)"`, and 164 once that `cd` is followed. By the first `cd` in each, the 164 are 141 `cd $var`, 14 `cd ~` and 9 that open with a followed substitution and then `cd` somewhere the hook can't place, or carry a `\$` that keeps it unread.
The filter is a reconstruction, since the 2026-11-01 replay that counted 1,216 here was not kept, so the two sets of numbers are not comparable; each replay judges the repositories as they stand on the day it runs.

Most of the residue is the shape the hook already follows into git arguments: by a regex over the 164, 130 `cd` to a variable that a literal assignment earlier in the same command sets (`S=/abs; … && cd "$S/repo" && git commit`), 85 of them `$S` and 25 `$SP`.
`bind_literal_vars` substitutes such a value into later git and gh words only, so the `cd` stays unfollowed; whether its positional rules accept all 130 is unmeasured.

Next step: have `bind_literal_vars` substitute a bound value into a `cd` target as well, re-run the replay, then decide on what is left whether a `cd` the hook still can't follow should ask on the branch-sensitive verbs the way Q331's redirects do.
