# foreground-guard reads a sleep after a loop as a sleep inside it

foreground-guard denies `for c in a b; do true; done; sleep 1; ls` as a
loop that polls with `sleep`. The `sleep` runs once, after the loop has
finished, so nothing polls.

Measured 2026-10-05 on `origin/main` at `26962b0`, driving
`plugins/foreground-guard/scripts/bash-foreground-guard.py` with a `Bash`
payload (installed: foreground-guard 0.7.0):

| command | foreground-guard |
|---|---|
| `for c in a b; do true; done; sleep 1; ls` | deny |
| `for c in a b; do true; done && sleep 1` | deny |
| `for c in a b; do true; done` + newline + `sleep 1` | deny |
| `for c in a b; do true; done; ls` (control) | none |
| `true; sleep 1` (control) | none |

It came up in a worker session as a real friction: a probe ran a `for` loop
over several commands and then a single `sleep 1` to let background children
finish, and was denied with the loop-poll reason.

The decision is
`plugins/foreground-guard/scripts/bash-foreground-guard.py:876:    if state['loop'] and loop_sleep:`.
`loop_sleep` is set by a foreground `sleep` in any segment, and `state['loop']`
by a loop anywhere in the string, so nothing ties the `sleep` to the loop's
body.

## Which way it gets built

Count a `sleep` toward the loop finding only when it sits between the loop's
`do` and its `done`. A `sleep` outside every loop falls through to the
bare-sleep and repeat-with-sleep findings, which already judge it on its own.
Fixtures: each row above, plus `while true; do sleep 1; done` as the denying
control.

## If it is never built

A loop followed by a short wait is denied with a reason that tells the model to
drop the loop. The model then rewrites a command that never polled.
