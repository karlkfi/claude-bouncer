# A depth-cap test times out under parallel load

`SubstDepthCapTests.test_pathological_nesting_does_not_kill_the_hook` asserts
the hook survives 1000-deep substitution nesting, and `run_hook` gives every
subprocess a hard `timeout=10`. The runner spreads the suite across 18
processes, so on a loaded machine the hook's own work slows past that bound and
the test errors on `subprocess.TimeoutExpired` — a red run that says nothing
about the behaviour it asserts.

Measured 2026-09-17 on the 1.12.1 release tree, macOS, Python 3.14.7:

```
full suite, machine busy   1567 tests, 50.6s wall   1 error (this test)
full suite, machine quiet  1567 tests, 21.8s wall   OK
this class alone            4 tests,  2.4s wall     OK
```

The wall-clock ratio is the whole finding: nothing about the assertion changed
between the runs, only how much of the machine the other 17 processes were
using.

## The fix

Either raise the bound for this one test — it is a liveness assertion, so the
number only has to be far below "hangs forever" — or mark the class to run
serially. Prefer whichever keeps the assertion honest: a bound so loose it
cannot distinguish a slow pass from a hang has stopped testing anything.

Worth checking whether any other `run_hook` caller leans on the same 10s bound
for a deliberately expensive input.
