# A subscript the parser cannot read whole still hides the command

Q214 taught the shared parser to peel `NAME[sub]=v`, but only where the
subscript reaches it as one token whose closing `]` it can find. bash keeps a
subscript's contents in one word whatever they hold, and three things lose
that before the assignment question is asked. Each of these reads `f` on
bash 5.3.15 and is still read as a command name by every guard:

| prefix | bash 3.2.57 | what the parser sees |
|---|---|---|
| `FOO[a b]=x` | reads | `FOO[a`, `b]=x` |
| `FOO[a;b]=x` | reads | `FOO[a`, `;`, `b]=x` |
| `FOO[a\|b]=x` | reads | `FOO[a`, `\|`, `b]=x` |
| `FOO[a<b]=x` | reads | `FOO[a`, `<`, `b]=x` |
| `FOO[$(echo 0)]=x` | reads | `FOO[$`, `(`, `echo`, `0`, `)`, `]=x` |
| `FOO[$((1+1))]=x` | reads | `FOO[$`, `((`, `1+1`, `))`, `]=x` |
| ``FOO[`echo 0`]=x`` | reads | ``FOO[`echo``, ``0`]=x`` |
| `FOO[""]=x` | reads | `FOO[]=x`, quoting recorded at the `]` |
| `FOO["a]b"]=x` | command name | `FOO[a]b]=x`, quoting recorded at the first `]` |
| `FOO[a\]b]=x` | command name | the same |
| `FOO[a\[b]=x` | command name | `FOO[a[b]=x`, which never closes by depth |
| `FOO[${x:-]}]=x` | command name | one token; the `]` inside `${...}` closes it |
| `FOO[$(echo ])]=x` | syntax error | split, as the `$(` rows |

Driven 2026-10-01 as
`env -i PATH=/usr/bin:/bin /opt/homebrew/bin/bash --norc --noprofile -c '<prefix> cat f'`,
and the same with `/bin/bash` for the 3.2.57 column. Name the binary: `env -i`
clears `PATH`, so a bare `bash` there is macOS's 3.2.57, which is how Q214's
first pass mis-attributed the quoted-`]` pair. The Bash tool runs the
Homebrew 5.3, so 5.3 is the shell that decides.

The three mechanisms:

- **The lexer splits** on every space and operator character first. The `;`
  and `|` rows are the sharp ones: the guards cut the command there, and the
  reader lands in a segment headed `b]=x`.
- **Quoting records only where it began.** `quoted_from` is one offset, so a
  quoted or escaped `]`, or an empty pair at the `]`, cannot be placed, and
  bash 5.3 treats a quoted `]` as not closing. `is_assignment` accepts quoting
  that starts strictly inside the subscript when the depth walk still finds an
  `=`, which covers `FOO["0"]=x`, and refuses the rest.
- **The depth walk does not skip expansions.** bash skips a `]` inside
  `${...}` or `$(...)`.

`SubscriptAssignmentTests.test_the_lexer_splits_what_bash_keeps_whole` in
`tests/test_bouncer_parse.py` holds every 5.3 row above as an assertion that
fails when its gap closes.

## The over-peel half

`is_assignment` now accepts quoting that starts inside a subscript, because
bash peels `FOO["0"]=x` and `FOO['a']=x`. It cannot tell whether that quoting
ran on past the `]`, so `FOO["0]"=x` peels too, where bash reports a syntax
error and runs nothing. That direction costs precision, not security: the
guard judges a command that never runs.

## Which way it gets built

A fix lives in the lexer: bracket depth, quoting and expansions have to be
tracked while words are split, which is what bash does. A narrower first step
is available for the quoted-`]` rows alone: when quoting starts inside the
subscript, accept the first later `]` followed by `+=` or `=`. That
over-peels at worst, and no caller reads a subscripted value. Either lands in
the shared parser every guard uses, so it reaches all five and needs
`make sync` and every suite.

## If it is never built

Each spelling is a one-token bypass for any guard, the same reach Q214 had,
behind a slightly stranger word.
