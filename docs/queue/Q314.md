# branch-guard records worktree grants at a TTL nothing ties to the reader

The worktree grant is written by one guard and read by another, and each picks
its own TTL. branch-guard records at the library default
(`plugins/branch-guard/hooks/branch-guard.py:1002:    record_grants(WORKTREE_NAMESPACE, data.get('session_id'), paths,`,
no `ttl=`, so `DEFAULT_TTL`), while workspace-guard loads the same namespace at
its own constant
(`plugins/workspace-guard/scripts/bash-workspace-guard.py:3340:SESSION_GRANT_TTL = 8 * 3600`).
Both are 8 hours today, so nothing misbehaves. Nothing keeps them equal.

Since Q307, `record_grants` judges a grant expired with the `ttl` it is given,
so the two values decide different things. If workspace-guard's TTL dropped
below the library default, a worktree grant it reads as expired would still be
live to branch-guard. Re-approving `git worktree add` would then record nothing,
and every read of that worktree would ask for the rest of the session. That is
Q307's defect again, on the worktree path only. If the reader's TTL rose
instead, grants would renew early, which costs nothing.

Found in review of Q307 (#278), measured by reading both call sites at
`a3457c2`. No test drives a divergent TTL across the two guards.

## Which way it gets built

Give the worktree grant one TTL that both guards import, for example a constant
beside `WORKTREE_NAMESPACE`, which both guards already hardcode as `'bouncer'`.
That constant would go in `lib/` only if a second shared grant appears. A
cheaper alternative is a test that fails when the two values differ. It pins
the coupling without moving any code.

**Who it is for:** whoever next changes either guard's grant TTL. Today it
reaches nobody, and the worktree grant is opt-in
(`BRANCH_GUARD_WORKTREE_GRANTS=1`).

**If never built:** nothing happens while both values stay at 8 hours. The
first edit to either one silently brings back Q307's prompt-per-command
behaviour for worktree reads.
