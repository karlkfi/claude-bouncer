# The unreachable-tip deny cannot see content origin already carries

`plugins/branch-guard/hooks/branch-guard.py:1579:return ('deny-unreachable',`
fires off one question, asked by
`plugins/branch-guard/hooks/branch-guard.py:1991:def tip_is_recoverable(cwd, name):`:
is this branch's tip reachable from a remote-tracking ref or main? That is a
question about *reachability*, and a rebase is where reachability and content
come apart. Replaying commits onto a moved base gives every one of them a new
object name, so the branch is genuinely unreachable while the tree it produces
is an object origin already holds.

## The probe: patch-id equivalence over the orphan set, bounded

Not a tree comparison. The row asked for one and the measurement rejects it:
tree equality answers only the case where the base did **not** move, which is a
republish rather than the rebase this row is named for.

| the base moved… | orphan tree == republished tree | patch-id finds an equivalent |
|---|---|---|
| not at all (cherry-pick onto the same base) | **yes** | yes |
| in the same file, outside the branch's diff context | no | yes |
| in a different file | no | yes |
| in the same file, **inside** the branch's diff context | no | **no** |

A moved base lands in the replayed commit's tree, so the trees differ in three
of four cases while the content the row cares about is present in all of them.
Patch-id covers three; the fourth is a real floor rather than a gap to close.
There the replayed commit's diff text genuinely changed — the context lines
moved — so no patch-id can match, and the probe returns unproven and the deny
stands. That is the safe direction, and it is why this row's fix narrows the
deny rather than removing it.

**Which refs it compares against: the whole `refs/remotes` set, never `main`.**
`git cherry origin/main claude/dup` returns `+` for every orphan in all four
variants above, because main is precisely where the republished commits are not.
`git cherry origin/claude/republished claude/dup` returns `-` for all five. The
republished branch is a remote-tracking ref, so it already sits inside
`plugins/branch-guard/hooks/branch-guard.py:176:RECOVERY_REF_PATTERNS = ('refs/remotes', 'refs/heads/main', 'refs/heads/master')`
— the existing constant is the right comparison set, and pointing the probe at
the base ref instead would find nothing, always.

## What it costs, and why it has to be bounded

The unbounded form is not affordable. Measured on a real large repository —
`~/workspace/kubernetes`, 140,324 commits, 126 remote-tracking refs, 20,739
commits on remotes not on `HEAD`:

| form | cost |
|---|---|
| one-pass patch-id over all remotes, uncapped | **26,337 ms** |
| enumerate that side only (`rev-list`, no hashing) | 141 ms |
| decide whether the side exceeds 200 (`--max-count=201`) | 104 ms |
| patch-id bounded to the newest 200 | 527 ms |
| patch-id bounded to the newest 1000 | 1,127 ms |
| patch-id of the ≤4 orphans alone | 35 ms |

`plugins/branch-guard/hooks/branch-guard.py:1937:def run_git(cwd, *args):` caps
every git call at five seconds, so the uncapped form does not merely run slowly
— it is killed, `run_git` returns `None`, and the probe answers unproven. It
would fail safe and buy nothing, on exactly the repositories where a rebase onto
a moved base is most likely.

So the bound goes on the **comparison** side, the mirror of
`plugins/branch-guard/hooks/branch-guard.py:189:MAX_EXAMINED_ORPHANS = 4`, which
already bounds the orphan side. Deciding whether to bail costs 104 ms, so the
probe can decline cheaply rather than starting work it cannot finish.

**The cap is safe for the case the row is about, and that is a property of
`rev-list`'s default order rather than luck.** It walks in reverse chronological
order and a republish is recent, so the commits being looked for are at the
front. Driven on a fixture carrying 1,005 commits on the other side: the five
republished commits sit at positions 1 to 5, a cap of 200 reaches all five, and
all five orphan patch-ids match. An *old* republish with heavy traffic since
falls outside the cap and the probe declines — the deny stands, which is right,
because at that age the session's claim to the content is what is in doubt.

On a small repository the same probe is cheap and scales sub-linearly: against a
process-spawn floor, 1.6× at 10 other-side commits, 3.2× at 100, 3.5× at 1000.
The existing reset probes sit at about 1.1× that floor, so this is a real
addition rather than a rounding error — and it lands only on the arm that was
already going to deny.

## Measured

Re-measured 2026-09-04 against this tree at `7e143fc5`, git 2.55.0, by driving
the hook on synthetic stdin. Four throwaway repos, one per row of the table
above: `main` on origin, branch `claude/dup` carrying five commits, those five
replayed onto `origin/main` under a different committer date and pushed as
`claude/republished`, with the base moved differently in each. Worktree clean.

| reading | value |
|---|---|
| `git log --oneline claude/dup --not --remotes` | 5 commits |
| `git for-each-ref --contains claude/dup` over the recovery refs | 0 refs |
| `git diff --stat claude/dup origin/claude/republished` | empty, variant 1 only |
| `git reset --hard origin/main` | **deny-unreachable**, all four variants |

The guard's reading is accurate in every variant: those five commits exist
nowhere else. What it cannot see is that origin carries the content they build.

**The 2026-09-01 note that the installed hook is byte-identical to this tree no
longer holds.** #85 has landed 232 diff lines into the file since, so the tree
is `7e143fc5…` against installed 1.10.0's `fe6798df…`. The verdicts above are
the tree's, which is where a fix lands.

**Absolute wall-clock is not measurable on this machine at present** — load
average was between 20 and 115 across the session, and an end-to-end hook timing
came back 17× its own subprocess cost. Every figure above is either a median of
repeated runs on a quiet-enough sample or a ratio to a floor measured in the same
breath; none is a single reading.

**The four-variant fixtures above cannot be used to time anything, and a future
session should not try.** They are three to eight commits, so a deliberately
costly control (`git log --stat` over the whole history) runs at the
process-spawn floor there, where on a real repository it runs 16 to 22× the
floor. A fixture that cannot separate cheap from costly cannot report that
something is cheap. Every cost figure in this row therefore comes from
`claude-bouncer` itself or from `~/workspace/kubernetes`, and the fixtures are
used only for verdicts, which are load-invariant.

## The message reasons about this and lands elsewhere

`plugins/branch-guard/hooks/branch-guard.py:525:way already has its content on main under another object name`
is the deny route arguing the neighbouring case, and it argues it on content
rather than reachability — a squash merge leaves the tip unreachable while the
content is on main, so the reset is unnecessary. Correct for a squash. A rebase
produces the same object-name change and the opposite conclusion: the reset is
wanted, and the route offers no path to it.

## The break-glass is not the problem, and the reporting session had it wrong

Reported as "the documented override does not open this rule". It does.
`plugins/branch-guard/hooks/branch-guard.py:1900:if inv is None or writes or inv['prog'] != 'git':`
admits `deny-unreachable` through `OVERRIDABLE_GIT`, and on the fixture above
`BRANCH_GUARD_OVERRIDE=x git reset --hard origin/main` allowed.

What the reporting session actually ran carried a redirect to a log file, `$( )`
substitutions and a leading assignment segment. Each of those defeats
`plugins/branch-guard/hooks/branch-guard.py:2296:liftable = (all(ovr for _, ovr, _ in asks)`
on its own, measured one at a time on the same fixture:

| command | verdict |
|---|---|
| `BRANCH_GUARD_OVERRIDE=x git reset --hard origin/main` | allow |
| … `2>&1` | allow |
| … `; echo done` | allow |
| … `> log 2>&1` | **deny** |
| … `; echo "$(git rev-parse HEAD)"` | **deny** |
| `SP=/path; BRANCH_GUARD_OVERRIDE=x git reset --hard …` | **deny** |

Re-confirmed 2026-09-04, with one precision worth having: it is a write to a
*real file* that costs the override. `… > /dev/null` still allows, because
`redirect_writes_file` exempts the device targets. That is what makes the
exit-status-guard collision below real rather than theoretical — the prescribed
form names a scratchpad log, which is a real file.

The tell is a sentence going missing: an unliftable denial drops
`Re-run it prefixed with BRANCH_GUARD_OVERRIDE=<reason>`, and nothing says why.
Over this machine's transcripts, 2026-08-22 to 2026-09-01, 21 distinct
`deny-unreachable` denials across 12 sessions (probe sessions excluded): 15 of
them withheld that sentence, in 10 of the 12 sessions. A session meeting one has
no path at all, which is what sends it to reshape the state the probe reads —
the bypass [Q135](Q135.md) argues against.

**That half is not this row's.** [Q146](Q146.md) owns it, filed against the
leading `cd` spelling and citing the same `liftable` line. Its own measurement
says the redirect suspect is wrong, having probed `2>&1` rather than `> file`;
the table above is the correction, and the `$( )` and assignment-segment shapes
are new to it.

Groomed 2026-09-01: this paragraph named that work as *the open pull request
#70*, which merged the same day. Q146 is the row it filed, and it is where the
break-glass half is tracked. Two
of the three are the shape
`plugins/exit-status-guard/README.md:90:make check > <scratchpad>/c.log 2>&1; rc=$?; echo "EXIT=$rc"; exit $rc`
prescribes, so a session obeying one guard writes a command the other cannot
lift.

**The collision is guard-wide rather than one documented example**, which the
README citation above understates. Measured 2026-09-04 by the Q136/Q154 stream
(#88) rather than here, by driving `decide` with a scratchpad resolved: every
remedy exit-status-guard emits prescribes a real file. Mind the taxonomy when
quoting a count — the working agreement documents **three rules**, folding
`$PIPESTATUS` into the piped one, while the source carries **four reason
strings** (`PIPESTATUS_REASON`, `PIPED_REASON`, `LOST_STATUS_REASON`,
`SEQUENCED_REASON`), and all four interpolate
`plugins/exit-status-guard/scripts/bash-exit-status-guard.py:665:LOG_PLACEHOLDER = '<LOG>'`.
It resolves to `plugins/exit-status-guard/scripts/bash-exit-status-guard.py:722:LOG_PLACEHOLDER, scratch + '/out.log')`
or, with no scratchpad, to
`plugins/exit-status-guard/scripts/bash-exit-status-guard.py:724:LOG_PLACEHOLDER, 'tmp/out.log')`
— a real file on both arms, never a device. So a session obeying exit-status-guard
writes an unliftable command whichever of its rules it met, and how far that
reaches is [Q146](Q146.md)'s to settle, not this row's.

## Rank

**Holds `a1i`.** The route is the second-most-fired denial measured — 18 of 47
real branch-guard denials across this machine's transcripts, in 11 sessions,
against [Q135](Q135.md)'s 27 in 24 — and the probe is now designed and costed,
which is what the row was waiting on. It does not rise, for two reasons the
measurement produced: the deny it removes is the narrower half of the case (the
fourth variant keeps denying and cannot be reached), and this is the only one of
the three branch-guard open questions whose fix adds real cost on the deny arm
rather than none.

**[Q146](Q146.md) should be re-ranked above this row**, which is a change to that
row rather than to this one. It is measured as independently fixable, its fix is
a classification change costing nothing, and the deny it repairs pushes sessions
toward the repo-wide `*_ENABLED=0` knobs — a worse outcome than the conservative
deny this row is about. The key belongs to a groom; the position is between
Q135 and this row.

## If nothing is done

The deny stands and it is defensible — it protects commits that exist nowhere
else, and its reading was accurate in the reported case. The cost is the case it
cannot see: a session discarding a rebase of already-published work is told to
read a squash-merge route that does not apply, and, three times in four, is not
told the break-glass exists.
