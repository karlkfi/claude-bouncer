# The unreachable-tip deny cannot see content origin already carries

`plugins/branch-guard/hooks/branch-guard.py:1579:return ('deny-unreachable',`
fires off one question, asked by
`plugins/branch-guard/hooks/branch-guard.py:1991:def tip_is_recoverable(cwd, name):`:
is this branch's tip reachable from a remote-tracking ref or main? That is a
question about *reachability*, and a rebase is where reachability and content
come apart. Replaying commits onto a moved base gives every one of them a new
object name, so the branch is genuinely unreachable while the tree it produces
is an object origin already holds.

**Measure:** the probe this needs and what it costs. A tree comparison of `HEAD`
alone proves only that the final state survives, not that each orphaned commit
does, so the honest form is a check over the orphan set — the same scope
`orphans_only_reproducible_merges` already takes. Whether that is cheap enough
to sit on the deny arm, and which refs it compares against, is unmeasured.
Nothing here proposes an answer.

## Measured

2026-09-01, branch-guard 1.10.0. The installed hook is byte-identical to this
tree (`diff` over `~/.claude/plugins/cache/claude-bouncer/branch-guard/1.10.0`,
exit 0). Throwaway repo: `main` on origin; branch `claude/dup` carries five
commits on top of it; those five are then cherry-picked onto `origin/main` under
a different committer date and pushed as `claude/republished`. Worktree clean.

| reading | value |
|---|---|
| `git log --oneline claude/dup --not --remotes` | 5 commits |
| `git rev-parse claude/dup^{tree}` | `106ea7d…` |
| `git rev-parse origin/claude/republished^{tree}` | `106ea7d…` — the same tree object |
| `git diff --stat claude/dup origin/claude/republished` | empty |
| `git reset --hard origin/main` | **deny-unreachable** |

The guard's reading is accurate: those five commits exist nowhere else. What it
cannot see is that origin carries the tree they build.

## The message reasons about this and lands elsewhere

`plugins/branch-guard/hooks/branch-guard.py:524:way already has its content on main under another object name`
is the deny route arguing the neighbouring case, and it argues it on content
rather than reachability — a squash merge leaves the tip unreachable while the
content is on main, so the reset is unnecessary. Correct for a squash. A rebase
produces the same object-name change and the opposite conclusion: the reset is
wanted, and the route offers no path to it.

## The break-glass is not the problem, and the reporting session had it wrong

Reported as "the documented override does not open this rule". It does.
`plugins/branch-guard/hooks/branch-guard.py:1900:if inv is None or writes or inv['prog'] != 'git':`
admits `deny-unreachable` through `OVERRIDABLE_GIT`, and on the fixture above
`BRANCH_GUARD_OVERRIDE=x git reset --hard origin/main` allowed.

What the reporting session actually ran carried a redirect to a log file, `$( )`
substitutions and a leading assignment segment. Each of those defeats
`plugins/branch-guard/hooks/branch-guard.py:2296:liftable = (all(ovr for _, ovr, _ in asks)`
on its own, measured one at a time on the same fixture:

| command | verdict |
|---|---|
| `BRANCH_GUARD_OVERRIDE=x git reset --hard origin/main` | allow |
| … `2>&1` | allow |
| … `; echo done` | allow |
| … `> log 2>&1` | **deny** |
| … `; echo "$(git rev-parse HEAD)"` | **deny** |
| `SP=/path; BRANCH_GUARD_OVERRIDE=x git reset --hard …` | **deny** |

The tell is a sentence going missing: an unliftable denial drops
`Re-run it prefixed with BRANCH_GUARD_OVERRIDE=<reason>`, and nothing says why.
Over this machine's transcripts, 2026-08-22 to 2026-09-01, 21 distinct
`deny-unreachable` denials across 12 sessions (probe sessions excluded): 15 of
them withheld that sentence, in 10 of the 12 sessions. A session meeting one has
no path at all, which is what sends it to reshape the state the probe reads —
the bypass [Q135](Q135.md) argues against.

**That half is not this row's.** [Q146](Q146.md) owns it, filed against the
leading `cd` spelling and citing the same `liftable` line. Its own measurement
says the redirect suspect is wrong, having probed `2>&1` rather than `> file`;
the table above is the correction, and the `$( )` and assignment-segment shapes
are new to it.

Groomed 2026-09-01: this paragraph named that work as *the open pull request
#70*, which merged the same day. Q146 is the row it filed, and it is where the
break-glass half is tracked. Two
of the three are the shape
`plugins/exit-status-guard/README.md:89:make check > <scratchpad>/c.log 2>&1; rc=$?; echo "EXIT=$rc"; exit $rc`
prescribes, so a session obeying one guard writes a command the other cannot

## If nothing is done

The deny stands and it is defensible — it protects commits that exist nowhere
else, and its reading was accurate in the reported case. The cost is the case it
cannot see: a session discarding a rebase of already-published work is told to
read a squash-merge route that does not apply, and, three times in four, is not
told the break-glass exists.
