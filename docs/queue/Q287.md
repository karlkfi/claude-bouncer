# prod-guard misses a bundled env -S, as in env -iS

`env -S STRING` splits STRING into words and runs them. prod-guard's
`env_split_string` reads `-S STRING`, `-SSTRING` and `--split-string`, and
nothing else
(`plugins/prod-guard/scripts/bash-prod-guard.py:655:def env_split_string(argv):`).
A bundle ending in `S` falls through to the ordinary option walk, so the
command inside the string is never classified.

Driven 2026-10-05 through the hook at `origin/main` `aa935df`, with an empty
`$HOME` so the `--context=` flag is the only target:

| command | guard |
|---|---|
| `env -S 'kubectl --context=gke_acme_prod-us delete pod x'` -- control | deny |
| `env -i -S 'kubectl --context=gke_acme_prod-us delete pod x'` -- control | deny |
| `env -iS 'kubectl --context=gke_acme_prod-us delete pod x'` | **silent** |
| `env -vS 'kubectl --context=gke_acme_prod-us delete pod x'` | **silent** |

Both envs run the command: `/usr/bin/env -iS '/bin/echo RAN_BSD'` (macOS) and
`genv -iS '/bin/echo RAN_GNU'` (GNU coreutils 9.11) each printed.

foreground-guard closed the same gap in Q246, and exit-status-guard in Q235,
both by taking `-S` through `wrapper_option`. This row is prod-guard's, where
the miss is a production mutation.

## Which way it gets built

Walk a short option word a character at a time, as the shared
`wrapper_option` does, and when the walk stops on `S`, treat the rest of the
word or the next word as the split string.

## If it is never built

A production delete written behind `env -iS` reaches the cluster with the
guard silent. `-S` is a shebang idiom and rare in a typed command, which is
also what makes it a one-line bypass for anyone who knows about it.
