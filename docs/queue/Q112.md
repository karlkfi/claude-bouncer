# Correct `maintaining-backlog.md`, which sends sessions into claimed IDs

The doc's invariant 1 tells a session to take the next number above the highest
the store has ever held, and says the claim allocator is future work -- "this is
the part of the process that does not survive two sessions filing at once, which
is what Q92 is for; until it lands, a second concurrent filer collides". The
allocator is live and in use: `git ls-remote origin 'refs/queue-ids/*'` returned
11 reservations on 2026-08-23, running through Q111.

So the doc is not merely stale, it misdirects. Measured 2026-08-23 from a
main-only view, which is what a fresh session on a fresh branch has: the highest
ID ever added to `docs/queue/` on `origin/main` is Q108, so the doc's own
procedure yields Q109 -- already claimed, as are Q110 and Q111. Three
consecutive collisions, each against a row that exists on an unmerged branch and
is therefore invisible to the procedure the doc prescribes. A clone that happens
to have fetched those branches computes Q112 instead and does not collide, which
is what makes the failure intermittent rather than obvious.

The fix is to say the allocator is the way to get an ID and point at
`alloc-queue-id.sh`, keeping the read-from-git rule only as the fallback for a
remote that refuses a custom ref namespace. Q92 covers adopting the allocator
and is a different item; this is the doc still describing the pre-allocator
world after the fact. Not Q97 either -- that is about re-vendoring `queue.py`
and naming what watches it.

Worth checking in the same pass whether a lint rule can hold this: the skill
describes `queue.py claims`, which fails an ID a branch adds that holds no
reservation. `make check` does not run it.
