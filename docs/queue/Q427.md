# branch-guard does not follow a literal cd out of a funsub

bash runs a funsub's list in the current shell, so `echo ${ cd ../r; }; git commit -m x` commits on the branch `../r` has checked out. bash 5.3.15 prints `main` for `echo ${ cd ../m; } >/dev/null; git branch --show-current` run from a feature worktree, `../m` a checkout of `main`.
Driven 2026-11-26 through `hooks/branch-guard.py` with the payload's `cwd` in a feature worktree and `../r` a checkout of `main`, on `origin/main` at `c0bc0235` and with Q383's fix at `67799f1`:

| command | `c0bc0235` | `67799f1` |
|---|---|---|
| `{ cd ../r; }; git commit -m x` | ask | ask |
| `echo ${ cd ../r; }; git commit -m x` | allow | none |
| `echo "${ cd ../r; }"; git commit -m x` | allow | none |

Q383's fix makes the cwd after a funsub unknown (`plugins/branch-guard/hooks/branch-guard.py:1895:if runs_funsub(seg):`), so the allow became a defer, and the commit still lands on `main` without a prompt in a session that allowlists `git commit`.
The same `cd` inside `{ }` asks.

## Which way it gets built

The funsub's body is literal text, and the cwd walk already reads a `cd` inside `{ }`.
So carry the body's exit cwd out of the funsub instead of `None`, and keep `None` where the body's own walk ends unknown.
Not measured.
Q347's next step would not reach this: it resolves `$(git rev-parse --show-toplevel)` and `$(pwd)` as a `cd` target, and nothing here is a substitution in a `cd` operand.

## If it is never built

A commit or push written after a funsub that changes directory reaches the user's own permission rules instead of branch-guard's prompt.
How often sessions write a `cd` inside a funsub is not measured.
