# prod-guard's tokenize recursion has no depth cap and fails open

`tokenize` and `_hoist_substitutions` call each other once per nested
substitution, with no depth bound
(`plugins/prod-guard/scripts/bash-prod-guard.py:384:def tokenize(raw):`).
Around 500 levels that exhausts Python's stack, and the `RecursionError` falls
into the catch-all at
`plugins/prod-guard/scripts/bash-prod-guard.py:3471:    except Exception:  # noqa: BLE001 — fail-open on any infrastructure error`,
so prod-guard defers.

The stream-A reviewer found it re-checking Q325 (#301). Driven 2026-11-01 by
Q325's worker on #301's tree, with Q325's trap nested `k` deep —
`'echo "$(' + nest(k, 'echo ")"') + ' ; kubectl --context gke_acme_prod-us delete ns payments)"'`,
where `nest` wraps `k` times in `echo "$(` … `)"` — and `PROD_GUARD_DEBUG=1` so
the traceback prints:

| k | #301 | `main` at `8e3a0269` |
|---|---|---|
| 480, 490 | deny | deny |
| 500 | exit 1, `RecursionError` (defer without the debug variable) | deny |

The traceback holds 496 `tokenize` and 495 `_hoist_substitutions` frames.
`main` denies at even `k` near 500 only because its parser misread the trap
(Q325) and stopped returning bodies long before that depth; at odd `k` it
defers on the same command anyway. So #301 does not make prod-guard worse at
any depth, and it is the first tree where a correct body reaches this
recursion. workspace-guard and exit-status-guard cap their own recursion at
`MAX_SUBST_DEPTH` in `lib/bouncer_parse.py` and are unaffected here.

## Which way it gets built

Bound the recursion with `MAX_SUBST_DEPTH`, the way the other guards do, and
decide what prod-guard does past the cap: deny or ask, not the defer the
catch-all gives. Pin `k = 500` and a shallow control in
`tests/test_prod_guard.py`.

## If it is never built

A production command written after about 500 levels of nested substitution
passes prod-guard unread. Nobody writes that by accident.
