# A guarded command in `<(…)` or `>(…)` on an unguarded one goes unjudged

workspace-guard asks before `rm -rf /etc/x`. Put the same command inside a
process substitution on an unguarded command, as in `true >(rm -rf /etc/x)`,
and the hook returns no decision. bash runs the body either way.

Measured 2026-10-05 on `origin/main` at `d43db6e`. The hook ran from a
`git archive` of that tree with its cwd inside the project root, and bash was
`env -i "$(command -v bash)" --norc --noprofile -c`, which is 5.3.15:

| command | workspace-guard |
|---|---|
| `rm -rf /etc/x` (control) | ask |
| `cat <(cat /etc/hosts)` (outer command guarded) | ask |
| `true <(rm -rf /etc/x)` | **none** |
| `true >(rm -rf /etc/x)` | **none** |
| `true >(tee /etc/x)` | **none** |
| `true 2>(rm -rf /etc/x)` | **none** |

`true >(touch pf1)` and `true <(touch pf2)` each created their file under
that bash, so the body does run. The independent review of #219 found this,
with a longer table that includes `true >(rm -rf $HOME/x)`, which is denied as
a plain command and gets no decision here. That table is in
https://github.com/karlkfi/claude-bouncer/pull/219#issuecomment-5989911630.

The mechanism is not traced. One lead: lib's `command_substitutions` returns
the body of a `$(…)` (`echo $(rm x)` gives `['rm x']`) and nothing for a
`<(…)` or `>(…)` (`true <(rm -rf /etc/x)` gives `[]`). So
`substitution_bodies` may never see a process substitution's body.

The ask on `cat <(…)` is not the body being judged. The body's words are read
as operands of the outer `cat`: on `origin/main` at `b3ff372`,
`cat <(cat /etc/hosts)` asks, naming `/etc/hosts`, while
`cat <(cat ./README.md)` allows. The outer command being guarded is what
produces the ask. The independent review of #224 traced this.

`true > >(rm -rf /etc/x)`, with a redirect before the substitution, asks at
`b3ff372`, unlike `true >(rm -rf /etc/x)`. The #219 review found that it asks
only because the `>(` is split from the `>`, so it is an accident of
tokenizing rather than a judgement of the body.

## Which way it gets built

Trace where the body is dropped first. If it is `command_substitutions`,
returning process-substitution bodies there is a `lib/` change that reaches
every guard calling it. Add the `lib` label then, and read Q277, whose
process-substitution half may share the cause. Cross the fixtures over `<(` ×
`>(` × an fd-prefixed `2>(`, with the unguarded outer command. Keep
`cat <(cat /etc/hosts)` as the control, and add `true > >(rm -rf /etc/x)` as
a fixture so a fix that changes tokenizing can't lose that ask.

## If it is never built

Any destructive command written inside a process substitution on an unguarded
command, as in `true >(…)`, reaches a path outside the workspace with no
prompt.
