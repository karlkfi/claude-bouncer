# Nothing remembers an approved ask, so one shape prompts 21 times a week

An `ask` verdict is re-asked every time. Claude Code's own allowlist
(`permissions.allow`) is evaluated before hooks and cannot answer for one, and
the hook API has no "remember this" reply — so a guard that prompts on a shape
the operator approves prompts on it again on the next call, forever. There is no
per-shape opt-out short of `WORKSPACE_GUARD_OVERRIDE` on every command or
turning the rule off.

## Measured

Seven days to 2026-08-31, 1,615 local transcript files, 19,580 emitted
`PreToolUse` decisions plus 903 denies recovered from blocked calls.

| | |
|---|---|
| asks (prompts an operator answers) | 245 |
| approved | 244 |
| declined | 1 |

The single decline was a deliberate probe — a `secret.txt` write into a
spill-guard test scratchpad. No prompt raised against real work was declined all
week.

Repetition is what makes the total large, not variety. `~/.claude/CLAUDE.md`
alone prompted 21 times; `~/.claude/settings.json` 5; one
`tests/launcher_check.py` under a single worktree 9. The operator answered the
same question about the same path on 21 separate occasions.

## Who it is for, and what it costs

The operator, and the cost is the review itself rather than the keystrokes. At
245 prompts a week against 1 real decline, the prompt stream is 0.4% signal, and
a prompt answered 244 times without incident stops being read — which is the
state the one prompt that matters would arrive into. The maintainer's own
report: "There are so many prompts that it's impossible to review them all in
depth and maintain velocity."

So this is not a request to loosen a boundary. Every rule below can keep its
current strictness and the prompt count still falls, because what is being
removed is the *repetition*, not the check.

## Which way it gets built

**The hook API has no field for this, and that is settled.** `permissionDecision`
takes `allow`, `deny` and `ask`, and nothing in `hookSpecificOutput` carries a
"remember this" flag (Claude Code hooks reference, read 2026-08-31). So the
guard has to hold the memory itself and answer `allow` on a later occurrence.

**The hard part is not storage, it is that a PreToolUse hook never learns
whether its own `ask` was approved.** It returns `ask` and is never told the
answer, so it cannot remember an approval it never saw. A guard that recorded
the shape at ask time would be remembering that it *asked*, which is true just
as often when the operator said no.

`PostToolUse` closes the loop, because it fires only when the tool actually
ran:

1. `PreToolUse` returns `ask` and does not record anything.
2. The operator approves; the tool runs; `PostToolUse` fires with the same
   `session_id` and `tool_use_id`. Declined, it does not fire at all.
3. `PostToolUse` re-derives the shape from `tool_input` — the same
   classification the PreToolUse hook ran, so no state is handed between them —
   and records it.
4. The next `PreToolUse` matching that shape returns `allow`.

The failure mode falls the right way: forgetting is safe and costs one more
prompt, while remembering takes positive evidence that the tool ran. A decline
records nothing, so the next occurrence asks again.

`PermissionRequest` fires when a call needs a decision and may suit step 1
better; it does not change the shape of the design.

Three decisions taken here, so a worker does not reopen them:

- **Keyed on the decision's shape**, not the command text: the reason category
  plus the class of target it resolved to — `outside:/Users/karl/.claude`, not
  `outside:/Users/karl/.claude/CLAUDE.md`, and never the command string, which
  differs on every call and would remember nothing.
- **Session-scoped, not persistent.** A remembered approval that outlives the
  session is a config entry the operator never wrote and cannot see. The
  session is also the unit the fatigue is measured in.
- **Opt-in, default off** — `Q84`'s rule, that looser behaviour ships as an
  explicit opt-in and the secure default does not move.

**Where the state goes is the one open point.**
`plugins/workspace-guard/PRIVACY.md` says the hook writes nothing to disk, and
a cache falsifies that. The session scratchpad, whose path is derivable from
`session_id`, is the obvious home; whichever is chosen, PRIVACY.md is reworded
in the same change rather than left standing and wrong.

## If it is never built

Every other row that reduces prompts does so by exempting a category, which
trades boundary for quiet one rule at a time. This is the only direction that
lowers the count without moving a boundary at all, so without it each future
reduction has to be bought with an exemption.

## Its own worked example

`plugins/workspace-guard/scripts/bash-workspace-guard.py:381:def allowed_read_prefixes(base):`
is this feature done by hand, ahead of time, for one category: a prefix list the
operator edits so a read stops prompting. It works, and what it cannot do is
learn from an approval the operator has already given 21 times.
