# A `-c` body reaching `eval` is expanded in the wrong shell

`evaluate_command_string` hands `eval`'s operands to the same recursion it
hands a `bash -c` body, with `child_env` — what a child process inherits. But
`eval` starts no child. It runs in the *current* shell, so its body resolves
against that shell's variables, exported or not, and it does so under either
quoting: single quotes stop the parent expanding the argument, and `eval` then
expands the same text itself a moment later against the same environment.

Probed 2026-09-01 against prod-guard at the Q131 head, one assignment and a
bare shell var:

| command | hook | bash |
|---|---|---|
| `C=gke_acme_prod-us; eval "kubectl --context $C delete pod x"` | **ask** | prod |
| `C=gke_acme_prod-us; eval 'kubectl --context $C delete pod x'` | **ask** | prod |
| `export C=…; eval "kubectl --context $C delete pod x"` | deny | prod |

Only the third agrees, and it agrees for the wrong reason — the name happened
to be exported, so `child_env` held it. The guard fails safe, as in Q131: an
ask is still a prompt. What it costs is the deny a production target is owed,
and a reason naming `$C` as matching neither pattern when it matches a
production one.

## Which way it gets built

Expand an `eval` body against `same_shell` rather than `child_env`,
unconditionally. Quoting does not enter into it, which is what separates this
from Q131, whose completing PR files this row: there the fix reads the
quoting off the token to decide who expanded the body, because a child really
is involved. Here there is no
child and no second environment, so there is nothing to read.

## If it is never built

The same false ask Q131 fixed for `bash -c`, on the one construction a session
reaches for when it is building a command string rather than running one — and
now inconsistent with its `bash -c` neighbour, which is worse than uniformly
wrong.
