# Rule 3 names a `;` the command lacks, and `&&` cannot follow a heredoc

The sequenced-mutation deny names an operator the command does not contain and
hands over a rewrite that has nowhere to go when the join it matched is the
newline that closes a heredoc. The verdict itself is right: in bash a newline is
a `;`, and a `git commit` that a pre-commit hook rejects leaves its files staged
for the next commit to fold in. What is wrong is the reason, which is the only
thing the model gets to act on.

## Measured

2026-09-07, exit-status-guard 2.0.1, a `claude-spill-guard` worker session
(worktree `zealous-nightingale-61f013`, working karlkfi/claude-spill-guard#121).
Fifteen seconds before this call the same worker had been denied under rule 3
on the `;`-joined form of the same command and had rewritten every join to
`&&`. This is the retry, with the commit body elided:

```bash
git reset -q -- docs/queue/Q131.md && echo "=== staged for commit 1:" && git diff --cached --stat && git commit -q -F - <<'MSG'
fix(bash,hook): scan the file an input redirect names (Q131)
…
MSG
echo "commit1: $(git log --oneline -1)" && git add -u docs/queue/Q131.md && echo "=== staged for commit 2:" && git diff --cached --stat && git commit -q -m "docs(queue): complete Q131" && echo "commit2: $(git log --oneline -1)" && git status --short && git log --oneline origin/main..HEAD
```

The denial, with the session's scratchpad path shortened to `<scratch>`:

> exit-status-guard: `git commit -q -F -` is sequenced before `git commit -q -m
> docs(queue): complete Q131` with `;`, which runs the second whatever the first
> returned -- the status is read correctly and then ignored, so a failed check
> still publishes. Join them with `&&` so the state change is conditional on the
> check passing. Where the second command has to run even when the first fails
> -- a restore after a gate whose failure is the assertion -- capture the status
> and check it afterwards: cmd > <scratch>/out.log 2>&1; rc=$?; restore; [ "$rc"
> -ne 0 ] || exit 1. If the status genuinely does not matter here, re-run
> prefixed with EXIT_STATUS_GUARD_OVERRIDE=<reason>. …

Rule 3 fired: `sequenced_mutation` accepts a `;` or a newline as the separator
after the gate
(`plugins/exit-status-guard/scripts/bash-exit-status-guard.py:652:if next_op(seg.post_ops) in`),
`git commit` is both a registry gate and a registry mutator, and the only
separator in the command that is not `&&` is the newline after `MSG`. The
reason then prints a fixed string that says `;` whichever one matched
(`plugins/exit-status-guard/scripts/bash-exit-status-guard.py:771:which runs the second whatever the first returned`).

Reproduced against the hook at 49ce73b, same registry, nothing executed:

| command | verdict |
|---|---|
| the call above | deny, rule 3 |
| `git commit -q -F - <<'MSG'` newline body newline `MSG` newline `git push` | deny, rule 3 |
| `git commit -q -F msgfile` newline `echo x && git commit -q -m second` | deny, rule 3, still says `;` |
| `git commit -q -F - <<'MSG' && echo commit1 && git add -u f && git commit -q -m second` newline body newline `MSG` | silent |

The last row is the form that works, and nothing tells the reader it exists.
A heredoc terminator has to end its line, so `&&` cannot follow `MSG`; the
operator goes on the redirect line, before the body, which is legal bash and
what the guard already accepts. The reason says to join with `&&` and the
README does not mention heredocs at all, so a session that has already
converted every `;` reads the second deny as the first one repeated. This
worker's way out was to split the two commits into two calls, which the guard
cannot see across and which gates nothing.

The same shape had fired in the same project on 2026-09-03: `git add …` newline
`git commit -F - <<'MSG'`, reported as `;`. A sweep of every transcript under
`~/.claude/projects` on 2026-09-07 — 1,718 files, 1,446 exit-status-guard
denials — found 421 under rule 3, of which 46 carried no `;` anywhere outside a
heredoc body, 41 of those in a command holding a heredoc. The heredoc bodies
were removed by a regex before counting, so treat the split as approximate; the
direction is not in doubt.

## Which way it gets built

Two edits in the guard, no parser change. The rule keeps firing on a newline —
`git add` newline `git commit` with the add failing is the false publish it
exists for — so the fix is in what the reason says.

1. Name the operator that matched. `sequenced_mutation` reads `next_op` and
   knows whether it saw `;` or `\n`; carry that into the reason and print "with
   a newline" when it is one, so the reader looks for the right thing.
2. When the gate's segment carries a heredoc, say where the `&&` goes. The
   `<<` operator survives into the token stream — `split_segments` drops it
   with its delimiter as a redirect — so the segment can be flagged at that
   point, and the reason for a flagged gate hands over the redirect-line form:
   `cmd <<'EOF' && next`, then the body. One README sentence beside the rule
   covers the case for a reader who never sees the deny.

## If it is never built

Every heredoc-then-command call costs two denies instead of one, and the second
reason is the first one verbatim, so the lesson a session takes is to split
calls rather than to gate the join. That is the case `hook-verdict` names: a
deny whose fix cannot be written into its reason spends the reviewer it was
meant to save.
