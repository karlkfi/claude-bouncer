# A checkout the session made itself is outside its own workspace

`plugins/workspace-guard/scripts/bash-workspace-guard.py:2761:proj = os.path.realpath(os.environ.get('CLAUDE_PROJECT_DIR') or cwd)`
fixes the workspace at the session's Claude Code project directory. A session
that creates a second working directory of the same repository — `git worktree
add` for a review checkout, a bisect, a build against another commit — is then
outside its own workspace on every guarded read of it.

**So the guard prompts on the practice the fleet is being told to adopt.**
Review sessions are supposed to take their own checkout of a branch rather than
read the author's worktree. One that does gets prompted for it, which trains the
opposite habit.

**Settles:** the sibling-worktree machinery already exists —
`plugins/workspace-guard/scripts/bash-workspace-guard.py:2783:def classify_outside(rp, ctx, is_read):`
and the `sibling` category it returns, plus `resolve_session_worktree`. The
question is which signal separates a checkout this session created from a peer
session's, and the answer is in that code plus the security note on cross-checkout
writes rather than in a new mechanism.

## Measured

Seven days to 2026-08-31, over 1,615 transcript files. All 67 peer-worktree ask
tokens came from **2 sessions**, which is why this is invisible in any daily
rate — 2 sessions against 73 moves nothing. They are two different problems:

| session | asks | what it did |
|---|---|---|
| a PR review in `github-actions-gateway` | 13 | created its own checkout and was prompted for using it |
| a worker in `claude-skills` | 54 | reached into `claude-ground-truth`'s worktrees — a different repo |

This row is the first. The second is fleet discipline and lands in
`karlkfi/claude-skills`.

The review session's own transcript carries the creation, so this is not
inferred from the directory's name:

```
git worktree add --detach ../pr1790-review-vb 3f0e49606a9873bb7ad84cb4d846237b946a855e
```

Its project directory is `.claude/worktrees/vigilant-blackburn-0b1407`; the
checkout it made is `.claude/worktrees/pr1790-review-vb`, a sibling. Thirteen
asks followed, all approved, on `bash`, `grep` and `sed` against a tree the
session had just created.

## Who it is for

A review session, and any session that needs a second commit checked out at
once — which is the only way to run a build or a test against another revision
without disturbing its own tree. There is no in-workspace alternative: a
worktree cannot live inside the worktree it is created from without being
committed or ignored, so the correct layout is always a sibling.

## What makes it hard, and why it is not obviously safe

A sibling worktree is indistinguishable from a peer session's by looking at the
filesystem, and peer-session worktrees are exactly what the maintainer does not
want read: "I don't really want sessions accessing the worktree of another
session, in general."

Two candidate signals, neither endorsed:

1. **Track the creation.** The guard sees the `git worktree add` go past and
   records the path for the session. Precise, and it needs per-session state the
   hook does not currently keep — the same state question `Q139` opens.
2. **Read the checkout's shape.** A `--detach` worktree holds no branch, so it
   is nobody's session root; a peer session's worktree has a `claude/*` branch
   checked out. Cheap and stateless, but a heuristic — a session working detached
   for its own reasons would be misread.

Whichever is chosen, the write path deserves separate treatment from the read
path, as it does everywhere else in this guard.

## If it is never built

Every review session pays a prompt per file it reads from the checkout it was
told to make, and the cheaper wrong habit — read the author's worktree directly —
costs exactly the same prompt, so nothing steers between them.
