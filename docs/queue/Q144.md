# A checkout the session made itself is outside its own workspace

Blocked by [Q139](Q139.md), which builds the session-scoped store of approvals
this rides on. Nothing here works without it: a deny never reaches an operator
and an `ask` never tells the hook it was approved, so there is no approval to
remember until that loop exists.

`plugins/workspace-guard/scripts/bash-workspace-guard.py:2777:proj = os.path.realpath(os.environ.get('CLAUDE_PROJECT_DIR') or cwd)`
fixes the workspace at one checkout, so **exactly one checkout of a repository is
usable at a time**. A session that creates a second working directory of the same
repository — `git worktree add` for a review checkout, a bisect, a build against
another commit — creates it unimpeded, and then cannot use it.

## Answered 2026-09-02: ask on the creation, then allow it for the session

Creating a second worktree is safe enough to permit and consequential enough to
confirm, so it asks once and its use is free for the rest of that session rather
than prompting per file. That is the general shape in
`plugins/workspace-guard/docs/design.md:46:What the boundary is for, and how it moves`
applied to this case: a worktree of the *same* repository is inside the repo, so
it does not engage the boundary's larger purpose, and it engages the smaller one
— sessions staying off each other's checkouts — only for a tree some peer owns.

**The creation is the event, and it is the only one that carries ownership.** An
ask at first *use* already fires today, and approving it means only that the
operator let this session touch that path; it cannot separate a checkout the
session made from a peer's, so it could never justify granting writes. An ask at
creation is unambiguous, because the session is the one creating it. That is what
retires the stateless `--detach` heuristic this row used to carry, which misread
a session working detached for its own reasons.

## Which way it gets built

**branch-guard hosts the ask, because it is already the guard that sees the
call.** It parses git subcommands today and has a `worktree` branch —
`plugins/branch-guard/hooks/branch-guard.py:1575:if first in ('add', 'list', 'lock', 'unlock'):`
allows `add`, `list`, `lock` and `unlock`, `remove` allows unless `--force`, and
`prune`/`move` ask. So `add` moves from `allow` to `ask` and the approval records
the created path. workspace-guard has no notion of git at all — its only mention
is `shutil.which('git')` at line 217, locating an MSYS root on Windows, and its
`SPEC` table maps commands to file-operand positions, which a directory being
created does not fit. Putting the recognizer there means a bespoke parser in a
guard deliberately built around one classification.

workspace-guard then reads the recorded paths and allows reads and writes under
them for that session. [Q139](Q139.md) already carries `workspace-guard`,
`branch-guard` and `lib` labels, so cross-guard session state is contemplated
there; whoever builds the store decides whether the path record shares it or sits
beside it.

Two things this does not cover, both of which degrade to today's behaviour rather
than to something worse. It catches `git worktree add` and nothing else, so a
`git clone` or a worktree created inside a script is unimproved. And it assumes
`PostToolUse` fires for an approved `git worktree add` — **unverified**; Q139's
design assumes it fires for any tool that ran, which should hold, but no run has
shown it.

## Measured 2026-09-02, workspace-guard 1.11.0

By driving `plugins/workspace-guard/scripts/bash-workspace-guard.py` on synthetic
PreToolUse payloads against a throwaway two-worktree repository, created and
removed by the probe. `A` and `B` are linked worktrees under the repository root;
`repo` is the primary checkout.

| session project dir | call | verdict |
|---|---|---|
| `A` | `cat B/README.md` | **ask** — outside-workspace path |
| `A` | `Edit` tool on `B/README.md` | **deny** — sibling-checkout write |
| `A` | `sed -i '' 's/a/b/' B/README.md` | **deny** |
| `A` | `Edit` tool on `repo/README.md` | **deny** |
| `A` | `git worktree add --detach ../C HEAD` | defer |
| `A` | `git -C B commit -am wip` | defer |
| `A` | `cat A/README.md` (control) | allow |
| `repo` | `cat B/README.md` | allow |
| `repo` | `Edit` tool on `B/README.md` | allow (defer) |

**The boundary turns on containment, not on read versus write.** Where the second
checkout is under the session's project directory, both halves pass — the
sibling-checkout rule is reached only after the path is found outside
(`plugins/workspace-guard/scripts/bash-workspace-guard.py:2815:if not path_is_outside(rp, ctx.proj):`
returns early, and the sibling test at
`plugins/workspace-guard/scripts/bash-workspace-guard.py:2838:Write into a sibling checkout of the same repo`
sits below it). Where it is not — a dispatched session, whose project directory
is itself a linked worktree — the read asks and the write denies. The dispatch
case is the one this row is about, and it fails on both halves.

Which checkout is the usable one follows `CLAUDE_PROJECT_DIR` when it is set and
the payload `cwd` otherwise, per the citation above; verdicts were identical with
the variable set and unset. Unset is the real shape — Claude Code does not export
`CLAUDE_PROJECT_DIR` into the Bash environment on this host, confirmed 2026-09-02
against a session environment carrying twenty other `CLAUDE_*` variables and not
that one.

**A read of a self-made worktree that allows is a venue artifact worth knowing
about.** The same probe run on 2026-09-01 inside `~/workspace/claude-skills`
reported every read allowing, because this host sets
`WORKSPACE_GUARD_READ_ALLOW_PREFIXES` to that tree and the exemption is checked
before the boundary. Clearing the variable is what produced the asks above. Any
future probe of this row's read half has to run outside a read-allow prefix or it
measures the prefix.

The deny, verbatim:

> workspace-guard: Sibling-checkout write(s) blocked: writing into a different
> checkout of this repo lands your change on the wrong branch. `<path>` is inside
> another checkout of this repo (`<root>`, on branch main) — write to `<path
> under this session's checkout>` under this session's checkout instead. For
> deliberate cross-checkout work set WORKSPACE_GUARD_OVERRIDE=<reason> to
> downgrade this to a prompt.

Its repair text misdirects this case, which is [Q155](Q155.md)'s — a mechanical
fix to the message, independent of everything above and shipping without it.

## Why the two halves needed separating

A read of another checkout carries no wrong-branch hazard, so a read-side
carve-out has no false-allow surface — the worst a wrong allow does is show a
session a file it did not need. A write does: a false allow lands a change on
another session's branch, or corrupts a live peer's tree mid-edit, and neither is
recoverable by the session that did it. A false deny only costs a workaround.

That asymmetry is why the answer above hangs on the creation rather than on first
use. It is also why [Q23](Q23.md) declined a general cross-checkout read
exemption on different grounds — `git -C <repo> show <branch>:<path>` reaches a
peer's committed work with no filesystem access — which covers a peer's checkout
and not this one, since a worktree the session just made has nothing committed to
read. Q23 owns the cross-checkout read measurement; this row owns the
self-created case.

## Unverified: Claude Code may hold the same invariant

Its `EnterWorktree` tool refuses to create a second worktree by `name` while the
session is already in one, and its documentation says that after switching,
previously-visited worktrees are no longer writable — return to one by re-issuing
`EnterWorktree` with `path`. **Read from the tool's own documentation, not from a
run.** If it holds, relaxing the guards alone moves the wall rather than removing
it, and this row's build has to account for the harness too.

## Who it is for

A review session, and any session that needs a second commit checked out at once
— which is the only way to run a build or a test against another revision without
disturbing its own tree. There is no in-workspace alternative for a dispatched
session: its project directory is a linked worktree, and a worktree cannot live
inside the worktree it is created from without being committed or ignored.

## Provenance

Seven days to 2026-08-31, over 1,615 transcript files, all 67 peer-worktree ask
tokens came from **2 sessions** — invisible in any daily rate. One was a PR review
in `github-actions-gateway` that created its own checkout with
`git worktree add --detach ../pr1790-review-vb` from
`.claude/worktrees/vigilant-blackburn-0b1407` and took 13 asks against a tree it
had just made; the other reached into another repository's worktrees, which is
fleet discipline and lands in `karlkfi/claude-skills`. This row is the first.

The write half surfaced on 2026-09-01 while amending `session-worker` in
karlkfi/claude-skills#432, whose §2 had told a stream worker to give each item its
own worktree. That instruction is unbuildable for the reason measured above, and
the skill now tells workers to stack branches in one worktree instead. Two
dispatched sessions had independently hit the deny and worked around it the same
way that day.

## If it is never built

A dispatched session that needs a second checkout pays an ask per file it reads
and cannot write at all, so it spends a worktree creation before learning the
worktree is unusable. The cheaper wrong habit — read the author's worktree
directly — costs the same ask, so nothing steers between them.
