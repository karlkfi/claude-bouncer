# A `cd` inside a command substitution moves the outer cwd

Bash runs a command substitution in a subshell, so a `cd` written inside one
changes nothing for the commands after it. The group loop does not know that.
`(` is a punctuation character the tokenizer keeps, so a bare `$(cd /x)` splits
into groups like any other command, the `cd` group reaches the cwd branch
(`plugins/workspace-guard/scripts/bash-workspace-guard.py:4007:kind, arg = classify_cd(g)`),
and the tracked directory moves for the rest of the string
(`plugins/workspace-guard/scripts/bash-workspace-guard.py:4009:group_cwd, group_cwd_unknown = apply_cd(`).

## Measured

2026-09-07, against the tree of the pull request that closed Q169 -- the defect
predates it and survives it. Project root `/Users/karl/probe-proj`;
`/Users/karl/outside` is outside the root. Nothing executed -- the hook resolves
lexically, so the paths need not exist.

| command | verdict | path named | bash would open |
|---|---|---|---|
| `echo $(cd /Users/karl/outside) && cat x` | **ask** | `/Users/karl/outside/x` | `<root>/x` |
| `echo $(cd sub) && cat x` | allow | -- | `<root>/x` |
| `cat x` | allow | -- | `<root>/x` |
| `echo "$(cd /Users/karl/outside)" && cat x` | allow | -- | `<root>/x` |
| ``echo `cd /Users/karl/outside` && cat x`` | allow | -- | `<root>/x` |

Row 1 is the defect: a prompt naming a path the command never touches, which is
the one claim a human at a prompt has to take on trust. Row 2 is the same
mechanism pointing the harmless way -- the tracked cwd moves into `sub`, and
`x` still resolves inside the root, so nothing surfaces.

Rows 4 and 5 are why this is labelled `bug` rather than `security`: only the
bare spelling reaches the defect. Quoted, the whole substitution arrives as one
token, so its `cd` never becomes a group; a backtick body is shredded into
tokens that classify as nothing. That is the same accident Q169 catalogued from
the other side -- what the group loop sees of a substitution is a property of
the spelling rather than a decision anyone made.

## Which way it gets built

Q169 left the outer token stream alone deliberately -- it added a second,
marker-based pass to answer *where did this body sit*, and changed no verdict
the group loop reaches on its own. Closing this one means the group loop
itself must stop reading into substitutions, which is the change Q169 declined
to make and the reason this is a row rather than part of it.

The mark that pass already builds is most of the mechanism
(`plugins/workspace-guard/scripts/bash-workspace-guard.py:3276:def substitution_bodies(cmd, base_cwd, base_cwd_unknown, stable_vars=None):`):
tokenizing the marked string instead of the raw one would put each substitution
in the outer stream as a single word, so its `cd` could not reach the cwd
branch and its operands would be checked once, by the recursion, at the right
directory.

**Weigh that against what the accident currently buys**, and do not assume it
is free. A bare `$(…)`'s operands are seen by the group loop today, so it is
the group loop that sets `guarded` for them -- and the recursion deliberately
drops `guarded`, so moving a body out of the outer stream turns some `allow`
verdicts into `defer`. That is not a hole (a defer leaves the user's own
permission settings in charge) but it is a behaviour change across a construct
that appears in most non-trivial commands, so it wants a differential run over
a corpus rather than a fixture or two. `paren` depth and `pipe` numbering also
move, which reaches the `ps`/`kill` classification that Q60 turns on.

## If it is never built

A prompt that names the wrong directory, on the one construct where the guard
currently reads a subshell's side effects as the parent's. The cost is a human
approving a path they cannot check, which is the direction Q169 called the more
visible of its two halves.
