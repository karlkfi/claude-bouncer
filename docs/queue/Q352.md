# branch-guard's test harness runs 1,045 hook calls on one core

`make check` spends more time in branch-guard's `test/run.sh` than in any
other stage, and every session that gates a change pays for it. The harness
can't be split across cores as it stands, so the fix is restructuring it, not
a flag.

## Measured

On 2026-11-02, on an 18-core Mac, the ten repo gates took 0.7s together, and
the plugin suites took:

| Suite | Serial |
|---|---|
| workspace-guard | 180s |
| branch-guard | 154s |
| prod-guard | 67s |
| foreground-guard | 22s |
| lib-test | 11s |
| exit-status-guard | 1.4s |

workspace-guard has since moved to its sharding runner in `make check`, as CI
already ran it, and dropped to 27s. That took `make check` from 436s to 279s
and left branch-guard at 154s of the 279s, about 55%.

A timestamped `bash -x` trace of one branch-guard run counted 1,045 `env`
launches of the hook through the launcher, 1,379 `jq` calls and 681 `git`
calls, for 1,061 passing checks. Twenty launches of the hook through
`hooks/run-python-hook.cmd` took 2.14s, about 107ms each, against 1.60s for
the same twenty run straight through `python3` and 0.49s for a bare
`python3 -c pass`. So about 112s of the 154s is hook launches. The launcher's
interpreter probe costs about 27ms of each, and the suite needs that cost
because it drives every case through the launcher on purpose.

Two cheap levers came back empty. Letting Python cache bytecode for the
vendored `lib/` modules changed twenty launches from 2.14s to 2.13s. Running
the five suites concurrently could not be measured: branch-guard took 330s in
that run, at a load average of 56 on 18 cores with an unrelated VM using
about three cores' worth of CPU, so the figure says nothing about contention
between the suites.

## Why it doesn't shard as written

Every hook call runs inside a command substitution in `decision_for` and
`reason_for`, at
`plugins/branch-guard/test/run.sh:117:decision_for() {`, so a counter
incremented there is lost when the subshell exits, and the call runs before
`check` learns which case it belongs to. The sections also share one
throwaway repo created at
`plugins/branch-guard/test/run.sh:75:WORK="$(mktemp -d "$REPO_ROOT/tmp/test-repo.XXXXXX")"`
and mutate it in sequence, so a later section depends on the state an earlier
one left behind.

## Which way to build it

Split the harness into section files that each build their own repo, so each
section is self-contained, and have `run.sh` run them in parallel and sum the
pass and fail counts. Keep the launcher-mode and `hooks.json` timeout checks
at the top of `run.sh`, run once. The `CASE_FLOOR` lower bound has to apply
to the summed count, or a section that dies early drops out silently, which is
exactly the failure the floor exists to catch.

Done is `make check` green with branch-guard at a fraction of 154s,
re-measured on a quiet machine, and the Windows Git Bash job still green,
since it runs the same harness.
