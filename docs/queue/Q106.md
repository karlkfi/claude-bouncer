# The sequencing deny recommends a form it then denies

Q100 widened the sequencing reason to name the capture form beside `&&`:
`cmd > <LOG> 2>&1; rc=$?; restore; [ "$rc" -ne 0 ] || exit 1`. That form is
still a gate sequenced before a mutator with `;`, so where the restore is
itself a registry mutator the guard denies the rewrite it just handed over. A
session copying the suggestion verbatim is denied a second time, and the only
sentence it gets next says the status does not matter here — which is exactly
backwards, since the whole point of the form is that the status was captured.

Measured 2026-08-22 against the widened reason, with the shipped registry:

    make check > c.log 2>&1; rc=$?; git reset --hard; [ "$rc" -ne 0 ] || exit 1
    make check > c.log 2>&1; rc=$?; kubectl delete -f f.yaml; [ "$rc" -ne 0 ] || exit 1

Both deny. `git checkout -- f` and `git stash pop` — the restores a mutation
control reaches for most — go silent, because neither is in `mutators`
(`plugins/exit-status-guard/exit-status-guard.json:57:cherry-pick`). So this is
the narrow tail of the shape rather than its middle, which is why Q100 shipped
the text without it.

The fix is the direction Q100 priced and did not take: teach
`plugins/exit-status-guard/scripts/bash-exit-status-guard.py:566:def sequenced_mutation`
a third question — is this mutator undoing what an earlier segment did — and
stay silent when the answer is yes. That question was deliberately left out of
the text change, so this row is where it goes rather than a defect in what
shipped.

`EXIT_STATUS_GUARD_OVERRIDE` is a working escape meanwhile, and the README says
so.
