# A backgrounded sleep inside a substitution still blocks

foreground-guard defers on `x=$(sleep 30 &)`, which holds the main thread for 30 s.
The `&` detaches the `sleep` from the substitution's shell, but the `sleep` inherits the substitution's stdout, and bash reads that pipe until every writer has closed it.
So the substitution, and the command around it, waits for the full sleep.

Measured 2026-11-16 on `origin/main` at `c3521476`, timing with `env -i /opt/homebrew/bin/bash --norc --noprofile -c` and driving `plugins/foreground-guard/scripts/bash-foreground-guard.py` with a `Bash` payload:

| command | bash | foreground-guard |
|---|---|---|
| `x=$(sleep 2 &)` | returns after 2 s | none (as `sleep 30`) |
| `x=$(sleep 2 >/dev/null &)` | returns at once | none |
| `while true; do x=$(sleep 1 &); done` | 1 s per iteration | none |
| `x=$(sleep 30)` (control) | | deny, bare-sleep floor |

The guard reads every backgrounded segment as detached, which holds for a top-level `sleep 30 &` and not inside `$( )`.
Found while working Q359, which counts a nested sleep toward the loop around it and keeps this exemption as it was.

## Which way it gets built

In a substitution body, treat a backgrounded segment as foreground unless its stdout is redirected away from the pipe (`>/dev/null`, `>file`, `>&2`).
A `2>&1`-only redirect still writes to the pipe.
Fixtures: each `none` row above whose bash column waits should deny, and the `>/dev/null` row keeps deferring.

## If it is never built

A command that waits through `$(cmd &)` holds the main thread while the guard treats it as detached, so the deny that would have pointed at `run_in_background` never fires.
