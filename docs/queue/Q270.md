# exit-status-guard ignores its override behind env or sudo

`has_override` reads only the assignments a segment opens with
(`plugins/exit-status-guard/scripts/bash-exit-status-guard.py:774:def has_override(segs):`),
so `env EXIT_STATUS_GUARD_OVERRIDE=r` and `sudo EXIT_STATUS_GUARD_OVERRIDE=r`
in front of a gate leave it denied. foreground-guard arms from both
spellings, and prod-guard from the `env` one since Q176.

Found while landing Q218. Driven 2026-10-04 through each hook on the Q218
branch; Q218 changed which operands are peeled, not how any guard reads its
override:

| command | guard |
|---|---|
| `EXIT_STATUS_GUARD_OVERRIDE=r make check \| tail -5` | silent |
| `env EXIT_STATUS_GUARD_OVERRIDE=r make check \| tail -5` | deny |
| `sudo EXIT_STATUS_GUARD_OVERRIDE=r make check \| tail -5` | deny |
| `env FOREGROUND_GUARD_OVERRIDE=r tail -f log.txt` | silent |
| `sudo FOREGROUND_GUARD_OVERRIDE=r tail -f log.txt` | silent |
| `env PROD_GUARD_OVERRIDE=r kubectl --context gke_acme_prod-us delete ns x` | ask, as the bare prefix does |

## Which way it gets built

Read the override from the operands `peel_wrappers` takes off `env` and
`sudo`, with the name verbatim, as foreground-guard does. The README's
"the name only counts in command position" still holds: an `env` operand is
an assignment `env` makes, not an argument naming the variable. A
subscripted name (`env EXIT_STATUS_GUARD_OVERRIDE[0]=r`) exports a variable
of that literal name and must not arm.

## Who it is for, and what happens if it is never built

A session that writes the hatch behind `env` gets a deny whose reason names
the bare prefix, so the cost is one retry, and the guard fails closed. The
case for building it is that the same spelling arms two sibling guards and
not this one.
