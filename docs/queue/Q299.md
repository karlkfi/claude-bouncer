# A variable source, read or unset reassigns keeps its stale value

prod-guard learns a variable's value from `NAME=value`, `export` and the other
assignment builtins, and from nothing else. bash also reassigns a variable in
`source`/`.`, `read`, `printf -v`, `mapfile`/`readarray`, `getopts`, a `for`
loop, `unset`, and a `BASH_ENV` file a child shell reads first, and a prefix on a
function call binds a value for that call alone. After any of
them, the guard still holds the old value and judges the target by it. When the
old value is non-production, a production command defers.

## Measured

2026-10-07. prod-guard at `e3f9275`, before Q269, and at `63ceb4d`, with it, using a
fixture `$HOME` whose current context is `gke_acme_prod-us`. Nothing ran
through the guard. Verdicts are the same at both heads unless marked.

| command | guard | bash 5.3.15 `$C` at kubectl |
|---|---|---|
| `C=kind-ci; source x.sh; kubectl --context $C delete ns x` | defer | `from-file` |
| `C=kind-ci; . x.sh; …` | defer | `from-file` |
| `C=kind-ci; read C; …` | defer | the line read |
| `C=kind-ci; printf -v C %s y; …` | defer | `y` |
| `C=kind-ci; mapfile C < f; …` (and `readarray`) | defer | the line read |
| `C=kind-ci; getopts a C; …` | defer | `a` |
| `C=kind-ci; for C in a b; do kubectl --context $C …; done` | defer | `a`, then `b` |
| `C=kind-ci; unset C; …` | defer | unset, so kubectl takes the ambient context |
| `C=kind-ci BASH_ENV=x.sh bash -c 'kubectl --context "$C" …'` | defer | `from-file` |
| `env C=kind-ci bash -c 'read C; kubectl --context "$C" …'` | ask at `e3f9275`, defer at `63ceb4d` | the line read |
| `env C=kind-ci bash -c 'source x; …'`, and `env C=kind-ci BASH_ENV=x.sh bash -c …` | ask at `e3f9275`, defer at `63ceb4d` | `from-file` |

The bash column was driven with `echo` in place of kubectl, under `env -i`, with
`x.sh` holding `C=from-file`. The last two rows changed when Q269 let `env`'s
operands reach a single-quoted body: the body now reads `kind-ci` the same way
the top level does, so it inherits the same gap.

A function call's prefix binds differently. `C=y f` doesn't persist: after the
call, `C` is back to its old value. But the body sees `y` for the duration of
the call. `C=kind-ci; f() { echo "in-body [$C]"; }; C=y f; echo "after [$C]"`
prints `in-body [y]` then `after [kind-ci]`, in default mode and under
`--posix` alike. Q300 judges a function body where it is written, against the
values in scope there, so the call's prefix never reaches it. Measured on the
Q300 branch:

| command | guard |
|---|---|
| `f() { kubectl --context $C delete pod x; }; C=gke_acme_prod-us f` | ask (`$C` unknown where the body is written) |
| `C=kind-ci; f() { kubectl --context $C delete pod x; }; C=gke_acme_prod-us f` | **defer** (reads `kind-ci`; bash runs it with `gke_acme_prod-us`) |

Modelling the binding means judging the body again at each call, with the
prefix's value for the call and the old value after it.

## Mechanism

Only the assignment builtins update the guard's scopes:

`plugins/prod-guard/scripts/bash-prod-guard.py:826:ASSIGN_BUILTINS = frozenset({'export', 'declare', 'typeset', 'readonly', 'local'})`

Every other way to set or clear a name passes through untouched, so the value
from before it stays known.

## Which way it gets built

For a builtin that reassigns a variable it is handed (`read`, `printf -v`,
`mapfile`, `readarray`, `getopts`, `unset`), drop the named variables from the
shell scope, and from the exported scope where it applies. The value then reads
as unknown and prompts. `unset` can do better, because the value is known to be
empty.

`source`, `.` and a `BASH_ENV` file can set anything, so after one, every
variable the guard holds is suspect. The conservative answer is to drop every
scope for the rest of the string.

A `for` loop's variable takes values from its word list, so it could expand
each one in turn, but dropping the name is enough to stop the defer.

## If it is never built

A command that reassigns a variable between the assignment the guard saw and
the kubectl that uses it reaches a production cluster without a prompt, as long
as the first value was non-production. Every shape above needs the command to
set the variable twice, so it is unlikely to happen by accident.
