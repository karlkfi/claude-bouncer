# An array subscript hides the command behind an assignment prefix

`ASSIGNMENT_RE` stops at the `[`, so `FOO[0]=x cat /outside/secret` is read as a
command *named* `FOO[0]=x` with no operands. The SPEC lookup misses, the group
contributes nothing, and every guard goes silent on a command bash runs in
full.

Bash peels the subscripted prefix and runs the reader behind it. It fails the
export at runtime -- `FOO[0]: not a valid identifier` on stderr -- and runs the
command anyway, leaving the variable completely untouched. The declared and
undeclared arms are identical, so "only when `FOO` is already an array" is not
a mitigation.

## Measured

Driven 2026-09-19 on bash 5.3.15 at `d2d54b8`, each guard's script fed a
`PreToolUse` payload with `cwd` set to this worktree. `(silent)` is no verdict
at all -- not an allow, and not a deferral anything records.

| guard | control | with `FOO[0]=x` prefix |
|---|---|---|
| workspace-guard, `cat /etc/hosts` | ask | **(silent)** |
| prod-guard, `kubectl --context=prod delete pod x` | deny | **(silent)** |
| exit-status-guard, `make check \| tail -5` | deny | **(silent)** |
| foreground-guard, `tail -f log.txt` | deny | **(silent)** |
| branch-guard, `git reset --hard HEAD~1` | allow | (silent) |

branch-guard's control does not deny from this branch, so its row separates
nothing and is **not** driven evidence. It shares the same head-peel loop
(`plugins/branch-guard/hooks/branch-guard.py:934:    while i < len(tokens) and is_assignment(tokens[i]):`),
so the defect is structural there rather than measured.

`FOO[a]b]=x cat /etc/hosts` is silent too, and correctly: bash reads that as a
command name and opens no file. The brackets are matched by depth, which is
why a regex cannot do this -- `FOO[a[0]]=x` is one subscript so the first `]`
does not always close, and `FOO[a]b]=x` is a command name so the last `]` does
not always close either. The first `]` at depth 0 closes.

Peels and reads the file: `FOO[0]=x`, `FOO[0]+=x`, `FOO[]=x`, `FOO[a]=x`,
`FOO[a[0]]=x`, `FOO[$((1+1))]=x`, `FOO[0]="a b"`, `FOO["a]b"]=x`,
`FOO[a\]b]=x`, `FOO[a b]=x`. Reads nothing: `FOO[a]b]=x`, `FOO[]]=x`,
`FOO[0=x`, `FOO[a[b]=x`, `0FOO[0]=x`, `'FOO[0]=x'`, `"FOO[0]=x"`,
`FOO\[0]=x`, `F'O'O[0]=x`.

## The trap: widening the regex alone trades one fail-open for another

This is Q174's lesson for `NAME+=value`, one shape over.
`lib/bouncer_parse.py:962:    name, _, value = token.partition('=')` yields
`FOO[0]`, a name no read of `FOO` will ever find -- so `poison_vars` deletes
the wrong key and leaves the real one on the map at a stale value
(`plugins/workspace-guard/scripts/bash-workspace-guard.py:1552:        varmap.pop(split_assignment(t)[0], None)`).

The sharpest consequence is the override hatch. `WORKSPACE_GUARD_OVERRIDE[0]=r
cmd` must **not** arm it: bash sets no variable of that name, so arming would
accept a spelling the shell never wrote. Today the name comparison rejects it
by accident -- `WORKSPACE_GUARD_OVERRIDE[0]` simply compares unequal -- and
that accident stops holding the moment `split_assignment` learns to strip the
subscript. All three hatches are the same shape:

- `plugins/workspace-guard/scripts/bash-workspace-guard.py:987:        if name == OVERRIDE_VAR and value.strip():`
- `plugins/exit-status-guard/scripts/bash-exit-status-guard.py:530:            if name in OVERRIDE_VARS and value.strip():`
- `plugins/branch-guard/hooks/branch-guard.py:1956:            if name == OVERRIDE_VAR and value.strip():`

So the peel and the split cannot land in separate pull requests, and neither
can the call-site audit: after the peel, sites that never saw a subscripted
token start receiving one.

## Which way it gets built

Three questions with three different answers, which is why
`lib/bouncer_parse.py:943:def split_assignment(token, append_is_operator=True):`
should report *which of three forms* the token spelled rather than a bool, so
no call site can read the wrong one silently:

- **The peel** accepts a subscript, because bash runs the reader behind it. A
  depth-matched walk replaces
  `lib/bouncer_parse.py:53:ASSIGNMENT_RE = re.compile(r'^[A-Za-z_][A-Za-z0-9_]*\+?=')`
  as the scanner, with the quote rule at
  `lib/bouncer_parse.py:806:    m = ASSIGNMENT_RE.match(token)` reading the new
  end offset.
- **The tracked value** drops the name, on a stronger reading than Q174's
  append: `$NAME` is `${NAME[0]}`, so `P=/lit; P[0]=/arr` gives `/arr` and
  `P=/lit; P[1]=/arr` gives `/lit` -- one syntactic shape, two answers, chosen
  by a subscript that can be arithmetic. Index 0 has at least eleven spellings
  in this shape, driven 2026-09-21 on bash 5.3.15: `0`, `-1` (a one-element
  array), `$((0))`, `0x0`, `00`, an unset name, `1-1`, `$((2-2))`, `+0`, and
  ` 0 ` with surrounding spaces. So there is no name-level test for "is this
  index 0", and dropping the name is the only reading that does not need one.
- **"Did bash set something by this name"** refuses a subscript. The three
  override hatches above, plus prod-guard's `KUBECONFIG` read and any
  `CDPATH`-style check. Driven downstream: `CDPATH[0]=<dir> cd target` does
  **not** search, while `CDPATH=<dir>` and `CDPATH+=:<dir>` both find target
  under `<dir>`.

Roughly 25 call sites across the five guards plus `lib/`, each needing its own
answer -- which is what makes this M rather than S. `lib/` reaches all five, so
it needs `make sync` and all five suites, and releases none of them.

[`karlkfi/claude-spill-guard` PR #175](https://github.com/karlkfi/claude-spill-guard/pull/175)
is the reference implementation: same segmentation layer, same defect, and the
shape was kept transferable by inspection. It carries the driven tables and six
inversions with their failure counts.

## What the fix will not close

Four spellings where the lexer destroys what the answer depends on before the
assignment question is asked: a subscript carrying whitespace or shell
punctuation arrives as several tokens, and one carrying a quoted or escaped `]`
arrives quote-stripped with a single "where quoting began" offset that cannot
say which `]` was covered. `FOO[$((1+1))]=x`, `FOO[a b]=x`, `FOO["a]b"]=x` and
`FOO[a\]b]=x` all peel in bash and will still be read as command names. Expect
the same residual here and file it rather than claiming the class closed.

## If it is never built

Every guard in the marketplace has a one-token bypass that costs nothing to
write and leaves no record of having been used -- no verdict, no prompt, and
nothing in a friction report to count. The reach is everyone who installs any
of the five plugins.

## Shell attribution

Every measurement above is bash 5.3.15 and dated as such. zsh 5.9 diverges,
and the divergence is wider than one index: **every subscript that evaluates
to 0** is fatal there, because zsh arrays are 1-based. Driven 2026-09-21 on the
prefix shape `FOO[<sub>]=x cat f`, which is a different question from the
value shape above -- `-1` aliases index 0 there and reads the file here:

| subscript | bash 5.3.15 | zsh 5.9 |
|---|---|---|
| `0`, `$((0))`, `0x0`, `00`, an unset name, `1-1`, `$((2-2))`, `+0` | reads | **fatal** |
| `-1`, `1`, `2`, `$((1))` | reads | reads |

Bash never evaluates a subscript in prefix position -- it fails the identifier
check and runs the command whatever the index -- so all twelve read there.
Under zsh the eight never run, which puts the divergence in the over-block
direction: a guard that peels them costs precision, not security. The Bash tool
runs bash through `CLAUDE_CODE_SHELL`, so bash is the shell that decides, and
none of this weakens the bash attribution.
