# A cd bash fails is still followed into the tree it named

`cd_destination` follows a literal `cd` whether or not bash's `cd` would succeed (`plugins/branch-guard/hooks/branch-guard.py:1668:def cd_destination(tokens, cwd):`). bash 5.3.15 leaves the shell where it was when the target does not exist or when `cd` gets a second operand ("too many arguments"), so a commit after a failed `cd` lands in the tree the session started in.
Driven 2026-11-27 through the hook on `main` 6f66f79, with the payload's `cwd` a checkout of `main` and `../feat` a feature worktree, each of these gets no decision and bash commits on `main`:

```
cd ./nonexist; git commit -m x
cd ../feat extra; git commit -m x
cd ../feat || true; git commit -m x
```

Q347's first step, merged as 6166f09, extended the same follow to the two substitution spellings, so `cd "$(git rev-parse --show-toplevel)/nonexist"; git commit -m x` moved from ask on 6f66f79 to no decision on 6166f09, the reviewer's finding on that change.

Next step: read a `cd` with a second operand as unfollowed, and decide whether a target that does not exist at judging time should be too.
The second half is the open question: `mkdir x && cd x; git commit` names a directory that does not exist when the hook runs and does when bash reaches the `cd`, so a plain existence check would stop following it.
How often sessions write either shape is not measured.
