# Deny a multi-statement Bash call at the prompt, not at PreToolUse

**Event:** Claude Code's `PermissionRequest` input starts naming which subcommands the permission matcher failed to match.
On 2.1.332 it carries no reason code at all (finding 4 below), so a hook cannot tell a prompt that splitting would clear from one it would not.

Deferred 2026-11-27, before implementation, because the measurement this row asked for came back negative: a split adds prompts rather than removing them.

## The idea

Permission prompts stall Karl's sessions far longer than guard denials do.
The idea was a `PermissionRequest` hook for `Bash` that denies a command with more than one top-level statement, asking for one command per call, on the theory that Claude Code's matcher prompts because it cannot analyse the compound and would allow each piece alone.
Single statements, pipelines, an inline `FOO=1 cmd` prefix, guard override prefixes and `for`/`while`/`if` compounds would pass.

## Why it is not worth building

Measured 2026-11-27 from local transcripts, 2026-10-27 to 2026-11-26.
Every tool result records a `permissionDecision` naming who decided (`config`, `hook` or `user_*`), how (`rule`, `classifier`, `mode`) and, for a matcher miss, a `reasonCode` such as `bashMiss:too-complex`.
Of 58,574 Bash calls, 797 reached a prompt.

**In auto mode there is nothing to save.** 433 of the 797 were in auto mode, and 406 of those had a `PreToolUse` hook return `ask` on the same call: workspace-guard 184, branch-guard 172, prod-guard 28, project hooks the rest.
Auto mode never prompts for a matcher miss; it asks the classifier, which decided 20,110 Bash calls in the window.
A split moves a guard's ask onto the piece holding the path or branch, so every denial there is a retry that saves nothing.
The hook would have to skip `permission_mode: auto`.

**In acceptEdits the split does not clear the prompt.** The other 364 prompts came from 24 sessions, 358 of them in acceptEdits and 6 with no mode recorded.
These sessions are mostly one repo: 828 of the window's 989 acceptEdits and default Bash calls ran in kube-headroom.
346 of the 364 had no guard ask, so the matcher was the cause.
The rule would deny 327, pass 32 single statements and 5 override prefixes.
Each denied command was split with `lib/bouncer_parse.py`, its leading `VAR=` values substituted into later pieces as the deny would tell a session to, and each piece run through the installed workspace-guard 1.16.0, branch-guard 1.15.0 and prod-guard 2.9.0 under the call's own session id and working directory.
A piece no guard decided took the matcher's verdict from how the same command head was decided when it ran alone.
Taking every piece the data cannot classify as running free, 24% of denials split into pieces that all run unprompted, and a denied command becomes 1.24 prompts on average instead of 1.
Taking those pieces as prompting, the figures are 1.7% and 3.39.
Both bounds add prompts.

The piece that keeps prompting is a Python script.
Of 1,077 `python3` script calls that ran alone with no guard deciding, none ran on a rule: 1,039 went to the auto-mode classifier and 38 to a person.
187 of the 327 denied commands hold one.
Splitting `x; python3 - <<EOF … EOF; echo rc=$?` leaves that call exactly as prompted as before.

At the medians, a matcher-miss prompt holds a session 55 s from tool call to result and a hook deny costs a 4 s retry, so the rule needed roughly 7% of denials to save a prompt with no split adding one.
The offline replay assumes a session splits literally; a session that merges two scripts into one could do better than the optimistic bound, and nothing here can see that.

**What the filing figures measured.** They were taken over all modes, and that is what the comparison with `PreToolUse` rested on.
The 1.6%, 1.2% and 0.7% prompt rates for a leading `VAR=`, a heredoc and a top-level `;` are diluted by auto mode, which held 98% of Bash calls.
In acceptEdits and default the same shapes prompted 56%, 61% and 36% of the time, so a `PreToolUse` rule gated on `permission_mode` would cost 1.6 to 2.8 denials per prompt it reached, not 64.
The objection to this design is that the pieces prompt, not which event it runs on.
Re-taken the same way, the window held 1,061 prompts with a median of 100 s, against the 1,039 and 132 s the row was filed with.

The exit-status capture the filing noted is now Q431, which is worth doing on its own: 217 of the 327 denied commands read `$?` in a statement of their own, and exit-status-guard's foreground fix texts hand back `; echo "EXIT=$?"`.

## What a `PermissionRequest` hook can do, measured 2026-11-26

From a throwaway plugin wired to `PreToolUse`, `PermissionRequest` and `PermissionDenied`, run headless on the PATH CLI 2.1.290 and both headless and in an interactive TUI on Desktop's bundled 2.1.331.
The output schema was re-read from the 2.1.332 binary on 2026-11-27: `decision` is `{behavior: "deny", message?, interrupt?}` or `{behavior: "allow", updatedInput?, updatedPermissions?}`.

1. **The deny `message` reaches the model as the call's tool result**, verbatim, with `is_error: true`.
   The filing said the transcript writes no `permissionDecision` record for one; it does, with `reasonCode: hook:PermissionRequest`, which a friction report can key on.
   The window holds 28, all from the probe's own sessions.
2. **Denials do not trip auto mode's fallback.** 21 consecutive `PermissionRequest` denials in an interactive auto-mode session, forced with an `ask` rule, left auto mode on.
   No positive control showed the counter tripping on real classifier blocks in the same setup, so this shows hook denials are not counted, not that the counter works.
3. **A `PreToolUse` `ask` reaches `PermissionRequest` interactively, and does not headless.** Headless (`-p`, both versions) converts the `ask` to a denial with the hook's reason and never fires `PermissionRequest`.
4. **The input carries no reason code.** Fields are `session_id`, `transcript_path`, `cwd`, `prompt_id`, `permission_mode`, `effort`, `hook_event_name`, `tool_name`, `tool_input` and an optional `permission_suggestions`, which cannot stand in for one: `python3 -c "print(1)"; echo rc=$?` came back with no suggestion although its `python3` half prompts alone.

The permission dialog renders while the hook runs and the hook's answer replaces it, so a click inside that window would race the hook; the hook logged 1.3–3.4 s after the `PreToolUse` that preceded it.

Adjacent, not a duplicate: Q401 denies a hard-to-parse shell subset at `PreToolUse` for parser confidence, on every call.
