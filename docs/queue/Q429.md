# Deny a multi-statement Bash call at the prompt, not at PreToolUse

Permission prompts, not guard denials, are what stall Karl's sessions: 1,039 reached him between 2026-10-27 and 2026-11-26, each blocking its session a median 132 s, against a median 4–6 s retry for a hook deny (both figures from the claude-skills session that filed this work, measured over local transcripts).
About a third were Bash commands Claude Code's own permission matcher could not analyse, so it sent them to a person.
The idea is to deny those with a request for one command per call, at the moment a prompt would show, and leave every other call alone.

A `PreToolUse` rule cannot do this.
It sees every call, and a leading `VAR=` falls through to a prompt in 1.6% of calls, a heredoc in 1.2%, a top-level `;` in 0.7%, so a shape-based deny there costs about 64 denials per prompt saved.
`PermissionRequest` is the only event that fires on just the prompted calls.

## What the hook would do

On `PermissionRequest` for `Bash`, deny with `decision.behavior: "deny"` and a `message` opening with the plugin's name ("split this into one command per Bash call; write paths literally, with no `S=`/`VAR=` prefix") when the command has more than one top-level statement — `;`, `&&`, `||`, `&`, a newline, a heredoc, or a leading standalone `NAME=value` statement.
Statement splitting comes from `lib/bouncer_parse.py` (`lex`, `split_operator_runs`, `strip_heredoc_bodies`), not a regex.
Pass through untouched: any single statement, including a pipeline and an inline `FOO=1 cmd` prefix, and any command whose leading assignment is a guard override (`*_GUARD_OVERRIDE=`, `*_GUARD_SESSION_OVERRIDE=`, `PR_SENTINEL_OVERRIDE=`), since those prompts are deliberate.
A compound `for`/`while`/`if` passes in the first cut; it splits into more than one call only by unrolling, and the right rewrite there is a script file.

It is a new plugin rather than a rule in exit-status-guard.
That guard's own working notes rule out any rule that is not about a lost exit status, and this one is about who answers a prompt.
It also needs a hook event none of the five guards registers.
The cost is a sixth plugin's plumbing: marketplace entry, version column, path filter and CI jobs, a sixth launcher copy for `make launcher-check`, and the vendored `lib/`.

**It has to act in default and acceptEdits, not only auto.** 315 of the 323 tool results that carried a `bashMiss:*` reason code over those 30 days came from sessions in acceptEdits, and none was attributed to auto mode.
In headless auto mode on 2.1.290, `touch x1.txt; echo rc=$?` ran with no `PermissionRequest` at all.
A hook gated on auto mode would almost never fire.

**exit-status-guard's own fix text is a shape this hook denies.** Its deny hands back `cmd > <log> 2>&1; echo "EXIT=$?"; grep … <log>`, three statements, and in acceptEdits `make backlog-lint; echo rc=$?` is a recorded `bashMiss:too-complex` prompt.
Shipping this without changing that text sends a session from one guard's deny to the other's.
The Bash tool already reports a non-zero exit, so the rewrite can be `cmd > <log> 2>&1` alone, with the log read in a second call.

## The four unknowns, measured 2026-11-26

All four come from a throwaway plugin wired to `PreToolUse`, `PermissionRequest` and `PermissionDenied`, logging every input.
It ran headless (`claude -p`) on the PATH CLI, 2.1.290, and both headless and in an interactive TUI on Desktop's bundled 2.1.331, which is the version Karl's sessions record.

1. **The deny `message` reaches the model as the call's tool result**, verbatim, with `is_error: true`.
   The session transcript carries it as an ordinary `tool_result` and writes no `permissionDecision` record, so a friction report finds these denials only by matching the message's opening text, the same as a `PreToolUse` deny.
2. **Denials do not trip auto mode's fallback.** In an interactive auto-mode session, 21 consecutive `PermissionRequest` denials (forced with an `ask` rule) left auto mode on, past both the 3-in-a-row and 20-total thresholds, and the next `python3 -c "print(5)"` ran with no prompt and no `PermissionRequest`.
   No positive control showed the counter tripping on real classifier blocks in the same setup, so this shows hook denials are not counted, not that the counter works.
3. **A `PreToolUse` `ask` does reach `PermissionRequest` interactively, and does not headless.** Interactive 2.1.331 in auto mode logged a `PermissionRequest` for a call a `PreToolUse` hook asked on, and the hook's deny decided it.
   Headless (`-p`, both versions) converts the `ask` to a denial with the hook's reason and never fires `PermissionRequest`.
   So workspace-guard's outside-root ask on a multi-statement command would be denied with the split message, and the split call re-asks if it truly needs Karl.
4. **The input carries no reason code.** Fields are `session_id`, `transcript_path`, `cwd`, `prompt_id`, `permission_mode`, `effort`, `hook_event_name`, `tool_name`, `tool_input` and an optional `permission_suggestions`; no `bashMiss:*` or anything like it.

Two more things the probe showed.
The permission dialog renders while the hook runs and the hook's answer replaces it, so Karl sees it flash, and a click inside that window would race the hook; the window was not timed, but the hook logged 1.3–3.4 s after the `PreToolUse` that preceded it.
And `permission_suggestions` cannot stand in for the missing reason code: `python3 -c "print(1)"; echo rc=$?` came back with none although its `python3` half prompts alone, and `ls .claude 2>&1; echo "rc=$?"` named its `echo` half although splitting avoids the prompt.

## The open question

**Measure:** how many prompts a deny actually saves.
The rule pays only when every piece of a split command runs unprompted; `python3 a.py && python3 b.py` splits into two prompts where there was one, and a heredoc write outside the working directories prompts again after any rewrite.
Taking the 132 s and 5 s medians above, a deny breaks even when about 4% of denials save a prompt and the splits add no prompts of their own.
An offline replay cannot answer it: of 798 prompted Bash calls in the window, the rule would deny about 646 and pass 53 single statements, leaving 99 compound or unreadable, but whether a split piece prompts turns on paths and working directories as often as on the command, which a transcript does not record per piece.
The hook can answer it itself, because every prompt in a session reaches it: log each deny with its pieces, then log any `PermissionRequest` in the same `session_id` within the next few calls whose command is one of those pieces.
Ship that log with the first release, read prompts-after-split per deny after a week, and narrow the rule (or withdraw it) if that ratio is near or above one.

Adjacent, not a duplicate: the Q401 design denies a hard-to-parse shell subset at `PreToolUse` for parser confidence, on every call; this rule acts only on calls already headed for a prompt.
The workspace-guard hint that used to recommend `VAR=./path; …` was fixed separately, in karlkfi/claude-bouncer#387.
