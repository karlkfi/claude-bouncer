# Token provenance ends at `expand_argv`, and the fallback is fail-open

`is_assignment` reads how a word was written from an attribute the lexer
attaches to the token, and falls back to matching `ASSIGNMENT_RE` against a
plain `str` that carries no such record. The fallback is deliberate and is
documented: a caller holding hand-built tokens gets the pre-fix behaviour.

What is not documented is that a token loses the record part-way through
prod-guard's own pipeline. `expand_argv` builds new strings for `$VAR`
expansion, and a new `str` is a plain `str`, so every token downstream of it
reaches `is_assignment` stripped of its provenance and is read as written
plain.

**For a command-position consumer that is the fail-open direction**, because
"written plain" is exactly what makes a quoted `'PROD_GUARD_OVERRIDE=x'` arm
the escape hatch again. Anything placed below `expand_argv` silently gets the
behaviour the quoting fix removed.

## Measured

2026-09-07, tracing one token through prod-guard on the head that fixes the
quoting defect:

```
raw: export 'AWS_PROFILE=prod'

  out of tokenize()                'AWS_PROFILE=prod'  QuotedStr  quoted_from=0
  after extract_env_prefix         'AWS_PROFILE=prod'  QuotedStr  quoted_from=0
  after expand_argv + strip_wrappers 'AWS_PROFILE=prod'  str      (attribute absent)
```

**No prod-guard site is exposed.** `extract_env_prefix`, the one
command-position reader in that file, runs on the pre-expansion group -- which
is why `argv_raw` above still carries the record. The `ASSIGN_BUILTINS` loop
that runs after expansion is an `export` operand reader, and an operand is
supposed to be read as written plain, so it wants the fallback it is getting.

**workspace-guard has a reader that IS downstream of a rebuild.**
`plugins/workspace-guard/scripts/bash-workspace-guard.py:4125:mk = classify_mktemp(g, inline_tmpdir(kw_g))`
passes `kw_g`, built at
`plugins/workspace-guard/scripts/bash-workspace-guard.py:3976:kw_g = strip_sh_keywords(sub_g)`
from `sub_g`, which is
`plugins/workspace-guard/scripts/bash-workspace-guard.py:3960:sub_g = [substitute_vars(t, varmap) for t in g]`.
`substitute_vars` returns
the same object unless the token carries a `$`, and rebuilds it when it does --
so a token containing `$` reaches `inline_tmpdir`'s classifier as a plain
`str`, with no record, and is read as written plain.

The neighbouring reader is not exposed and shows the intended shape:
`plugins/workspace-guard/scripts/bash-workspace-guard.py:3978:assigned = apply_assignment_group(g, varmap, persists)`
passes the pre-substitution `g`, and that function's docstring already states
the rule -- *must be called on the PRE-substitution tokens*. Two readers, two
lines apart, one on each side of the boundary.

All line numbers here are `origin/main`. The fixing branch moves them, which is
the reason each carries the text of its own line.

**It is getting the right answer for the wrong reason, and nothing can catch a
change to that.** Converting that operand site to `is_assignment` on a copy of
the tree -- asserting the edit was present in the file first -- changed no
output at all across seven probe rows, including two controls that move in
opposite directions on every other site. A swap there is undetectable, so no
fixture can pin the site and no test can fail if a later change makes it wrong.

That is the finding rather than the token trace: a silent degradation with no
instrument over it.

**At the exposed site the verdict moves, and both wrong verdicts land on a
command bash will not run.** Driven end to end against the fixing head, project
root as `cwd`, every row carrying an `H=...;` assignment first so the varmap is
non-empty in all of them and the `$` is the only difference:

```
  mktemp -d                              deny    no TMPDIR at all
  H=<proj>; TMPDIR=$H/t mktemp -d        allow   bound, correctly
  H=/tmp;   TMPDIR=$H/t mktemp -d        deny    host temp, correctly
  H=/tmp;   'TMPDIR=/tmp/t' mktemp -d    (none)  no `$`, record intact, NOT read as an
                                                 assignment -- argv[0] is the word itself,
                                                 an unrecognised command
  H=/tmp;   'TMPDIR=$H/t' mktemp -d      deny    `$` present, record LOST, read as an
                                                 assignment
  H=<proj>; 'TMPDIR=$H/t' mktemp -d      allow   the same loss, and the value happens to
                                                 be in-workspace
```

Rows 4 and 5 are one shape either side of the boundary, and the verdict moves
between them. Rows 2 and 3 are the controls that make the instrument mean
something: they differ only in the target and they answer differently, so a
uniform result would have been the tool failing rather than the sites agreeing.

**It is still not a security defect, for a reason the earlier reading of this
row got wrong.** Both wrong verdicts sit on a command bash will not execute as a
`mktemp` at all: the word is quoted, so the command name is the literal
`TMPDIR=$H/t` and `mktemp` is an argument. Row 5 over-guards a dead command and
row 6 permits one. Nothing reaches a live `mktemp` holding a target it should
not have, and no correct verdict on a runnable command changes.

The first draft of this section claimed the verdict did *not* move, on a
measurement taken against `main`. That is the wrong tree for a claim about what
survives the fix: on `main` the record never exists, so rows 4 and 5 agree
trivially and the boundary this row is about is invisible. The reading only
exists on the fixing head.

## Who it is for, and what it is worth

The next person to add an assignment reader to prod-guard. The cost is paid
once, by whoever places one below `expand_argv` and gets pre-fix behaviour with
a green suite -- the guard arms an override on a word bash would have run as a
command, and every test still passes.

Frequency is low and the blast radius is not: this is the same defect the
quoting fix closed, reachable again through a door nobody is watching. It ranks
here rather than higher because the one exposed site's wrong verdicts both land
on commands bash will not run, and above the general hygiene rows because the
failure is silent in both directions -- the wrong behaviour and the absent test.

## What happens if it is never built

The fix holds while the pipeline does not change, and stops holding the first
time somebody moves or adds a reader without knowing that expansion strips the
record. Nothing in the code says so, and no gate reports it.

## Which way it gets built

Unknown, and this row does not guess -- there are three shapes and they have
different costs, only one of which is now priced.

Carrying the record through `expand_argv` is the direct fix and the widest: the
function rebuilds strings from several inputs, so what a merged token's
provenance even *means* is a question rather than a detail. Making the fallback
loud instead -- refusing to answer for a plain `str` where the caller says it
is asking about command position -- is narrower, and turns a silent wrong
answer into a caller that must say which it wants; the cost is every existing
hand-built-token call site, including the tests. Documenting the boundary and
gating it, so a reader below the expansion line fails a check rather than a
runtime, is the cheapest and leaves the degradation in place.

**A fourth, purely local shape is already eliminated, with a measured
regression.** The repair that suggests itself at the exposed site is to hand
`inline_tmpdir` the pre-substitution tokens, the way the reader two lines above
it is required to be called. There are none in scope: `g` is rebound at
`plugins/workspace-guard/scripts/bash-workspace-guard.py:4022:g = sub_g[head:]`,
so by the `classify_mktemp` call it is both post-substitution *and* env-stripped.

Substituting `strip_sh_keywords(g)` for `kw_g` there hands `inline_tmpdir` a
list whose assignment prefix is already gone, so it returns `None`
unconditionally, falls back to the ambient host temp, and denies. Measured
2026-09-07 on a disposable copy of the fixing head, with the edit asserted
present in the file before probing: rows 2, 3, 5 and 6 of the table above all
`deny`. Row 2 is the one that matters -- an unquoted, legitimate, in-workspace
binding that bash really does execute -- so this trades a wrong verdict on a
dead command for a false deny on a live one, which is the regression
`inline_tmpdir` exists to prevent.

So a repair here needs assignment-ness from the raw token and the value from the
substituted one. That is the first priced datapoint for the three shapes above,
and what it prices out is the idea that any of them can be avoided by a local
edit at the call site.

**Measure:** which readers exist below a rebuild today, in all five guards. Two
are known -- prod-guard's `ASSIGN_BUILTINS` loop, which wants the fallback, and
workspace-guard's `inline_tmpdir`, which does not, and whose wrong verdicts
are absorbed by the command being unrunnable rather than by the site being
correct. `substitute_vars` and `expand_argv` are two rebuild
boundaries and `MARK_RE.sub` in `substitution_bodies` is a third -- `re.sub`
returns a plain `str` even when nothing matches, so that one strips the record
off every token it touches rather than only the ones it rewrites.
`expand_tilde`, `ps_expand_tilde` and `expand_loop_candidates` are named in
workspace-guard and unread. Then say what each reader would need if the
fallback started refusing. Then write the chosen shape into this row and drop the label.

## A site WAS exposed, and it is fixed

This row was filed saying no site is exposed. That was true of prod-guard,
where it was measured, and false of the tree in two places. The
`strip_env_prefix` inside `substitution_bodies` reads tokens rebuilt by
`MARK_RE.sub` and then by `substitute_vars`, so it took the pre-fix reading on
every input; the group loop's own `strip_env_prefix(kw_g)` reads `sub_g`, so it
took it for every token carrying a `$`. The second ends in an `allow`, which
speaks for the whole command string. `'d=sub' cd sub; echo "$(cat ../in.txt)"`
peeled the quoted word, found a `cd` bash never runs, applied it, and resolved
a read that lands above the project root back inside it -- silently. Fail-open,
and it read the same before the quoting fix, so it belonged to this row's class
rather than to that change's regressions.

It is repaired in the same pull request that closed the quoting defect, by
counting the peel on the pre-rebuild tokens and applying it to the rebuilt ones
by index. That is a per-site repair and not this row's answer: it makes one
caller stop depending on provenance rather than making provenance survive, and
the other readers below a rebuild are untouched.

**The same pull request widened what this row covers.** `is_reserved_word` now
makes `strip_sh_keywords` quote-aware, so the rebuild boundary bites for
reserved words too and not only for assignments. The surviving instance is
`plugins/workspace-guard/scripts/bash-workspace-guard.py:3976:kw_g = strip_sh_keywords(sub_g)`,
which reads plain `str` and so takes the written-plain answer for a quoted
keyword the way it already did for a quoted assignment. Same fix, same
residue: one more reader below a boundary this row exists to close properly.

**Provenance is not the whole reason to decide before a rebuild.** A token can
also be assignment-shaped only *after* substitution, and there the record is
not merely lost -- there was never anything to lose. `n=foo; $n=x cd sub` is a
command called `foo=x`: bash settles what the word is before expanding it, so
nothing is assigned and no `cd` runs. Measured on bash 5.3.15,
`n=foo; $n=x true` prints `bash: foo=x: command not found` and leaves `foo`
unset. A peel decided on the rebuilt tokens sees the literal `foo=x` and cannot
get this right whatever function it calls, because by then the question is
about a different word. So counting on the pre-rebuild tokens is the only
position where the question is well-posed, and carrying the record through a
rebuild -- the first of the three shapes below -- would not on its own be
enough.

What it settles for the `Measure` below is the cost of one of the three shapes.
Threading the pre-rebuild tokens to a single reader took two lines and three
fixtures. Doing it at every reader is the same work times the census, which is
the number this row still does not have.
