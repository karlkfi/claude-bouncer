# pipefail set before a command substitution is not carried into it

`set -o pipefail; out=$(make check | tail -5)` is denied, but the pipeline is
covered. A command substitution inherits the shell's options, so the
substitution's status is the gate's failure, and so is the assignment's. Driven
2026-10-04 under `env -i "$(command -v bash)"` 5.3.15:
`set -o pipefail; x=$(false | true); echo $?` prints 1.

The guard judges a substitution's body in a fresh `decide` call
(`plugins/exit-status-guard/scripts/bash-exit-status-guard.py:1124:            reason = decide(body, False, reg, scratch, depth + 1)`),
which starts with pipefail off. The pipefail state the outer command had built
by then is never passed in
(`plugins/exit-status-guard/scripts/bash-exit-status-guard.py:612:def pipefail_in_effect(segs):`).

This is a false deny, the safe direction. It was the same before Q148: the old
any-segment check suppressed only the outer pipe verdict, and the recursion
denied the body all the same.

## Which way it gets built

Pass the pipefail state at the substitution's position into the recursive
`decide`, and seed `pipefail_in_effect` from it. The hard part is the position:
the bodies come from a raw-text scan of the whole command, not from the
segment that holds them, so a body has to be matched to a segment first.
Where that match is not certain, keep today's deny.

## Who it is for, and what happens if it is never built

A session that writes `set -o pipefail` and captures a gate's filtered output
into a variable. It is denied and has to rewrite a command that was correct.
How often this shape appears has not been measured. The cost of delay is flat.
