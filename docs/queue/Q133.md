# The denial names zsh, and the remedy it gives is empty in bash

`PIPESTATUS_REASON` and `PIPED_REASON` both assert that the Bash tool runs zsh,
and the first prescribes a fix from that premise: `$PIPESTATUS` "does not exist
in zsh", and "zsh spells it $pipestatus (lowercase, 1-indexed)".

Measured 2026-08-24 inside the Bash tool: `BASH_VERSION` is `5.3.15(1)-release`,
`ZSH_VERSION` is unset, and `ps -p $$ -o comm=` prints `/opt/homebrew/bin/bash`.
So `PIPESTATUS` exists and works, and the lowercase form the reason recommends
is not an array in bash at all -- a second session on this machine wrote
`${pipestatus[1]}` on a real pipeline that day and got an empty expansion,
printing a bare `EXIT=`.

That is the sharp end: the remedy does not merely fail to help, it reinstates
the defect the guard exists to catch. An agent that follows it reads an empty
string where it expected a status, and a failure again looks exactly like a
pass.

The shell is configured rather than incidental, so the premise is not a stale
guess about an unknown environment -- `CLAUDE_CODE_SHELL` in the user's
`settings.json` points the tool at homebrew bash, with a note that this is to
avoid zsh and bash-3 gotchas. The guard's README does not repeat the claim; it
is in these two strings only.

The advice both reasons lead with -- redirect and read `$?` rather than pipe --
is correct in either shell, which is why this has cost nothing so far. Only the
justification and the alternate spelling are wrong.

The fix has a second half that is easy to miss. `friction-report.py` classifies
a decision by matching `does not exist in zsh`, and the comment above that table
says it matches such a phrase deliberately, because a phrase carrying the
diagnosis is "stable when the advice text is reworded, which it is more often
than the diagnosis". Here the diagnosis is the false part, so correcting the
reason silently drops every `pipestatus` decision into another bucket unless the
pattern moves with it. The report is a consumer no path sweep over the guard
would name.

So: state that the exit status is the filter's and that a pipeline's per-stage
status is not portable, drop `$pipestatus` rather than swapping in
`$PIPESTATUS` -- a reason naming one shell's array is wrong again the moment the
tool is pointed elsewhere -- and re-key the report's pattern onto a phrase that
survives it. Both reasons want a test pinning the absence of a shell name: the
claim read as authoritative for as long as it did because nothing grades reason
text against the environment it describes.
