# `env -S` carries a command string the guard never parses

`env --split-string=STRING` splits its operand into words and runs them, so the
string *is* a command — the same shape as a `bash -c` body, which
`evaluate_command_string` already recurses into. `strip_wrappers` treats `-S`
as an ordinary flag instead: the value stays in `argv`, becomes the tool, and
the segment defers.

This is the false-negative direction, which
[`plugins/prod-guard/CLAUDE.md`](../../plugins/prod-guard/CLAUDE.md) names as
the failure mode to fear.

## Measured

2026-09-04, prod-guard at `4a81387` with Q152's fix applied, fixture `$HOME`
with ambient context `gke_acme_prod-us`:

| command | verdict |
|---|---|
| `env KUBECONFIG=/nonexistent kubectl delete ns foo` | deny — correct |
| `env -u FOO kubectl delete ns foo` | deny — correct |
| `env -S 'kubectl delete ns foo'` | **defers** |

Q152 could not close it. That row's fix skips a value-taking flag *and* its
value, and skipping `-S`'s value discards the command rather than classifying
it — the arity is right and the handling is not.

## Which way it gets built

Not in the flag tables. `-S`'s value goes where a `bash -c` body goes: recurse
into it from `evaluate_command_string`. All three spellings have to be read —
`-S'…'`, `--split-string=…`, and a bare `-S` with a separate operand.

Which env the body expands against is the open part, and it is what makes this
size `S` rather than a one-liner: `env` starts a child, so `child_env` is the
first answer, but `-S` does its own `$VAR` substitution against the environment
`env` is building — including the `NAME=val` operands on the same command line,
which the child branch has no equivalent of. Settle that against `env(1)`
before writing the recursion, and pin whichever it is with a fixture carrying
an inline assignment.

## If it is never built

A `kubectl delete` against production that the guard never sees, on the one
`env` form an agent reaches for when it is holding a command as a string.
