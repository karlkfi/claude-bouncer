# The override counter is labelled for one of the two variables it counts

`OVERRIDE_SIG` matches `prod-guard: override acknowledged` and `prod-guard:
session override acknowledged` alike, which is right -- both are downgrades and
both belong in the friction total. The summary line then prints that combined
count under the name of just one of the two variables.

A reader sizing per-command override use therefore reads a number that includes
every session override. Measured 2026-08-24, both forms occur in the local
transcripts -- 97 and 58 raw reason lines respectively across all history,
which is a ratio rather than a decision count -- so the conflation is not
hypothetical.

The fix is the label rather than the regex: `override downgrades` covers both.
Splitting it into two counted lines is better still, because that split is what
answers whether a batch should have reached for the session form, which is
Q127 (completed).

`plugins/prod-guard/scripts/friction-report.py:71:session )?override acknowledged`
