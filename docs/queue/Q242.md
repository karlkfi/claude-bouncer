# The friction report counts a repeated attachment line twice

A transcript can carry the same attachment record more than once: the same
`uuid`, the same `hookName`, the same decision. `iter_decisions` yields one
decision per line, so each repeat is counted as another prompt.

Measured 2026-10-04 over every local transcript, counting workspace-guard
`ask` attachments per file by `(uuid, hookName)`: 19 extra `PreToolUse:Bash`
lines and 3 extra `PreToolUse:Write` lines. Out of 2,261 Bash asks and 70 Write
asks, so the effect is small. The Bash repeats predate Q85. Q85 made the
report read Write too, and with it those 3 repeats, so Write reads 70 where it
saw 67 distinct calls. Found by the independent review of the Q85 pull request
(#176), and re-measured to the same counts.

Why a line repeats is not established. A resumed or forked session rewriting
its history is the likely cause, but it is a guess. Whether the deny pass's
tool results repeat the same way was not checked.

## Which way it gets built

Deduplicate in `iter_decisions` on the record's `uuid` within a file, falling
back to `(hookName, toolUseID)` where a record has no `uuid`. Add a fixture with
a repeated line that must count once, and run the report over the real corpus
before and after: the delta should be the 22 above, give or take what has been
written since.

**Who is worse off:** anyone reading the report's counts as exact. They are
floors in every other respect (see `measuring-friction.md`), and this is the
one place they overcount.
