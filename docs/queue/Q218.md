# `env` assigns from any operand with an `=`, and the guards do not

`env(1)` is a program, not the shell, and its rule for what counts as an
assignment is wider than bash's: any operand containing `=` sets a variable of
that literal name. The guards' `env` peel matches `ASSIGNMENT_RE`, which is
bash's identifier rule, so the peel stops at the first operand bash would not
call an assignment, and that operand becomes the command head.

Driven 2026-10-01 on bash 5.3.15 and the macOS `/usr/bin/env`: each of these
prints `f`.

```
env FOO[0]=x cat f
env 'a b=c' cat f
env 1=x cat f
```

Each guard fed its own control behind the same three prefixes, on the branch
that landed Q214:

| guard, control | `env` | `env FOO[0]=x` | `env 'a b=c'` | `env 1=x` |
|---|---|---|---|---|
| prod-guard, `kubectl --context=prod delete pod x` | deny | **(silent)** | **(silent)** | **(silent)** |
| exit-status-guard, `make check \| tail -5` | deny | deny | **(silent)** | **(silent)** |
| foreground-guard, `tail -f log.txt` | deny | deny | **(silent)** | **(silent)** |

exit-status-guard and foreground-guard catch the subscript only because their
peel loops back through `strip_env_prefix`, which Q214 taught the subscript;
the other two spellings fail `is_assignment` too, so nothing catches them.
`sudo` takes the same operands and is peeled the same way in the same three
places.

The sites:

- `plugins/prod-guard/scripts/bash-prod-guard.py:662:                elif ASSIGNMENT_RE.match(argv[0]):`
- `plugins/exit-status-guard/scripts/bash-exit-status-guard.py:253:                while tokens and ASSIGNMENT_RE.match(tokens[0]):`
- `plugins/foreground-guard/scripts/bash-foreground-guard.py:376:            while argv and ASSIGNMENT_RE.match(argv[0]):`
- `plugins/foreground-guard/scripts/bash-foreground-guard.py:393:                elif ASSIGNMENT_RE.match(argv[0]):`

prod-guard's site sits in `strip_wrappers`, which the Q196 and Q200 lane was
editing when this was filed.

## What a fix has to keep

`env` operands are the case `split_assignment(..., append_is_operator=False)`
already exists for: the name is everything before the first `=`, verbatim. So
the peel predicate is "contains `=` and does not start with one", and the name
it records is literal -- `env PROD_GUARD_OVERRIDE[0]=r` exports a variable
called `PROD_GUARD_OVERRIDE[0]`, which arms nothing. Check what macOS and GNU
`env` each do with an operand that starts with `=` before choosing.

workspace-guard is not in this row: Q219 gave it a peel of its own,
`peel_wrappers`, which applies env(1)'s rule -- any operand holding `=` is an
assignment -- from the start.

## If it is never built

A one-word bypass of three guards behind a wrapper the guards already claim to
read through.
