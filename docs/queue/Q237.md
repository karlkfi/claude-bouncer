# A guarded command run by find -exec is never judged

`find` is not in `SPEC`, so neither its starting points nor the command its
`-exec` runs are checked. Driven on the Q219 branch, `cwd` set to a scratch
workspace:

| command | decision |
|---|---|
| `cat /q219-x` -- control | ask |
| `find . -exec cat /q219-x \;` | **(silent)** |

Driven on bash 5.3.15, `find . -name f -exec cat {} \;` reads every match, so
the `{}` names files under `find`'s own starting points, which are the operands
that decide whether the read leaves the workspace.

`find` is in `LOCAL_SHELL_WRAPPERS` only so that an `-exec sh -c '…'` body is
re-analysed (Q61). Q219's wrapper peel deliberately left it out: `find` is not
a prefix wrapper, since the command sits inside its expression and ends at
`;` or `+`.

## What a fix has to settle

The starting points are the paths before the first expression primary, and
`-exec`, `-execdir`, `-ok` and `-okdir` each carry a command up to a `;` or
`+`. A fix judges the starting points as reads, judges each embedded command as
its own group with every `{}` standing for a path under them, and withholds
`allow` where a `{}` sits under a start the hook cannot resolve. `-delete` and
`-fprint FILE` write; `-fprint` names its file directly.

## If it is never built

`find /anywhere -exec cat {} \;` reads any tree on the host with no verdict. The
reach is everyone who installs workspace-guard. Flat cost of delay.
