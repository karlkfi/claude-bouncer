# `dangling-link` is advisory in one gate and binding in two others

The `Makefile` states the design at the `backlog-lint` target:

    # `dangling-link` stays advisory: a link across a live batch is legitimately
    # in flight, and failing on it would redden the store after every merge.

`queue.py lint` honours it -- with a row deleted and a sibling still linking to
it, the gate printed `queue: 33 item(s) OK` and exited 0. Two other assertions
fail hard on the identical fact:

- `tests/test_backlog.py`, `StoreTests.test_every_link_resolves` --
  `assertTrue(os.path.exists(...))` over every relative link in the store.
- `tests/test_doc_links.py`, `DocLinkTests.test_every_relative_link_resolves` --
  `assertEqual([], bad)` over every relative link in the repo.

Neither is escapable by a path filter. The `shared-parser` job that runs them
(`.github/workflows/tests.yml`) carries no `needs:` and no `if:`, so it runs on
every pull request. The advisory is therefore advisory in one gate and binding
in the run that decides whether a PR is green, which is the opposite of what
the comment says the repo wants.

The cost is not cosmetic, because the two designs prescribe opposite actions.
Under the advisory reading, a worker completing a row that a sibling links to
leaves the sibling alone and the link resolves again when the sibling's own PR
lands -- which is the whole reason a per-item store keeps one file per item.
Under the hard gate, that worker must edit the sibling's row file to go green,
which is the one backlog change that contends between concurrent workers.

Measured 2026-08-24 completing Q127, which Q129 linked. The dispatch brief for
the item asserted the advisory behaviour, having read the `Makefile` comment;
`make check` went red on both assertions above; the repair was a one-line edit
to the sibling's row, in a file the brief had fenced off precisely because a
concurrent worker held it.

The decision is which of the two is the intent, and it is not obvious from
here. Making the assertions advisory restores the stated design and gives up
catching a link that dangles because someone mistyped it. Deleting the
`Makefile` comment and keeping the gates is the smaller change and makes the
repo honest, but it means every row-completing PR that breaks an inbound link
owns a cross-worker edit -- so it wants a note in `docs/queue/README.md` saying
so, since nothing there warns about it today. A third reading is that
`test_every_link_resolves` should skip a link to an ID the same commit deletes,
which is narrower than either.

Adjacent but not the same defect: Q123 covers `test_doc_links.py` raising
`FileNotFoundError` on a tracked file already deleted from the working tree.
That is the reader crashing on a missing *source*; this is two gates failing on
a missing *target*, and fixing either leaves the other standing.

## Settled 2026-09-01: there were never two intents to weigh

Groomed 2026-09-01. The decision above assumed the `Makefile` comment and the
two assertions record competing designs, so one had to be chosen. They do not.
`git log -S` dates both to the **same commit**:

    git log origin/main -S'dangling-link` stays advisory' -- Makefile
    git log origin/main -S'test_every_link_resolves' -- tests/test_backlog.py

Both return `d93f202` (#8, 2026-08-22), which *adds* the advisory comment and
`test_every_link_resolves` together. `test_every_relative_link_resolves` follows
two commits later in `6339ed3` (#10), a repo-wide link gate that swept the store
in as a side effect rather than as a ruling on it. The comment has not been
reworded since — that `-S` search returns `d93f202` and nothing after.

So the contradiction is drift authored in one breath, not a considered override,
and the stated design is the only intent on record.

**The direction is therefore reading 1: make the two assertions honour the
advisory.** What that gives up is smaller than the row assumed, because the
class is still *reported* either way — `dangling-link` is on `queue.py`'s
advisory list and the note is still emitted, so a mistyped link is surfaced by
`make backlog-lint` and simply does not fail the build. The choice is between a
hard failure and a note, not between catching a typo and missing it.

**Reading 3 is ruled out on the evidence rather than on taste.** Skipping a link
to an ID *the same commit deletes* does not reach the case the `Makefile`
comment is about: across a live batch the sibling's own PR does the deleting, on
another branch, so the narrow rule would leave the stated design unsatisfied
while looking like it had addressed it.

What is left is implementation, not a decision: scope both assertions off the
store's inter-item links, keep them binding for links pointing outside
`docs/queue/`, and say in `docs/queue/README.md` which of the two a dangling
link now trips.
