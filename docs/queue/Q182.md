# One regex drops three classes of citation, and reports none

`CITATION_RE` in `scripts/queue.py` is two lines, and drops three classes of
citation on the floor. None is a note the window suppresses and none is a class
`--strict` can promote: nothing is emitted, at any window, under any flag.

`scripts/queue.py:86:CITATION_RE = re.compile(`

**The path half** — line 87 — requires the cited path to end in one of a fixed
list of extensions (`go|py|sh|md|ya?ml|json|ts|js|rs|java`). A path with no
extension matches nothing, so the citation is never recognised as a citation.

**The fragment half** — line 88 — opens the fragment group with `\S`. A fragment
whose first character is whitespace fails it, the optional group does not match,
and the citation silently degrades to bare `path:line`. That is worse than a
miss: it still resolves, so it reads as checked.

**The same group also truncates** — `[^`\n]*` excludes a backtick, so a fragment
containing one binds only as far as it. The citation resolves against a shorter
string than its author wrote, and a shorter fragment is *easier* to match, so
this one does not merely go unchecked: it goes green on a prefix. Q168's was
two characters long.

Measured on `origin/main`, driving the regex on three strings — the second
differs from the first only in leading spaces, the third only in carrying an
inline backtick:

```
'`exhibit:a/b.py:12:def foo():`'      -> fragment='def foo():'
'`exhibit:a/b.py:12:    def foo():`'  -> fragment=None
'`exhibit:a/b.py:12:x = `a` + b`'     -> fragment='x = '
```

(The `exhibit:` prefix on those two is not part of the input being demonstrated —
it is there because a synthetic citation inside this row is still a citation to
the checker, which is the same class of self-reference the row is about.)

**`grep -n` on an indented line produces the second form**, so the whitespace
case is what a *careful* copy looks like rather than a careless one. The trigger
is the fragment opening with whitespace, not the line being indented — a copier
who trims the indent is safe and does not know why.

**Specificity subsumes truncation only where truncation does harm, and Q194 is

which is the difference from Q168's: the harm came from the prefix being

**Q132's is the truncation class's other instance**, and the path half rejects

## Who it is for

Anyone who writes a citation the regex does not recognise — and every later
reader who takes a clean `--citation-window 0` run to mean the store's citations
were checked. That reader is the one this costs, because the run is clean and
the belief is wrong.

## What happens if it is never built

The convention keeps its gate for source files cited without indentation and has
none for anything else: sixteen citations in other rows are invisible to it,
under a run that reads as the store's citations having been checked. The cost
falls on the reader who follows a number to the wrong line and believes it,
which is the failure the fragment field was added to prevent.

## Which way it gets built

**Assert specificity, do not enumerate the failure modes.** The obvious build
is a check per class — reject a whitespace opening, admit an extensionless
path, refuse a truncated fragment. Resist it. One invariant subsumes all three
and the ones nobody has thought of yet: **does the fragment occur on exactly one
line of the cited file?** Q168 is the argument. Its verdict — checked, passed,
asserted nothing — is a statement about specificity rather than about
truncation, and its two-character fragment failed the invariant for matching 67
lines whether or not anyone ever names truncation as a class. The enumeration is also demonstrably beyond one reader:
three sessions worked this regex on one afternoon and each missed a different
mode.

The convention already exists in prose. `session-backlog` tells an author to
pick words that occur once, because the linter reports the first matching line.
Asserted in a skill, enforced nowhere — the Q183 shape one level down.

**Measured on the live store, so the rung is a reading rather than a guess.**
Three citations pinned more than one line — Q160 at 3, Q200 at 4, Q168 at 67 —
and every other bound fragment pinned exactly one. Three is not a backlog to
drain, so specificity lands **binding** rather than advisory: an advisory gate
over a list of three gets switched off instead of satisfied.

**The three are repaired**, in the groom on `c21424d`, so whoever builds this
inherits no drain list and can land the check binding in the same change. On
that tree every bound fragment in the store pins exactly one line, and `lint
--strict stale-citation --citation-window 0` is clean. Re-measure before
building rather than trusting that sentence — the reading moves on every merge,
which is what this row is about.

The violations are named rather than counted against a total on purpose. The
total moves on every merge — completing a row deletes its citations, filing one
adds them — and it moved three times while this paragraph was first being
written. The three names are stable and checkable; a denominator taken today is
the snapshot this row is otherwise about.

**Q200 is the third, and it is the reason to prefer this invariant over the
three checks.** Filed the same day this guidance was written, by a session with
no part in it, and its citation passed every enumerated test: the path carries
an extension, the fragment opened with a non-space, and it held no backtick. It
failed only specificity — `argv = argv[2:] if argv[0] in value_flags else
argv[1:]` occurs at 629, 643, 660 and 684, and the row cited 629. An
enumerating checker admits it; the invariant does not. The count moved from two
to three while this paragraph was first being written, which is the same
argument arriving as a demonstration. The groom repointed it to line 620, where
the branch computes `value_flags` once.

**Q160 is the second, and it shows a repoint is not the repair.** It cited line
385 for a fragment that occurs at 360, 394 and 402 — all inside `strip_head` —
while 385 itself held none of them. The linter's "now at line 360" names the
*first* match, so taking its advice would have left the citation pinning three
lines and still failing specificity. The repair is a fragment that occurs once,
not a new number: the groom moved it to the `PLAIN_WRAPPERS` branch header at
line 400, which is the branch the row is about and occurs once in the file. That
is what the drift note under-describes.

**One regex, both halves, or the fix manufactures a false close.** Under
specificity this stops being a rule to remember and becomes arithmetic, but it
still governs the order: an implementer who fixes only the path half goes green,
closes this row, and ships a checker that still degrades every
whitespace-opening fragment silently — and the completed row then reads as the
defect being gone. The two halves are one line apart in one expression, so
whoever edits either is already holding the other.

The path half has two candidates and the choice is the item. Widening the
extension list is smaller and keeps the anchor that stops the pattern matching
ordinary prose like `Q92:1`; it fixes today's instances and leaves the next
extensionless file out. Matching a path with no extension needs a different
anchor to stay safe — most plausibly requiring the path to resolve in the tree
before treating the match as a citation, which is a check the linter already
performs one step later.

**Widening the extension list converts a silent miss into a false pass**, which
is the sharpest reason the halves cannot ship separately. Q132's citation is
invisible today only because `Makefile` has no extension. Admit it and the group
binds `` `dangling-link `` where the author wrote the whole clause — and that
prefix still occurs at the line it cites, so a citation that reports nothing
today would then report success. Fixing the path half alone does not leave the
truncation where it was; it recruits into it.

**The group has a second gate, and a rewrite must not drop it.** The fragment is
also bound by a closing-backtick lookahead, so a citation not closed by a
backtick loses its fragment the same way a leading space does. That one has
**zero** instances in the store, measured rather than assumed, so it is not a
defect anyone has — it is a constraint on whoever rewrites the group. Both the
count and the reading are the workspace-guard stream's; the row records it here
rather than as a class for exactly the reason they gave.

The fragment half is narrower: `\S` exists to stop a fragment opening with a
space, which `grep -n` never emits *for the line's own text*. It does emit one
when the line is indented. Relaxing it wants a rule that still refuses an empty
fragment, and the fragments already in the store are the fixtures.

**Strip the leading whitespace rather than reject it.** The nine instances are
not carelessness — copying an indented source line brings its indentation with
it, so the obvious authoring action is what produces the defect, and anyone
repointing those citations re-introduces it unless something stops them.
Rejection is silent and teaches nobody at the moment they write it; stripping
makes the obvious action correct. That is this row's fix-order argument seen
from the other end: fixing the path half arms the truncation, and fixing the
fragment half *by rejection* leaves the authoring trap standing.

**Fix it upstream first.** `scripts/queue.py` is vendored from
`karlkfi/claude-skills`, so a repair made only here is reverted by the next
vendor drop — the hazard `docs/development/maintaining-backlog.md` already
names. The `lib` label is for that reach rather than for `lib/`: the fix lands
in a file five guards' repos share by copy.

the amendment that added the fragment half. Worth recording how, because the
finding survived a bad instrument: their first attribution of citations to rows
came from a `grep -oh` under ugrep, which strips filenames and reorders across
files, and their second read a fragment as empty because their own pattern
stopped at the same inline backtick. Both readings were wrong and the defect
they pointed at is real — the tool that misled them was demonstrating the very
truncation it hid.

recording the truncation at all** — their reading was that it had no instances
and that naming it would repeat this row's earlier speculation, which was fair
on the evidence then in hand and is why it was worth re-measuring rather than
answering. They had measured the lookahead gate, which has none. The truncation
is a different mode of the same group, and a wider probe found Q168's. The
warning was right about the standard and wrong about the count, and it produced
the strongest exhibit in the row.

**The specificity reframing is the workspace-guard stream's, routed through the
orchestrator session**, along with the live-store census and the Q160 reading.
