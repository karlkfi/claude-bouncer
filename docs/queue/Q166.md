# `exit $((rc|rc2))` is read as a pipeline, so the background deny fires

An unquoted arithmetic expansion enters the segment loop as a command
substitution holding a pipeline. A backgrounded compound that captures two
gates' statuses and re-raises their OR — the documented fix, generalised to two
gates — is therefore denied under rule 2, and the rewrite the deny hands back is
the one the command already has.

## Measured

2026-09-07, exit-status-guard 2.0.1, a `claude-spill-guard` worker session
(worktree `zealous-nightingale-61f013`, working karlkfi/claude-spill-guard#121).
The call was backgrounded (`run_in_background: true`), with the scratchpad path
shortened to `<scratch>`:

```bash
cd <worktree>; S=<scratch>; make check > $S/check1.log 2>&1; rc=$?; echo "EXIT=$rc" >> $S/check1.log; make queue MERGED=true > $S/queue1.log 2>&1; rc2=$?; echo "EXIT=$rc2" >> $S/queue1.log; exit $((rc|rc2))
```

The denial:

> exit-status-guard: `make check` runs in the background, but this call's exit
> status is its LAST statement's -- an echo exits 0 whatever the gate did, so
> the task notification reports success for a failed gate. Capture the status
> and re-raise it: cmd > <scratch>/out.log 2>&1; rc=$?; echo "EXIT=$rc"; exit
> $rc. If the status genuinely does not matter here, re-run prefixed with
> EXIT_STATUS_GUARD_OVERRIDE=<reason>. …

The status is not lost. The last statement is `exit $((rc|rc2))`, which is
non-zero when either gate failed, so the task notification would have reported
the failure. Rule 2 fired: `lost_background_status` asked `carries_status`
whether the last statement carries a failure out, got no, and named the first
gate.

Reproduced against the hook at 49ce73b. `tokenize` runs shlex with `(` and `|`
as punctuation
(`plugins/exit-status-guard/scripts/bash-exit-status-guard.py:95:lex = shlex.shlex(cleaned, posix=True`),
so `$((rc|rc2))` leaves it as `$`, `(`, `(`, `rc`, `|`, `rc2`, `)`, `)`. The
shared glue then reattaches one paren
(`lib/bouncer_parse.py:744:def glue_dollar_paren(tokens):`), and the stream
reaches `split_segments` as

```
['exit', '$(', '(', '(', 'rc', '|', 'rc2', ')', ')']
```

which segments as `exit $(` at depth 0, then `rc` piped into `rc2` at depth 2.
`last_statement` returns that whole chain, and `carries_status` reads it left to
right: the `|` yields only its right side, `rc2` is neither `exit` nor a gate,
so the chain does not carry
(`plugins/exit-status-guard/scripts/bash-exit-status-guard.py:510:def _seg_carries(seg, reg):`).

Controls, same command with only the tail changed:

| tail | verdict |
|---|---|
| `exit $((rc\|rc2))` | deny |
| `exit $((rc+rc2))` | deny |
| `exit $((rc))` | deny |
| `exit $(( rc \| rc2 ))` | deny |
| `exit "$((rc\|rc2))"` | silent |
| `exit $rc2` | silent |

The trigger is the unquoted `$((`, not the `|`: `$((rc))` with no operator
inside denies too, and quoting keeps shlex from splitting the word. The
raw-string scanners in the shared library already step over arithmetic
(`lib/bouncer_parse.py:92:def _skip_balanced_parens(text, start):`); the token
stream never benefits, because that knowledge lives in the scanners and not in
the tokenizer.

Frequency, from a sweep of every transcript under `~/.claude/projects` on
2026-09-07 (1,718 files, 1,446 exit-status-guard denials): 35 under rule 2, and
2 of those on an `exit $((…))` tail — this one, and `exit $((rc+rc2))` in a
`github-actions-gateway` worktree on 2026-08-27. Rare and flat. What it costs
per occurrence is that the deny cannot be complied with: the command is already
in the shape the reason prescribes, so the session's only moves are to drop a
status or split the call. This worker split, running one gate in the
background and the other in the foreground.

## Which way it gets built

Keep an unquoted `$((…))` as one word through tokenizing, so arithmetic never
reaches `split_segments` as parens and a pipe. The natural place is beside
`glue_dollar_paren`, which is what turns `$` `(` into `$(` today, and that file
is shared — hence the `lib` label. Re-check it when the row is picked: the other
four guards tokenize the same way, and whether any of them reads `$((` in a
position that changes a verdict decides whether the fix is a five-guard change
or belongs in this guard's `tokenize`.

The alternative — teaching `carries_status` that a chain opening with `exit`
carries whatever follows — is narrower and wrong for `exit $(gate | tail)`,
where the pipe really does swallow the gate.

## If it is never built

A backgrounded compound that gates two commands has no form the guard accepts
except quoting the expansion, which no reason mentions. The single-gate form
and the quoted form both pass, so the cost is bounded to the two-gate compound
and to the retry it takes to discover the quoting.
