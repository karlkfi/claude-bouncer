# Reading Claude's own config prompts 49 times a week

`plugins/workspace-guard/scripts/bash-workspace-guard.py:312:def claude_code_dirs():`
read-exempts `~/.claude/plugins/` and `~/.claude/skills/`, and
`plugins/workspace-guard/scripts/bash-workspace-guard.py:290:def claude_projects_dir():`
adds `~/.claude/projects/`. Everything else under `~/.claude` prompts on every
read, and the exemption's own stated reason already covers most of it — this
code is installed by the user, deliberately, and a user who can rewrite it has
already won.

## `settings.json` is excluded, and that is the point of this row

The obvious version of this change exempts everything under `~/.claude`. It must
not, because `settings.json` holds the `env` block, and an `env` block is where
a credential would sit.

Measured 2026-08-31 on this machine: settings.json carries 2 env vars, both
paths, no secrets. But the exposure does not depend on that file's contents
today. **Every var in the `env` block is injected into every Bash tool process** —
verified by reading them back from inside a tool call — and a Bash process's
environment is one `env` away from the model's context and from the transcript
on disk, which keeps it. The same call showed `CLAUDE_CODE_MESSAGING_TOKEN`
present in that environment, put there by the harness rather than by any config.

So a read of `settings.json` is the one read under `~/.claude` whose output can
carry a secret into a transcript, and it is the one this row leaves prompting.
Anything else that grows an `env`-like block later inherits the same treatment.

That exclusion costs 5 of the 61 asks and keeps the rule defensible on a machine
whose settings this measurement never saw.

## Measured

Seven days to 2026-08-31, over 1,615 local transcript files. Of 181
outside-workspace asks, 61 resolved only to Claude-owned directories:

| target | asks | this row |
|---|---|---|
| `~/.claude/CLAUDE.md` | 21 | exempt |
| `~/.claude/scripts/`, `plugins/marketplaces/` | 15 | exempt |
| `~/.local/share/claude/versions/` | 10 | exempt |
| `~/.claude/projects/` memory files | 10 | see below |
| `~/.claude/settings.json` | 5 | **keeps prompting** |

59 of the 61 were reads; the 2 writes were `rm -rf` under
`~/.claude/plugins/cache/`, which keep prompting because the exemption is
read-only. All 61 were approved.

`~/.claude/projects/` is the odd one: the read is already exempt and the
**write** is not, so a session told to record something in `memory/` is prompted
for it. Whether memory writes join the exemption is a separate call from the
reads, and this row does not make it.

## Which way it gets built

Extend the exemption to the inert files named above, and make the extension
configurable rather than only widening the hardcoded default — a preference held
on one machine is not every user's, and `Q84` sets the precedent that looser
behaviour is opt-in. `WORKSPACE_GUARD_READ_ALLOW_PREFIXES` already exists and
already carries an entry on this machine.

Exempt by path, never by a wildcard on `~/.claude`: the plugin cache under it
holds third-party code, `settings.json` is excluded above, and the write path
stays guarded throughout.

## If it is never built

49 prompts a week answered yes, and the exemption's stated rationale stays
half-applied — a line that cannot be defended from the file's own comment.
