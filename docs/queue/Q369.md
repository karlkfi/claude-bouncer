# A test of the capture that passes on failure still gates the publish

`tested_form` credits a mutator joined by `&&` to any `[`, `[[` or `test` that
reads the captured status. It never asks which way the test points
(`plugins/exit-status-guard/scripts/bash-exit-status-guard.py:1054:        if tokens and tokens[0] in STATUS_TESTS and reads_var(`).
So `make check > l 2>&1; rc=$?; [ "$rc" -ne 0 ] && git push` is silent on
`main` at `09d7ed79`, though it pushes only when the check failed. Driven
2026-11-16 against `main`'s hook, with `[ "$rc" -eq 0 ]; git push` denied beside
it as the control.

Q351 added the exit-on-failure forms beside this walk, and those do read the
direction: `status_verdict` takes `-eq`, `=` and `==` against 0 as a pass, and
`-ne` and `!=` as a failure. The `&&` walk was left as it was, so the two
halves of `tested_form` now disagree.

**Who is worse off.** A session that inverts the test by mistake. It publishes
a failed build, and the guard says nothing. The typo is rare. The cost when it
lands is a publish, so this is a missed deny with a high per-occurrence cost.
Flat urgency.

**Next step.** Credit the `&&` chain only where `status_verdict` reads the test
as `passed`. Keep `[[ $rc -eq 0 ]] && git push` and `test "$rc" -eq 0 && git
push` silent. Decide whether a test it reads as neither, such as `[ "$rc" -lt
1 ]`, still credits; the table today has no case for it. Pin
`[ "$rc" -ne 0 ] && git push` as a deny.
