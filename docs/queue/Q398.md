# A script written by an unguarded command still vouches

An in-workspace script stops vouching for the blanket `allow` when the same string writes it, but only the writes workspace-guard already reads count: redirect targets and the write operands of guarded commands.
A command the guard does not judge can write the script unseen, so `cat README.md; curl -o t.sh URL; bash t.sh` still returns `allow`, as do `git checkout`, `tar x`, `unzip`, `patch`, `install`, `touch` and `truncate` in the writer's slot.
Measured by Claude on 2026-11-17 against the fix that introduced the write check.

Some run sites are not recorded as runs either, so a script the string writes still vouches there (measured by the PR 368 reviewer at `192866a`): `find . -name t.sh -exec bash {} \;`, whose operand is the placeholder; a program file a guarded command runs (`awk -f t.awk`, `sed -f`, `jq -f`); `eval ./t.sh`; and a build tool's implicit config (`cat > Makefile …; make`, `> package.json; npm test`).

The PowerShell frontend has the same exemption in `ps_operand_inside` and no write check at all, so `Set-Content t.py …; python3 t.py` beside a clean `Get-Content` is the original hole on that side.

Next step: decide whether any unguarded command in the string withholds the script's vouch (simple, costs a defer on `make build && bash scripts/x.sh` beside a guarded read) or only a named set of known writers does, then give the PowerShell side the same `ScriptWrites` tracking.
