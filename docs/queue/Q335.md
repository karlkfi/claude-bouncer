# A sed script built from an expansion is read as its literal text

Q328 taught workspace-guard to read the files a sed script names. It reads the
script as the hook sees it, after the tokenizer has dropped the quoting, so a
script that bash completes at runtime is judged on text that is not the text
that runs. A `w` command can arrive in the value:

| Command | Verdict |
|---|---|
| `sed "s/a/$b/" f` | allow |
| `sed "$prog" f` | allow |

Measured 2026-11-01 against the Q328 branch, with the hook run directly against
a temporary workspace holding `f`. With `b='x/w /q-fake/leak;s/q'` or
`prog='w /q-fake/leak'` either would write `/q-fake/leak` — reasoned from the
grammar, not run against a real sed for these two shapes. Q328's probes did
show macOS sed creating a `w` file named in a literal script.

## Why it is not a one-liner

Treating any `$` in a script as unreadable asks on the commonest sed there is,
`sed "s/$old/$new/g" f`, which agents write constantly, and on `sed -n '$p' f`,
where `$` is sed's last-line address: once quoting is gone the two are the
same token. A fix needs the quoting back — a token-level record of which spans
were single-quoted — or a rule about which expansion positions can reach
command structure (a delimiter in an `s` part can; a value that is wholly a
filename is already judged as `expand`).

The README's Limitations carries this today, beside the `-f FILE` case.
