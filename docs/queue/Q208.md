# An ln target is judged as a write, so a symlink install denies

`ln -s TARGET LINKNAME` writes only at LINKNAME. TARGET is a string stored
inside the new symlink — the file there is never opened, and it need not exist.
The guard judges both operands in write context anyway, so a symlink whose
target sits in a sibling checkout of the session's own repo hits the
wrong-branch deny for a write that cannot happen.

Measured 2026-09-13 against workspace-guard 1.12.0, from a session whose cwd was
the worktree `/Users/karl/workspace/claude-skills/.claude/worktrees/writing-skills-extraction-470c29`:

```bash
ln -s /Users/karl/workspace/claude-skills/output-styles/clarity.md ~/.claude/output-styles/clarity.md
```

denied with `Sibling-checkout write(s) blocked`, naming the root checkout
`/Users/karl/workspace/claude-skills` on branch `main`. Expected was the
ordinary outside-workspace ask on `~/.claude/output-styles/clarity.md`, which is
the one path the command actually writes.

**The repair the deny hands back is wrong for this shape**, which is what lifts
this above ordinary friction. It offers the in-session path — pointing the
installed symlink at a worktree that disappears when the branch is deleted — so
the only exit is `WORKSPACE_GUARD_OVERRIDE`, on an operation that is routine.
Every entry in `~/.claude/skills/` on this machine is a symlink into
`~/workspace/claude-skills`, created by that repo's `scripts/install-skills.sh`,
so any session running the installer from a worktree of that repo meets this.

## Where it lands

`plugins/workspace-guard/scripts/bash-workspace-guard.py:4098:Every operand is judged in write context`
checks `sources + [dest]` with `check_file`, which defaults to write context.
Q80 (#25) chose that deliberately, and its stated reason is about **hard** links:
a hard link hands the source inode a second name inside the workspace, so a
later write through that name resolves to a path the guard reads as in-workspace.
That argument does not reach `ln -s`, and it reaches nothing at all when the
link name is outside the workspace, since no in-workspace alias is created.

The PowerShell frontend carries the same defect:
`plugins/workspace-guard/scripts/bash-workspace-guard.py:4589:'value': 'write', 'target': 'write'`
binds `New-Item`'s `-Target`/`-Value` as a write, and that is the link's target.
PR #37 already applied this exact principle one command over — judging a
PowerShell unlink by the link rather than its target — so the precedent is in
the tree.

## What to evaluate

Downgrading a symbolic link's source to **read** context, rather than dropping
it, is the shape to check first: it keeps Q80's outside-path ask, and read
context never reaches `sibling_checkout_for`, which is only called for writes.
Whether the hard-link form keeps write context is the open half — Q80's inode
argument still holds there, and whether the parser wants a general
written-versus-merely-named operand role is the question behind both frontends.

Whatever lands needs a test pair: the deny still fires on a genuine
sibling-checkout write (`cp X /other/checkout/path`), and no longer fires on
`ln -s /other/checkout/path ~/outside/link`.

Not `lib` — `ln_operands` and `PS_NEW_ITEM_LINK_SPEC` are both in the plugin's
own script, and `lib/` holds only `bouncer_parse.py` and `bouncer_grants.py`.
