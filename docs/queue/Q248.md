# A failure-branch restore, or an `--abort`, trips the sequenced deny

Rule 3 denies a gate sequenced with `;` before a state change. Its deny hands
back a capture-and-restore rewrite for the case where the restore has to run
anyway. Two shapes of that intent still deny, and the rewrite it suggests is
one of them.

## Measured

2026-10-04, exit-status-guard 2.1.0 as installed and the in-tree hook at
`a3c9052`, both giving the same verdicts:

| command | verdict |
|---|---|
| `git rebase -q origin/main > log 2>&1; rc=$?; [ $rc -eq 0 ] \|\| { cat log; git rebase --abort; }` | deny |
| `git rebase -q origin/main > log 2>&1; rc=$?; if [ $rc -ne 0 ]; then git rebase --abort; fi` | deny |
| `git rebase -q origin/main > log 2>&1; rc=$?; git rebase --abort; [ "$rc" -ne 0 ] \|\| exit 1` (the deny's own rewrite) | deny |
| `make check > log 2>&1; rc=$?; [ $rc -eq 0 ] \|\| git reset --hard` | deny |
| `make check > log 2>&1; rc=$?; if [ $rc -ne 0 ]; then git reset --hard; fi` | deny |
| control: `make check > log 2>&1; rc=$?; [ $rc -eq 0 ] \|\| git push` | deny, correctly |
| control: `make check > log 2>&1; git push` | deny, correctly |

The first row is the one reported. A worker rebasing several branches
wrote it, and the guard read the abort as unconditional, though the `||` runs
it only when the rebase failed. The deny text named the `;` before it.

**Two mechanisms, and the reported command needs both fixed.**

- **`--abort` is a mutator and not a restore.** `restores` holds one pattern,
  `^git\s+reset`
  (`plugins/exit-status-guard/exit-status-guard.json:73:"^git\\s+reset(\\s|$)",`).
  `git rebase --abort` matches the `git rebase` mutator, so even the restore
  form the deny recommends is denied when the restore is an abort. `--abort`
  on `rebase`, `merge`, `cherry-pick`, `am` and `revert` undoes exactly what
  the gate started, which is the registry's own test for a restore.
- **A restore in the failure branch is not credited.** The rule lets a
  mutator through in two forms: a registered restore with a recheck of the
  capture after it
  (`plugins/exit-status-guard/scripts/bash-exit-status-guard.py:708:def restore_form(segs, reg, words, gate_at, mutator_at):`),
  and a mutator joined to a test of the capture by `&&`
  (`plugins/exit-status-guard/scripts/bash-exit-status-guard.py:731:def tested_form(segs, gate_at, mutator_at):`).
  `[ $rc -eq 0 ] || restore` and `if [ $rc -ne 0 ]; then restore; fi` are
  neither. The README already documents that the `if` form is not recognised
  for a publish
  (`plugins/exit-status-guard/README.md:150:is not recognised; all`),
  where denying is right. For a registered restore, running only on failure is
  the most precise way to write the intent, so the deny has no better rewrite
  to offer.

## Which way it gets built

Add the `--abort` forms to `restores` (they are already `mutators`). In
`sequenced_mutation`, let a **registered restore** through when it sits in the
failure branch of a test of the capture: `||` after a `[`/`[[`/`test` reading
it, or the `then` of an `if` whose condition reads it. Keep both through the
same restore screen, so `[ $rc -eq 0 ] || git push` still denies, because
publishing on failure is the defect the rule exists for. Table cases go in
both directions: the five deny rows above become passes, and both controls
stay denies. Update the README paragraph cited above to say the failure-branch
form is credited for a restore and still denied for a publish.

**Who is worse off:** a session that writes a teardown after a trial merge or
rebase, which is what parallel workers do when they check a branch against
`main`. The deny's rewrite fails for them a second time when the restore is an
abort, so the session either rewrites the logic into a worse shape or reaches
for the override.

**How often.** A transcript walk over this machine's last 60 days found 736
distinct tool calls denied by rule 3. Of those, 3 had a restore in a `||` or
`then` branch, and 14 more carried an `--abort` somewhere in the command. Two
of the 17 were this row's own probes. I read the 14 one by one rather than
judging them by pattern, and nearly all were a trial `git merge` or
`git rebase` followed by an abort teardown, which is the restore case. So
about 15 real hits in 60 days, at about one rewrite each. Flat urgency.

`S`: one registry pattern, one branch in `sequenced_mutation`, a table of
cases, and a README paragraph.
