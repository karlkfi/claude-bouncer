# An `--abort` reads as a gate, and its restore form is denied

Rule 3 denies a gate sequenced with `;` before a state change. A
`git rebase --abort` or `git merge --abort` trips it from both sides: as the
gate when it cleans up before a fresh rebase or merge, and as an unregistered
mutator when it tears down after one. The second case includes the
capture-and-restore rewrite that the deny itself recommends.

## Measured

2026-10-04, exit-status-guard 2.1.0 as installed and the in-tree hook at
`a3c9052`, both giving the same verdicts. Re-run at `9f90e5c`, after
Q222 changed the hook, with the same verdicts and the same replay counts
below:

| command | verdict |
|---|---|
| `git rebase --abort; git rebase --onto origin/main OLD` | deny, the abort named as the gate |
| `make check > log 2>&1; git rebase --abort` | deny |
| `git rebase -q origin/main > log 2>&1; rc=$?; git rebase --abort; [ "$rc" -ne 0 ] \|\| exit 1` (the deny's own rewrite) | deny |
| control: `make check > log 2>&1; rc=$?; [ $rc -eq 0 ] \|\| git push` | deny, correctly |
| control: `make check > log 2>&1; git push` | deny, correctly |

The deny's rewrite re-raises with `[ "$rc" -ne 0 ] || exit 1`, which asserts
that the gate *failed*. It is written for a gate whose failure is the
assertion. A teardown after a rebase wants `-eq`, which the restore form also
accepts.

**Two mechanisms.**

- **The abort is a gate.** The gate pattern for git names `rebase`, `merge`,
  `cherry-pick`, `am` and `revert` with no exclusion for `--abort`
  (`plugins/exit-status-guard/exit-status-guard.json:41:"^git\\s+(pull|push|rebase|merge|cherry-pick|apply|am|commit|revert|add|stash|clone|fetch|checkout|switch|worktree|reset)(\\s|$)",`).
  An abort's exit status answers nothing. It fails when there is nothing to
  abort, which is the expected case for a cleanup run first.
- **The abort is a mutator but not a restore.** `restores` holds six
  patterns, `git reset`, `git apply`, `kubectl delete`, `kubectl rollout undo`,
  `helm uninstall|rollback` and `terraform|tofu destroy`
  (`plugins/exit-status-guard/exit-status-guard.json:72:"restores": [`), and
  none is an `--abort` form. An abort undoes exactly what the gate started,
  which is the registry's own test for a restore, so the restore form
  (`plugins/exit-status-guard/scripts/bash-exit-status-guard.py:819:def restore_form(segs, reg, words, gate_at, mutator_at):`)
  never credits it.

## Which way it gets built

Treat an `--abort` the way the registry already treats `git reset`. Add
`^git\s+(rebase|merge|cherry-pick|am|revert)\s+--abort(\s|$)` to `restores`,
and keep the same forms out of `gates`, with a negative lookahead in the git
gate pattern or an equivalent exclusion. A teardown then passes in the restore
form and still denies when it skips the re-check, exactly as `git reset` does.

Replayed against the 13 real commands counted under How often with a patched registry passed
through `EXIT_STATUS_GUARD_REGISTRY`, this remedy allows 8. The other 5 deny on
an abort after a gate with no re-check of the capture, and the restore-form
rewrite, which passes in the table's third row once this lands, is
open to them. That was measured on the table row, not on each of the five. Both controls stay denies.

**Two alternatives, measured the same way and rejected.**

- **Add the forms to `restores` only.** That allows 2 of the 13. It fixes the
  deny's own rewrite and leaves every abort-as-gate case denied.
- **Add the forms to `exempt`.** That allows 11 of the 13, but `exempt` wins
  over `mutators`, so `make check > log 2>&1; git rebase --abort` would pass
  with no re-check. That makes an abort looser than `git reset`, and the
  registry describes `exempt` as informational targets whose output, not
  status, is the point.

**Out of scope: a restore in the failure branch.** The row as filed also asked
to credit `[ $rc -eq 0 ] || restore` and the `if` spelling. The re-walk found
no real command of that shape: the seven matches for the pattern were a
checkout `||` fallback with a reset on a later line or after a `;`, plus one success-branch
`if` around `git apply`, and none of them involved a failure-branch restore.
The one reported case is this row's own, and under the remedy above its
restore-form rewrite passes. File it again if a real one turns up.

**Who is worse off:** a session that writes a teardown after a trial merge or
rebase, or a cleanup before one. Parallel workers do both when they check a
branch against `main`.

**How often.** 2026-10-04, a walk over this machine's transcripts found 833
rule-3 denies. That counts distinct tool calls whose result carries the
rule's reason, in every transcript file modified in the last 60 days,
sub-agent files included. Because it keys on file time rather than event
time, it differs from other walks: an earlier one found 736 and the
reviewer's found 728. Nothing below depends on the total. 17 carried an `--abort`. Of those, 3
were probes for this row and its review, and in 2 the abort was not the
segment the deny named. That leaves 13 real commands across 12 sessions: in 7
the deny named the abort as the gate, and in 6 as the mutator. Flat urgency,
about one rewrite each.

`S`: one `restores` pattern, one gate exclusion, a table of cases in both
directions, and a sentence in the registry comment saying an abort is a
restore and not a gate.
