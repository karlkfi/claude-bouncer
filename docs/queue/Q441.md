# prod-guard cannot split on an IFS it cannot read

Q423 made prod-guard split a held command on the IFS the shell assigned, and an IFS it cannot read is judged as the default split.
That misses an unreadable IFS holding a non-whitespace separator, so a comma-joined command still runs with no prompt.
Measured 2026-11-27 through the hook on Q423's branch, with `~/.kube/config` on `kind-ci`:

| command | prod-guard |
|---|---|
| `IFS=,; X="kubectl,--context,gke_acme_prod-us,delete,ns,x"; $X` (control) | deny |
| `IFS=$(printf ,); X="kubectl,--context,gke_acme_prod-us,delete,ns,x"; $X` | **defer** |
| `read IFS < f; X="kubectl,--context,gke_acme_prod-us,delete,ns,x"; $X` | **defer** |
| `source ./env.sh; X="kubectl,--context,gke_acme_prod-us,delete,ns,x"; $X` | **defer** |

bash runs the second whenever the substitution prints a comma: `IFS=,; X="/bin/echo,RAN"; $X` printed `RAN`.
The guard cannot enumerate the separators an unknown IFS may hold, so no split it can choose covers every value.

## Which way it gets built

Where IFS is unknown and a word from an unquoted expansion holds a character outside `[A-Za-z0-9_./=-]`, ask: the word may split into a command the guard has not judged.
Keep the default-split reading beside it, so a production target found that way still denies.

## If it is never built

A production mutation runs with no prompt when a session sets IFS from a file, a substitution or a sourced script and then runs a command held in a variable.
It needs both an unreadable IFS and a command joined on the separator it holds, so it is an adversarial shape rather than one a session writes by accident.
