# A script fed to a shell on stdin is judged by no guard

A shell started with no script argument reads its script from stdin, so
`bash <<< "P"`, a heredoc into `bash`, and `echo 'P' | bash` all run `P`. Every
guard reads a `bash -c` body as a script and none reads stdin as one: the
here-string's word, the heredoc's body and the pipe's producer are all treated
as data. The heredoc case is the sharpest: every guard but branch-guard already
strips the body out before lexing (`strip_heredoc_bodies` in `lib/`), so it
holds the exact script bash will run and then judges only `bash`.

Measured 2026-11-17 on `origin/main` at `a3a43e4d`, with the harness and traps
described in Q349. A `shlex` trace showed each guard lexing only the outer
command, with no lex error, so these are unread rather than misread. bash
5.3.15 printed `RAN` for `echo RAN` in every row:

| command | prod | ws | exit | branch | fg |
|---|---|---|---|---|---|
| `bash -c 'echo x; P'` -- control | deny | ask | defer | ask | deny |
| `bash <<< "P"` | **defer** | **defer** | **defer** | **defer** | **defer** |
| `sh <<< 'P'` | **defer** | **defer** | **defer** | **defer** | **defer** |
| `bash <<'EOF'` newline `P` newline `EOF` | **defer** | **defer** | **defer** | **defer** | **defer** |
| `echo 'P' \| bash` | **defer** | **defer** | **defer** | **defer** | **defer** |
| ``bash <<< "echo \`P\`"`` | **defer** | **defer** | **defer** | **defer** | **defer** |
| `bash <<< "\$X P"` | **defer** | **defer** | **defer** | **defer** | **defer** |

exit-status-guard's defer on the control is its documented `bash -c`
limitation, so on that guard this row adds the stdin forms to a gap it already
states. The last two rows are the shapes Q349 was filed with; once the script is
read, the `\$X` row reaches the child as an unset `$X` command word, which is
Q279's.

## Which way it gets built

Recognise a shell invoked with no script operand and no `-c`, and hand what it
will read to the same path a `bash -c` body takes. A here-string's word and a
quoted-delimiter heredoc's body are literal text, so they are read outright; an
unquoted heredoc gets the expansion the guards already apply to a double-quoted
`-c` body. A pipe is read only when its producer is a literal `echo` or
`printf`; any other producer is a script the guard cannot see, and gets the
verdict Q279 chooses for a command the guard cannot resolve. The predicate is
the same question in all five guards, so it belongs in `lib/`.

## If it is never built

Any guarded command runs unjudged when it is fed to a shell on stdin. Agents on
this machine do not write the shape: on 2026-11-17, lexing all 261,089 Bash
commands in its session transcripts with `lib`'s `lex` found no shell given a
here-string, a heredoc or a piped script. Its 2 heredoc matches were both a
backgrounded `bash <script>` with a heredoc into `python3` on the next line,
which the count's own segmenting ran together. The same count caught each shape
in synthetic controls. So the exposure is a
command written to slip past, or one copied from install instructions of the
`curl … | sh` kind.
