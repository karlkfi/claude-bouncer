# A capture reassigned before its test still credits the mutator

Both halves of `tested_form` find a `$?` capture and then credit a later test of that variable.
Neither checks that the variable still holds the gate's status when the test reads it.
The `&&` walk is one half.
The exit-on-failure walk is the other, added by Q351 (`plugins/exit-status-guard/scripts/bash-exit-status-guard.py:1164:def exits_on_failure(segs, var, gate_at, mutator_at):`).
Driven 2026-11-16:

- `make check > l 2>&1; rc=$?; rc=0; [ "$rc" -eq 0 ] || exit 1; git commit -m x` is silent on `main` at `48035427`.
  It was denied at `09d7ed79`, before Q351 merged, so Q351 (#344) made it newly silent.
- `make check > l 2>&1; rc=$?; rc=0; [ "$rc" -eq 0 ] && git commit -m x` is silent at both commits.

In bash 5.3.15, run with `false` as the gate, each of these reaches the commit:

- `rc=0;`
- `for rc in 0; do :; done;`
- `unset rc;` before `[[ $rc -eq 0 ]]`

Review of PR #344 found these, along with `exit() { :; };` defined before the exit.
That last one was not re-driven here.

This is not Q369.
Q369 is a test that points the wrong way on an intact capture.
This is a correct test of a value the gate never set.

**Who is worse off.** A session that reuses its status variable between the capture and the test, for instance by capturing a second command's status into the same name.
It loses the first gate's verdict without a word.
Rare, and a missed deny.
Flat urgency.

**Next step.** In one place shared by both walks, refuse the credit when anything between the capture and the test can rebind the variable:

- an assignment to it
- `unset`
- a `for` or `read` naming it
- `declare`, `local`, `export` or `readonly` naming it
- a function definition named `exit`

Measure whether matching on those words alone over-denies before narrowing further.
Pin the commands above as denies, and keep Q351's exit-on-failure cases silent.
