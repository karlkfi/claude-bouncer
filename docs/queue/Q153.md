# The `open-question` label misses rows that end in an unendorsed choice

`open-question` marks a row that ends in a decision rather than a task, so a
batch can dispatch it as a scoping pass instead of handing a worker something
it must guess at. The label is only as complete as the last groom applied it,
and a dispatching session that reads the label and stops inherits that groom's
gaps in silence.

## Measured

2026-09-01, selecting a seven-item batch from the ten ready `bug` rows. Four
rows in the store carried the label. Reading every candidate to its end found
**two more that ended in an unendorsed choice and carried none**:

| row | how it ends |
|---|---|
| `Q136` | "Three directions, none endorsed here" — and "The decision is what a guard that cannot see its own shell should do, and it is not obvious" |
| `Q146` | "So the fix is either to resolve a literal `cd` and keep the exclusion, or to treat `cd` as benign only when its target resolves inside the current repository" |

Both were dispatchable only because the reading happened. `Q136` went out as a
scoping pass and closed its question; had it gone out as an implementation the
worker would have had to pick one of three directions with nothing behind the
choice.

A phrase sweep over those candidates flagged both, and re-running it over the
whole store while filing this row showed what it costs. Grepping for
`none endorsed`, `none of them chosen`, `is either`, `the decision is`,
`not obvious`, `three directions`:

| row | label | verdict |
|---|---|---|
| `Q135`, `Q144`, `Q145` | yes | true positives |
| `Q146` | no | **true positive — still unlabelled** |
| `Q132`, `Q136` | no | **false positives**: both questions were settled, and the prose keeps the phrases as history |
| `Q153` | yes | false positive: this row quotes the phrases |

So the heuristic is useful for a groom to run and wrong about a third of the
time, and its false positives are *settled* rows rather than random noise —
which is a shape a reader can dismiss in one glance. It is a prompt to look, not
a verdict.

## Who it is for

Whoever grooms next, and every batch selected afterwards. The cost of the gap
is not that these rows are lost — reading them finds them — but that the
reading has to be redone by every session that selects, because nothing records
the answer. `session-orchestrator` already instructs a dispatching session to
read every candidate for exactly this reason, so the work is currently done
once per batch instead of once per groom.

## Which way it gets built

Two halves, and the first is the whole of it:

1. **A groom step**: when re-reading a row, ask whether it ends in a choice, and
   apply the label with a `**Settles:**` / `**Measure:**` / `**Ask:**` route in
   the same edit. This is a habit rather than a mechanism, and it belongs in
   `docs/development/maintaining-backlog.md` where the repo's own invariants
   live.
2. **Optionally a lint heuristic** over the phrase set above, reported as a
   note rather than an error — the phrasing is open-ended and a row can end in a
   choice without using any of those words, so a binding gate would be both
   incomplete and irritating. The table above is the argument against making it
   a gate and for making it a groom command: three of seven hits were rows whose
   question had been *settled*, so a gate would redden on rows that are correct.

## If it is never built

Selection keeps finding these by reading, which works and costs a pass per
batch. The failure case is a session that trusts the label — the store says four
and the answer is six — and dispatches a decision as an implementation.

## Notes

Filed from the retrospective of the 2026-09-01 batch (#73-#80). Neither row was
mis-filed: both were written before the label existed in its current form, and
`Q146` was filed the same morning by a session with no reason to know the
convention. The gap is that nothing brings a row back past the question once it
is written.
