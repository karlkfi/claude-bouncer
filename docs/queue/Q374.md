# BSD sed -l takes no argument, so the sed row hides the file after it

The `sed` row consumes one argument after `-l`
(`plugins/workspace-guard/scripts/bash-workspace-guard.py:988:    'sed':  {'consume': {'-e':1,'--expression':1,'-l':1,'--line-length':1},`),
which is GNU's `-l N` line length. BSD sed, the macOS `/usr/bin/sed`, reads
`-l` as line-buffered output and takes no argument. So in `sed -l p ../x` the
hook takes `p` as `-l`'s value and `../x` as the script, and judges no file,
while macOS sed reads `../x`. Measured 2026-11-16 on `origin/main` at
`36d05ed8`, with the hook run from a scratch workspace and `../x` a planted
file outside it:

| command | workspace-guard | `/usr/bin/sed` |
|---|---|---|
| `sed -l p ../x` | allow | printed `../x` |
| `/usr/bin/sed -l p ../x` | allow | printed `../x` |
| `sed -l 5 p ../x` | ask | |
| `sed -l -n p ../x` | ask | |
| `sed -nl p ../x` | ask | |
| `sed p ../x` (control) | ask | |

Found by review-r1 on #347. Q341 aliased `gsed` to this row, which is right
for `gsed`: it is GNU sed, and GNU's `-l` does take `N`.

## Which way it gets built

Read the operands under both seds and union them, as `sed_script_files` and
`sed_detached_empty_suffix` already do for the other places the two disagree.
Under the BSD reading `-l` consumes nothing, so `../x` is a file. Pin the
`sed -l p ../x` row as an ask, and `gsed -l 5 p in.txt` as an allow so the
GNU reading still holds.

## If it is never built

On macOS, `sed -l` followed by a script and a path outside the workspace reads
that path silently.
