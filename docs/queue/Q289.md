# find -execdir under an unreadable start blames an untracked cd

Q237 judges the command a `find -execdir` runs from the directories it can run
in, which are derived from each start point. Where a start is a word the hook
cannot read, such as `"$D"`, none of those directories is known, so the body is
analyzed with the cwd unknown and a relative operand in it comes back as
`untracked`. The verdict is right, a deny, but the reason names the wrong cause:

| command | reason |
|---|---|
| `find "$D" -execdir cat foo \;` | `Relative path(s) after an untracked cd: foo. Fix: give cd a literal target …` |

There is no `cd` in that string, so the fix the reason hands the model does not
apply. The start point is the unreadable word, and it is never named.

## Which way to build it

Name the start. Where a `-execdir` start is unreadable, check it as an operand
in the outer `find` group, so the reason carries the `expand` advice for `$D`
beside the `untracked` line. That needs no new reason category and keeps the
deny.

## If it is never built

The model is told to fix a `cd` it never wrote, once per such command. The shape
is rare: `-execdir` with a `$VAR` start and a relative operand other than `{}`.
Flat cost of delay.
