# prod-guard trusts an environment sudo resets

sudo's default `env_reset` hands the command a fresh environment: a variable
set before `sudo` reaches it only through `-E`, `--preserve-env`, or the
policy's `env_keep`. prod-guard resolves the tool's target from the segment's
environment with sudo peeled away, so a non-production `KUBECONFIG` set before
`sudo` decides the verdict, while the `kubectl` sudo runs reads whatever config
the target user has.

Driven 2026-10-07 through the hook at `origin/main` `b76477a`, and the same on
the Q287 branch. Fixture `$HOME` with current context `gke_acme_prod-us`;
`dev.yaml` is a kubeconfig whose only context is `kind-ci`:

| command | guard |
|---|---|
| `sudo kubectl delete ns x` -- control | deny |
| `KUBECONFIG=dev.yaml sudo kubectl delete ns x` | **defer** |
| `env KUBECONFIG=dev.yaml sudo kubectl delete ns x` | **defer** |
| `export KUBECONFIG=dev.yaml; sudo kubectl delete ns x` | **defer** |
| `KUBECONFIG=dev.yaml sudo -E kubectl delete ns x` | defer -- correct |
| `sudo KUBECONFIG=dev.yaml kubectl delete ns x` | defer -- an operand sudo sets (Q240) |

sudo was not run past its password prompt. That `env_reset` is on by default
and `KUBECONFIG` is not in the default `env_keep` is read from the sudoers
manual, and a host's own policy can keep it.

Found by the orchestrator's review of the Q240 pull request.

## Which way it gets built

When the wrapper walk peels `sudo` without `-E` or a `--preserve-env` naming
the variable, judge the tool against an environment without the variables set
outside sudo, so the target falls back to ambient resolution or reads as
unknown. Keep sudo's own `NAME=value` operands (Q240). Whether `HOME` is reset
too, and so which `~/.kube/config` the tool reads, decides whether that fallback
is right or should be `ask`; read the sudoers `always_set_home` and
`set_home` defaults before choosing.

## If it is never built

Any production command written behind `sudo` with a dev `KUBECONFIG` exported
earlier in the session passes silently.
