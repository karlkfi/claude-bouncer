# `--latest=false` cannot stop GitHub handing one plugin the Latest badge

`release-process.md` lists `--latest` under Anti-patterns because the badge points
at one release and whichever plugin it names is the wrong answer for the other
four, and it prescribes `--latest=false` on every release here. The first cut from
this repository ran that on all four releases and the badge landed anyway:
`gh api repos/karlkfi/claude-bouncer/releases/latest` returns
`workspace-guard/v1.11.0`, and `gh release list` prints `Latest` beside it.

The flag did what it says. None of the four is *flagged* latest — `make_latest`
takes `true`, `false` or `legacy`, and there is no value meaning "this repository
has no latest release". With nothing claiming the badge GitHub computes a holder
from the non-draft, non-prerelease set, so a repository publishing any release at
all has one. The four tags all point at `1d09ffe`, and the holder is the release
whose tag was pushed first rather than the newest: `created_at` runs 20:29:08 to
20:29:12 in push order and the winner is the 20:29:08 one. That ordering is not
documented, so treat which plugin wins as arbitrary rather than as first-wins.

So the runbook states an outcome its own instruction cannot reach, which is worse
than stating the trade: a reader following it believes the badge is unset and it
is not. Rewrite the anti-pattern to say what `--latest=false` buys — no plugin
*claims* the badge, and GitHub picks one regardless — and decide whether to leave
the pick arbitrary or make it deliberate. Marking releases `prerelease` would
clear it and is not worth it: they are not prereleases, and saying so to get a
badge unset trades a cosmetic problem for a false statement about five shipping
plugins.
