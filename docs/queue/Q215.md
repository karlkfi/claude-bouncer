# Nothing keeps the five launcher copies, or their LF pins, in step

Every guard now launches its hook through its own copy of
`run-python-hook.cmd`, and nothing checks that the copies agree. Q206's fix
has to land in all five, and any change that misses one leaves that guard
behind with no gate noticing.

## Measured

`git ls-files -s -- '*run-python-hook.cmd'` lists five copies on one blob,
`d23e339`, all mode `100755` (2026-10-01, on the Q205 branch). Two copies
are under `plugins/prod-guard/scripts/` and `plugins/foreground-guard/scripts/`,
added by Q205; the other three are under `plugins/branch-guard/hooks/`,
`plugins/exit-status-guard/scripts/` and `plugins/workspace-guard/scripts/`.

`scripts/sync-lib.py:24:MODULES = ('bouncer_parse.py', 'bouncer_grants.py')`
does not cover the launcher, and naming it there is not a two-line change.
The script prepends a `#` banner (`scripts/sync-lib.py:27:BANNER = (`), which is
not a comment in cmd.exe and would break the polyglot's first line
`: << 'CMDBLOCK'`. It writes every module to `plugins/<name>/lib/`
(`scripts/sync-lib.py:51:return os.path.join(PLUGINS, name, 'lib', module)`),
while the launcher has to sit next to the script it runs, and branch-guard
keeps it in `hooks/` rather than `scripts/`. It also has no root copy under
`lib/` to sync from.

**exit-status-guard is the one copy with no LF pin.** `git check-attr text eol`
on `plugins/exit-status-guard/scripts/run-python-hook.cmd` reports both as
`unspecified`. workspace-guard, prod-guard and foreground-guard pin `*.cmd text
eol=lf`, and branch-guard pins `* text=auto eol=lf`. No test in
`plugins/exit-status-guard/tests/` checks for a carriage return either. The
workspace-guard `.gitattributes` comment says what a CRLF checkout does: it
turns the shell half into a syntax error.

## Inferred

Not measured: whether any real install has taken a CRLF copy of
exit-status-guard's launcher. That needs a Windows clone under
`core.autocrlf=true`, and none was tried. The `exit-status-guard-launcher` CI
job runs on `windows-latest` and passes, but this row does not establish which
`autocrlf` that checkout uses.

**One gate closes both.** A check in `make check` that reads every
`run-python-hook.cmd` under `plugins/` and requires three things of each: one
digest across all copies, mode `100755` in the index, and `git check-attr eol`
returning `lf`. It should name the copy that fails. Doing it as a sibling of
`sync-check`, rather than as another mode of `sync-lib.py`, keeps the
module-shaped assumptions out of the launcher's way. The exit-status-guard
`.gitattributes` line belongs in the same PR, because without it the new gate
is red on day one.

A root copy under `lib/` that the gate compares against is optional. With five
identical copies, the digest check alone catches drift. A root copy only
decides which side is right when they disagree.
