# A relative ln -s target resolves from the cwd, not the link directory

The kernel resolves a relative symlink target against the directory the link
sits in. workspace-guard resolves it against the command's cwd, both where it
judges `ln`'s source operand and where `stage_ln` records the link for a later
write through it. When the link lands in a different directory from the cwd,
the two disagree, and the guard can judge an in-workspace path while the
write lands outside.

Measured 2026-11-01 on the `SiblingCheckoutTests` fixture (session worktree
`wt-a`, sibling checkout `main` beside it), on the branch of #293 after its
review fixes; its reviewer reported the same verdict on `main`:

```bash
cd a/b && ln -s ../main/root.txt ../../rel && echo hi > ../../rel
```

allows. The hook reads `../main/root.txt` from `wt-a/a/b`, which is
`wt-a/a/main/root.txt`, in-workspace, so the source raises nothing and nothing
is staged. The kernel reads it from the link's directory, `wt-a`, which is
`main/root.txt` in the sibling checkout. The reviewer drove the macOS
`/bin/ln` form and saw the write land there. `ln -s ../main/root.txt ../../rel`
on its own also allows.

## Where it lands

`plugins/workspace-guard/scripts/bash-workspace-guard.py:4758:tkind, trp = resolve_token(target, group_cwd, group_cwd_unknown)`
in `stage_ln`, and the source check in the `ln_operands` branch, which calls
`check_file` with the cwd. A hard link's source really is cwd-relative, so the
fix is for the symbolic form only: resolve a relative target against
`dirname` of the link's resolved path. Where the link is under `-t DIR` or the
multi-source form, the directory is `DIR`.

The PowerShell `New-Item -ItemType SymbolicLink` row has the same question
for `-Target`, unmeasured.

A test pair: the command above denies as a sibling-checkout write, and
`ln -s ../x ./sub/link` with `x` in-workspace still allows.
