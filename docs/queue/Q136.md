# `$PIPESTATUS` is denied, `$pipestatus` silences the pipe verdict

`reads_var` matches case-sensitively
(`plugins/exit-status-guard/scripts/bash-exit-status-guard.py:420:if rest.startswith(name) and not re.match(`),
so the two spellings of the pipeline-status array reach opposite branches. The
uppercase read hits the deny; the lowercase read reaches
`not reads_var(cleaned, 'pipestatus')` and switches the piped-gate verdict off
entirely.

Measured 2026-08-26 by running the hook, on a machine whose `CLAUDE_CODE_SHELL`
points the Bash tool at `/opt/homebrew/bin/bash` (5.3.15, `ZSH_VERSION` unset):

| command | in this shell | verdict |
|---|---|---|
| `make check 2>&1 \| tail -5; [ "${PIPESTATUS[0]}" -eq 0 ]` | works | deny |
| `make check 2>&1 \| tail -5; [ "${pipestatus[1]}" -eq 0 ]` | expands empty | allow |
| `make check 2>&1 \| tail -5` | status lost | deny |

So the polarity is inverted wherever the tool runs bash: the guard denies the
recovery that works, and goes quiet for the one that does not. The bare pipe
still denies, so this is a real discrimination rather than a probe that allows
everything.

Until Q133 shipped, `PIPESTATUS_REASON` also *prescribed* the lowercase form,
which closes the loop: an agent that followed the guard's own advice wrote the
spelling that both produced a false green and suppressed the check that exists
to catch one. Q133 corrected the text and deliberately left the suppression
alone, so the steering is gone and the hole is not.

**The decision is what a guard that cannot see its own shell should do**, and it
is not obvious. Under zsh, `$pipestatus` really is the correct recovery and the
suppression is right; under bash it is a false green that silences the verdict.
Three directions, none endorsed here: drop the suppression and accept a denial
that is wrong for zsh users; read `CLAUDE_CODE_SHELL` and suppress per shell,
which is the only signal available and is absent whenever the setting is
unset; or suppress on either spelling and stop denying the uppercase read,
which trades this defect for trusting a recovery the guard cannot verify.

A release note is owed whichever way it goes -- a decision moves for the person
running the hook -- and the tests at
`plugins/exit-status-guard/tests/test_exit_status_guard.py` carry the current
behaviour in both directions, including the row that pins the suppression.
