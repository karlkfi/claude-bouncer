# `$PIPESTATUS` is denied, `$pipestatus` silences the pipe verdict

The piped-gate deny is suppressed whenever the command reads `$pipestatus`
(`plugins/exit-status-guard/scripts/bash-exit-status-guard.py:808:not reads_var(cleaned, 'pipestatus')`),
and denied whenever it reads `$PIPESTATUS`. `reads_var` compares with
`startswith`
(`plugins/exit-status-guard/scripts/bash-exit-status-guard.py:420:if rest.startswith(name) and not re.match(`),
so the two spellings reach opposite branches.

Measured 2026-09-01 by driving `decide` against the shipped registry, with a
bare pipe as the control:

| command | in bash | verdict |
|---|---|---|
| `make check 2>&1 \| tail -5` | status lost | deny |
| `make check 2>&1 \| tail -5; [ "${PIPESTATUS[0]}" -eq 0 ]` | works | deny |
| `make check 2>&1 \| tail -5; [ "${pipestatus[1]}" -eq 0 ]` | expands empty | allow |

`/opt/homebrew/bin/bash -c 'false | true; echo "[${pipestatus[1]}]"'` prints
`[]`, so under the shell `CLAUDE_CODE_SHELL` points this machine's Bash tool at,
the allowed form recovers nothing and the test against it reads as success.

## The decision: drop the suppression

The row was filed with three directions and none endorsed. Two of them rest on
`$pipestatus` being the correct recovery under zsh, and measurement narrows that
claim: it is the correct *spelling*, but the suppression is not scoped to the
pipeline it is supposed to mitigate, so it is unsound under zsh as well. Both
holes were driven the same day, each against a control that denied:

- One read silences **every** pipeline in the command.
  `make check | tail; echo ${pipestatus[1]}; make lint | tail` is allowed, and
  `make lint`'s status is recovered by nothing. `/bin/zsh -c 'false | true;
  echo ${pipestatus[1]}; true | true; echo ${pipestatus[1]}'` prints `1` then
  `0`: the array holds the most recent pipeline only.
- A read **before** any pipeline silences too. `echo ${pipestatus[1]}; make
  check | tail` is allowed, and recovers nothing in any shell.

So there is no shell in which the suppression does what it claims, and the
remaining choice is between deleting it and rewriting it to track pipeline
order. Delete it, for three reasons the tree already holds:

- **The deny branch's own reason is verbatim true of the lowercase spelling.**
  `PIPESTATUS_REASON` denies `$PIPESTATUS` because "the array is a bash feature,
  and under a shell without it the read expands to empty, so the test against it
  reads as success whatever the pipeline did"
  (`plugins/exit-status-guard/scripts/bash-exit-status-guard.py:746:the array is a bash feature, and under a shell`).
  Swap bash for zsh and that is the case against `$pipestatus`. The guard
  already denies a recovery that works under the shell in use — it denies
  `${PIPESTATUS[0]}` on this machine, where it works — so denying the other
  spelling takes no new position.
- **The remedy the guard prints is portable, so a denied zsh user loses
  nothing.** `cmd > <LOG> 2>&1; echo "EXIT=$?"` is correct in both shells, and
  `EXIT_STATUS_GUARD_OVERRIDE=<reason>` covers the caller who wants the pipeline
  anyway. The cost of a false deny is one rewrite; the cost of the false allow
  is a failed gate reported green, which is the whole of what this plugin is
  for.
- **Reading `CLAUDE_CODE_SHELL` does not answer the question.**
  `CLAUDE_CODE_SHELL=/opt/homebrew/bin/bash` is in the tool environment here, so
  the read is available — but it is absent whenever the setting is unset, and
  the guard must then pick a default, which is this question again. It also
  leaves both scope holes above untouched.

The remaining direction — suppress on either spelling and stop denying the
uppercase read — reverses shipped, tested behaviour in order to extend a
suppression that is unsound in both shells. It is out.

## Who it is for, and what happens if it is never built

The reader is a session whose gate fails while the hook stays silent. The bite
rate is low and no longer growing: until Q133 shipped on 2026-08-27 in `e91af6d`,
the guard's own denial prescribed `$pipestatus`, so it was manufacturing the
reads that silence it, and that steering is gone. What is left is a guard carrying a token
that turns its own verdict off — the same shape as the override, without the
reason the override demands. Never building it leaves that token in place.

## What lands

One clause deleted, so all three holes close together, plus:

- Invert the pinning row at
  `plugins/exit-status-guard/tests/test_exit_status_guard.py:118:zsh's $pipestatus suppresses the pipe verdict`,
  which currently asserts the allow. Add the two ordering cases above as denies,
  so a re-introduced suppression cannot pass by matching on the segment order it
  was written for.
- Check `friction-report.py`: Q133 records that it classifies on reason text, so
  confirm no bucket keys on a `pipestatus` allow.
- A release note. The change denies a command shape that passes today, and the
  reason names the portable rewrite.
