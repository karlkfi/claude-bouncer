# A substitution body starts from the string cwd, not the tracked one

The group loop tracks a cwd across the string and carries it with every shell
`-c` body it queues —
`plugins/workspace-guard/scripts/bash-workspace-guard.py:3707:shell_bodies.extend((b, group_cwd) for b in shell_c_bodies(g))`
— so each of those is later recursed into against the directory in force where
it sat:
`plugins/workspace-guard/scripts/bash-workspace-guard.py:3918:for body, body_cwd in shell_bodies:`.

Command substitutions get none of that. They are scanned once over the whole
string *after* the loop has finished, from the string's starting cwd:
`plugins/workspace-guard/scripts/bash-workspace-guard.py:3898:sub_off, _, sub_kf = _analyze_command(body, ctx, base_cwd,`.
A `cd` earlier in the string is therefore not reflected inside a `$(…)` body,
and the comment above that call states the behaviour as a property rather than a
gap:
`plugins/workspace-guard/scripts/bash-workspace-guard.py:3872:ops would otherwise be invisible. Each body resolves against the same`.

## What it costs, here and downstream

For workspace-guard the consequence is a prompt that names the wrong directory —
the human is asked to approve a path that is not the one the command reads.

For `karlkfi/claude-spill-guard`, which ports this layer, it is sharper: the
substitution body's relative operand becomes a coverage record, so
`cd sub && echo $(cat x)` gets no verdict while `cd sub && cat x` beside it
resolves and is scanned. Measured 2026-09-06 over one machine's transcripts: 137
coverage records on the relative-after-`cd` arm carry a cd-family command, and
**11** of them carry a `$(…)` or a backtick after it.

## Which way it gets built — two readings, and the row does not pick

The recursion needs to know something about each body that
`lib/bouncer_parse.py:615:def command_substitutions(text, quotes=True):` does not
currently return. Two candidates:

- **A kind** — tell a `$(…)` body from a backtick body. The `$(…)` case is
  already flattened into the in-order pass where the tracker resolves it
  correctly, so the queue could skip its operands and exist only for the nested
  backticks and heredocs inside it.
- **An offset** — where in the string each body sat, so the recursion starts from
  the directory tracked at that point. This is the answer for a backtick too.

**The offset reading closes a second half the kind reading does not**, which is
the argument for it. The same missing position forces each queued body to start
with an empty variable map rather than the parent's, since a value the string
assigns *after* the body would otherwise be substituted into text bash expanded
with the environment's value. This repo works around that by seeding the
recursion with `stable_vars` — names holding one literal at every point in the
string, so the seed is safe whether the body sits before or after the assignment.
That seed only ever adds a prompt here, which is why it is affordable; it is
deliberately *not* ported into spill-guard, where the same substitution would
pick which file gets read.

**The shortcut to refuse** is matching `"$(" + body + ")"` against the raw text to
guess the kind. It is a second parser over text the lexer already read, and it
disagrees with the lexer the first time a body appears in both forms. The tree
already shows the cost of keying bodies by their text:
`plugins/workspace-guard/scripts/bash-workspace-guard.py:3204:raw.setdefault(strip_heredoc_bodies(body), body)`
builds a text-keyed map, so two identical bodies collapse to one entry.

**Settles:** read `_analyze_command`'s `seed_vars=stable_vars` argument against
the `shell_bodies` pattern two hundred lines above it — that pattern is already
the offset reading's shape, carried per body, for the one construct that gets it.
Whether that is enough to choose, or whether the backtick and heredoc cases need
driving first, is what the settling pass decides; write the choice into this row
and drop the label.

## Scope

The return shape is `lib/`, so the change reaches every consumer, not only the
call site that motivates it.
`plugins/exit-status-guard/scripts/bash-exit-status-guard.py:936:bodies = command_substitutions(cleaned)`
is the other in-tree consumer and takes two calls; branch-guard has its own
`extract_command_substitutions` and is untouched. Say which suites were re-run.
