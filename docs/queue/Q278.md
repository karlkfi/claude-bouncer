# branch-guard does not split on `|&`, so the command after it is unjudged

`|&` is a pipe that also carries stderr, and bash runs the command on its
right. branch-guard's `SEPARATORS` has `|` and not `|&`, so a `|&` never ends
a segment, and the command after it is never classified.

Measured 2026-10-05 on `origin/main` at `d43db6e`, in a fresh repository on
`main`. bash was `env -i "$(command -v bash)" --norc --noprofile -c` (5.3.15),
where `echo a |& echo RAN` prints `RAN`:

| command | branch-guard |
|---|---|
| `echo a; git commit -m x` (control) | ask |
| `echo a \| git commit -m x` (control) | ask |
| `echo a \|& git commit -m x` | **none** |
| `echo a\|&git commit -m x` | **none** |

The independent review of #219 (Q268) found it. Q239 and Q263 mention `|&`
for foreground-guard and exit-status-guard and do not cover this guard.

`has_shell_substitution` flags any `|&` run as unknown, which is why
`git status |& touch PWNED` defers today and is pinned by the
`|& operator run -> none (defer)` fixture. That only stops a would-be allow,
and nothing here was an allow.

## Which way it gets built

Add `|&` to `SEPARATORS`, as lib's own `SEPARATORS` already has it. Then
`split_separator_runs` splits a glued `)|&` too. Keep the `|& touch PWNED`
fixture: once split, `touch` is a non-git segment and still defers. Add the
commit-on-`main` ask for both spacings.

Two docstring nits from the #219 review ride along, since this edits the same
code. `tokenize`'s docstring still says it peels newline separators, though it
now splits every separator run. And the sentence Q268 added to
`has_shell_substitution`'s docstring runs past the file's line width.

## If it is never built

`… |& git commit` or `… |& git push` on a protected branch runs with no
prompt.
