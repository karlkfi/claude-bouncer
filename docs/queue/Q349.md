# Six shapes bash runs are judged by no guard

The stream-A reviewer found these while reviewing #314 at `fcd44b0`, driving each guard's hook
script with `P` standing in for that guard's trap command. Every one defers from all five guards
on `main` at `1d0fe4e6` and on #314, and bash 5.3.15 runs `P` in each:

| command | what bash does |
|---|---|
| ``echo \\`P\\` `` | `\\` is a backslash, and the backtick after it is live |
| ``bash -c "echo \\`P\\`"`` | the parent turns `\\` into `\` and runs the backtick |
| the same with 6 backslashes | as above, one level deeper |
| ``bash <<< "echo \`P\`"`` | the here-string is the child's script |
| `bash <<< "\$X P"` | the same, with an unset `$X` |
| `bash -c 'echo x; \` newline `P'` | a continuation inside a single-quoted body |

Two more belong to existing rows: ``eval "$(echo \`P\`)"`` evaluates a substitution's output,
which is Q279's command word the guard cannot resolve. The five-backslash
``bash -c "echo \\\\\`P\\\\\`"``, noted on #314, is likely the first group's cause below.

**Measure:** the cause of each group, before any fix. The first three plausibly share one:
each ends a backtick body on an escaped backslash, so the body handed to the guard ends in a bare
`\`, which `shlex` rejects as `No escaped character`, and a guard that cannot lex defers. On #314
that is what prod-guard's `tokenize` did with the five-backslash body. The here-string rows are
unhandled rather than misread: no guard treats a string fed to a shell's stdin as a script. The
continuation row is unmeasured. Split the row by cause once each is known.

## If it is never built

A command written in any of these shapes goes unjudged by every guard. Each needs an unusual
backslash count, a here-string fed to a shell, or a continuation inside a single-quoted body, so
the shapes are likely rare.
