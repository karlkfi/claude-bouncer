# An ANSI-C quoted apostrophe inverts quote tracking for the rest

`$'\''` is one literal apostrophe in bash. `command_substitutions` and
prod-guard's shlex lexer both read it as a closed single-quoted string followed
by an opening quote, so everything after it reads as single-quoted, and a
substitution there is treated as literal.

Found by the independent review of the Q196 pull request. Re-driven 2026-10-01
through the hook (fixture `$HOME`, ambient context `gke_acme_prod-us`) at
`b27be8d` and at the Q196 head, with identical results. That bash runs the
payload was driven under `env -i bash --norc --noprofile -c` with a payload
absent from `PATH`:

| command | guard | bash runs it |
|---|---|---|
| `echo $'\'' "$(kubectl delete ns payments)"` | **defer** | yes |
| `echo $'\'' $(kubectl delete ns payments)` | **defer** | yes |

The review found `echo $'$(…)'` correctly left alone: inside `$'…'` nothing
substitutes.

## Which way it gets built

Teach the quote scanners `$'…'`, where a backslash escapes the next
character, including `'`. `command_substitutions` is in `lib/`, so the scan
fix reaches every guard. prod-guard's shlex lexer needs the same reading, or
it keeps the wrong quote state for the words it hands the evaluators. Probe
the other four guards on the same two shapes before scoping, because the lexer
half may be prod-guard's alone.

## If it is never built

One `$'\''` anywhere before a mutating command hides it. That spelling is the
usual way to embed an apostrophe, so it is not exotic.
