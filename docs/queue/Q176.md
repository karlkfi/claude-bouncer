# A break-glass passed through `env` never arms prod-guard

`env PROD_GUARD_OVERRIDE=<reason> kubectl …` denies. The same reason written
as a plain command prefix downgrades the deny to an `ask`, and
foreground-guard honours both spellings, so the two guards disagree about a
form bash treats identically.

## Measured

2026-09-07, against `origin/main` at `17df02a`, driving the hook directly:

```
PROD_GUARD_OVERRIDE=incident-42 kubectl --context gke_acme_prod-us delete ns x
  -> ask   ("override acknowledged")

env PROD_GUARD_OVERRIDE=incident-42 kubectl --context gke_acme_prod-us delete ns x
  -> deny  (no mention of the override)
```

The cause is which dict each reader consults.
`plugins/prod-guard/scripts/bash-prod-guard.py:2411:seg_env, argv_raw = extract_env_prefix(group, shell_env)`
builds the inline-prefix env, and the override test at
`plugins/prod-guard/scripts/bash-prod-guard.py:2419:if 'PROD_GUARD_OVERRIDE' in seg_inline:`
reads that one. The `env` wrapper's operands are parsed separately in
`strip_wrappers` and merge into the segment env used for *target pinning* --
`KUBECONFIG`, `AWS_PROFILE` -- which the override check never looks at.

foreground-guard reads the override from both positions, in the `env` branch of
`plugins/foreground-guard/scripts/bash-foreground-guard.py:336:def strip_head(argv, state):`.

## Who it is for, and what it is worth

The direction is fail-safe: the guard denies where the caller asked for a
prompt. It costs a round trip and reads as a guard bug, because the denial
names `PROD_GUARD_OVERRIDE=<reason>` as the way out and the caller then writes
it in a form the guard does not read.

`env NAME=v cmd` is a per-command prefix, not a persistent export, so it does
not weaken the rule the existing test
`plugins/prod-guard/tests/test_prod_guard.py:911:def test_override_must_be_an_inline_prefix(self):`
protects -- that one is about a var *exported into the environment*, which
pre-arms every later command. An `env` wrapper is restated per command exactly
as the bare prefix is.

## What happens if it is never built

The two guards keep disagreeing about one spelling, and the prod-guard denial
keeps advertising a route that does not work when written behind `env`.

## Which way it gets built

Merge the `env`-wrapper operands into the dict the override check reads, or
have that check consult the segment env as well. Both readers already exist;
what is missing is that the override test only looks at one of them.

Fixtures in both directions: `env PROD_GUARD_OVERRIDE=r` must arm,
`PROD_GUARD_OVERRIDE=r` must keep arming, and an *exported*
`PROD_GUARD_OVERRIDE` must still not arm.
