# An allow from a generically labelled hook names no guard

Some hook attachments record `command hook 7` where the hook's command line was.
The number does not identify a guard: `command hook 7` carried branch-guard asks, and so did `command hook 4`.
The friction reports name such a record from its reason's opener, which every ask and deny has. workspace-guard's and branch-guard's `allow` reasons have none, so those records are dropped.

**Measure:** what makes Claude Code record the generic label, and does the rate keep rising?
Whether this is worth a change to what two hooks print depends on both.

## What is measured

2026-11-24, over 215,000 `PreToolUse` attachments: 839 carry the generic label.
By version it is 49 of 16,439 on 2.1.309, 431 of 7,061 on 2.1.321, 208 of 608 on 2.1.325 and 175 of 7,100 on 2.1.330, where the count includes a few records with no command at all.
In the last seven days 362 were an `allow` with no opener, against 6,129 decisions workspace-guard's report called `allow`.
679 of the unopened ones over all time are workspace-guard's own wording.
All 7 generic asks carry an opener, so no prompt is missing from a report.

The effect is on workspace-guard's friction share, which divides by decisions: losing an allow raises it.
A test for the first half of the question is whether the generic records cluster by session, plugin order or entry point.

## Which way it gets built

Either give `allow` reasons the opener too, or leave them and say so in the reports. branch-guard leaves it off on purpose, on the argument that an `allow` reason "is read only by something already holding the record that attributes it" (`plugins/branch-guard/hooks/branch-guard.py:already holding the record that attributes it`).
A generic label is a record that does not attribute it, so that argument is the one to re-judge.
