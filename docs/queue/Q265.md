# A cd in a function definition moves the tracked cwd

Defining a function runs none of its body, but the group loop reads the body's
`cd` as if it had run. Every relative path after the definition is then judged
against a directory the shell never entered.

## Measured

2026-10-04. The hook was driven with `cwd` set to a scratch workspace that has
a `sub/` directory, on `main` at 5e19aab and on the Q173 branch, which agree.
bash 5.3.15 ran the same strings under `env -i`, with a file named `q173-x` in
the workspace and another in its parent, so the output shows which one was
read.

| command | hook | bash reads |
|---|---|---|
| `f() { cd sub; }; cat ../q173-x` | **allow** | the parent's |
| `function f { cd sub; }; cat ../q173-x` | ask | the parent's |
| `f() { cd sub; }; f; cat ../q173-x` | allow | the workspace's |

Row 1 is the defect: an `allow` for a read outside the workspace. Row 2 asks,
but not because the guard models a definition. Nothing in it does, and why
that spelling escapes the `cd` branch wasn't traced. Row 3 is right only
because the call does run the `cd`.

## Which way it gets built

Q173 gave `split_groups` a `scopes` out-parameter, which says which subshells
each group sits in. A function body needs a different answer from a subshell's:
its `cd` doesn't run where it is written, and it does run, in the calling
shell, each time the function is called. The safe reading is to treat a
definition's `cd` as moving nothing and to make the cwd unknown at a call to a
function whose body changes directory. Then a relative read after the call
denies instead of resolving against a guessed directory.

## If it is never built

Any string that defines a helper function with a `cd` in it gets an `allow` for
a relative read outside the workspace written after the definition. The `allow`
short-circuits the user's own permission settings.
