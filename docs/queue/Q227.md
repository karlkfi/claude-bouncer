# The republish probe allows a reset that loses a reworded message

Q145 lets `git reset --hard` through when every commit it would orphan has a
`git patch-id --verbatim` match on the recovery refs. A patch-id hashes the
diff and never the commit message. So a published commit whose message was
reworded locally (`git commit --amend -m …`, not pushed) matches its original,
and the reset is allowed and drops the new message. Before Q145 that reset was
denied.

Measured 2026-10-01 on git 2.55.0, by driving the hook at the head that
shipped the probe: one published commit, `--amend -m` with no content change,
one orphan by `git rev-list --count claude/x --not --remotes`, and
`git reset --hard origin/claude/x` returned `allow`. The independent review of
that pull request raised it first, as a note rather than a hold.

Who it is for: a session that rewrote a commit message and then resets to the
remote, which loses the message without being told. If nothing is done that
loss stays silent; it is rare, since rewording without pushing and then
resetting to the old version is an unusual sequence, and the code is intact.

The fix that costs the rebase case nothing: a rebase carries each message over
unchanged, so `orphans_republished` can also require that each orphan's match
has the same message (`git log --format=%B`) as the orphan. A reword then
denies, and every allow fixture in `test/run.sh` section 28 should keep
passing. Add a reword fixture beside the whitespace-amend one.
