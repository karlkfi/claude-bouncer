# prod-guard and workspace-guard each split find -exec their own way

Two guards now decide which words a `find` runs as a command, and each has its own copy of the walk. workspace-guard's is inside `find_parts`, at `plugins/workspace-guard/scripts/bash-workspace-guard.py:2325:        if t in FIND_EXEC_PRIMARIES:`, and prod-guard's is `find_actions`, at `plugins/prod-guard/scripts/bash-prod-guard.py:1394:def find_actions(argv):`, added for Q389.

They agree today, read from both sources: an `-exec`, `-execdir`, `-ok` or `-okdir` runs up to its `;`, or up to a `+` straight after `{}`, and a missing terminator takes the words to the end.
BSD find measured that rule for Q389: `-exec /bin/echo RAN + \;` printed `RAN +`, and `-exec /bin/echo RAN {} +` printed `RAN .`.
Nothing makes the two copies keep agreeing, so a fix to one reaches only that guard: workspace-guard's `find_bodies` docstring records, unmeasured here, that GNU find refuses a `+` command holding a second `{}`, and prod-guard reads none of that.

This is the case the repo's rule for the shared parser names: a primitive belongs in `lib/` once a second guard needs the same behaviour.

## Which way it gets built

Move the terminator walk into `lib/` as a function returning each command's words and whether it ended in `+`, which is the part both guards read. workspace-guard keeps its start-point, `-delete` and file-primary parsing in `find_parts`, which only it needs, and calls the shared walk for `commands`. prod-guard's `find_actions` becomes a call to it.
Re-run all five suites, since the module is vendored into each.

## If it is never built

Nothing breaks today.
The cost arrives when one guard's `find` handling is corrected and the other's is not, which nobody will see unless the same shape is measured against both.
