# workspace-guard misses an -exec a -path operand hides; share the walk

workspace-guard's `find_parts` reads the first `-exec`-family word as a primary even where it is another primary's operand, so the real `-exec` after it is never judged.
Measured 2026-11-26 through the hook, with workspace-guard as `main` holds it at `920e2fe`, project root the worktree:

| command | workspace-guard |
|---|---|
| `find . -exec cat /tmp/q414-fake-target \;` (control) | deny |
| `find . -path -exec -o -exec cat /tmp/q414-fake-target \;` | **defer** |

`find_parts` returns the one command `['-o', '-exec', 'cat', '/tmp/q414-fake-target']` for the second, whose command word is `-o`.
BSD find runs the `cat`: `find . -maxdepth 0 -path -exec -o -exec /bin/echo RAN \;` printed `RAN`, and so did the same shape with `-name -ok`.
The cause is the scan at `plugins/workspace-guard/scripts/bash-workspace-guard.py:2457:        if t in FIND_EXEC_PRIMARIES:`, which resumes after each command's terminator.

prod-guard had the same defect and Q389's review fixed it there: its `find_actions`, at `plugins/prod-guard/scripts/bash-prod-guard.py:1404:def find_actions(argv):`, starts a command at every `-exec`-family word.
So two guards now carry their own copy of one walk, and they already disagree.
That is the case the repo's rule for the shared parser names: a primitive belongs in `lib/` once a second guard needs the same behaviour.

## Which way it gets built

Move the walk into `lib/` as a function returning each command's words and whether it ended in `+`, starting a command at every `-exec`-family word as prod-guard does.
That over-judges an `-exec` written as another command's argument (`-exec echo ONE -exec echo TWO \;` runs one `echo`), and never misses one find runs. workspace-guard keeps its start-point, `-delete` and file-primary parsing in `find_parts`, which only it needs, and takes `commands` from the shared walk. prod-guard's `find_actions` becomes a call to it.
Re-run all five suites, since the module is vendored into each.

## If it is never built

A read or write outside the workspace written behind a primary-shaped operand runs without a prompt under workspace-guard.
It needs a `-path`, `-name` or similar operand spelled exactly like an `-exec`-family primary, so it is an adversarial shape rather than one a session writes by accident.
