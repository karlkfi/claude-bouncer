# branch-guard follows a cd behind && or || that bash may skip

branch-guard follows a literal `cd` for every segment after it. Behind `&&` or
`||` the `cd` may not run, so the command after it can land in the tree it
started in while being judged in the `cd`'s target. From a checkout of `main`,
each of these commits to `main` and gets no decision, where a bare
`git commit` there asks:

| command (cwd on `main`, `../feat` a worktree on a feature branch) | verdict |
|---|---|
| `false && cd ../feat; git commit -m x` | none |
| `true \|\| cd ../feat; git commit -m x` | none |

Measured 2026-10-07 against both `main` `5a5552d` and the Q302 fix; both give
the same two verdicts. The miss is a defer rather than an allow, because a
`cd` into another worktree is a non-git segment. The Q302 fix did close the
fork half of this, a `cd` in a pipeline stage or before `&`.

## Which way it gets built

`compound_layout` in `plugins/branch-guard/hooks/branch-guard.py` already
records the operator before each segment. A `cd` reached through `&&` or `||`
leaves the cwd unknown after its list ends, which judges the next command
against the session's own checkout, as after a `cd $VAR`.

## If it is never built

A commit or reset that lands on `main` after a conditional `cd` gets no prompt.
