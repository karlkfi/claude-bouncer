# branch-guard follows a cd that bash skips or runs in a subshell

branch-guard follows a literal `cd` for every segment after it, in source
order. That is right after `;`, and wrong in three places bash does not move
the shell: the right side of `&&` or `||`, which may not run, a pipeline
stage, and a backgrounded command, both of which run in a subshell. From a
checkout of `main`, each of these commits to `main` and gets no decision,
where a bare `git commit` there asks:

| command (cwd on `main`, `../feat` a worktree on a feature branch) | verdict |
|---|---|
| `false && cd ../feat; git commit -m x` | none |
| `true \|\| cd ../feat; git commit -m x` | none |
| `cd ../feat \| true; git commit -m x` | none |
| `cd ../feat & git commit -m x` | none |

Measured 2026-10-07 against both `main` `5a5552d` and the Q302 fix, which
scopes a `cd` by `( )`, `{ }`, conditionals and loops but not by these
operators; both give the same four verdicts. The miss is a defer rather than
an allow, because a `cd` into another worktree is a non-git segment.

## Which way it gets built

`command_segments` already sees the separator before each segment. Hand it to
the same scope tracker Q302 adds: after `&&` or `||` a `cd` leaves the cwd
unknown, and a `cd` in a pipeline stage or before `&` does not move it.

## If it is never built

A commit or reset that lands on `main` after a conditional or piped `cd` gets
no prompt.
