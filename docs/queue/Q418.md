# A pipe after a semicolon-closed subshell is not read as the gate's pipe

`(make check;) | tail` is silent, and bash returns `tail`'s status for it: `(false;) | true; echo $?` prints 0 on bash 5.3.15.
Without the `;`, `(make check) | tail` denies.
Found by the review of #379 (Q400) on `main` and at that PR's head `6b323c5`, where the `-c` splice reaches the same shape through `bash -c 'make check;' | tail`, also silent.
The `;` and `git push` versions of both deny correctly, so only the pipe verdict misses.

**Why.** The segment holding `make check` carries the operator run `;`, `)`, `|`, and `next_op` returns the first operator that is not a paren (`plugins/exit-status-guard/scripts/bash-exit-status-guard.py:139:    for op in ops:`).
So `piped_gate` reads a `;` where the status actually leaves through the `|` (`plugins/exit-status-guard/scripts/bash-exit-status-guard.py:1020:        if next_op(seg.post_ops) not in PIPE_OPS:`).
A `;` or newline right before a `)` terminates the group's last statement rather than sequencing another one after it.

**Which way it gets built.** Have `next_op` pass over a `;` or newline that a `)` follows, the same way it passes over parens.
Every rule reads it, so re-run the sequenced rule's cases: `(make check;); git push` has to stay a deny.
A `{ make check; } | tail` already denies, since `}` is a word rather than an operator, and pins the shape the fix should match.
