# prod-guard reads env options after `--`

`env -- -S 'STRING'` runs a program called `-S`: `--` ends env's options, so
nothing after it is split or assigned by env. prod-guard's `env` branch skips
the `--` as an ordinary option word and keeps reading options, so the `-S`
behind it splits and the command inside the string is judged
(`plugins/prod-guard/scripts/bash-prod-guard.py:1041:if argv[0].startswith('-') and not assigned:`).

Driven 2026-10-07 through the hook, fixture `$HOME` with current context
`gke_acme_prod-us`, at `origin/main` `b76477a` and on the Q287 branch, which
reads a bundle ending in `S` through the shared `wrapper_option` walk:

| command | `main` | Q287 branch |
|---|---|---|
| `env -S 'kubectl --context=gke_acme_prod-us delete pod x'` -- control | deny | deny |
| `env -- -S 'kubectl --context=gke_acme_prod-us delete pod x'` | **deny** | **deny** |
| `env -- -iS 'kubectl --context=gke_acme_prod-us delete pod x'` | defer | **deny** |

Both envs run a program called `-S` there: `/usr/bin/env -- -S 'echo hi'`
(macOS) and `genv -- -S 'echo hi'` (GNU coreutils 9.11) each exit 127 with
`-S: No such file or directory`.

## Which way it gets built

Stop taking options after `--` in the `env` branch, as `peel_sudo` already
does for sudo (Q240). An `env -- A=1 cmd` still assigns `A`: `--` ends options,
not operands, which is where env and sudo differ: `env -- A=1 sh -c 'echo $A'`
prints `1` under both builds.

## If it is never built

A false deny on a shape nobody types: the cost is one rewrite. It is the strict
direction, which is why it ranks below the wrapper false negatives.
