# A prefix assignment resolves its own command's words

Bash expands a simple command's words before it applies the assignments in
front of it, so in `CTX=kind-dev kubectl --context=$CTX …` the word gets the
`$CTX` the shell already had, not `kind-dev`. With `CTX` unset, kubectl gets
`--context=`, which falls back to the current context. prod-guard expands the
words against the prefix too, reads `kind-dev`, and defers.

Found by the prod-guard reviewer on the Q298 pull request (#288), and
re-measured 2026-11-01 on the Q290 branch at `a4ad697`, fixture `$HOME` with
current context `gke_acme_prod-us`:

| command | bash 5.3.15 | guard |
|---|---|---|
| `kubectl --context=$CTX delete pod x` (control) | -- | ask |
| `CTX=kind-dev kubectl --context=$CTX delete pod x` | `--context=` | **defer** |

The bash column ran `CTX=kind-dev /bin/echo "[--context=$CTX]"` under
`env -i /opt/homebrew/bin/bash --norc --noprofile`, which printed
`[--context=]`. No kubectl was run, so that kubectl reads an empty
`--context=` as the current context is the row's reading, not a measurement.
It does not change the verdict owed: an unresolved target asks.

## Where it happens

`same_shell`, the env the segment's words are expanded against, merges the
segment's own prefix in:
`plugins/prod-guard/scripts/bash-prod-guard.py:3339:same_shell = {**shell_env, **seg_inline}   # for this command's args`.
The prefix belongs in what the command *inherits* (`child_env`), and in the
expansion of the next segment only where it persisted.

## Which way it gets built

Expand a segment's words against `shell_env` alone. Check what else reads
`same_shell` first: the `env -S` alternates and a double-quoted `bash -c` body
are expanded against it too (Q131), and a prefix does not reach those either.

## If it is never built

A mutation written with its target in a prefix assignment it also reads, which
is a natural way to write it, passes silently against the current context.
How often sessions write it is not measured.
