# A prod-guard nesting test outruns its 30s cap under load

`test_alternating_nest_past_the_old_limit_does_not_defer` drives the hook twice on a command nested 1,000 levels deep, alternating `${X:-…}` and `$( )`, and each call runs under the suite's per-subprocess cap (`plugins/prod-guard/tests/test_prod_guard.py:161:        capture_output=True, text=True, env=env, cwd=home, timeout=30)`).
On 2026-11-26 a `make check` over Q400's branch, which changes nothing under `plugins/prod-guard` or `lib`, failed on this one test with `subprocess.TimeoutExpired ... timed out after 30 seconds`.
The machine's load average was 18 to 28, with about ten sessions running.
The prod-guard suite took 162s in that run against 105s in a green run of the same tree an hour earlier.
Run alone on the same machine minutes later, the test passed in 10.1s, so each hook call takes about 5s idle and the cap leaves a factor of six.

The harm is a red local gate on code nobody broke, during exactly the parallel runs that load the machine.
It was one failure in two full runs that day; the rate is not measured beyond that.

Which way it gets built is open between two options.
One is to raise the cap for this test alone, since its point is that the nest is read rather than that it is fast.
The other is to shrink the nest to the smallest depth that still crashed the old unbounded recursion.
Measure the hook's time at the current depth and at the smaller one first, so the choice rests on numbers.
