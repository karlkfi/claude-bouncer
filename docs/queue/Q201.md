# The cd relaxation does not fire for two Windows path spellings

Q146 made a `cd` recognized-safe when its literal target resolves into the same
worktree, which is what reaches the break-glass behind the `cd` most sessions
lead with. On Windows two common spellings of an absolute target never resolve,
so the relaxation does not fire and the command keeps the verdict it had before
Q146.

**Fail-closed, so this is a limitation rather than a defect.** An unresolvable
target lands on `nongit`, the segment stays outside the set `liftable` accepts,
and the command keeps its ask or its deny. Nothing opens. What is lost is the
repair Q146 shipped, on one platform, for two of four spellings.

**Q146 made this visible rather than creating it.** Both mechanisms below are
`cd_destination`/`resolve_path`, which arrived with Q135 for probe aiming;
until Q146 nothing depended on the answer being *right* rather than merely
safe, so a target that resolved nowhere cost a stood-down probe and no one
noticed.

## Measured

Run against this tree, on macOS, using the vendored `lex` and Python's
`ntpath` — the second is what makes the Windows half checkable without a
Windows machine, since `ntpath` implements exactly the path semantics that
platform gets.

| spelling | survives `lex` | `ntpath.isabs` | relaxation fires |
|---|---|---|---|
| `cd D:\a\repo\wt` | **no** — `['cd', 'D:arepowt']` | — | no |
| `cd 'D:\a\repo\wt'` | yes | True | **yes** |
| `cd D:/a/repo/wt` | yes | True | **yes** |
| `cd /d/a/repo/wt` (MSYS) | yes | **False** | no |

Two failures, two different causes, and neither is the one a reader would
guess:

- **Unquoted backslashes are eaten by the lexer.** `lex` is POSIX `shlex`, where
  `\` is an escape, so `D:\a\repo\wt` tokenizes to `D:arepowt` — a relative path
  that resolves under the session's own tree and answers a confident, wrong
  "not this worktree".
  `plugins/branch-guard/hooks/branch-guard.py:1018:def is_literal_path(token):`
  passes it, because by then the backslashes are gone and nothing about the
  token looks non-literal.
- **The MSYS spelling is not absolute to `ntpath`.** `ntpath.isabs('/d/a/…')` is
  False, so
  `plugins/branch-guard/hooks/branch-guard.py:1025:def resolve_path(cwd, path):`
  takes its relative branch and joins it onto the session cwd —
  `ntpath.join('D:\\a\\x', '/d/a/y')` is `D:/d/a/y`, which exists nowhere. The
  probe then fails and the answer is None.

The quoted backslash form and the forward-slash drive form both work today, so
this is not "absolute `cd` is broken on Windows" — which is how it was first
described in review, from reasoning rather than from the table above.

## Who is worse off

A Windows session that leads with an absolute `cd`, which is the spelling a
session writes when it is being careful about which tree it is in. It meets the
pre-Q146 behaviour with no indication that a relaxation exists — the same
silent shape Q146 was filed for, one platform over.

## What happens if it is never built

Unmeasured, and honestly probably small: no Windows session appears in the
corpus Q146 counted, and this repository's own agents run on macOS. The cost is
mostly that the fix reads as platform-independent in the README and is not.

## Which way it gets built

Undecided between two shapes, and they are not equivalent.

**Measure:** first establish whether any Windows session hits this at all, since
that decides whether either shape is worth the surface. If it is:

- Normalising the MSYS spelling is a small, contained change to `resolve_path`
  and closes the fourth row of the table.
- The unquoted-backslash row is **not** a `cd` question. It is the lexer, shared
  through `lib/bouncer_parse.py`, so it reaches all five guards and any change
  there is a `lib` change with that blast radius. Treating a `\` as literal on
  Windows would be a parsing-model change, not a branch-guard one, and it should
  not be made from this row alone.

The rows are separable and the second may well be *wontfix*: the guard's whole
parsing model is POSIX shell, and a session on Git Bash is writing POSIX shell.

## Notes

Found while fixing Q146's own fixtures, which failed on the `branch-guard-windows`
job for the same reason: the suite interpolated an absolute path bare into the
command string, so the hook received the MSYS spelling. That is repaired with
the harness's `nat` helper. This row is the part `nat` cannot reach, because a
real session's `cd` is written by the session rather than by the suite.

Two of the four repaired fixtures had been *passing* on Windows for the wrong
reason — negatives expecting `ask`, where an unresolvable path and a correctly
rejected sibling worktree give the same verdict — so the platform gap was
invisible from a green run in both directions at once.
