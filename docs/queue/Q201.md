# The cd relaxation does not fire for the MSYS path spelling

**Demand:** a Windows session in this machine's transcripts, or a report from
someone running the guard on Windows, whose `cd /d/…` (MSYS spelling) kept a
prompt or a deny that the same `cd D:/…` would have lifted.

Deferred 2026-10-04 after measuring. Of the two spellings this row named, one
is not a defect: the guard reads it exactly as bash does. The other is a real
gap, and nothing in the corpus has ever met it.

## What the row asked

Q146 made a `cd` recognized-safe when its literal target resolves into the
same worktree. That is what lets the break-glass reach a command that opens
with a `cd`. The row found two Windows spellings of an absolute target for
which the relaxation does not fire. Both fail closed: the target lands on
`nongit`, and the command keeps the ask or deny it had before Q146.

| spelling | lexes to | relaxation fires |
|---|---|---|
| `cd D:\a\repo\wt` | `D:arepowt` | no |
| `cd 'D:\a\repo\wt'` | `D:\a\repo\wt` | yes |
| `cd D:/a/repo/wt` | `D:/a/repo/wt` | yes |
| `cd /d/a/repo/wt` (MSYS) | `/d/a/repo/wt` | no |

## Measured

**The unquoted backslash is bash's reading, not a lexer defect.** Bash removes
an unquoted `\` as an escape. Under `env -i "$(command -v bash)"`, which is
GNU bash 5.3.15, and under `/bin/bash`, which is 3.2.57, `set -- D:\a\repo\wt`
yields the one word `D:arepowt`. The shared lexer gives the same token:
`cd D:\a\repo\wt && git status` lexes to `['cd', 'D:arepowt', '&&', 'git',
'status']`. A `cd D:arepowt` then fails in bash 5.3.15 with "No such file or
directory", so in a `cd … && git …` chain git never runs. The guard's "not
this worktree" describes a command that does nothing. Git Bash is bash, so
the reading is the same there. Changing it would mean the guard parsing a
command differently from the shell that runs it.

**The MSYS spelling is a real gap.** Git Bash's MSYS runtime maps
`/d/a/repo/wt` to `D:\a\repo\wt` (the row's premise, not re-driven here,
since there is no Windows machine), and Python's `ntpath` does not. On Python 3.14.7,
`ntpath.isabs('/d/a/repo/wt')` is False. So `resolve_path`
(`plugins/branch-guard/hooks/branch-guard.py:def resolve_path(cwd, path):`)
joins it onto the session's cwd, and `ntpath.join('D:\\a\\x', '/d/a/y')`
normalises to `D:\d\a\y`, which exists nowhere. Before Python 3.13, by the
`ntpath.isabs` docs, a path with one leading slash counted as absolute. It
would then reach `realpath` and land on the current drive as `D:\d\a\y`, the
same nonexistent directory. That half comes from the docs: no Python older
than 3.14 was run.

**Nothing in the corpus meets it.** All 2,441 transcripts under
`~/.claude/projects/` were walked, reading the first `cwd` each one records.
2,434 are POSIX paths, 7 record none, and none starts with a drive letter. So
no Windows session has ever run on this machine. The CI job
`branch-guard-windows` is the only Windows evidence, and its fixtures pass
paths through the harness's `nat` helper, which exists to avoid sending this
spelling.

## The answer

**Measure (answered):** no Windows session hits this in the corpus. By the
row's own rule, neither half is worth the surface until one does.

- Drop the backslash half. It is the shell's own reading, and matching the
  shell is the guard's parsing model. It is not a `lib` change waiting to be
  made.
- Build the MSYS half only on the trigger above. When it fires, the change is
  confined to `resolve_path`: on Windows, rewrite a leading `/<letter>/` to
  `<letter>:/` before the absolute check. Add a `branch-guard-windows`
  fixture that sends `cd /d/…` raw, bypassing `nat`, with the `D:/` spelling
  beside it as the control.

The README needs no change for either half. It already says that a `cd` the
hook cannot place keeps its prompt, and the MSYS spelling is one of those.

## Notes

Found while fixing Q146's own fixtures, which failed on `branch-guard-windows`
because the suite put an absolute path into the command string bare, so the
hook received the MSYS spelling. `nat` repairs the suite. It cannot reach a
real session's `cd`, which the session writes itself.
