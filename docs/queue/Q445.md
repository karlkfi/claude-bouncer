# An assignment behind && or || is read as though it ran

The hook binds `NAME=value` whenever it reaches the group, so an assignment that a `&&` or `||` skips still replaces the value bash keeps.

Measured 2026-11-27 with the hook run against this checkout at `a593a83f`; `bash -c 'D=/etc/q8-fake; false && D=./a; echo "$D"'` printed `/etc/q8-fake`:

| command | verdict |
|---|---|
| `D=/etc/q8-fake; cat "$D/x"` (control) | ask |
| `D=/etc/q8-fake; false && D=./a; cat "$D/x"` | **allow** |
| `D=/etc/q8-fake; true \|\| D=./a; cat "$D/x"` | **allow** |
| `D=/etc/q8-fake; test -d x && D=./a; cat "$D/x"` | **allow** |
| `D=./a; false && D=/etc/q8-fake; cat "$D/x"` | ask |

An assignment inside `if` or a loop body already drops the name, so `D=/etc/q8-fake; if false; then D=./a; fi; cat "$D/x"` denies.
The last row shows the bind is not one-sided: an in-workspace value is replaced by an outside one, and that direction only asks too often.

Next step: an assignment group reached through `&&` or `||` drops the name instead of binding it, the way the compound bodies already do, so a later use keeps the runtime-expanded deny.

## If it is never built

A string that sets a path variable outside the project, then reassigns it in-workspace behind a test that fails, reads or writes outside with no prompt.
