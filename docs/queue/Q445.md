# An assignment behind && or || is read as though it ran

The hook binds `NAME=value` whenever it reaches the group, so an assignment that a `&&` or `||` skips still replaces the value bash keeps.

Measured 2026-11-27 with the hook run against this checkout at `a593a83f`; `bash -c 'D=/etc/q8-fake; false && D=./a; echo "$D"'` printed `/etc/q8-fake`:

| command | verdict |
|---|---|
| `D=/etc/q8-fake; cat "$D/x"` (control) | ask |
| `D=/etc/q8-fake; false && D=./a; cat "$D/x"` | **allow** |
| `D=/etc/q8-fake; true \|\| D=./a; cat "$D/x"` | **allow** |
| `D=/etc/q8-fake; test -d x && D=./a; cat "$D/x"` | **allow** |
| `D=./a; false && D=/etc/q8-fake; cat "$D/x"` | ask |

An assignment inside `if` or a loop body already drops the name, so `D=/etc/q8-fake; if false; then D=./a; fi; cat "$D/x"` denies.
The last row shows the bind is not one-sided: an in-workspace value is replaced by an outside one, and that direction only asks too often.

prod-guard fixed the same bug as Q301 in `00c94bc` (#307) by keeping both readings: where the list ends, the name holds its value before and after the assignment, and each later command is judged under both.
Its commit gives the reason against forgetting the name, which is that forgetting turns a deny into an ask.
The same holds here, where forgetting would give the runtime-expanded `deny` to `D=./a; false && D=./b; cat "$D/x"`, a pair that never leaves the project.

Next step: follow Q301.
An assignment group reached through `&&` or `||` gives the name both values where the list ends, and a later use is judged under each.
The loop-candidate map already judges a name under every value it may take, which looks like the place to hold the pair.
That is not yet measured against how the map is fed.
Dropping the name, as the compound bodies do, is the fallback if the pair cannot be carried there.
