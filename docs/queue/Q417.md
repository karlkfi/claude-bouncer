# A double-quoted bash -c body is judged before the caller expands it

The calling shell expands `$?` and `$NAME` inside a double-quoted `-c` string before the child shell runs, so a status re-raise written in double quotes reaches the child with its values already spent. exit-status-guard reads the body as the shell received it from the tokenizer, quotes removed and nothing expanded, so it credits that re-raise as though it had been single-quoted.
Found by the review of #379 (Q400), at its head `6b323c5`, and re-driven there on bash 5.3.15:

| command, backgrounded | bash exits on a failed gate | guard |
|---|---|---|
| `bash -c 'make check > log 2>&1; rc=$?; echo EXIT=$rc; exit $rc'` | the gate's status | silent, correctly |
| `bash -c "make check > log 2>&1; rc=$?; echo EXIT=$rc; exit $rc"` | 0 | silent |

With `false` in place of the gate, the double-quoted form prints `EXIT=` and exits 0, and the single-quoted one prints `EXIT=1` and exits 1.
In the double-quoted form the caller has replaced `$rc` with the empty string, so the child runs a bare `exit`.

**Who is worse off.** A session that writes the documented re-raise inside a double-quoted `bash -c`, as a body holding a single quote of its own has to be.
The task notification reports success for a failed gate, the false green rule 2 exists to catch, and it fails silent.

**Which way it gets built.** Some part of the body token has to say which characters the caller expanded. prod-guard already reads that from the shared lexer's token (`quotes` and `quoted_chars` on the body word), and it expands the parent's variables in a body with no single-quoted run.
The narrower fix is to give no credit to a `$?` capture or an `exit $NAME` in a body whose `$` sat in double quotes. Whether that alone is enough depends on the bare-`exit` case, which is filed apart as Q419, because a caller-expanded `exit $rc` becomes exactly that.
Not measured: which of the two shapes a fix should key on.
