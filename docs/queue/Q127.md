# Deny reasons never name the session override

All four reason builders advertise `PROD_GUARD_OVERRIDE` and none of them
mentions `PROD_GUARD_SESSION_OVERRIDE`, so an agent reading a deny reaches for
the per-command form every time -- including during a sanctioned batch, which
is the case the session variant exists for.

`deny_prod` already knows which denies qualify. It takes `grant_targets`,
passed only when the prod classification came from an explicit pin, and that is
exactly the eligibility condition for a session grant: the information needed
to name the session override is computed and then not surfaced.

Measured 2026-08-24 across the local transcripts, reason lines carrying
`override acknowledged` outnumber `session override acknowledged` 97 to 58.
Those are raw line counts over all history rather than decision counts -- a
reason can echo on more than one record -- so the ratio is the signal and the
totals are not. The session form is in use, so this is a default-path problem
rather than an undiscovered feature.

The fix is a clause in `deny_prod`'s reason, emitted only where `grant_targets`
is non-empty, naming `PROD_GUARD_SESSION_OVERRIDE` as the form that asks once
for a batch. The other three builders pass no `grant_targets` and must keep
advertising only the per-command form: an ambient or shared-state-switch deny
is deliberately not session-grantable, and offering the batch form there would
be wrong.
