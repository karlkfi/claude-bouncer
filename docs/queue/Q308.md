# worktree remove --force asks inside the session's own scratchpad

`git worktree remove --force` asks for every worktree, including one the
session made in its own scratchpad to check out a pull request. Reviewer
sessions do this at the end of every review, so the ask lands on the
maintainer once per reviewed PR.

Measured from 2026-09-25 to 2026-10-25: 51 asks across about 40 sessions,
mostly reviewers removing `<scratchpad>/prN`. Driven 2026-10-25 against
branch-guard 1.12.0: the `--force` form asks on a path under this session's
scratchpad, and the plain form allows
(`plugins/branch-guard/hooks/branch-guard.py:2025:if first == 'remove':`).

The ask guards uncommitted work, and in a session's own scratchpad that work
is the session's: nobody else writes there, and workspace-guard already denies
a write into another session's scratchpad. The untracked files a reviewer
leaves are build output.

## Which way it gets built

Allow `worktree remove --force` when the worktree path resolves under this
session's own scratchpad. Keep the ask everywhere else, including another
session's scratchpad and `.claude/worktrees/`.

"This session's scratchpad" is a fact two guards must agree on, so it moves to
`lib/`. workspace-guard already answers it with `is_session_tmp_path` and
`claude_tmp_root`
(`plugins/workspace-guard/scripts/bash-workspace-guard.py:438:def is_session_tmp_path(rp, session_id, tmp_root):`).
Lift those two into a shared module and have both guards call it. The path
check needs the resolved path, so a `$VAR` or `$(…)` operand keeps the ask.

**Who it is for:** the maintainer, who approves a reviewer's cleanup about 50
times a month and never refuses one. **If never built:** that keeps happening,
at the rate of reviews.
