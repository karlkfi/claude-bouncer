# The suppression escalation has no in-band break-glass

`WORKSPACE_GUARD_OVERRIDE` cannot downgrade or clear a suppression escalation.
`escalate_suppression(signal, mode)` never sees `ctx.override`, so the only
escape is `WORKSPACE_GUARD_ESCALATE=off`, which switches the whole mechanism off
rather than excusing one command.

Harmless while the verdict in attended modes is `ask`, since a prompt reaches
somebody who can answer it. It stops being harmless if anyone proposes flipping
that verdict to `deny` — which the `hook-verdict` skill's routing test invites,
because a deny's reason reaches the model where an ask's does not. The cases
left after Q211 are the ones a deny cannot fix: `docker run … bash -c`,
`ssh host '…'`. Neither has a "run the body as a plain command" rewrite, so a
deny with no override the model can apply in-band would strand the agent on
precisely the commands whose reason offers no repair.

So the two changes are coupled, and the order matters: an in-band override is a
precondition for any deny here, not a follow-up to it.

## What to evaluate

Threading `ctx.override` into `escalate_suppression` is mechanical. The
question is which tier it gets — see the two tiers `hook-verdict` describes —
and whether an override should clear the escalation outright or downgrade a
`deny` to an `ask`. The `bypassPermissions` arm already denies today, and it has
the same no-rewrite problem for a container or remote body, so the reasoning is
not hypothetical even before any flip.

**Settles:** compare against how the other four guards thread their override
into a verdict, then pick the tier.
