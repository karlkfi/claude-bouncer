# The escalation's bypass deny offers routes its reader cannot take

Q310 threaded `ctx.override` into the escalation
(`plugins/workspace-guard/scripts/bash-workspace-guard.py:3677:def escalate_suppression(signal, mode, override=None, prefixable=True):`),
on the terms settled below, as the precondition for denying the wrapper and
kill signals in `auto` and `acceptEdits`. What remains is the text every
escalation deny ends with.

## Which way it gets built

**Settles (answered).** The other four guards and this guard's own `decide()`
were compared on two questions: who may arm the override, and what it lands
on.

- **Tier: the existing inline override, no new variable.**
  `WORKSPACE_GUARD_OVERRIDE` is already model-settable from the command's
  prefix and already in `ctx.override`. The human-set tier exists too:
  `WORKSPACE_GUARD_ESCALATE=off` is read only from the hook's environment,
  which a session cannot set
  (`plugins/workspace-guard/README.md:1622:is the exception, and only in its prefix form above,`).
- **Destination: a deny downgrades to `ask`, and nothing clears.** That is
  what this guard's override already does for its cross-checkout categories
  (`plugins/workspace-guard/scripts/bash-workspace-guard.py:3776:cross_deny = (bool(cross_cats) and ctx.override is None`),
  and what prod-guard's does. foreground-guard's override defers and
  branch-guard's allows, but the cost of a wrong override there is a wait or a
  git operation. Here, clearing would run a body the hook says it cannot read,
  on the model's word. That is a loosening the plugin's secure-by-default rule
  keeps off the default.
- **`bypassPermissions` keeps its deny, override or not.** `decide()` already
  denies under bypass whatever `ctx.override` says, and prod-guard turns its
  downgraded `ask` back into a deny there
  (`plugins/prod-guard/scripts/bash-prod-guard.py:3245:if decision == 'ask' and data.get('permission_mode') == 'bypassPermissions':`),
  because an `ask` with nobody present strands the agent.

**What remains is the deny's tail.** Driven 2026-10-04 at `442c86e`, the
bypass deny for `docker run img sh -c 'cat notes.txt'` beside a guarded command
ends "Fix: run the body as a plain command so its paths are checked, or approve
this one. Set WORKSPACE_GUARD_ESCALATE=off to restore the silence." Neither of
those last two routes is available to its reader. There is nobody to approve
under bypass, and the agent cannot set a variable in the hook's environment.
Since Q310 the wrapper and kill denies in `auto` and `acceptEdits` drop
"or approve this one" and name the override instead, but still close on the
same `WORKSPACE_GUARD_ESCALATE=off` sentence
(`plugins/workspace-guard/scripts/bash-workspace-guard.py:3752:"%s Set WORKSPACE_GUARD_ESCALATE=off to restore the silence."`).
Under bypass, drop "or approve this one". On every deny, name
`WORKSPACE_GUARD_ESCALATE=off` as something the operator sets before the
session starts, not something the agent can do. Pin each verdict's wording
with a test.

**Who is worse off:** an agent under `bypassPermissions` that meets a container
or remote body. The reason offers it two routes it cannot take, so it either
stalls or tries an inline `WORKSPACE_GUARD_ESCALATE=off`, which does nothing.
**If never built**, that costs a wasted retry each time a bypass session meets
one. Q209's replay found 99 escalating commands in 198,868 over 60 days, and
only the bypass share of those reaches this text. Flat.

Rank: it keeps its place. It is a reason-text change, and the
release note should say that the bypass deny now names only routes the agent
can take.
