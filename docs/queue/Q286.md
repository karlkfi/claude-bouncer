# foreground-guard judges the command behind sudo -l, -v and -U

`sudo -l` lists privileges, `sudo -v` refreshes the timestamp, and `-U` is
valid only beside `-l`, so none of them runs the command after it.
foreground-guard has no run-nothing modes for sudo. Its `strip_head` peels
sudo's options and judges what follows
(`plugins/foreground-guard/scripts/bash-foreground-guard.py:446:        elif head == 'sudo':`),
so a listing query about a watch command is denied as the watch.

Driven 2026-10-05 through the hook at `origin/main` `aa935df`:

| command | guard |
|---|---|
| `tail -f log.txt` -- control | deny |
| `sudo -l tail -f log.txt` | **deny** |
| `sudo --list tail -f log.txt` | **deny** |
| `sudo -v tail -f log.txt` | **deny** |
| `sudo -U bob -l tail -f log.txt` | silent |

The last row is silent only because `-U` was missing from this guard's value
table, so `bob` was read as the command. Q233 gives it sudo's real `-U` arity,
after which the same command denies like the others.

prod-guard (`SUDO_RUN_NOTHING`) and exit-status-guard (`RUN_NOTHING`) already
stop at these modes.

## Which way it gets built

Stop peeling at sudo's run-nothing modes, the way exit-status-guard's
`wrapper_operands` does: walk the short word a character at a time, stopping
at the first value-taking letter, and return before the command on `l`, `v`,
`e`, `K` or `U` and their long forms.

## If it is never built

A session asking sudo whether it may run a watch gets denied as if it had run
it. The fix it is handed, backgrounding the command, does not apply, so the
denial costs a retry with nothing to change. `sudo -l <cmd>` is rare in an
agent's commands.
