# `x=$(…);` or `cat <(…);` before a git command hides it from branch-guard

branch-guard asks before `git commit` on `main`. With `x=$(true);` or
`cat <(true);` in front of it, the hook returns no decision. With `echo a;` or
`echo $(true)b;` in front of it, the hook still asks. bash runs the commit in
all four cases.

The module docstring says a command or process substitution "downgrades a
would-be `allow` to defer". These rows downgrade an `ask`, which that sentence
doesn't describe. The mechanism has not been traced: the substitution itself
isn't enough, since `echo $(true)b;` keeps the ask.

Found 2026-10-04 while driving the Q264 shapes through every hook. bash runs
are under `env -i /opt/homebrew/bin/bash --norc --noprofile -c`, which prints
`5.3.15(1)-release`. The hook ran on `origin/main` at `8c4d8f4` in a fresh
repository on branch `main`, with `P` set to `git commit -m x`:

| command | bash runs P | branch-guard |
|---|---|---|
| `echo a; P` -- control | yes | ask |
| `echo $(true)b; P` | yes | ask |
| `x=$(true); P` | yes | **defer** |
| `cat <(true); P` | yes | **defer** |
| `x=$(cat <(echo a)); P` | yes | **defer** |

## Which way it gets built

Trace where the two deferring shapes leave the classifier before choosing a
fix. The likely candidates are the substitution downgrade being applied to an
`ask`, or an assignment-only or process-substitution segment ending the walk.
Either way, a segment that cannot be judged should not erase a later
segment's `ask`.

## If it is never built

Any `x=$(…);` in front of a `git commit` on `main` removes branch-guard's
prompt, and agents write that prefix routinely.
