# prod-guard's comment masking no longer changes a verdict

`_strip_comments` in prod-guard masks every command substitution before it
calls the shared `strip_comments`, then puts the text back. Q224 added it because
`strip_comments` read a `#` inside backticks as a comment. Q254 taught
`strip_comments` to hold a backtick span and a `${...}` whole, and Q257 a
`$(...)` inside double quotes, which were the two cases the masking covered.

Measured 2026-10-05 on the Q257 branch, stacked on Q254: with the first line of
`_strip_comments` replaced by `return strip_comments(raw)`, prod-guard's suite
passed (525 tests). On the 22 shapes driven for Q254 and Q257, prod-guard gave
the same verdict as with the masking in place: 21 deny, and 1 defer where bash
does not run the command either. Nothing was driven beyond that. In
particular, no expanded heredoc body was tried, and those are the one caller
that passes `quotes=False`.

## Which way it gets built

Find a shape where the masking still changes a verdict, starting with an
unquoted heredoc body that holds a substitution and a quote character. If one
exists, pin it with a test and say so in the docstring. If none does, delete
the masking and call `strip_comments` directly, so prod-guard reads comments
the way the other guards do.

## If it is never built

A 15-line function keeps running on every command: an extra
`command_substitutions` scan plus a mask and an unmask. Nothing proves any of
it is needed, so a later change to it would be tested against nothing. Flat cost of delay; nobody meets it in a session.
