# A git global option before the subcommand hides the gate

Every git row in the `gates` registry is anchored on `git` followed directly by
the subcommand
(`plugins/exit-status-guard/exit-status-guard.json:41:    "^git\\s+(pull|push|rebase|merge|cherry-pick|apply|am|commit|revert|add|stash|clone|fetch|checkout|switch|worktree|reset)(\\s|$)",`).
A global option between the two means the pattern never matches. Every rule
then treats the command as having no gate. Driven 2026-11-16 against the hook
at `5ac40bdd`, which is Q351's branch, with `git commit -m x | tail` denied
beside them as the control:

- `git -C . commit -m x | tail` is silent.
- `git -c user.name=x commit -m y | tail` is silent.
- `git --no-pager pull | tail` is silent.

Review of PR #342 found the same commands silent on `main` at `be1be080`, along
with `git -C sub push | tail`. git runs each of them as the plain subcommand.

**Who is worse off.** A session working in another checkout through `git -C`,
which is how a worktree session reaches the main checkout, and a session that
adds `--no-pager` to keep output out of a pager. Either one loses the exit
status the guard exists to keep. That is a missed deny, so it fails silent.
`git -C` is an ordinary spelling in agent sessions, so this is met more often
than the probe-word miss in Q366.

**Next step.** Match the gate after skipping git's global options: `-C <path>`,
`-c <k=v>`, `--git-dir`, `--work-tree`, `--no-pager`, `-P`, `--bare`, and the
rest of `git --help`'s list. Count from the subcommand wherever a word position
is read. Q350's completion-helper test is `len(words) == 3`, and it would
otherwise deny `git -C . checkout --git-completion-helper-all`, which git
honours; that interaction is not measured. Pin the four commands above as
denies, and keep `git -C . log | tail` silent.
