# Drop the `-Recurse` entry-role withdrawal: the target survives

`Remove-Item -Recurse` over a directory link unlinks the entry. It does not
walk into the target, on either PowerShell, for either kind of link.

Measured 2026-08-24 in CI run 32692159539 by
`plugins/workspace-guard/tests/test_windows_link_semantics.py`, which creates a
link at a sibling directory holding one file, runs `Remove-Item -Recurse` on
the link, and reads the file before anything is cleaned up. Eight observations
-- both Windows jobs, both hosts, both link kinds -- and every one reported the
link gone, `rc=0`, empty stderr, and the target's directory and file intact:

| Host | Junction | Symlink |
|---|---|---|
| Windows PowerShell 5.1.26100.33296 | link removed, target intact | link removed, target intact |
| PowerShell 7.6.5 | link removed, target intact | link removed, target intact |

The same run carried an inverted copy of each assertion, claiming the target
was reached, and all four went red on these exact observations. So the answer
is a measurement rather than a green run that would have been green either way.

## What is left

Q76 gave `Remove-Item`/`Move-Item`/`Rename-Item` an entry role -- a link
operand is judged as the link rather than by its target -- and withdrew it
whenever `-Recurse` was bound, because this was the one shape where the
premise behind the role was unestablished. The premise holds, so the
withdrawal has nothing left to protect. Two edits, both in
`plugins/workspace-guard/scripts/bash-workspace-guard.py`:

- **Drop the `recursive` pre-pass in `ps_bind_args`** and let `-Recurse` take
  the entry role like any other operand. `Remove-Item -Recurse ./dirlink`
  currently asks where `rm -rf ./dirlink` allows; that was the last of the
  eight shapes Q76 measured as divergent, and this closes it.
- **Correct the comment above it**, which still says the question cannot be
  settled here:
  `plugins/workspace-guard/scripts/bash-workspace-guard.py:4461:cannot settle from here (Q114)`.
  It should carry the answer and the run that measured it.

`test_workspace_guard.py` has two assertions pinning the current behaviour --
`test_recurse_withdraws_the_entry_role` expects `ask` from PowerShell against
`allow` from Bash, and `test_recurse_withdraws_the_flag_from_every_operand`
pins the bind-level withdrawal across every spelling of the switch. Both flip
with the guard, and the first becomes a parity assertion rather than a
deliberate divergence.

## Why the row said this was unmeasurable

It claimed the repo had no Windows host. It has had two the whole time:
`.github/workflows/tests.yml` runs the workspace-guard suite on
`windows-latest` twice, `workspace-guard-windows` under pwsh and
`workspace-guard-windows-gitbash` under Git Bash, with both PowerShell hosts on
the PATH of each. The 2026-08-23 measurement behind the claim was of the
*workstation*, where PowerShell is absent and a junction cannot be created,
which says nothing about what CI can run. The experiment sat in the row as an
instruction to a future session for as long as it could have been a test.
