# Does PowerShell `-Recurse` follow a directory link when deleting?

Q76 gave `Remove-Item`/`Move-Item`/`Rename-Item` an entry role, so a symlink
operand is judged as the link rather than by its target. The role rests on one
premise, stated in
[the plan](../../plugins/workspace-guard/docs/plan/entry-operands.md): the
command unlinks the entry and cannot reach what it points at. POSIX `rm -rf
dirlink` behaves that way -- it removes the link.

Whether `Remove-Item -Recurse` over a directory link does the same on Windows
is the open question. It has a long-reported history of recursing into the
target instead, and this repo has no Windows host to settle it from: measured
2026-08-23 on macOS, where PowerShell is not installed and a junction cannot be
created.

So Q76 withdraws entry treatment whenever `-Recurse` is bound, and that is a
deliberate divergence from Bash rather than an oversight. `Remove-Item -Recurse
./link` asks where `rm -rf ./link` allows. The asymmetry is what decided it:
declining the exemption costs one prompt on a rare shape, and assuming it away
would cost a silent `allow` on a recursive delete reaching outside the root.

To close this, run on a real Windows host with a junction and a symlink into a
sibling directory, on a supported PowerShell:

    New-Item -ItemType Junction -Path .\j -Target ..\outside
    Remove-Item -Recurse .\j          # does ..\outside survive?

If the target survives, drop the `recursive` guard in `ps_bind_args` and let
`-Recurse` take the entry role like any other operand, restoring Bash parity.
If it does not, keep the guard and say so in its comment, which currently cites
this row as unresolved. Either way the answer belongs beside the code, because
the next reader will otherwise re-derive it from the same absent evidence.
