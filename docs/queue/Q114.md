# Does PowerShell `-Recurse` follow a directory link when deleting?

Q76 gave `Remove-Item`/`Move-Item`/`Rename-Item` an entry role, so a symlink
operand is judged as the link rather than by its target. The role rests on one
premise, stated in
[the plan](../../plugins/workspace-guard/docs/plan/entry-operands.md): the
command unlinks the entry and cannot reach what it points at. POSIX `rm -rf
dirlink` behaves that way -- it removes the link.

Whether `Remove-Item -Recurse` over a directory link does the same on Windows
is the open question. It has a long-reported history of recursing into the
target instead.

So Q76 withdraws entry treatment whenever `-Recurse` is bound -- the guard is
the `recursive` pre-pass in `ps_bind_args`. `Remove-Item -Recurse ./link` asks
where `rm -rf ./link` allows.

Read that as a residual, not as a new risk. Before Q76 the PowerShell frontend
diverged from Bash on *every* one of these shapes, because every operand
resolved and the target sat outside: measured 2026-08-23 across eight of them
-- link, dangling link, directory link, move, rename, `-LiteralPath`, and the
two `-Recurse` forms -- **8 of 8 diverged before, 2 of 8 after**. Q76 removed
the divergence everywhere it could establish the premise the entry role rests
on, and left it standing on the two shapes where it could not. Closing this row
closes what is left of an existing gap rather than reviewing something Q76
introduced.

The asymmetry is what decided the default: keeping the guard preserves a prompt
that already existed on a rare shape, and dropping it would newly permit a
recursive delete reaching outside the root.

## The premise this row was filed on was false

The row said this repo had no Windows host to settle the question from. It has
had two the whole time. `.github/workflows/tests.yml` runs the workspace-guard
suite on `windows-latest` twice -- `workspace-guard-windows` under pwsh and
`workspace-guard-windows-gitbash` under Git Bash -- and both PowerShell hosts
are on the PATH of each. The 2026-08-23 measurement behind the claim was of the
*workstation*, where PowerShell is absent and a junction cannot be created, and
that says nothing about what CI can run.

The same claim sits in the code, and correcting it is the rest of this row:
`plugins/workspace-guard/scripts/bash-workspace-guard.py:4332:cannot settle from here (Q114)`.

So the experiment is a test rather than an instruction now.
`plugins/workspace-guard/tests/test_windows_link_semantics.py` creates a
junction at a sibling directory holding one file, runs `Remove-Item -Recurse`
on the junction, and then reads the file. Four things it does deliberately:

- **Both hosts.** `powershell.exe` is Windows PowerShell 5.1 and `pwsh.exe` is
  PowerShell 7 -- separate products with separate histories, and the guard has
  to be right for whichever one the user is in.
- **Fails rather than skips on Windows.** The two Windows jobs ratchet a skip
  ceiling, so a probe that stood down on the one platform it is about would
  spend that ceiling to assert nothing.
- **The junction carries the answer, and the symlink is labelled separately.**
  `New-Item -ItemType Junction` needs no elevation; `-ItemType SymbolicLink`
  needs admin or Developer Mode and a runner may refuse it, so it cannot be
  load-bearing.
- **Teardown cannot manufacture the result.** The target is read before
  anything is cleaned up, and the link is then removed with `os.rmdir`, which
  has no recursive mode and cannot descend into what it points at.

## What each answer means

If the target survives, drop the `recursive` guard in `ps_bind_args` and let
`-Recurse` take the entry role like any other operand, restoring Bash parity.
If it does not, the guard is correct as it stands and the comment says so
instead of citing this row as unresolved. Either way the answer belongs beside
the code, because the next reader will otherwise re-derive it from the same
absent evidence.
