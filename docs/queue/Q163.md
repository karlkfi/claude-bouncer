# A cancelling `+n` is missed, because noexec is read first-match

`shell_noexec` returns on the first option carrying noexec
(`plugins/foreground-guard/scripts/bash-foreground-guard.py:698:if 'n' in opt[1:] or ('o' in opt[1:] and arg == 'noexec')`),
so it never sees a later token that turns noexec back off. bash resolves its
options last-wins, so `bash -n +n gate.sh` really does run the script while the
guard reads it as parse-only and defers.

That is Q149's class — silence on a command that runs — reached by a different
mechanism. Q149 was the peel not reading option *arity*; this is `shell_noexec`
not reading option *order*, and the Q149 fix does not close it.

## Measured

2026-09-04, against this tree with the README's own registration
`{"scripts/gate\\.sh": 3600000}`. `want` is what bash itself does, measured
first — whether `gate.sh` runs:

| command | guard | bash runs it? | |
|---|---|---|---|
| `bash -n scripts/gate.sh` | defers | no | correct |
| `bash +n scripts/gate.sh` | deny | yes | correct |
| `bash +n -n scripts/gate.sh` | defers | no | correct |
| `bash +o noexec -o noexec scripts/gate.sh` | defers | no | correct |
| `bash -n +n scripts/gate.sh` | **defers** | **yes** | **missed** |
| `bash -o noexec +o noexec scripts/gate.sh` | **defers** | **yes** | **missed** |

Both directions of the cancellation were driven against GNU bash 5.3.15 rather
than assumed, which is what establishes last-wins rather than "a trailing `+n`
wins":

    bash -n +n -c 'echo T2_RAN'                  -> T2_RAN     (runs)
    bash -n    -c 'echo T2C_RAN'                 -> (nothing)  control
    bash +n    -c 'echo T2D_RAN'                 -> T2D_RAN    control
    bash +n -n -c 'echo T2E_RAN'                 -> (nothing)  noexec comes back on
    bash -o noexec +o noexec -c 'echo T2F_RAN'   -> T2F_RAN    same for the -o form

The `-o` form is half the defect and is easy to miss: a fix that special-cases
the `-n` letter alone leaves `bash -o noexec +o noexec gate.sh` deferring.

## Who is worse off

Whoever registered the gate, as in Q149 — but this token is reachable
deliberately, which Q149's was not. `foreground-guard` ships
`FOREGROUND_GUARD_OVERRIDE` as the sanctioned way past a finding, and that
leaves an attributable trace in the reason. `-n +n` leaves none: the guard
emits nothing at all, so no friction report can count it and nothing
distinguishes it from a command that was never guarded. Q148 kept an equally
pathological case in a sibling guard on that reasoning — the token is the only
thing between a command and a deny, so it is the one an agent reaches for once
a deny is otherwise unavoidable.

Rate is low. It needs somebody to write `-n` and `+n` in one invocation, which
is close to meaningless except as a bypass.

## Which way it gets built

Track the state across the whole option list instead of returning early — set
it on each `-n`, each `-o noexec`, and each cluster carrying `n`, clear it on
the `+` forms of the same, and return what is left at the end. Roughly:

    noexec = False
    for opt, arg in opts:
        if opt.startswith('--'):
            continue
        if 'n' in opt[1:] or ('o' in opt[1:] and arg == 'noexec'):
            noexec = opt[0] == '-'
    return noexec

That shape is **unverified** — it is written from the measurement above rather
than driven, and it has not been run against the suite. It reads correctly on
each row of the table, but treat it as a starting point and drive it, including
the two `correct` rows that a careless last-wins rewrite would break.

The existing tests to keep green are `test_parse_only_run_defers`,
`test_script_own_dash_n_still_runs`, `test_plus_options_still_run` and
`test_noexec_through_an_option_argument_defers`.

## If it is never built

The guard keeps a silent, unattributable bypass, and `shell_noexec`'s docstring
keeps having to warn readers that it reads first-match — which is where Q149
left it, deliberately, rather than fixing order in a diff scoped to arity.
