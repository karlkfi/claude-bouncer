# An escaped `$` in a double-quoted `bash -c` body hides a vanishing word

Inside double quotes bash removes the backslash from `\$`, so
`bash -c "\$X kubectl …"` hands the child `$X kubectl …`, and with `X` unset
the child runs kubectl. That is the shape Q298 fixed, one quoting level down.
prod-guard reads the body with the backslash still in, so `$X` is an escaped
word rather than one that may expand to nothing, and the command defers.

Found by the prod-guard reviewer on the Q298 pull request (#288), and
re-measured 2026-11-01 on the Q290 branch at `a4ad697`, fixture `$HOME` with
current context `gke_acme_prod-us`; `<prod delete>` is
`kubectl --context=gke_acme_prod-us delete pod x`:

| command | bash 5.3.15 | guard |
|---|---|---|
| `bash -c '$X <prod delete>'` (control) | runs it | deny |
| `bash -c "\$X <prod delete>"` | runs it | **defer** |
| `eval "\$X <prod delete>"` | runs it | **defer** |

The bash column ran each with `/bin/echo` in place of kubectl under
`env -i /opt/homebrew/bin/bash --norc --noprofile`, with the inner `bash` on
`/opt/homebrew/bin`. Both printed `RAN`.

## Where it happens

Python's `shlex` keeps the backslash in posix mode:
`shlex.split('bash -c "\\$X kubectl"')` returns `['bash', '-c', '\\$X kubectl']`.
Bash removes the backslash before `$`, `` ` ``, `"`, `\` and a newline inside
double quotes. Not measured: whether the shared `QuoteTrackingLexer` in
`lib/bouncer_parse.py` is where to fix it, and so whether the other four
guards see the same body. Settle that before labelling the row `lib`.

## If it is never built

A production command behind an unset variable inside a double-quoted
`bash -c` or `eval` body passes silently. It takes an escape the author had
to write on purpose, so it is rarer than Q298's top-level shape.
