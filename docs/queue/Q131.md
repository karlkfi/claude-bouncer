# A double-quoted `bash -c` body loses the parent's expansions

`evaluate_command_string` treats a shell's `-c` body as a child process
"inheriting only exported vars", and passes it `child_env`. That is right for a
single-quoted body, where the child does the expanding and an unexported name
really is unset. It is wrong for a double-quoted one: the *parent* expands
`$CTX` while building the argument, so the resolved value reaches the tool
whether or not the name was ever exported.

Probed 2026-08-24 against a temp HOME, one assignment and four spellings of the
same command:

| command | hook | bash |
|---|---|---|
| `C=gke_acme_prod-us; kubectl --context $C delete pod x` | deny | prod |
| `export C=…; bash -c 'kubectl --context $C …'` | deny | prod |
| `C=…; bash -c "kubectl --context $C …"` | **ask** | prod |
| `C=…; bash -c 'kubectl --context $C …'` | ask | unset |

Only the third row disagrees with the shell. The guard fails safe -- an ask is
still a prompt, and `bypassPermissions` escalates it back to a deny -- so this
is not a bypass. What it costs is the deny a production target is owed, and a
reason that tells the reader the target "matches neither a production nor a
non-production pattern" when it matches a production one.

It is also the whole of the unresolved-target friction in the local
transcripts: measured 2026-08-24 over a 365-day window, all 16 such prompts
were this shape -- a double-quoted `-c` body with the assignment in the same
command string. Q128, completed in the pull request that filed this row, read
those same 16 as assignments made in an earlier Bash call the hook never saw.
That reading was never measured and holds for none of them.

The fix is to expand a double-quoted `-c` body against the full segment env
rather than `child_env`, which needs the quoting context the body was written
in -- so it turns on what the tokenizer hands back, not on `evaluate_command_string`
alone.
