# Move the wrapper option tables and arity walk into lib

Four guards peel command wrappers (workspace-guard, the fifth, peels none:
Q219), and each keeps its own table of which wrapper options take a separate
value. Each older guard has an open row where
its table is wrong, and the mistakes go both ways: a value the table misses
leaves it standing as the command (`sudo -u root git`), and a value the table
invents swallows the command (`env -i git`). Either one hides the command from
the guard.

These open rows are the same defect, one guard at a time:

| row | guard | the table's gap |
|---|---|---|
| Q160 | foreground-guard | separate-value flags on `PLAIN_WRAPPERS` |
| Q221 | foreground-guard | a value flag inside a bundle (`-nu root`) |
| Q222 | exit-status-guard | drops no option at all |
| Q228 | prod-guard | abbreviated long options (`--us root`) |
| Q229 | prod-guard | `nice` is not a wrapper |
| Q219 | workspace-guard | no peel |

Q158 (`sudo -h`) is the one arity call that has no right answer, so whatever
lib decides there is the answer for every guard.

Another gap, measured 2026-10-04 at `442c86e` by driving prod-guard with an
empty `$HOME`, so the `--context=` flag is the only target:

| command | guard |
|---|---|
| `sudo kubectl --context=gke_acme_prod-us delete pod x` | deny -- control |
| `sudo -u root kubectl --context=gke_acme_prod-us delete pod x` | deny -- control |
| `sudo -r role kubectl --context=gke_acme_prod-us delete pod x` | **(silent)** |

`WRAPPER_VALUE_FLAGS['sudo']` has no `-r` (SELinux role). It also lacks `-t`,
`-a` and `-c`, which sudo's usage line lists as taking a value. Only `-r` was
driven.

The Q223 fix gave branch-guard a sixth table, `WRAPPER_VALUE_OPTS`, plus a
`wrapper_option` walk. The walk reads short options one character at a time
and matches long options by unique prefix, the way prod-guard's `flag_arity`
does after Q200 and Q228's proposal would. That is the second guard needing
the same behaviour, so by `CLAUDE.md`'s rule for `lib/` it can now move.

## Which way it gets built

Move the data and the per-word arity function to `lib/bouncer_parse.py`. That
is the wrapper → value-option table and a `wrapper_option(argv, value_opts)`
returning words consumed, the option and its value. The peel loop stays in
each guard. What a guard does with what it peeled is where they differ:

- prod-guard merges `env` assignments into the target's environment and stops
  at sudo's run-nothing modes.
- foreground-guard carries state through the loop.
- branch-guard turns a wrapped `allow` into a defer and stands its probes down
  behind a chdir option.

Forcing one loop onto those would repeat the drift `CLAUDE.md` describes for
segmentation. Each guard row above then shrinks to "use the shared table",
plus whatever wrapper that guard does not peel yet.

## If it is never built

Every new wrapper option gets fixed six times, and each guard misses it
until somebody drives that guard. Today that leaves `sudo -r` hiding a
production delete from prod-guard.
