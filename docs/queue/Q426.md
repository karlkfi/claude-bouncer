# prod-guard never expands a glob a held command word holds

An unquoted expansion goes through pathname expansion after the split, so `X="/usr/local/bin/kubect*"; $X …` runs `/usr/local/bin/kubectl` wherever that file exists. prod-guard reads the command word as `kubect*`, which names no covered tool.
Measured 2026-11-26 through the hook, on Q382's branch at `dcdfcdf`:

| command | prod-guard |
|---|---|
| `X="/usr/local/bin/kubect*"; $X --context gke_acme_prod-us delete ns x` | **defer** |
| `X="/usr/local/bin/kubectl"; $X --context gke_acme_prod-us delete ns x` (control) | deny |

bash expanded it: with a symlink to `/bin/echo` named `fakekubectl` in a scratch directory, `X="<dir>/fakekub*"; $X RAN` printed `RAN`.
The guard takes the tool from `os.path.basename(argv[0])` with no glob handling.

## Which way it gets built

The hook cannot read the filesystem the command would glob against without changing what it is (no access beyond local config reads), so match instead: when a command word that came from an unquoted expansion holds `*`, `?` or `[`, judge it as every covered tool whose name the basename pattern matches, via `fnmatch`.
A pattern matching none defers as now.

## If it is never built

A production mutation runs with no prompt when the tool's name is written as a glob inside a variable.
That is an adversarial shape; no session writes a command word that way by accident.
