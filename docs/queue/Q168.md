# A `KUBECONFIG` the command exports is not the file the guard reads

`kubectl` reads the kubeconfig its environment names. The guard reads the one
the *segment's inline prefix* names, and otherwise the hook's own environment,
so `export KUBECONFIG=<path>; kubectl apply …` is classified against
`~/.kube/config` while the command runs against `<path>`. When the two files
disagree about `current-context`, the deny names a target the command never
touches -- on the measured call, a production one.

## Measured

2026-09-07, prod-guard 2.5.2, a `github-actions-gateway` session (worktree
`gallant-knuth-52593f`, working Q1015 there). One Bash call:

```
export KUBECONFIG=/Users/karl/workspace/github-actions-gateway/.claude/worktrees/gallant-knuth-52593f/tmp/q1015/kubeconfig; kubectl config current-context; kubectl apply -f tmp/q1015/infra.yaml; ...
```

The file named by the literal path had `current-context: kind-q1015-calico`
(written by `kind` via `KUBECONFIG=<path> make e2e-cluster
KIND_CLUSTER=q1015-calico KIND_CNI=calico`).

Denial text:

> prod-guard: `kubectl apply` targets the ambient kube-context (currently
> 'gke_actions-gateway-dogfood_us-east1-b_gag-dogfood') (ambient), which
> matches a production pattern. Mutating commands against production targets
> are blocked. If this is intentional, prefix the command with
> PROD_GUARD_OVERRIDE=<reason> to downgrade the block to a confirmation prompt.

Expected: resolve the context from the file a literal `KUBECONFIG=<path>`
assignment (or `export KUBECONFIG=<path>`) earlier in the same command names,
the way workspace-guard resolves a variable assigned a plain literal earlier in
the command string, and evaluate that context against the patterns.
github-actions-gateway's `docs/development/kind-iteration.md` recommends
exactly this private-kubeconfig recipe for e2e runs, so every session following
it meets this deny. Workaround used: `kubectl --kubeconfig <path> --context
kind-q1015-calico ...` on every call, which the guard accepted. A
`--kubeconfig <path>` flag without `--context` is worth checking in the same
row: whether the guard reads the file's current-context or falls back to
ambient.

## Reproduced

Against the hook at c3a3615 with a fixture `$HOME` whose `~/.kube/config` has
`current-context: gke_actions-gateway-dogfood_us-east1-b_gag-dogfood` and a
second file `<kc>` with `current-context: kind-q1015-calico`. Nothing
executed.

| command | context the reason names | verdict |
|---|---|---|
| `export KUBECONFIG=<kc>; kubectl config current-context; kubectl apply -f x.yaml` | gke (ambient) | deny, pin `--context` |
| `KUBECONFIG=<kc>; kubectl apply -f x.yaml` | gke (ambient) | deny, pin `--context` |
| `KUBECONFIG=<kc> kubectl apply -f x.yaml` | **kind-q1015-calico** | deny, pin `--context` |
| `kubectl --kubeconfig <kc> apply -f x.yaml` | gke (ambient) | deny, pin `--context` |
| `kubectl --kubeconfig <kc> --context kind-q1015-calico apply -f x.yaml` | -- | silent |
| `kubectl apply -f x.yaml` (control) | gke (ambient) | deny, pin `--context` |

The fixture's `gke_…` name does not match the built-in production patterns, so
the fixture gets the pin deny where the live session got the production one;
the file being read is the same in both.

Two defects and a design question, and the third row is what separates them.

**The file.** `_kubeconfig_paths` reads `KUBECONFIG` from the dict it is
handed and falls back to the hook's own environment
(`plugins/prod-guard/scripts/bash-prod-guard.py:676:kc = seg_env.get('KUBECONFIG') or os.environ.get('KUBECONFIG')`),
and the evaluator is handed the segment's inline prefix only
(`plugins/prod-guard/scripts/bash-prod-guard.py:2492:findings += evaluator(argv, seg_inline, ctx)`).
An `export` earlier in the command lands in `exported` and `shell_env`, which
is what `child_env` is built from, and `child_env` is what a child process such
as `kubectl` actually inherits -- so it is the right dict and the evaluator
never sees it. The prefix form works because the prefix *is* `seg_inline`. The
bare `KUBECONFIG=<kc>;` row is correct as it stands: a shell variable that was
never exported does not reach `kubectl` either, unless the name was already in
the environment, which the guard cannot know.

**The flag.** `--kubeconfig` is listed only so its value is not mistaken for a
verb
(`plugins/prod-guard/scripts/bash-prod-guard.py:1350:'--context', '--kube-context', '--kubeconfig', '-n', '--namespace',`);
`_kube_target` reads the context flags and nothing else
(`plugins/prod-guard/scripts/bash-prod-guard.py:1508:ctx = first_flag_value(argv, context_flags)`),
so the file the flag names is never opened and the fourth row reads
`~/.kube/config`.

**The pin.** Fixing both reads on its own changes which context the reason
names, and not the verdict. The third row shows why: the prefix form already
resolves `kind-q1015-calico`, and an unpinned mutation is denied whatever the
ambient context is -- that is the design
(`plugins/prod-guard/docs/design.md:91:### Why an unpinned mutation is denied, not prompted`),
and the README's own table has the kind case
(`plugins/prod-guard/README.md:132:| `kubectl delete pod x` (ambient kind context, no `--context`) | **deny** (pin `--context`) |`).
So the expectation above -- evaluate the resolved context against the patterns
and defer on nonprod -- holds only if a kubeconfig the command itself names
counts as pinning the target.

**Ask (answered):** it does, decided 2026-09-07 when this row was filed. The
design's argument against the ambient context is that it is shared mutable
state a parallel session can repoint between writing the command and running
it. A kubeconfig named by path in the command is not shared with any session
that does not also name it, which for the gateway recipe means one worktree, so
its `current-context` is as stable as the `--context` value the guard already
accepts. The cost accepted with it: the file is still one `kind` rewrites, and
reading it widens what the guard defers on.

## Which way it gets built

Three changes in `bash-prod-guard.py`, no parser change.

1. Hand the evaluators the env a child inherits -- `child_env`, which already
   holds every `export` earlier in the command on top of the hook's own
   environment -- in place of `seg_inline`. The kube readers then see an
   exported `KUBECONFIG`; a bare, never-exported `KUBECONFIG=<kc>;` keeps
   reading `~/.kube/config`, which is what `kubectl` would read too. Check
   the other readers that take the same dict (`gh_strict_enabled`,
   `aws_profile_fields`, `_kubeconfig_paths`): each already falls back to
   `os.environ`, so the widening is only ever an export they could not see
   before.
2. Read `--kubeconfig <path>` in `_kube_target`, and let its file stand in
   for `$KUBECONFIG` when the flag is present. Its `current-context` then
   goes through `classify_kube` like any other, and the server URL resolves
   against the same file.
3. Treat a kubeconfig the command names -- by either route -- as a pin: defer
   when the file's current-context classifies nonprod, deny when prod, and
   keep the pin deny for a command that names no file and no `--context`. The
   reason for a prod hit should say which file the context came from, the way
   the `--context` form says `(from --context)`.

Table cases in both directions for each route: the six rows above, plus a
prod current-context in the named file, a file that does not exist (an
unresolvable target is an ask, as today), and `--kubeconfig` with a relative
path. The README's decision table gains the named-file rows beside the
ambient-kind one it already has.

Frequency, from a sweep of every transcript under `~/.claude/projects` on
2026-09-07 (1,901 files): 63 ambient-kube-context denials, 8 of them on a
command that set `KUBECONFIG` -- 5 by `export`, 2 as a prefix -- all in
`github-actions-gateway`, between 2026-07-29 and 2026-09-07. Seven got the pin
deny; the one above got the production deny, because that day's
`~/.kube/config` pointed at the dogfood cluster. That is the accruing half: the
recipe is written down in that repository's docs, so every e2e session there
meets it, and a session that overrides a *production* deny to reach a kind
cluster is being taught the override is routine.

## If it is never built

Every session following the kind-iteration recipe rewrites each `kubectl`
call to carry `--kubeconfig <path> --context <name>`, which works and is what
the deny asks for. The cost is the reason: a production target named for a
command that targets a kind cluster, on the one deny whose override presents a
human with that claim.
