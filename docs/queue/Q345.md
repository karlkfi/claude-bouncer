# A relative New-Item -Target may resolve from the wrong directory

Q326 found that a relative `ln -s` target is read by the kernel from the
directory the link sits in, while workspace-guard read it from the cwd, and
fixed the bash side. The PowerShell side has the same question for
`New-Item -ItemType SymbolicLink -Path LINK -Target TARGET`: the hook binds
`-Target` and resolves it from the current location like any other operand, at
`plugins/workspace-guard/scripts/bash-workspace-guard.py:6766:                bound = ps_bind_args(words[1:], spec)`.

Unmeasured: there is no PowerShell on the machine where Q326 was done. What
PowerShell stores for a relative `-Target` decides whether this is a defect at
all. If it resolves the target against the current location and stores an
absolute path, the hook already judges the right file. If it stores the string
as given, the operating system reads it from the link's directory and the hook
judges the wrong one, as `ln -s` did.

**Measure:** on Windows PowerShell 5.1 and PowerShell 7, from a location two
directories below the root, run
`New-Item -ItemType SymbolicLink -Path ..\..\rel -Target ..\x` and read the
link back with `(Get-Item ..\..\rel).Target`. A relative result means the fix
is Q326's: resolve a relative `-Target` from `dirname` of the link's resolved
path, or from `-Path` itself where `-Name` puts the link under it.
