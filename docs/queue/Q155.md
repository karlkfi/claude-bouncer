# The sibling-checkout deny's repair misdirects a self-made checkout

The sibling-checkout write deny leads with one rewrite — write to the same
relative path under this session's own checkout
(`plugins/workspace-guard/scripts/bash-workspace-guard.py:2591:session's own checkout (same relative path).`) —
and mentions `WORKSPACE_GUARD_OVERRIDE` only in a trailing sentence
(`plugins/workspace-guard/scripts/bash-workspace-guard.py:2564:def override_hint(what, prefixable):`,
whose two arms are both tails — Q156 reworded that tail per route and did not
move it).
That ordering is right for an accidental cross-checkout write, where the session
meant its own tree and reached the wrong one. It is wrong for a session that
deliberately created a second worktree — a review checkout, a bisect, a build
against another revision — where the whole point is that the edit belongs in the
other tree and the corrected path names a file the session does not want.

Measured 2026-09-02 on workspace-guard 1.11.0, driving
`plugins/workspace-guard/scripts/bash-workspace-guard.py:2613:Sibling-checkout write(s) blocked: writing into a different`
on synthetic payloads over a throwaway two-worktree repository: an `Edit` and a
`sed -i` into a sibling worktree both deny and both hand back the same-relative-path
rewrite. Q144 carries the full verdict table and the design question
this row does not touch.

**The failure also arrives late.** Both guards allow the setup: branch-guard
auto-approves `git worktree add`, workspace-guard defers it and defers
`git -C <sibling>`, and reads of the new tree ask rather than deny. The first
edit is the wall, so a session spends a worktree creation, and whatever it built
there, before learning the tree is unusable. Nothing can move that earlier —
the guard inspects file operands and never sees the creation — so this is the
cost of the late deny, not a second fix.

**Who is worse off.** The agent that has just been denied. It applies the rewrite
it was given, writes into its own checkout, and gets a change on the wrong branch
in the other direction — or it stalls, having been told to do the one thing it
was deliberately not doing. Two dispatched sessions hit this on 2026-09-01 and
each derived the override by hand.

**Which way it gets built.** Give the two routes equal standing in the lead
rather than promoting one and burying the other: name the same-relative-path
rewrite for the accidental case and `WORKSPACE_GUARD_OVERRIDE=<reason>` for the
deliberate one, saying which is which, so the agent picks on a fact it holds and
the guard does not have to guess. Choosing *for* it needs a signal separating a
self-made checkout from a peer session's, which Q144 answered on
2026-09-02 and Q139 built — both shipped, and this row needed neither.
The prompting variant at
`plugins/workspace-guard/scripts/bash-workspace-guard.py:2609:prompting because`
already drops the tail, so only the deny branch's wording moves.

**If it is never built.** Every deliberate second checkout costs a round trip
that teaches nothing, on a guard whose case for denying rather than asking is
that the reason carries the rewrite the agent applies. Same defect as
[Q87](Q87.md) in another guard: the deny is correct and its repair is not
applicable, which is the one class of deny that spends the agent's turn and
leaves it no better off.
