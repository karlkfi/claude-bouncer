# exit-status-guard registers every gh api call as a gate, reads included

The default registry lists `api` among the `gh` gates
(`plugins/exit-status-guard/exit-status-guard.json:44:workflow\\s+run|run\\s+rerun|api)(\\s|$)`),
so `gh api … | jq` is denied even when the call is a GET whose output is the
answer. The registry's own comment says to register a subcommand's write forms
and leave its reads alone. A plain `gh api <path>` is a GET, which makes it a
read.

Measured from 2026-09-25 to 2026-10-25: exit-status-guard denied 554 calls in
245 sessions. About 70 were `gh api …check-runs | jq`, the second-largest
shape. Driven 2026-10-25 against 2.2.0: `gh api …/check-runs | jq …` and
`gh api …/pulls/1 | jq .state` deny, and `gh api …/check-runs --jq …` is
silent. The deny's rewrite suggests a log file and a grep for
`FAILED|Error [0-9]|^make:`, which fits a build and not an API read. It never
mentions `--jq`, which keeps `gh`'s exit status and needs no pipe.

The largest shape, `git push … | tail` (72), was checked and is not a defect.
A push publishes, and a rejected push piped into `tail` reads as a success, so
that deny is the rule working.

## Which way it gets built

Replace `api` in the gate pattern with its write forms: `-X`/`--method` with
anything but `GET`, and `-f`/`-F`/`--field`/`--raw-field`/`--input`, which turn
the request into a POST. In the deny for any `gh` call that remains a gate,
name `--jq` (or `-q`) as the rewrite before the log-file form.

**Who it is for:** every session that polls CI by reading check runs, which an
orchestrated run does on every PR. **If never built:** about 70 denies a month,
each costing a round trip and a rewrite, for a status nobody was going to read.
