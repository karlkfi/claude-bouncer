# An awk program that writes a file is never judged

awk is a guarded command, and its program is the `awk` row's skipped leading
positional, the same opaque operand Q328 found in sed. awk's own output
redirection names a file the hook never reads, so a write outside the
workspace is allowed silently:

| Command | Verdict |
|---|---|
| `awk '{print > "/q-fake/x"}' f` | allow |

Measured 2026-11-01 on the Q328 branch, with the hook run directly against a
temporary workspace holding `f`; `main` has the same `awk` row and was not run
separately.

The same program can also read with `getline < "FILE"` and run a command with
`system()`, `print | "cmd"` and `"cmd" | getline`. Those were not run through
the hook.

## Where it lands

Unlike sed, an awk program's filenames are expressions: `print > "/x"` is a
literal, `print > f` is a variable, and `print > "/" dir "/x"` concatenates.
So a fix reads string literals in a redirection position as files and treats
any other redirection target as unreadable (ask), and puts `system()` and the
pipe forms with the interpreter suppression (`INTERPRETER_SIGNAL`), as Q328 did
for sed's `e`. `-f PROGFILE` stays out of scope for the reason it does in sed:
the file is already judged as a read.

The `ps … | awk '/x/ {print $1}' | xargs kill` handling reads no awk program
either, deliberately (README, "An awk program is not read"), and is a different
question: a kill anchor rather than a file operand.
