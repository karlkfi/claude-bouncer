# branch-guard never judges a git command inside an sh -c body

`sh -c 'git commit -m x'` run from a checkout on `main` gets no decision, while
the bare `git commit -m x` there asks. `parse_invocation` returns None for any
segment whose program is not `git` or `gh` after `peel_wrappers`, so a shell's
`-c` body is never lexed. `sh` and `bash` are not wrappers in
`WRAPPER_VALUE_OPTS`, and nothing else in the hook reads the string.

Measured 2026-10-07 with the hook at Q251's head (`4cffec0`), from scratch repos
holding a primary checkout on `main` and a linked worktree on a feature branch:

| command | cwd | decision |
|---|---|---|
| `git commit -m x` (control) | main checkout | ask |
| `sh -c 'git commit -m x'` | main checkout | none |
| `sh -c 'git commit -m x'` | feature worktree | none |
| `bash -c 'git commit -m x'` | feature worktree | none |
| `env -C ../repo sh -c 'git commit -m x'` | feature worktree | none |

The last row is how the orchestrator reviewing #258 met it. That PR made
`env -C` follow its directory, and the body behind it still goes unread. The
gap is the same on `main`.

## Which way it gets built

Lex the `-c` string with `tokenize` and judge its segments the way `main()`
judges top-level ones, starting from the cwd the outer invocation reached
through `invocation_cwd`. Treat the body as wrapped: its `ask`s and `deny`s
stand, and its `allow` downgrades to defer, since the shell can change the
environment the classifier never reads. A body that will not lex, or a `-c`
with no string after it, defers as it does now.

Four other guards already read a `-c` body, each in its own code:
workspace-guard's `shell_c_bodies`, prod-guard's nested evaluation,
foreground-guard's and exit-status-guard's `SHELL_NAMES`/`SHELL_WRAPPERS`. That
makes the body extraction a candidate for `lib/`. Leave it out of this row: the
shared surface wants its own row once two guards need the same answer, and
branch-guard can land the fix without waiting for one.

**Who is worse off:** a session that wraps a commit or a reset in `sh -c`, often
to chain a `cd` or to quote a message. Where commits are allowlisted, that
commit lands on a protected branch with no prompt. Elsewhere a prompt still
appears, but it doesn't carry the guard's reason. How often sessions do this is
unmeasured.
