# A pure-report `make` target is denied as a gate

The `make` gate matches every invocation
(`plugins/exit-status-guard/exit-status-guard.json:5:"^make(\\s|$)",`) and the
exempt row beside it enumerates report targets by literal name
(`plugins/exit-status-guard/exit-status-guard.json:48:(help|list|-n|--dry-run|--just-print)`).
A target whose name is not in that alternation falls through to the gate, so a
report whose exit status carries no verdict is denied for losing a status it
never had.

Reported 2026-09-01 from a parallel dispatch run on `karlkfi/claude-spill-guard`,
where `make list-gates 2>&1 | sed -n '8,11p'` was denied. Reproduced here the
same day against the shipped registry on exit-status-guard **2.0.1**, which is
also the version in this tree. Driven through the hook, with the gates as
controls:

| command | status carries a verdict | verdict |
|---|---|---|
| `make help \| head` | no | allow |
| `make backlog \| head` | no | **deny** |
| `make backlog-next \| head` | no | **deny** |
| `make list-gates 2>&1 \| sed -n '8,11p'` | no | **deny** |
| `make backlog-lint \| tail -5` | yes | deny |
| `make check \| tail -5` | yes | deny |

`make help` is allowed only because `help` happens to be one of the five names
the exempt row lists. Two of this repository's own thirteen phony targets are
pure reports outside it, so the guard trips on its home repository: the first
`make backlog` of a session filing this row was denied.

## The structural read rule deliberately does not reach a target

`is_read` skips the first two words, because "at the second, a read verb is as
likely to be a `make` target or a branch name as a subcommand", and says a report
target belongs "in
(`plugins/exit-status-guard/scripts/bash-exit-status-guard.py:221:the registry where its Makefile can be read`)".
That position is correct and the measurement above is what confirms it, not what
overturns it: `make backlog` and `make backlog-lint` share a prefix and need
opposite verdicts. No rule over target *names* can separate them, because only
the Makefile knows which target asserts something. Widening the default exempt
list is therefore out — it would have to guess, and the registry's own comment
already rejects per-tool read patterns for fixing one tool and leaving the class.

## The cost is a silent no-op edit, not a prompt

A deny runs nothing —
`plugins/foreground-guard/docs/development/cross-guard-deny-convention.md:26:A deny does not. The call never runs, so nothing writes the attachment.`
— so a file mutation bundled into the same call did not happen, and a later
command's `OK` reads exactly like the edit's would have. That is this
repository's own write-side failure mode, reached here by a deny that is correct
in principle and wrong on this command. A false deny on a gate costs one
rewrite; this one can cost an edit nobody knows was skipped.

## What lands

The per-project registry already solves it and is the only thing that can.
Verified 2026-09-01 by running the hook against a scratch project carrying
`.claude/exit-status-guard.json` with
`^make(\s+-C\s+\S+)?\s+(backlog|backlog-next|list-gates)(\s|$)` in `exempt`: the
three reports flipped to allow and `make backlog-lint` and `make check` still
denied. So:

- **Add `.claude/exit-status-guard.json` here**, exempting `backlog` and
  `backlog-next`. It stops the repository tripping its own guard and is the
  worked example the docs can point at.
- **Name that file in the deny's reason.** The tail offers three exits — redirect,
  `EXIT_STATUS_GUARD_OVERRIDE`, and
  `plugins/exit-status-guard/scripts/bash-exit-status-guard.py:737:report it at https` —
  and none of them is the durable fix. A session meeting this denial has no way
  to learn that its project can teach the guard, so it overrides or files, which
  is the reflexive-override outcome the registry comment warns about. One
  sentence in `OVERRIDE_TAIL` reaches every consumer and is the class fix.
- A test pinning a report target and a gate target that share a prefix, so a
  later widening of the default exempt list cannot pass.

The fix is entirely inside this plugin: `lib/bouncer_parse.py` carries no part of
the registry, `is_read`, or the read-word table, so no `lib` label and no
re-vendor.
