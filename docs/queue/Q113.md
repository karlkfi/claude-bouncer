# A stripped heredoc leaves an armed `<<` that a second strip mis-reads

`strip_heredoc_bodies` removes a body but deliberately leaves `<<WORD` on the
command line, so the redirect handling downstream still sees it. That is right
for its own output, which goes straight to `lex`. It is wrong for text that
gets stripped twice, and a substitution body does get stripped twice: the guard
extracts it from the already-stripped string and `_analyze_command` recurses,
stripping again. The second pass sees an armed `<<WORD` with its body gone and
swallows everything after the newline as an unterminated body.

Measured 2026-08-23 against the Q109 branch, with `/etc/t` outside the
workspace:

    echo "$(cat <<EOF
    body
    EOF
    cat /etc/t)"

defers, where the same command without the enclosing `"$( )"` asks. The
guarded read is simply gone by the time anything looks. It does not need an odd
quote and it does not need a `case` clause -- both the apostrophe and the plain
form defer, which is what separates it from Q109.

Q109 leaves this untouched and, oddly, makes clause shapes behave *better* than
plain ones: in a clause the top-level strip stops early, so the body survives
into the substitution and the recursion strips it correctly, while outside a
clause the top-level strip succeeds and arms the trap. `CaseClauseSubstEndToEnd`
covers the clause side; nothing covers this.

Two candidate fixes, neither obviously right: drop the `<<WORD` operator along
with the body so the output is idempotent under a second strip, or hand the
recursion the substitution body from the raw string rather than the stripped
one. The first changes documented behaviour five guards share and the second is
guard-side. Worth deciding before writing.
