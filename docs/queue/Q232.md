# sed -i '' with an address script asks as an absolute path

On macOS, `sed -i '' '/^#/d' notes.txt` deletes comment lines in place. It
prompts as `Outside-workspace path(s): /^#/d`, because the guard reads the
script as a file operand. Re-driven 2026-10-04 against the hook at `442c86e`:
that command asks, and `sed -i '' -e '/^#/d' notes.txt` allows. The fix for the
`sed -i '' "s/x/$a/"` deny takes an `s`/`y` command holding an expansion as the
script
(`plugins/workspace-guard/scripts/bash-workspace-guard.py:2992:def sed_detached_empty_suffix(tokens):`)
and leaves every other token after a detached `''` judged as a path.

The two seds disagree about that token. BSD sed (macOS) reads `''` as the
backup suffix and the next token as the script. GNU sed reads `''` as an empty
script and the next token as the first file. So an address script starting
with `/` cannot be told apart from a GNU absolute path by its shape.

**Who is worse off.** An agent on macOS writing the BSD form with an address
(`/re/d`, `/re/s/…/`), which is the common in-place form there, and the person
answering the prompt. The ask's reason never reaches the agent, so an approval
teaches it nothing and it writes the same shape next time. The prompt's own
text is also wrong for this case: it says "use a path inside the project root"
about a token that is not a path.

**If it is never built**, every such edit costs one prompt naming a "path" the
operator has to recognise as a sed script, once per occurrence. That is
nothing worse than the friction: the token is still judged, so nothing
outside the workspace slips through. Flat urgency.

## Which way it gets built

**Ask (answered):** the row asked whether the guard may pick a reading by
host, skipping the token on `darwin` when `sed` resolves to `/usr/bin/sed`.
It may not, and the evidence rules it out without needing a preference:

- Skipping the token is a loosening under GNU sed, and the plugin's rule is
  that the more secure behaviour stays the default "even partially, even with
  mitigations"
  (`plugins/workspace-guard/CLAUDE.md:51:**Secure by default, not opt-in.**`).
  A host heuristic is exactly a partial weakening with a mitigation.
- The hook cannot see the `sed` the command will run. It runs as a child of
  Claude Code, while the Bash tool's shell restores the user's own functions
  and `PATH` from a shell snapshot, and the command can set `PATH` itself. So a
  lookup in the hook answers a different question. This is carried from the
  workstation's `CLAUDE.md` (`grep` there resolves to a snapshot function that
  dispatches to `ugrep`) and was not re-measured for `sed`.

## Why it waits on a sed-script parser

Karl chose a deny with the `-e` rewrite on 2026-10-04, and #296 built it. Review
showed the rewrite is only safe for a script that names no file and runs
nothing: the hook read no filename inside an `-e` script before Q328, so handing
`/x/w F` the rewrite steers an ask onto an allow. The reviewer confirmed on
macOS `/usr/bin/sed` that the `-e` form wrote the file.

Telling such a script apart with a regex leaked three times in one review:

- No check at all: `/x/w F`, `/x/r F`, `/x/W F`, `/x/R F`.
- Ignoring `w`/`W`/`r`/`R`/`e` inside `/…/` pairs: stripping the pairs left to
  right mis-paired an `s` command's delimiters, so `/x/s/a/b/w F`,
  `/x/s/a/b/gw F`, `/x/s/a/b/;w F` and their `{…}` forms read as inert.
- Refusing any script holding one of those letters anywhere is safe, but
  leaves almost nothing eligible. Of 42 distinct absolute-looking tokens after
  `sed -i ''` in this machine's session transcripts (measured 2026-11-01), 1
  (`/^#/d`) passed and 41 kept the ask, real edits like `/GH-ARGS/d` and
  `/^import copy$/d` among them. The sample includes the review's own probes,
  not separated out.

Karl's call on 2026-11-01: re-scope #296 to the README correction and tests
pinning today's ask, and keep this row. The fix needs a real parser of the
script's commands: `s` and `y` delimiters, `\cREc` addresses, `{…}` blocks,
`;`-separated commands, and the `w`/`r` filenames. That is the parser Q328
describes, so build it there first; this row then denies with the rewrite
only for a script that parser reads as naming no file and running nothing.

What #296 left in place: the README Limitations entry
(`plugins/workspace-guard/README.md:1798:denied. Use`), whose
parser paragraph Q328 removed, and tests under `# --- Q232` in
`test_workspace_guard.py` pinning the ask for every shape above. A relaxation
that lets any of them through fails those tests. Q328 adjusted two of them
without loosening either: the reason now names the script's own `w`/`r` file
beside the token, so the helper finds the token in the list rather than at its
head, and the five `w ../l` shapes deny, because `../l` from the test
workspace is host temp.

The parser has landed with Q328: `sed_script_reads` in
`plugins/workspace-guard/scripts/bash-workspace-guard.py` returns the files a
script names and whether it runs a command, read every way GNU and BSD sed can
read it.
