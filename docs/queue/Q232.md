# sed -i '' with an address script asks as an absolute path

On macOS, `sed -i '' '/^#/d' notes.txt` deletes comment lines in place. It
prompts as `Outside-workspace path(s): /^#/d`, because the guard reads the
script as a file operand. Measured 2026-10-03 against the in-tree hook after
the fix for the `sed -i '' "s/x/$a/"` deny landed. That fix takes an `s`/`y`
command holding an expansion as the script, and leaves every other token after
a detached `''` judged as a path.

The two seds disagree about that token. BSD sed (macOS) reads `''` as the
backup suffix and the next token as the script. GNU sed reads `''` as an empty
script and the next token as the first file. So an address script starting
with `/` is indistinguishable by shape from a GNU absolute path, and dropping
it would let GNU `sed -i '' /outside/file` through unjudged. That is a
loosening, which the plugin's secure-by-default rule says needs sign-off.

It is met on every in-place edit an agent writes in BSD form with an address
(`/re/d`, `/re/s/…/`), which on macOS is the common form. The workaround is
`sed -i '' -e SCRIPT FILE`, which both seds read the same way and which the
README's Limitations now names, so the cost is one prompt and one rewrite per
occurrence rather than a block.

**Ask:** whether the guard may pick a reading by host. On `darwin`, with `sed`
resolving to `/usr/bin/sed`, the token is the script and could be skipped. A
Homebrew `gnubin` ahead of it on `PATH` makes that reading wrong, so the
question is whether a PATH lookup is a trustworthy enough signal to loosen on,
or whether the `-e` workaround plus a deny reason that names it is the fix.
