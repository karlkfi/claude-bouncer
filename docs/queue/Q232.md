# sed -i '' with an address script asks as an absolute path

On macOS, `sed -i '' '/^#/d' notes.txt` deletes comment lines in place. It
prompts as `Outside-workspace path(s): /^#/d`, because the guard reads the
script as a file operand. Re-driven 2026-10-04 against the hook at `442c86e`:
that command asks, and `sed -i '' -e '/^#/d' notes.txt` allows. The fix for the
`sed -i '' "s/x/$a/"` deny takes an `s`/`y` command holding an expansion as the
script
(`plugins/workspace-guard/scripts/bash-workspace-guard.py:2850:def sed_detached_empty_suffix(tokens):`)
and leaves every other token after a detached `''` judged as a path.

The two seds disagree about that token. BSD sed (macOS) reads `''` as the
backup suffix and the next token as the script. GNU sed reads `''` as an empty
script and the next token as the first file. So an address script starting
with `/` cannot be told apart from a GNU absolute path by its shape.

**Who is worse off.** An agent on macOS writing the BSD form with an address
(`/re/d`, `/re/s/…/`), which is the common in-place form there, and the person
answering the prompt. The ask's reason never reaches the agent, so an approval
teaches it nothing and it writes the same shape next time. The prompt's own
text is also wrong for this case: it says "use a path inside the project root"
about a token that is not a path.

**If it is never built**, every such edit costs one prompt naming a "path" the
operator has to recognise as a sed script, once per occurrence. That is
nothing worse than the friction: the token is still judged, so nothing
outside the workspace slips through. Flat urgency.

## Which way it gets built

**Ask (answered):** the row asked whether the guard may pick a reading by
host, skipping the token on `darwin` when `sed` resolves to `/usr/bin/sed`.
It may not, and the evidence rules it out without needing a preference:

- Skipping the token is a loosening under GNU sed, and the plugin's rule is
  that the more secure behaviour stays the default "even partially, even with
  mitigations"
  (`plugins/workspace-guard/CLAUDE.md:51:**Secure by default, not opt-in.**`).
  A host heuristic is exactly a partial weakening with a mitigation.
- The hook cannot see the `sed` the command will run. It runs as a child of
  Claude Code, while the Bash tool's shell restores the user's own functions
  and `PATH` from a shell snapshot, and the command can set `PATH` itself. So a
  lookup in the hook answers a different question. This is carried from the
  workstation's `CLAUDE.md` (`grep` there resolves to a snapshot function that
  dispatches to `ugrep`) and was not re-measured for `sed`.

What is left is the row's own other option: **deny, with the `-e` rewrite in
the reason.** The routing test in the `hook-verdict` skill is whether the fix
can be written into the reason as a command the model could run instead. It
can: for the BSD sed that reads this argv as an address script,
`sed -i '' -e SCRIPT FILE` is the same edit, and an `ask` would send the
question to a person whose approval never reaches the agent. This is not the
skill's "could not parse" case. A person can see that `/^#/d` is a sed script,
so the prompt is answerable, but it teaches the agent nothing.

**The deny is Karl's call, made 2026-10-04.** It overrides the plugin's default
for this one shape: outside-workspace paths ask, and hard-blocking is opt-in
(`plugins/workspace-guard/CLAUDE.md:42:Default decision for outside-workspace paths is`).
It also turns GNU's reading of the same argv from an ask into a deny:
`sed -i '' /etc/hosts` asks today, re-driven 2026-10-04 with
`/opt/q232-fake/target` as the path, and denies after this lands. Under GNU sed
4.9, measured in a `debian:stable-slim` container, that command runs an empty
script and leaves the file as it was. With an address script as the token,
it fails with `can't read /^#/d` and exit 2.

The rewrite is exact for BSD sed and close for GNU. In the same container,
`sed -i '' -e '/^#/d' FILE` made the edit, then reported `can't read :` for
the empty operand and exited 2. The reason should say it is the macOS
spelling.

The build: where `sed_detached_empty_suffix` holds and the token after the
`''` would be judged outside the workspace, deny with a reason naming
`sed -i '' -e SCRIPT FILE`, instead of asking. A token that resolves inside the
workspace keeps today's verdict. Under GNU's reading the argv runs an empty
script over the file and changes nothing, so the deny strands no GNU command
that edits anything. Update the README Limitations entry
(`plugins/workspace-guard/README.md:1693:which both seds read the same way.`)
and the decision table with it, and correct that entry's claim: GNU makes
the same edit but exits 2 on the empty operand, as measured above. Pin it with a test for each verdict: the
address form denies with the rewrite, `-e` allows, and a relative token after
`''` behaves as before.

Rank: it keeps its place. One prompt per occurrence on the platform the agents
here run on, against a fix that is one branch in `files_in_command` and its
reason.
