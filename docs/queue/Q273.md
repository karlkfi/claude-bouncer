# A case pattern's paren closes the subshell scope early

`split_groups` treats every `)` as closing the innermost `(`. A `case` pattern
written without its optional leading `(`, as in `x)`, ends in a `)` that closes
nothing. Inside a subshell, that `)` pops the subshell's scope, so a `cd`
written later in the same subshell moves the tracked cwd for the rest of the
string.

## Measured

2026-10-04, from the review of the Q173 pull request, reproduced on that
branch. Same fixture as Q272: `cwd` is a scratch workspace with a `sub/`, and
bash 5.3.15 ran each string under `env -i` with a `q173-x` in the workspace and
another in its parent.

| command | hook, `main` | hook, branch | bash reads |
|---|---|---|---|
| `(case x in x) ;; esac; cd sub); cat ../q173-x` | **allow** | **allow** | the parent's |
| `(case x in (x) ;; esac; cd sub); cat ../q173-x` | **allow** | ask | the parent's |

The second row balances its parens, so Q173's scope tracking reads it
correctly. On `main`, every subshell `cd` leaked.

## Which way it gets built

The paren count needs to know when it is inside `case … esac`. There, a `)`
with no matching `(` since the last `in` or `;;` ends a pattern, not a
subshell. Tracking `case` and `esac` as words at command position in
`split_groups`, with a pattern flag set after `in` and after `;;`, `;&` and
`;;&`, is enough to tell the two apart.

## If it is never built

A `case` inside a subshell lets a later `cd` in that subshell escape it, so a
relative read after the subshell can get an `allow` for a file outside the
workspace. Writing a `case` in a one-line subshell is uncommon, which is why
this ranks below Q272.
