# An `eval` body's assignments never reach the segments after it

Q151 taught the recursion that an `eval` body runs in the invoking shell, so a
bare `$C` set outside it resolves inside. The flow back out is still missing:
the sub-evaluation gets its own `shell_env`, and whatever the body assigns dies
with the call. `eval 'C=gke_acme_prod-us'; kubectl --context $C delete ns x`
therefore reads `$C` as unset in the segment that uses it, and the target is
UNKNOWN when bash resolves it to a production one.

Fail-safe, unlike its two siblings: the target is unknown rather than nonprod,
so the guard asks. What it costs is the deny a production target is owed, and a
reason naming `$C` as unresolved when it resolves.

## Measured

2026-09-04, on the branch carrying Q151's fix, fixture `$HOME` with no ambient
context. Both columns run the hook; nothing is executed.

| command | before Q151 | after Q151 | bash |
|---|---|---|---|
| `C=gke_acme_prod-us; eval 'kubectl --context $C delete ns x'` | ask | deny | prod |
| `eval 'C=gke_acme_prod-us; kubectl --context $C delete ns x'` | deny | deny | prod |
| `eval 'C=gke_acme_prod-us'; kubectl --context $C delete ns x` | **ask** | **ask** | prod |

The middle row is what makes the third one a gap rather than a design: an
assignment and a use inside one body already work, because the body is a
command string the recursion walks segment by segment. Only crossing back out
of the body fails.

## Which way it gets built

`evaluate_command_string` returns three values and would need a fourth — the
body's resulting `shell_env` — for the `eval` branch to merge back into the
caller's. Check first whether the `sh -c` branch must be held out: a child's
assignments really do die with it, so the merge belongs to `eval` alone, the
same way the `shell` parameter does.

Two shapes to settle while building it, neither measured here. An `eval` inside
a subshell — `( eval 'C=x' ); kubectl --context $C …` — assigns nothing the
parent can see, and the guard does not model subshells at all. And an `eval`
whose body is not parseable already fails open, so the merge has to leave
`shell_env` untouched on that path rather than clearing it.

## If it is never built

One ask where a deny belongs, on a construction rarer than the two Q151 closed:
setting a variable through `eval` and using it in a later segment, rather than
building the whole command inside the body. It is the safe direction, and it is
the last inconsistency between `eval` and the shell it claims to model.
