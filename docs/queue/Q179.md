# Two guards arm their break-glass on an empty reason

`PROD_GUARD_OVERRIDE= <command>` and `FOREGROUND_GUARD_OVERRIDE= <command>`
both lift the guard. Two of the five behave this way, not one, and the two are
not the pair the asymmetry argument would predict.

## Measured

2026-09-07, re-driven 2026-09-08, each hook on a command it otherwise acts on:

```
kubectl --context gke_acme_prod-us delete ns x                              -> deny
PROD_GUARD_OVERRIDE=         kubectl --context gke_acme_prod-us delete ns x -> ask
PROD_GUARD_SESSION_OVERRIDE= kubectl --context gke_acme_prod-us delete ns x -> ask
PROD_GUARD_OVERRIDE=why      kubectl --context gke_acme_prod-us delete ns x -> ask

sleep 5; git status; sleep 5; git status                                 -> deny
FOREGROUND_GUARD_OVERRIDE=     sleep 5; git status; sleep 5; git status  -> defer
env FOREGROUND_GUARD_OVERRIDE= sleep 5; git status; sleep 5; git status  -> defer

WORKSPACE_GUARD_OVERRIDE= cp a b                  -> reason is None, guard still acts
BRANCH_GUARD_OVERRIDE= git restore file.txt       -> ask (not lifted)
EXIT_STATUS_GUARD_OVERRIDE= make check | tail -30 -> deny (not lifted)
```

An empty reason is indistinguishable from a real one: `=why` lands on the same
verdict as `=`. The three that refuse gate on `value.strip()`. The six sites
that do not test content at all:

`plugins/foreground-guard/scripts/bash-foreground-guard.py:356:                state['override'] = _val`
`plugins/foreground-guard/scripts/bash-foreground-guard.py:371:                    state['override'] = _val`
`plugins/foreground-guard/scripts/bash-foreground-guard.py:388:                        state['override'] = _val`
`plugins/foreground-guard/scripts/bash-foreground-guard.py:871:    if override is not None:`
`plugins/prod-guard/scripts/bash-prod-guard.py:2510:        if 'PROD_GUARD_OVERRIDE' in seg_inline:`
`plugins/prod-guard/scripts/bash-prod-guard.py:2605:        if session_reason is None:`

The middle foreground-guard site is `sudo`'s operand loop, added by Q170's
fix (#110) after this row was filed -- it copied the shape of the site above
it, empty-reason defect included. It is listed so this census stays a census;
closing this row means all six.

The last is the sharpest, and the only one that writes anything: an empty
reason survives into `record_session_grants` and is recorded as the
justification for a session-long grant against a production target. The other
four decide one command.

## Who it is for, and what it is worth

The reason exists so the caller says *why*, and a bare `NAME=` is the spelling
that says nothing. Every denial these guards emit names the prefix as the way
out, so the empty form is a plausible thing to type when someone wants the
guard gone rather than wants to explain themselves.

The asymmetry that would excuse it does not survive the census. foreground-guard
only defers, so a wrong disarm there is cheap -- but prod-guard gates the
destructive actions and has the same hole in both of its break-glasses. Whatever
rule is chosen has to be chosen for prod-guard first, and foreground-guard then
follows it or documents why it is exempt.

## What happens if it is never built

The five guards keep disagreeing about what an empty reason means, and the
disagreement is invisible until someone compares them. In prod-guard, a reason
nobody wrote keeps being accepted as one, and stored.

## Which way it gets built

Add `.strip()` at the six sites, or write down in each guard's README why
lifting on nothing is intended. Decide for prod-guard and apply the answer to
both. The foreground-guard half is asserted deliberately, in
`plugins/foreground-guard/tests/test_foreground_guard.py:557:    def test_override_empty_reason_still_defers(self):`
so a test changes with the decision either way; nothing asserts prod-guard's
behaviour in either direction.

## Notes

Found in review of the Q174 pull request; the prod-guard half in the re-review
of the same, where the first census of this row was wrong -- it counted three
guards requiring a reason and left prod-guard out. Q174 widened `ASSIGNMENT_RE`
so `NAME+=` parses as an assignment too, which reaches both holes through a
second spelling. `+=` and `=` now behave identically, which is correct, and
identical here means both lift on empty. Pre-existing; Q174 neither created the
behaviour nor widened it beyond making the two spellings agree.
