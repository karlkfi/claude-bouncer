# A bundled short flag whose value is separate hides the command behind it

`strip_wrappers` decides a flag's arity by testing the whole token against the
wrapper's value-flag set, so it only ever recognises a flag written on its own.
Bundle that flag with any other short option and the token matches nothing, one
token is dropped instead of two, and the flag's value is left standing as the
command word. The covered tool one place to its right is never classified and
the segment defers.

`sudo -nu root kubectl delete ns foo` is the shape: `-n` and `-u` are both
ordinary sudo options and bundling them is ordinary usage, but the guard reads
`root` as the command.

This is the false-negative direction, which
[`plugins/prod-guard/CLAUDE.md`](../../plugins/prod-guard/CLAUDE.md) names as
the failure mode to fear.

## Measured

2026-09-09, through `strip_wrappers` directly rather than through a verdict, so
the reading is the parse rather than its consequence. Each unbundled twin is the
control:

| argv | `strip_wrappers` leaves |
|---|---|
| `sudo -n -u root kubectl delete ns x` | `kubectl delete ns x` — correct |
| `sudo -uroot kubectl delete ns x` | `kubectl delete ns x` — correct |
| **`sudo -nu root kubectl delete ns x`** | **`root kubectl delete ns x`** |
| **`sudo -bg wheel kubectl delete ns x`** | **`wheel kubectl delete ns x`** |
| `env -u FOO kubectl delete ns x` | `kubectl delete ns x` — correct |
| **`env -iu FOO kubectl delete ns x`** | **`FOO kubectl delete ns x`** |
| **`exec -ca gate kubectl delete ns x`** | **`gate kubectl delete ns x`** |

So it reaches at least three wrappers, and the attached form (`-uroot`) is
unaffected — a separated value is the whole of the defect.

That these are real invocations rather than shapes nobody writes was checked
against the tools themselves, with `echo RAN` as the payload and no covered tool
involved: `env -iu FOO echo RAN` and `exec -ca gate echo RAN` each print `RAN`
under `env -i PATH="$PATH" bash --norc --noprofile -c`. For sudo the evidence is
its own usage rather than an execution — `usage: sudo -v [-ABkNnS] [-g group]
[-h host] [-p prompt] [-u user]` puts `-n` in a bundleable group and `-u` among
the flags taking a separate value.

## Which way it gets built

Walk the characters of a short token and decide arity per character, stopping at
the first value-taking one, because the rest of the token is that flag's value —
and when the flag ends the token, the next operand is. `is_sudo_run_nothing`
already walks exactly that way (Q157 shipped it, after review caught the whole-
token version scanning an attached value), so this is applying a mechanism the
file has rather than inventing one. The two walks sitting a few lines apart and
disagreeing is itself the argument for doing it.

The token test is written out four times in `strip_wrappers` — once per branch
— so the fix is one helper and four call sites, not one edit.

Bundling is the second half of the arity problem [Q160](Q160.md) covers in
foreground-guard, where the missing half was the separated value; that row's
tree, function and flag sets are all different, so neither fix closes the other.
Check the sibling guards' own peels while here rather than assuming.

## If it is never built

A mutating command written behind bundled wrapper flags reaches production with
the guard silent. Nothing reports it: being wrong about the command word
produces no signal in either direction, so the miss is invisible to any friction
count.
