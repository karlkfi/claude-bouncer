# Ship release dates so the friction report can bucket by release

The friction report ranks every decision in its window as the current
guard's, so a shape a later release stopped prompting on keeps its rank. Q98
asked for decisions to be bucketed by the release window their timestamp falls
in, with the boundary shown in the category and path tables. That needs a date
for each release, and none is readable where the report runs: it runs from the
installed plugin (`/workspace-guard:friction-report`), not from a checkout of
this repo.

Measured 2026-10-04 on one machine:

- **The decisions carry no version.** Across 128,358 workspace-guard
  `PreToolUse` attachments, the recorded hook `command` is unexpanded:
  `"${CLAUDE_PLUGIN_ROOT}/scripts/run-python-hook.cmd" bash-workspace-guard.py`
  (107,440) or `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/bash-workspace-guard.py"`
  (20,912). Nothing in the path names a version.
- **The installed copy has no dates.**
  `~/.claude/plugins/cache/claude-bouncer/workspace-guard/1.12.1/` has no
  `.git`, and its `docs/releases/v*.md` notes carry no date (checked
  `v1.12.1.md` and `v1.0.0.md`).
- **The marketplace clone has no history.**
  `~/.claude/plugins/marketplaces/claude-bouncer` is shallow:
  `git rev-parse --is-shallow-repository` prints `true`, `rev-list --count HEAD`
  prints `1`, and `for-each-ref 'refs/tags/workspace-guard/*'` prints nothing.

So the tag dates Q98 named exist only in a developer's checkout. Q98 shipped
the half that needs no data: the coverage note and `measuring-friction.md` say
a multi-release window mixes releases.

## Which way it gets built

Ship the dates inside the plugin, where the installed report can read them. Two
shapes:

- a date line in each `docs/releases/vX.Y.Z.md`, written by the release
  tooling at cut time and back-filled from this repo's tags; or
- a small data file listing version and date.

`scripts/release.py` writes it at cut time, and a gate fails when the current
`plugin.json` version has no date. Then the report reads it, buckets decisions
by the window their timestamp falls in, and shows the boundary in the category
and path tables. Boundaries are approximate at the edges, since a machine that
upgraded late runs the old guard after the date. The report should say so.

A smaller option needs no shipped data: `lastUpdated` for the guard's entry in
`~/.claude/plugins/installed_plugins.json` is when this machine installed the
running version. On 2026-10-04 it matched the creation time of the installed
version's cache directory to the minute for all five guards. That gives one
boundary, current against everything earlier, rather than a window per
release. It is unmeasured whether the field moves on every upgrade, since the
cache keeps only the installed version. It is also unmeasured whether a
session already open at upgrade keeps running the old hook. The report could
read the field and split at it, and that may be enough on its own.

Whichever shape is chosen, decide whether the other guards with a friction
report (prod-guard, foreground-guard, exit-status-guard) get it too. They share
the blind spot.

**Who is worse off:** whoever ranks workspace-guard's friction to decide what
to fix. On 2026-08-22 a 30-day run ranked `$f` top among `expand` paths with
228 prompts, and every one of those shapes already allowed on the installed
1.10.0 (Q98's measurement).
