# `python3 -m unittest` reads the module name as a file path

`-m` takes a module name, which the interpreter resolves on `sys.path` and never
as a relative file. The guard classifies the operand after it as a path anyway,
joins it to the tracked cwd, and reports a file that has never existed.

## Measured

2026-08-31, workspace-guard 1.11.0, repo tree. Session cwd is this worktree; the
command crosses into another repo:

```
cd /Users/karl/workspace/github-actions-gateway && python3 -m unittest discover -s tests
```

```
ask | workspace-guard: Outside-workspace path(s): unittest ->
/Users/karl/workspace/github-actions-gateway/unittest.
```

`unittest` is the only token named, so the rule can raise a prompt on its own —
`tests`, the one real path in the command, is not reported at all, which is a
second question this row does not answer.

Across seven days of transcripts to 2026-08-31 the token appears in 13 asks, in
every case beside a genuinely outside path, so it added no prompts that week and
made 13 reasons name a file that does not exist. Both readings matter and they
point different ways: the wild data says low cost, the probe says the cost is
not bounded at zero.

## Who it is for

Whoever reads the denial. A reason naming a nonexistent file is unactionable —
there is no literal in-root path to substitute, because there was no path — so
the operator approves without being able to check, which is the failure this
guard's reason text is otherwise careful to avoid.

## Which way it gets built

Skip the operand after `-m` when classifying interpreter arguments. The same
holds for `-c`, whose operand is a program string, and both sit beside the
existing script-argument handling rather than needing new structure.

## If it is never built

A prompt class whose reason is false, in a guard whose denials are otherwise
followable — the cheapest way to teach a session that these reasons do not
repay reading.
