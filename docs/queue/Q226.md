# An escaped backtick inside a backtick substitution is never judged

Inside a backtick substitution, bash removes the backslash from `` \` `` and
runs the inner substitution. `command_substitutions` returns the outer body
with the backslashes still in place, so re-scanning that body finds no
substitution, and the inner command is never classified.

Found by the independent review of the Q196 pull request. Re-driven 2026-10-01
through the hook (fixture `$HOME`, ambient context `gke_acme_prod-us`) at
`b27be8d` and at the Q196 head, with identical results. That bash runs the
inner payload was driven under `env -i bash --norc --noprofile -c` with a
payload absent from `PATH`:

| command | guard | bash runs it |
|---|---|---|
| ``echo `echo \`kubectl delete ns payments\``` `` | **defer** | yes |
| ``echo "`echo \`kubectl delete ns payments\``"`` | **defer** | yes |

The review also found that `` "\`x\` $(…)" `` is right today: an escaped
backtick outside a backtick substitution stays literal, and the real
substitution is judged.

## Which way it gets built

Un-escape a backtick body the way bash does before returning it: inside
backticks, a backslash followed by `` ` ``, `$` or `\` loses the backslash.
Then the caller's re-scan finds the nested substitution. The function lives in
`lib/`, so check workspace-guard, which also recurses through it.

## If it is never built

A mutating command nested two backtick levels deep runs with no deny. This is
rarer than a quoted or commented command, so it ranks below those rows.
