# A brace group or function body hides the command inside it

prod-guard never strips a leading shell reserved word, so `{`, `if`, `then`,
`!`, `do` and `function` become the segment's command. None of them is a tool
it covers, so the segment defers, along with the production command behind
the word. `{ …; } 2>&1` is the commonest of these shapes in agent-written
commands, and it needs no unusual syntax to hide a delete.

## Measured

2026-10-07, prod-guard at `main` `63ceb4d`. The verdicts were taken twice, with
`diffverdict.py` and with the suite's own `run_hook` and `make_home(kubeconfig=
KUBECONFIG_PROD)`, and both agree:

| command | verdict |
|---|---|
| `kubectl --context gke_acme_prod-us delete pod x` (control) | deny |
| `( kubectl --context gke_acme_prod-us delete pod x )` (control) | deny |
| `{ kubectl --context gke_acme_prod-us delete pod x; }` | **defer** |
| `{ kubectl --context gke_acme_prod-us delete pod x; } 2>&1` | **defer** |
| `true && { kubectl --context gke_acme_prod-us delete pod x; }` | **defer** |
| `if kubectl --context gke_acme_prod-us delete pod x; then echo ok; fi` | **defer** |
| `if true; then kubectl --context gke_acme_prod-us delete pod x; fi` | **defer** |
| `! kubectl --context gke_acme_prod-us delete pod x` | **defer** |
| `while true; do kubectl --context gke_acme_prod-us delete pod x; done` | **defer** |
| `for i in 1; do kubectl --context gke_acme_prod-us delete pod x; done` | **defer** |
| `f() { kubectl --context gke_acme_prod-us delete pod x; }; f` | **defer** |
| `function f { kubectl --context gke_acme_prod-us delete pod x; }; f` | **defer** |
| `f() ( kubectl --context gke_acme_prod-us delete pod x ); f` | deny |

Only prod-guard was driven. workspace-guard and exit-status-guard call the
shared `strip_sh_keywords`; whether branch-guard and foreground-guard miss
the same shapes was not checked.

## Mechanism

Each segment's words go straight to the env-prefix and wrapper walk, with no
keyword step before them:

`plugins/prod-guard/scripts/bash-prod-guard.py:2807:seg_env, argv_raw = extract_env_prefix(group, shell_env)`

The shared parser already has the step. Its docstring names this exact gap for
workspace-guard ("so the whole group defers — a silent gap in the guard (Q28)"):

`lib/bouncer_parse.py:1832:def strip_sh_keywords(tokens):`

## Which way it gets built

Call `strip_sh_keywords` on each group before `extract_env_prefix`, which is
bash's own order (reserved words, then assignments, then the command name) and
the order workspace-guard uses. A function definition needs one step more: the
`f()` before the `{`, and `function f`, are not reserved words, so the body is
still hidden behind them. Judging a definition's body where it is written is
the strict reading, since the guard cannot follow the call.

Q299's `C=… f` shape lands here once the body is judged. The binding is
temporary, for the call only, so a body that reads `$C` should then see the
prefix's value.

## If it is never built

A production mutation written inside a brace group, a conditional or a loop,
or behind `!`, reaches the cluster with no prompt.
