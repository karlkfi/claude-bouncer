# A reference-style link from one item to another is reported by nothing

Since #213 (Q132), both link tests leave a dangling link between two items to
`queue.py lint`, which notes it as `dangling-link`. That hand-off holds only for
an inline link. A reference-style one, `[r]: Q999.md`, falls through all three
readers:

- `tests/test_doc_links.py` reads reference definitions
  (`tests/test_doc_links.py:26:REFDEF = re.compile(`) and skips this one,
  because both ends are items.
- `tests/test_backlog.py` matches inline links only
  (`tests/test_backlog.py:42:LINK = re.compile(r'\]\(([^)]+)\)')`).
- `queue.py`'s `ITEM_LINK_RE` matches inline links only
  (`scripts/queue.py:41:ITEM_LINK_RE = re.compile(`), so no note is printed.

So an item whose reference definition points at a deleted or mistyped row
passes `make check` with nothing printed. No item uses a reference definition
to another item today (`git grep -n '\]: Q' -- docs/queue` on `5da5818` returns
nothing), so this is latent. The independent review of #213 found it as a
non-holding note.

## Which way it gets built

The smaller fix is in `test_doc_links.py`: skip a missing target only when the
link is one `queue.py` will note, which means passing the link's form to the
`advisory` predicate and skipping inline links alone. A reference definition
to a missing item then fails the build, which is stricter than an inline link
gets. That is acceptable for a form nobody uses. The alternative is teaching
`queue.py` to read reference definitions, but that is vendored from
`claude-skills`, so the change belongs upstream.

## Who is worse off

A row author who writes a reference-style link to a sibling, and the reader
who later clicks it.
