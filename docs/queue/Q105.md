# `$var:path` is a zsh modifier, so the path becomes a bare ref

The Bash tool runs zsh. `$ref:path/file` there is not a variable followed by a
colon — `:s` is the *substitute* modifier, and it swallows the rest of the
word. The expansion is the variable's bare value, so a command built that way
runs against a different argument than it reads as.

Measured 2026-08-22, this repository, zsh 5.9:

```
for ref in origin/main; do echo $ref:session-worker/SKILL.md; done   -> origin/main
for ref in origin/main; do echo "$ref:session-worker/SKILL.md"; done -> origin/main
for ref in origin/main; do echo ${ref}:session-worker/SKILL.md; done -> origin/main:session-worker/SKILL.md
```

**Double-quoting does not rescue it**, which is what makes it worse than the
usual expansion traps: the defensive reflex produces the same wrong answer.
Only braces do.

The damage is that it usually **succeeds**. `git show $ref:path | wc -l`
returned 124 lines against the file's 1,365, because `git show origin/main`
is a valid command that prints the commit instead of the blob — well-formed
output of the wrong object, at exit 0. It was caught only because the line
count was absurd on its face; a plausible number would have been believed. In
the session that measured it, that reading briefly supported a false claim
about a pull request under review.

**There is precedent for guarding a zsh-vs-bash divergence rather than only
documenting one.** `${PIPESTATUS[0]}` is the same class — bash syntax that
expands to nothing under zsh — and
`plugins/exit-status-guard/scripts/bash-exit-status-guard.py` already denies
it with the working alternative in the reason. The documentation route has
been tried here and did not hold. The `verify-claims` skill, in
`references/shell-traps.md` (that skill lives in `karlkfi/claude-skills`, so
no citation from this store can resolve into it), describes this exact shape,
names `:s`, records that quoting does not help, and carries a 33-of-33
measurement — and a session with that skill loaded still wrote the unbraced
form.

**Open, and not settled by this row: which guard.** The shape produces a wrong
*path*, which is workspace-guard's subject, but it is a zsh divergence with a
one-line rewrite as the fix, which is exit-status-guard's charter and its
existing `PIPESTATUS` precedent. Labelled `exit-status-guard` on the
precedent; re-label if the argument goes the other way.

The detection is narrow — a `$name:` or `"$name:` immediately followed by a
non-modifier character, in a word that is not already braced. Sizing is `M`
rather than `S` because the false-positive question is real: a bare `$var:` is
legitimate in a URL, a `sed` script, and a `PATH`-like assignment, and a guard
that denies those is worse than the trap.
