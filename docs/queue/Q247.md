# Class B denies a slow command the shell already backgrounded

A registered slow command followed by a shell `&` is denied as though it ran
in the foreground. Class A skips a backgrounded segment
(`plugins/foreground-guard/scripts/bash-foreground-guard.py:if bg or state['timeout_wrapped']:`),
but Class B's walk discards each segment's terminator
(`plugins/foreground-guard/scripts/bash-foreground-guard.py:for group, _term in split_segments(tokens):`)
and judges every segment the same way.

Measured 2026-10-04 by driving the hook with `{"scripts/gate\\.sh": 3600000}`
registered:

| command | guard |
|---|---|
| `gh run watch 456 & ls` | defer -- Class A, control |
| `scripts/gate.sh` with `run_in_background: true` | defer -- control |
| `scripts/gate.sh &` | **deny** |
| `scripts/gate.sh & ls` | **deny** |

The deny says the command "would run in the foreground with the default
120000 ms timeout -- the Bash tool will kill it before it finishes". The `&`
makes the first half false. A Bash call in this session ran
`(sleep 4; echo LATE) & echo NOW` and returned without `LATE`, so the call did
not wait for the child. Whether the child is later killed or only loses its
output was not measured.

Both of the plugin's own documents say this shape passes. The README's
Exemptions list "A trailing `&` that detaches the blocking command" with no
class qualifier, and `plugins/foreground-guard/CLAUDE.md` lists "backgrounded
segments" among the forms that "must defer silently".

Found while testing Q178, where `nohup A=1 scripts/gate.sh & ls` denied on
`main` for this reason rather than the one Q178 is about.

## Which way it gets built

Skip a segment whose terminator is `&` in `simple_commands`, as
`analyze_class_a` does, with a test for the trailing and mid-command forms.
The documented contract settles the direction. A deny worded for lost output
would be a new rule, and it would need its own row.

## If it is never built

An agent that backgrounds a gate with `&` is told something false and is
taught a rewrite it did not need. It is uncommon, because the Bash tool's
`run_in_background` is the usual spelling, and the cost is one retry each
time.
