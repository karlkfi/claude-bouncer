# An append assignment is not read as an assignment

`NAME+=value` sets a variable in bash exactly as `NAME=value` does -- it
appends rather than replaces, and it is an assignment in command position
either way. `lib/bouncer_parse.py:42:ASSIGNMENT_RE = re.compile(` requires the
`=` to follow the name directly, so the `+` ends the match and the word is read
as a command name.

Every consumer inherits it, in both positions: the command-head strip all five
guards run, each guard's break-glass reader, and the `env` / `export` operand
readers that are deliberately left matching the token.

## Measured

2026-09-07, bash 5.3.15 on darwin, `SG_OVR+=x printenv SG_OVR` in command
position:

```
SG_OVR=x  printenv SG_OVR   -> x     assignment
SG_OVR+=x printenv SG_OVR   -> x     assignment  <-- ASSIGNMENT_RE misses this
'SG_OVR=x' printenv SG_OVR  -> command not found
```

Against the parser, `ASSIGNMENT_RE.match('SG_OVR+=x')` is `None`, so
`strip_env_prefix` stops at that token and every guard reads `SG_OVR+=x` as the
command word.

It is the one case in a 20-case adversarial set where the parser and bash
disagree once Q170 has landed, and it is unaffected by that fix in either
direction -- the quoting rule and the `+=` spelling are independent, so this
was as true before Q170 as after it.

## Who it is for, and what it is worth

The session whose command defers for a reason nobody can see. The direction is
fail-safe throughout, which is why this ranks below the parser rows it
neighbours rather than beside them:

- **The command-head strip** hands the guard `SG_OVR+=x` as `argv[0]`, which
  matches no SPEC entry, so the lookup misses and the segment defers. A prompt
  nobody expected, on a command that would have been classified.
- **A break-glass prefix written `PROD_GUARD_OVERRIDE+=why`** does not arm.
  The guard prompts or denies where the caller asked it not to, which is the
  safe direction and still not what they wrote.

Neither is an allow, and no path here loosens a verdict.

Frequency is the honest argument against doing it soon: `+=` in command
position is rare in hand-written commands and rarer still as a break-glass
prefix, where the documented spelling is `=`. It is worth a row because it is
a two-character fix to a regular expression whose job is to agree with bash,
and because the disagreement is now the only one left in the set.

## What happens if it is never built

The guards keep disagreeing with bash about one spelling of an assignment, in
a direction that costs a prompt rather than a breach. The cost is friction
that reads as a guard bug, on a command whose text gives no clue why it
deferred.

## Which way it gets built

Widen the name class to admit a trailing `+`, so the pattern accepts
`NAME=` and `NAME+=` and nothing else:

```python
ASSIGNMENT_RE = re.compile(r'^[A-Za-z_][A-Za-z0-9_]*\+?=')
```

That is the whole change, and it is correct in both positions -- `env
'SG_OVR+=x' cmd` and `export SG_OVR+=x` are appends too, so the operand
readers want the same widening rather than an exception.

Where it needs care is the two readers that split a token on `=` to recover a
name: `plugins/prod-guard/scripts/bash-prod-guard.py:491:while i < len(argv) and ASSIGNMENT_RE.match(argv[i]):`
peels the prefix with `partition('=')`, which would yield a name of `SG_OVR+`
rather than `SG_OVR`. Strip the trailing `+` where the name is taken, and
decide per consumer whether an append should replace the tracked value or be
ignored -- workspace-guard's variable tracker is the one where the answer is
not obviously "replace", since it resolves paths from that map and an append
to an unknown value is not resolvable. Dropping the name from the map is the
fail-safe answer there and matches what it already does for a value it cannot
prove.

Fixtures in both directions per consumer: `NAME=v`, `NAME+=v`, and a quoted
`'NAME+=v'`, which must stay a command word once Q170 has landed.
