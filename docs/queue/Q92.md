# Claim Q-IDs on the remote instead of hand-picking them

Three namespaces merged into one store and nothing reserves an ID, so two
sessions filing rows can both pick the next number. `session-backlog` ships
`alloc-queue-id.sh`, which claims `refs/queue-ids/QN` as a compare-and-swap, and
`queue.py claims`, which fails an ID a branch adds without one.

**Land it after the consolidation PR merges, not inside it.** `claims` keys on
the IDs a branch adds *against its merge base*, so once the rows are on `main` a
later branch adds none of them and the gate passes with no backfill at all.
Landing it in the same PR instead means creating 26 refs whose only purpose is to
satisfy a gate that would have passed a day later.

**Use the `gh api` path rather than the bundled allocator.** Measured 2026-08-22
by running branch-guard's own hook against both forms: the push form,
`git push --force-with-lease=refs/queue-ids/Q96: origin <blob>:refs/queue-ids/Q96`,
returns `ask` — "a tag or other non-branch ref rather than the worktree branch" —
so the allocator would prompt on *every* claim, permanently, not only during a
backfill. `gh api -X POST repos/karlkfi/claude-bouncer/git/refs` defers, no
opinion. The bundled script has only the push form, so this repo needs a wrapper
around the API call, and the missing mode is worth an issue on
`karlkfi/claude-skills`.

CI runs the gate with `--strict`, which needs `fetch-depth: 0` on the checkout: a
shallow clone has no merge base, and under `--strict` that is a failure rather
than the skip it is locally.

**Re-measure the prompt before building the wrapper, because the premise it
rests on did not reproduce.** Groomed 2026-08-24: the bundled allocator's push
form claimed `refs/queue-ids/Q133` from a session here with no prompt reaching
the operator, and Q127 through Q132 were claimed the same way earlier that day.
That is not a refutation -- the session was in auto mode, where an `ask` is
answered without surfacing as a blocking prompt, so the reading cannot separate
"branch-guard defers" from "branch-guard asked and something approved it". It is
enough to stop treating the wrapper as settled: if the push form does not prompt
in a mode where an `ask` would surface, this row is only the gate, and the
`gh api` wrapper plus the upstream issue are work nobody owes. Neither half is
shipped as of that date -- `claims` is absent from the `Makefile` and no
workflow sets `fetch-depth`.
