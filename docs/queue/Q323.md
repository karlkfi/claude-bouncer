# A subshell's assignment does not reach its own later commands

Inside `( … )` or `$( … )`, an assignment reaches the commands after it in the
same subshell. prod-guard drops every assignment in a segment that runs apart,
so the subshell's own later commands read the name as unset and ask:

| command | bash 5.3.15 `$C` | guard at `a4ad697` |
|---|---|---|
| `C=kind-ci; kubectl --context $C delete ns x` (control) | `kind-ci` | defer |
| `(C=kind-ci; kubectl --context $C delete ns x)` | `kind-ci` | ask |
| `x=$(C=kind-ci; kubectl --context $C delete ns x)` | `kind-ci` | ask |

The bash column printed `$C` in place of the kubectl command, under
`env -i /opt/homebrew/bin/bash --norc --noprofile`. Measured 2026-11-01 with
`run_hook` and a fixture `$HOME` whose current context is `gke_acme_prod-us`.

The `( … )` row has asked since Q300 scoped those assignments. Q290 put
substitution bodies through the same scoping, so the `$( … )` row moved from
defer to ask there. Both are extra prompts and neither lets anything through.

## Where it happens

`segment_layout` reports only whether a segment runs apart, and `_assign` drops
an `'apart'` assignment outright:
`plugins/prod-guard/scripts/bash-prod-guard.py:734:elif maybe == 'apart':`.
Nothing records which subshell a segment is in.

## Which way it gets built

Give each `( … )` its own copy of the shell and exported scopes: copy them on
the way in, assign into the copy, and drop it on the way out. Pipeline stages
and backgrounded lists keep dropping theirs as Q300 has them, since nothing
after them on the line runs in their process.

## If it is never built

A subshell or substitution that sets its own target and then uses it prompts
when it need not. The cost is a prompt, and nothing here measures how often.
