# branch-guard does not join a backslash-newline continuation

bash joins a backslash-newline into one line before it reads words, so `echo x; \` newline `git commit -m x` runs `git commit`. branch-guard lexes the raw command without that fold, at `plugins/branch-guard/hooks/branch-guard.py:1009:    return split_separator_runs(lex(cmd))`, and the lexer keeps the escaped newline as part of the next word: `tokenize("echo x; \\\ngit commit -m x")` returns `['echo', 'x', ';', '\ngit', 'commit', '-m', 'x']`.
The command word is `\ngit`, which is not `git`.
The other four guards call `strip_comments` from `lib/` first, which folds continuations, and none of them misses this.

Measured 2026-11-17 on `origin/main` at `a3a43e4d` in a fresh repository on `main`, with the harness described in Q349 and bash 5.3.15 running each:

| command | branch-guard |
|---|---|
| `echo x; git commit -m x` -- control | ask |
| `echo x` newline `git commit -m x` | ask |
| `echo x; \` newline `git commit -m x` | **defer** |
| `bash -c "echo x; \` newline `git commit -m x"` -- parent folds it | ask |
| `bash -c 'echo x; \` newline `git commit -m x'` -- child folds it | **defer** |

## Which way it gets built

Call `lib`'s `strip_comments` before `lex` in `tokenize`, as the other guards do, and lex a `bash -c` body the same way.
The comment half changes at least one verdict, in the safe direction: `git commit -m x # \` defers today because the comment's lone backslash reaches the lexer (Q349's table).
With comments stripped it should ask as `git commit -m x` does, which is unmeasured with the fix in place.
Check that it changes no other verdict.

## If it is never built

A git command branch-guard would ask about runs unjudged when a continuation precedes it on the same logical line.
Agents write continuations often in long commands, so the shape is ordinary rather than adversarial, though one placed before `git` itself is less common than one between arguments.
Rate unmeasured.
