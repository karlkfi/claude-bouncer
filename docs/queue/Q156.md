# workspace-guard's override cannot be set from the call it is named on

Every deny this guard downgrades names `WORKSPACE_GUARD_OVERRIDE=<reason>` as
the way out, and a session cannot set it. `guard_override` reads the process
environment and nothing else
(`plugins/workspace-guard/scripts/bash-workspace-guard.py:879:v = (os.environ.get('WORKSPACE_GUARD_OVERRIDE') or '').strip()`),
resolved once into the context
(`plugins/workspace-guard/scripts/bash-workspace-guard.py:2898:override=guard_override(),`).
The hook is a child of Claude Code rather than of the shell the command would
run in, so an inline `VAR=value cmd` prefix never reaches it.

Measured 2026-09-04 on workspace-guard 1.11.0, driving the hook against a real
two-worktree repository built the way `SiblingCheckoutTests` builds one, one
fresh session id per payload:

| Payload | Decision |
|---|---|
| `cp ./a.txt <sibling>/root.txt` | deny |
| the same command behind a `WORKSPACE_GUARD_OVERRIDE="…"` prefix | deny, reason byte-identical to the first |
| the same command, variable in the hook's own environment | ask |

So the escape hatch works from one route, and the deny that advertises it is
emitted unchanged on the route it advertises.

**Three guards to one, and this is the one.** The others read the override off
the command string:
`plugins/prod-guard/scripts/bash-prod-guard.py:2429:if 'PROD_GUARD_OVERRIDE' in seg_inline:`,
`plugins/exit-status-guard/scripts/bash-exit-status-guard.py:437:def has_override(segs):`,
and `plugins/branch-guard/hooks/branch-guard.py:1849:def override_reason(segments):`.
All three read only a segment's leading assignment run, so the name quoted in a
commit message or echoed into a pipe disarms nothing. prod-guard's denial says
"prefix the command with `PROD_GUARD_OVERRIDE=<reason>`", which is the form a
session reaches for by default — and the form that fails here.

**The tests prove the route that works and never touch the one the deny names.**
Every override assertion in `plugins/workspace-guard/tests/test_workspace_guard.py`
goes through the harness's `env_extra`
(`plugins/workspace-guard/tests/test_workspace_guard.py:5780:env_extra={"WORKSPACE_GUARD_OVERRIDE": "deliberate sync"})`
and eight more like it). Not one puts the assignment on a command string, so
the suite could not have caught this.

**The README states the per-command scoping the code cannot deliver.** It calls
the variable
`plugins/workspace-guard/README.md:1426:both, read at hook time (no restart needed):`
and tells the reader to scope it
`plugins/workspace-guard/README.md:1436:override to the moment you actually need it (e.g. one command), not the whole`
session. The paragraph on setting it then says
`plugins/workspace-guard/README.md:1442:your shell takes effect on the next command. To make one stick, put it in the`
`env` block of a settings.json — true for a human at a terminal before `claude`
starts, false inside a session, where each Bash call is its own shell and none
of them is the hook's parent. Both surviving routes are things the operator
does between sessions, which is the opposite of per-command.

**Half of this an inline prefix cannot fix.** The same sentence is emitted on
`Edit` and `Write` denies, where there is no command string to carry a prefix —
measured, both deny with the identical tail
(`plugins/workspace-guard/scripts/bash-workspace-guard.py:2542:WORKSPACE_GUARD_OVERRIDE=<reason> to downgrade this to a prompt.")`).
So the native-tool path needs an answer of its own rather than the same one.
The session grants shipped in [#85](https://github.com/karlkfi/claude-bouncer/pull/85)
are the candidate: `sibling:<root>` is already a grant shape
(`plugins/workspace-guard/scripts/bash-workspace-guard.py:2806:def grant_shape(token, cat, detail, cwd):`)
and `plugins/workspace-guard/scripts/bash-workspace-guard.py:2832:def granted_worktrees(session_id):`
already honours an operator approval for that category.

**Who is worse off.** The agent holding the denial. It writes the prefix it was
handed, gets the same deny back with no signal that the reason was inert, and
has spent a round trip to learn nothing. Q155 records two dispatched sessions
deriving this override by hand on 2026-09-01 — which, on this measurement,
could not have worked from a Bash call either.

**Which way it gets built.** Two pieces, and the second is the question.

1. Read the override off the leading assignment run of the Bash command
   string, falling back to the environment. The plumbing is one field, since
   `build_context` already resolves `override` in one place, so this is a local
   reader of the shape the other three guards each keep locally. Do not promote
   it to `lib/` on the strength of a fourth copy: those three return three
   different things — a dict, a bool, a reason string — the primitive they
   genuinely share is already there as `ASSIGNMENT_RE` and `strip_env_prefix`,
   and this repo shares a behaviour only where two guards need it identical.
   Worth re-asking once the fourth exists.
2. Decide what the `Edit`/`Write` deny says instead. Either name the routes
   that work for a tool call, or route that path to a session grant.

Accepting the prefix is not a loosening: the override lands on `ask`, so an
operator still confirms. It is how the agent reaches them, which is the posture
prod-guard already runs on its own destructive targets.

**Neighbour.** Q155 asks for this variable to be given equal standing in the
same deny's lead rather than buried in its tail. That fix is worth little until
this one lands — promoting an instruction the agent cannot follow makes the
wasted round trip more prominent, not less likely.

**If it is never built.** Every deliberate cross-checkout write costs a round
trip that cannot succeed, on a guard whose case for denying rather than asking
is that the reason carries the repair the agent applies.
