# Decide whether `auto` still belongs in `UNATTENDED_MODES`

`plugins/foreground-guard/scripts/bash-foreground-guard.py:433:UNATTENDED_MODES = frozenset`
converts a would-be `ask` into a `deny`. Both classes deny by default, so the
set only fires on a config-de-escalated `ask` — where a repo wrote
`"action": "ask"` and asked to be prompted.

**Half of this is settled by precedent and needs no decision.** branch-guard
dropped `auto` from `NON_INTERACTIVE_MODES` in v1.7.0, for #33 and #78: an `ask`
in `auto` reaches Claude Code's standard permission prompt and somebody answers
it, so converting it removed the human rather than protecting them.
workspace-guard treats `bypassPermissions` alone as human-free.
foreground-guard is the last of the three still holding `auto`, and "the mode
reads as unattended and is not" applies to it identically.

**What is left is a preference, which is why the label stays.**
foreground-guard's own comment gives a different reason for `auto` than the one
branch-guard retired — not "nobody can answer" but that the prompt interrupts a
run the operator chose not to babysit. That is a considered divergence rather
than an oversight, so the question is narrower than it was: should a
config-declared `ask` be honoured in a mode the operator chose not to watch,
against a cross-guard convention that `auto` is interactive? `dontAsk` and
`bypassPermissions` stay in the set either way, and dropping `auto` is a
one-line change plus the fixtures that assert today's behaviour.
