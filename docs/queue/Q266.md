# A \x1e byte in the command puts every substitution body at the start

Both frontends find where a substitution body sits by replacing it with a
numbered marker, which is the `\x1e` byte around the body's index. Q169 did
this for bash and Q172 for PowerShell. A command that already contains that
byte anywhere can't be marked, so every body falls back to the directory the
string started in, which is what both frontends did before those fixes.

## Measured

2026-10-04, with the hook driven and `cwd` set to a scratch workspace.
`<\x1e>` stands for the literal byte inside double quotes. `q172-x` is a
synthetic name outside the workspace.

| command | decision |
|---|---|
| `cd ..; echo "$(cat q172-x)"` (control) | ask |
| `cd ..; echo "$(cat q172-x)" "<\x1e>"` | (silent) |
| `Set-Location ..; Write-Output $(Get-Content q172-x) "<\x1e>"` (PowerShell tool) | (silent) |

The review of Q172's pull request found the PowerShell case. The bash line is
the same fallback in `mark_substitutions`.

## Which way it gets built

The fallback is silent because the cwd it falls back to is known, but stale. The
remedy the review suggested is unmeasured: when the marking gives up and the
walk has moved the cwd anywhere in the string, recurse with the cwd unknown, so
a relative read in a body denies as `untracked` instead of resolving at the
start. One place covers each frontend: `mark_substitutions` returning
`texts=None` on the bash side, and `ps_subexpression_marks` returning None on
the PowerShell side. On PowerShell, None also covers the two scans
disagreeing, which a 4,651-string enumeration hit once.

## If it is never built

A command carrying a `\x1e` byte reads outside the workspace through a
substitution after a `cd` with no prompt. A model rarely writes that byte on
its own. An injected command could carry one on purpose.
