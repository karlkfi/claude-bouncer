# foreground-guard's friction report counts a decision twice across files

The report dedupes a repeated record by `uuid` within one transcript file, and never across files.
A tool call whose records appear in two files is counted once per file.

Found by the stream reviewer on the Q408 pull request, #413, at `6c62641`.
Re-measured 2026-11-27 over this machine's 3,520 transcript files, reading every error tool result that opens with `foreground-guard: `: 585 unique `tool_use_id`s, 6 of them in two files each.
The report's own count over the same files, at #413's head, is 591, which is the 585 plus those 6.
All twelve files are top-level session transcripts, none under a `subagents/` directory.
Why two sessions hold one call is not traced; a forked or resumed session copying the conversation it came from is the likely cause and is unverified.

## Which way it gets built

Key the dedupe on `tool_use_id` across the whole walk rather than on `uuid` per file, for the deny recovery and the attachment stream alike.
The denominator has the same exposure, since the call tally reads the same records, and was not measured.
Not measured either: whether the other four guards' reports, which share the walk's shape, double-count the same way.

## If it is never built

The report overstates by about 1% here (6 of 591), and a fork-heavy workflow would overstate more.
