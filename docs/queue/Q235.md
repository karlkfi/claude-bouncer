# `env -S` hides the gate inside its string from exit-status-guard

`env -S STRING` splits STRING into words and runs them, so the command is
inside the string. exit-status-guard treats `-S` as an option that takes a
value and drops the string with it
(`plugins/exit-status-guard/scripts/bash-exit-status-guard.py:105:    'env': frozenset({'-u', '--unset', '-C', '--chdir', '-P',  # -P is BSD's`),
which leaves nothing to match, so a gate piped into a filter goes through.

Measured 2026-10-04 by driving the hook with a JSON payload. These are silent
both on `main` at 442c86e and on the Q222 branch, so Q222 did not cause this
and did not fix it:

| command | guard |
|---|---|
| `env -S 'make check' \| tail -5` | silent |
| `env --split-string='make check' \| tail -5` | silent |
| `env -S make check \| tail -5` | silent |

The macOS `/usr/bin/env` runs the string. Under `env -i "$(command -v bash)"`
5.3.15, `/usr/bin/env -S 'sh -c "exit 3"'; echo $?` prints 3.

## Which way it gets built

prod-guard already reads all four spellings and splices the split words back
in front of the remaining operands, in `env_split_string`
(`plugins/prod-guard/scripts/bash-prod-guard.py:680:def env_split_string(argv):`).
Its docstring explains why that is a splice and not a recursive parse. Port
that shape into this guard's `wrapper_operands`, and leave a string that will
not tokenize as `-S`'s value, which is a missed deny.

## Who it is for, and what happens if it is never built

Anyone writing a gate as a split string. That is rare by hand and mostly
appears in shebang lines (`#!/usr/bin/env -S ...`), which this guard never
sees. Left alone, `env -S 'make check' | tail` loses its exit status with no
deny.
