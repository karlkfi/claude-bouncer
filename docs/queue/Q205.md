# Two plugins invoke bare python3, which the launcher exists to avoid

Three of the five guards launch their hook through `run-python-hook.cmd`. Two
call `python3` directly, which is the exact failure the launcher was written to
prevent, and on the machines where it bites neither guard enforces anything and
neither says so.

## Measured

`plugins/foreground-guard/hooks/hooks.json:9:python3 \"${CLAUDE_PLUGIN_ROOT}/scripts/bash-foreground-guard.py\"`
is the only hook foreground-guard registers. prod-guard registers the same form
twice, at
`plugins/prod-guard/hooks/hooks.json:9:python3 \"${CLAUDE_PLUGIN_ROOT}/scripts/bash-prod-guard.py\"`
and again on line 21 for its `PostToolUse`. Neither plugin ships a launcher at
all: `find . -name run-python-hook.cmd` returns three copies, under
`plugins/branch-guard/hooks/`, `plugins/exit-status-guard/scripts/` and
`plugins/workspace-guard/scripts/`, all one digest (2026-09-10).

Both files are unchanged since the subtree import that created them --
`git log --oneline --all -- plugins/foreground-guard/hooks/hooks.json` returns
one commit, `Add 'plugins/foreground-guard/' from commit ...`, and prod-guard's
returns one likewise. So the form predates the marketplace and no commit here
ever chose it.

The repository already states the rule at
`plugins/workspace-guard/CLAUDE.md:39:directly from`, whose mechanism is that
on Windows `python3` usually resolves to the Microsoft Store alias stub, which
is on PATH, exits 9009 when run, and which a presence check finds. The
launcher's own header says the same at
`plugins/workspace-guard/scripts/run-python-hook.cmd:15:silently enforces nothing on those machines.`

## Inferred

**Who is worse off**: a Windows user with the Store stub on PATH and no real
Python 3. Claude Code treats a failed `PreToolUse` hook as non-blocking, so
prod-guard and foreground-guard return nothing and every command they would
have gated proceeds. There is no stderr either, because the two lines that
would have said so live in the launcher these plugins never reach -- so the
failure is silent where the other three guards are loud.

**Exposure is unmeasured here and is probably small.** The stub case needs
Windows plus no working interpreter, and the marketplace's install instructions
do not distinguish platforms. That bounds the urgency, not the correctness:
this is the one failure shape where a guard looks installed and enforces
nothing. It bites once per install on an affected machine, and then on every
command for the life of that install, which is why it ranks above rows that
bite once per session.

**Which way it gets built.** Vendor the launcher into both plugins and point
each `hooks.json` at it, the way the other three do. Two things the change has
to carry: the copy ships executable, with the mode set by
`git update-index --chmod=+x` rather than `chmod` alone, since `hooks.json`
execs it directly; and the plugin's `.gitattributes` must force LF, because the
POSIX tail dies on CRLF. Check what each plugin already declares before
assuming.

**Nothing keeps the copies in step, which this change makes worse.** The
launcher is not named in
`scripts/sync-lib.py:24:MODULES = ('bouncer_parse.py', 'bouncer_grants.py')`,
so `make sync-check` does not see it and three hand-maintained copies become
five. Either add it to the sync -- it is not a Python module, so check the
script's assumptions first -- or add a separate digest gate. File that half as
its own row if it turns out not to be a two-line change.

**Not to be confused with Q134**, which is about nothing driving the launcher's
not-enforcing path in tests. That row assumes a plugin reaches the launcher;
these two do not.
