# workspace-guard's allow speaks for commands it did not judge

One guarded command whose files stay in the workspace earns an `allow` for the whole string, whatever else the string runs.
The other commands get no verdict of their own, and in some modes that `allow` replaces a check that would have run without the guard.

**Measure:** does a `PreToolUse` `allow` stop auto mode's classifier from deciding the call?
Until the test below runs, the cause is unproven for `auto`.

## What is measured

Measured 2026-11-24 (Pacific), with workspace-guard 1.16.0 and Claude Code 2.1.290 on the probe.

The handler, at `adac4904`: `gh pr comment 1 --body x` defers alone, and with an in-repo `cat` in the same string the pair is `allow`.
`git push`, `kubectl delete` and an upload by `curl` give the same two verdicts.
The verdicts did not change across `default`, `plan`, `dontAsk`, `auto`, `acceptEdits` and `bypassPermissions`.
In the prompting modes the `allow` therefore removes a prompt for a command the guard never read.
PowerShell has the same exit, read in the source and not run.
The two sites are `plugins/workspace-guard/scripts/bash-workspace-guard.py:decision, reason = "allow", "Guarded commands target workspace/pipe only"` and `plugins/workspace-guard/scripts/bash-workspace-guard.py:decision, reason = "allow", "Guarded cmdlets target workspace only"`.

Thirty days of one machine's transcripts, Bash only, main and subagent calls deduplicated by tool-use id, hold 53,245 results: 49,767 in `auto`, 950 in `acceptEdits`, 7 in `default`, 2,521 with no recorded mode.
Leaving out calls the classifier refused or a guard denied, 24,699 in `auto` carry this guard's recorded `allow` and 22,564 carry no record from it.
A pattern for `gh` writes and `git push` matches 1,161 of the first group, 2,523 of the second and 92 of the refused calls.
There were 107 classifier refusals, 106 in `auto` and 1 with no recorded mode; 7 of the 107 were the classifier giving no verdict.

The recorded verdicts alone do not show that no refused call had an `allow`.
None of the 107 carries a completed record from any guard, and it is not known whether Claude Code keeps one for a call the classifier refuses.
Replaying each command through the hook, as `auto` and with its own session id and root, answers instead: 106 of the 107 defer, 1 denies, and none is `allow`.
The same replay gives `allow` for 990 of 1,000 sampled recorded allows, so it can produce one.
That is still correlation.
The refused commands are a different mix: 57 carry one category, "Safety Bypass Flag", and only 18 name a command this guard judges.

The published docs do not settle it.
The [hooks page](https://code.claude.com/docs/en/hooks) says `allow` skips the permission prompt.
The [permission modes page](https://code.claude.com/docs/en/permission-modes) lists the order auto mode decides in and puts a hook's `allow` in it only for messages to another agent.
Where the server reviews a session's calls, it reviews the input Claude wrote, so a hook may be too late to skip that review.

## Why the set of modes is not `DEFER_RUNS_MODES`

`plugins/workspace-guard/docs/permission-modes.md:12:Each cell below is an end-to-end run` opens the matrix behind that set, and its one command was `touch`.
The docs say `acceptEdits` approves a fixed list (`mkdir`, `touch`, `rm`, `rmdir`, `mv`, `cp`, `sed`) and prompts for other commands that are not read-only.
A headless probe agrees, one trial per cell, with no user settings or plugins loaded:

| mode | command | hook | ran |
|---|---|---|---|
| `acceptEdits` | `touch sentinel` | none | yes |
| `acceptEdits` | `python3 -c` that creates `sentinel` | none | **no** |
| `acceptEdits` | the same `python3 -c` | `allow` | yes |
| `default` (control) | the same `python3 -c` | none | no |

So `acceptEdits` belongs with the prompting modes for a command outside that list, and `auto` was never measured on a command the classifier would stop.
`permission-modes.md` does not mention the classifier, and calls Bash pre-approved in both modes.
`escalate_suppression` reads the same set, so its denies in `acceptEdits` rest on the same cell.

## First step

In a throwaway repository, take one command the classifier refuses reliably and run it from the same transcript state in each cell, several trials each:

- no hook, and a hook forced to `allow`
- alone, and joined to an in-repo read, under both hooks, so a change caused by the extra text is not read as the hook's
- the real guard, joined to the same read

Record whether the session's calls are reviewed by the server (`/status`, `Auto mode server`), and run both kinds if the machine can reach both.
Read a refusal from the tool result, not from the hook records.
Re-run the matrix in the same sitting with a command outside the `acceptEdits` list, since a verdict conditional on mode triggers the re-measure rule in `permission-modes.md`.
Do not write the refused command into this repository.

## The change, if the test confirms it

- In `auto`, return no verdict where the hook now returns `allow`.
  In `bypassPermissions` an `allow` and no verdict both run, so it can go the same way with no effect.
- In every other mode, `acceptEdits` included, return `allow` only when every command in the string is one the guard understands.
  `plugins/workspace-guard/docs/permission-modes.md:103:spend it only where the hook genuinely understands the whole command string` already states that rule, and the same page gives sparing the operator prompts as the `allow`'s job.
- `ask` and `deny` do not change, the escalations included: a suppressed `allow` is a different case from one the mode makes pointless.
- Both frontends, the README's decision table, `design.md` and `permission-modes.md` move with it.

If the test shows the classifier decides anyway, the `auto` half is dropped.
The narrower `allow` still stands on the handler results above, and so does correcting the `acceptEdits` cell.

Overlaps: Q398 is the narrower `allow`'s case for a script written by a command the guard does not judge, and Q401 asks which strings the lexer reads with confidence.

## Costs to measure

- Classifier delay on about 25,000 calls a month, not measured.
  The docs say read-only commands skip the classifier where the server does not review the session, and that the server's review makes no separate call, so the affected share is smaller by an unknown amount.
- Extra refusals: at the rate of the group with no record, 106 in about 22,700, the 24,699 would draw about 115 a month.
  Fewer are expected, because the two groups run different commands.
- More prompts in `manual`, `plan` and `acceptEdits`, and more blocks in `dontAsk`, for a string that mixes a guarded read with a command the guard does not judge.
  How many of the 24,699 are such strings was not counted.
- No added protection in `bypassPermissions`.
  In `acceptEdits` the gain is the prompt that mode already gives without the guard.

## If it is never built

In prompting modes, an unjudged command keeps running with no prompt when an in-workspace read shares its string.
In `auto`, if the test confirms the cause, the same strings skip the classifier, and so does a string that gets a wrong `allow` from a parsing bug such as Q404's.
