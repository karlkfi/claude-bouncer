# `push_overlap` measures the session worktree, not the ref being pushed

`plugins/branch-guard/hooks/branch-guard.py:1190:def push_overlap(cwd, branch):`
diffs `HEAD` against the base in `cwd`, and `cwd` is the session's working
directory. The call site takes that answer as the push's own:
`plugins/branch-guard/hooks/branch-guard.py:1538:base, paths = push_overlap(cwd, branch)`,
and a non-empty path list turns a would-be `allow` into
`plugins/branch-guard/hooks/branch-guard.py:1540:return ('deny-rebase', push_overlap_reason(base, paths))`.

The reading is only about the push while those two are the same repository. A
session that rebases in a **second worktree** and pushes from there gets its
push judged against whatever branch the session worktree happens to hold — a
different branch, a different diff, an overlap the push does not contain.

`plugins/branch-guard/hooks/branch-guard.py:1741:def targets_other_repo(globals_):`
is the guard against exactly this, and it only sees `git -C`, `--git-dir` and
`--work-tree`. A `cd` into another worktree is invisible to it, so the probe
runs and answers about the wrong tree.

## Measured

2026-08-27, branch-guard 1.10.0 (the installed copy is byte-identical to this
tree). Throwaway repo: `origin/main` moves on `CLAUDE.md`; worktree `wtX` holds
branch `X`, which edits the same line of `CLAUDE.md`; worktree `wtY` holds
branch `Y`, which edits `docs.md` only. Session cwd is `wtX` in every row.

| command | verdict | what the probe measured |
|---|---|---|
| `git push --force-with-lease` | `deny-rebase` | `X` — correct |
| `cd wtY && git push --force-with-lease` | `deny-rebase` | `X`, while `Y` is what gets pushed |
| `git -C wtY push --force-with-lease` | `allow` | nothing; the probe is skipped |
| `git push --force-with-lease=Y origin Y:Y` | `ask` | nothing; the probe is not reached |

The last row is worth keeping in view, because it rules out the reproduction
that first comes to mind. Under the default `strict` policy an explicit
`<src>:<dst>` naming a branch other than the session's `HEAD` is answered by
`push_decision` before any probe runs, so a cross-name refspec never mints this
verdict. The false positive arrives through the *no-refspec* form, from a cwd
the guard was never told had moved.

## The half that turns it into a bypass

`cd wtY && git push` is denied **and the break-glass is refused**. Prefixing
`BRANCH_GUARD_OVERRIDE=<reason>` in either segment position leaves the verdict
`deny`, and the reason drops the sentence that would have named the prefix.
Cause is
`plugins/branch-guard/hooks/branch-guard.py:2190:and all(v in ('allow', 'filter', 'benign', 'ask')`:
the `cd` segment classifies `nongit`, `liftable` goes false, and the whole
all-segments rule that protects the override does its job on a segment that
carries no risk.

So the responses available to a session meeting this are: abandon the push, or
reshape the state the probe reads. The session that found it did the second —
checked the rebased head out in the session worktree under a temp branch,
pushed, restored — which is a guard bypass performed by an agent with nobody in
the loop. That is the argument for fixing the probe rather than documenting the
workaround: a false positive clearable only by making the probe measure
something else teaches the bypass, and the bypass generalizes to the true
positives.

Observed in `karlkfi/claude-spill-guard` while rebasing PR #31 onto a moved
`main`. The push carried four files, all under `docs/queue/`; the denial named
`CLAUDE.md` and `README.md`, which belonged to the session worktree's branch.

## Directions, none of them chosen

1. **Resolve the ref actually being pushed** and measure that, instead of the
   session cwd's `HEAD`.
2. **Skip the probe** where the push names a ref that is not the session's
   `HEAD` — it has no opinion it can honestly offer.
3. **Keep the session-cwd read** and detect the multi-worktree case with
   `git worktree list`, downgrading the verdict there.

Whoever takes it should weigh these against the comment the current read was
written under —
`plugins/branch-guard/hooks/branch-guard.py:1535:these read the SESSION cwd, so a`
— which is a considered choice rather than an oversight: it is what keeps a
`git -C` from measuring a repository the command does not act on. Any fix has
to keep that property. The break-glass refusal above is separable and cheaper,
and may deserve its own row once the direction is settled.

Fixtures go on the push-overlap block, whose
`plugins/branch-guard/test/run.sh:1781:make_overlap_repo() {` builds a single
checkout and so cannot express this at all. The shape it needs already exists a
thousand lines up — §5c's
`plugins/branch-guard/test/run.sh:298:git -C "$WORK" worktree add -q "$WT" claude/x`
proves the payload-cwd rule for an `Edit`, which is the same question one tool
over.
