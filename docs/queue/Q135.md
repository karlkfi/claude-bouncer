# `push_overlap` measures the session worktree, not the ref being pushed

`plugins/branch-guard/hooks/branch-guard.py:1266:def push_overlap(cwd, branch):`
diffs `HEAD` against the base in `cwd`, and `cwd` is the session's working
directory. The call site takes that answer as the push's own:
`plugins/branch-guard/hooks/branch-guard.py:1621:base, paths = push_overlap(cwd, branch)`,
and a non-empty path list turns a would-be `allow` into
`plugins/branch-guard/hooks/branch-guard.py:1623:return ('deny-rebase', push_overlap_reason(base, paths))`.

The reading is only about the push while those two are the same repository. A
session that rebases in a **second worktree** and pushes from there gets its
push judged against whatever branch the session worktree happens to hold — a
different branch, a different diff, an overlap the push does not contain.

`plugins/branch-guard/hooks/branch-guard.py:1840:def targets_other_repo(globals_):`
is the guard against exactly this, and it only sees `git -C`, `--git-dir` and
`--work-tree`. A `cd` into another worktree is invisible to it, so the probe
runs and answers about the wrong tree.

One cwd is read for the whole command and never revised —
`plugins/branch-guard/hooks/branch-guard.py:2239:cwd = data.get('cwd') or os.getcwd()`
— and the branch comes from the same place,
`plugins/branch-guard/hooks/branch-guard.py:2240:branch = current_branch(cwd)`.
So a moved cwd misdirects the whole push classification, not only the overlap
probe: `push_decision` is answering about the session's branch too.

## Measured

Re-measured 2026-09-04 against this tree at `7e143fc5`, by driving the hook on
synthetic stdin. Throwaway repo: `origin/main` moves on `CLAUDE.md`; worktree
`wtX` holds branch `X`, which edits the same line; worktree `wtY` holds branch
`Y`, which edits `docs.md` only.

| session cwd | command | verdict | what the probe measured |
|---|---|---|---|
| `wtX` | `git push --force-with-lease` | `deny-rebase` | `X` — correct |
| `wtX` | `cd wtY && git push --force-with-lease` | `deny-rebase` | `X`, while `Y` is what gets pushed |
| `wtX` | `git -C wtY push --force-with-lease` | `allow` | nothing; the probe is skipped |
| `wtX` | `git push --force-with-lease=Y origin Y:Y` | `ask` | nothing; the probe is not reached |
| `wtY` | `git -C wtX push --force-with-lease` | **`allow`** | nothing; the push really does overlap |

The last row is new, and it is the inverse of the row's own complaint: the same
blindness that mints a false deny also mints a false **allow**. `git -C` from a
worktree whose own branch is clean auto-approves a push that would land the
merge the check exists to stop, and it does not defer — the reason reads
`Safe git/gh operation on branch 'Y' — auto-approved`. The `cd` spelling of it
defers instead, because the `cd` segment is `nongit` and blocks auto-approve, so
only the `git -C` spelling is actively waved through.

The fourth row still rules out the reproduction that first comes to mind: under
`strict` an explicit `<src>:<dst>` naming a branch other than the session's
`HEAD` is answered by `push_decision` before any probe runs. The false positive
arrives through the *no-refspec* form, from a cwd the guard was never told had
moved.

**The 2026-08-27 note that the installed copy is byte-identical to this tree no
longer holds.** #85 landed 232 diff lines into this file since, so the tree is
`7e143fc5…` against installed 1.10.0's `fe6798df…`. Every verdict above is the
tree's, which is where a fix lands. Line numbers moved with it; the citations
here were re-checked against `7e143fc5`.

## The direction: resolve the cwd the push runs from

Direction 1 of the three below, and the measurement settles it by eliminating
the other two rather than by preferring it.

Its cost is the surprise. Tracking a literal `cd` is string work, and the probes
then run with a different `-C` — so the fix adds **no git subprocess at all**.
Counted by a `PATH` shim on 2026-09-04: the deny arm and the allow arm each
spawn exactly six git processes (`symbolic-ref` ×2, `merge-base`, `rev-parse`,
`git diff` ×2), and resolving the cwd changes which tree those six run against,
not how many there are. `current_branch` in the resolved cwd replaces
`current_branch` in the session cwd; it does not join it.

That also fixes the false allow, because the probe stops being skipped and
starts being aimed. Keeping the property the current read was written for —
`plugins/branch-guard/hooks/branch-guard.py:1618:these read the SESSION cwd, so a`
— means keeping *measure the tree the command acts on*, which is what the
comment is protecting; the skip is the mechanism, not the property.

Two things a fix has to get right, both measured here:

- **A literal target only.** A `$VAR` or an unresolved `$( )` target cannot be
  resolved by the hook, and the honest answer there is the current skip.
- **Worktree identity, not repository identity.** `wtX` and `wtY` return the
  same `--git-common-dir` and different `--show-toplevel`. A same-repository
  test re-admits this exact defect. And `--git-common-dir` answers `.git`
  relative from a primary checkout and an absolute path from a worktree, so a
  string comparison calls one repo two; `--path-format=absolute` settles it.

## What the measurement rules out

**Direction 2 — skip the probe where the push names a ref that is not the
session's `HEAD` — cannot reach the defect, and costs a correct deny.** Under
`strict`, `push_decision` returns `allow` only where every refspec resolves to
the session branch, or on the one leased cross-name rewrite at
`plugins/branch-guard/hooks/branch-guard.py:1133:leased_rewrite = (not delete and src_b == current`.
The failing case names *no* ref, so the condition is false and nothing changes.
The leased rewrite is the only shape where `dst != current` reaches the probe —
and there `src` **is** the session `HEAD`, so the probe is right. Driven both
ways: `git push --force-with-lease=Z origin HEAD:Z` denies from `wtX` and
allows from `wtY`. Direction 2 would skip precisely that one, turning a correct
deny into no opinion, while leaving both false verdicts standing.

**Direction 3 — detect the multi-worktree case with `git worktree list` and
downgrade — would disable the check in the repositories that use it.** This
repository has 56 worktrees, so every session is in one and the downgrade fires
on every push. It is also the most expensive candidate probe, and it buys a
verdict weaker than the one it replaces. Medians of 21 runs, all in one pass on
a quiet machine (load average 5.5), against this repository:

| call | cost | vs floor |
|---|---|---|
| `rev-parse --git-dir` (process-spawn floor) | 9.04 ms | 1.00× |
| `rev-parse --show-toplevel` | 8.72 ms | 0.96× |
| `git worktree list` | 16.51 ms | 1.83× |
| `git log --stat` (costly control) | 198.00 ms | 21.89× |

The worktree-identity read direction 1 needs is indistinguishable from the cost
of starting a process at all; `git worktree list` is nearly twice that. The
control is in the table because a set of near-identical numbers cannot otherwise
be told from an instrument that has stopped discriminating.

## The half that turns it into a bypass, and where it now sits

`cd wtY && git push` is denied **and the break-glass is refused** — confirmed
again 2026-09-04. Cause is
`plugins/branch-guard/hooks/branch-guard.py:2297:and all(v in ('allow', 'filter', 'benign', 'ask')`:
the `cd` segment classifies `nongit`, `liftable` goes false, and the rule that
protects the override does its job on a segment carrying no risk.

**That half is [Q146](Q146.md)'s, and the two rows are now separable.** The
boundary is what each one changes:

- **Q146 owns whether the break-glass is reachable** — the `liftable` gate. Its
  fix is a classification change and touches no probe, so a `cd` whose literal
  target is the **same worktree** can be made liftable on its own. That is the
  case the measurement finds in the wild.
- **Q135 owns what the probe measures** — the cwd handed to `push_overlap` and
  `current_branch`. Only this row can fix a `cd` into a *different* worktree,
  because until the probe is aimed there is no correct verdict to lift to.

So Q146 is not blocked on this row, and a cross-worktree `cd` stays denied under
Q146's fix alone, which is the right residual: the override should not lift a
verdict the guard measured in the wrong tree. Whichever lands first, both need
the worktree-identity test above, and that is the shared piece.

## Prevalence

Across every session transcript on this machine (this one excluded), 47 real
branch-guard denials in 34 sessions — counted by requiring the guard's line at
position 0 of the tool result, since the guard's own text also appears in test
output and probe logs, and a looser match reports 217 across 89 sessions.
**27 of the 47 are this row's `deny-rebase` route, across 24 sessions** — the
most-fired denial in the store. 5 of those 27 led with a `cd`, two of them from
the `claude-spill-guard` session named below.

Observed in `karlkfi/claude-spill-guard` while rebasing PR #31 onto a moved
`main`. The push carried four files, all under `docs/queue/`; the denial named
`CLAUDE.md` and `README.md`, which belonged to the session worktree's branch.

## Rank

**Keeps `a0`.** Nothing displaces it: the route fires more than any other, the
direction is now settled, the fix costs no additional subprocess, and it is the
only row that can close the false allow — which is worse than the false deny it
was filed for, because a wrong deny is visible to the session and a wrong allow
is not.
