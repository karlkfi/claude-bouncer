# git config --glo defers where --global asks

`git config --glo user.name x` gets no decision from branch-guard, while
`git config --global user.name x` asks. git expands `--glo` to `--global`, as it
does any unique prefix of a legacy config flag (`--get-r` is `--get-regexp`).
Found by the independent review of PR #295 as a note; this row has not
re-driven the `--glo` case.

Q285 left `git config` out of `GIT_LONG_OPTS` because
`git config --git-completion-helper-all` lists only the config subcommands,
not the legacy flags, so the expansion never sees them. The config rule reads
whole flags
(`plugins/branch-guard/hooks/branch-guard.py:2476:        if flags & {'--global', '--system', '--add', '--unset', '--unset-all',`)
and lands an abbreviation on its ambiguous `git config key value` defer.

A defer reaches the normal permission flow, so this only bites a session that
allowlists `git config`, where an abbreviated global write then runs with no
prompt. Next step: add a `config` entry to `GIT_LONG_OPTS` written from
`git config -h`'s legacy usage, probe every prefix against git as Q285 did, and
pair `--glo` with `--global`. The remedy is unmeasured.
