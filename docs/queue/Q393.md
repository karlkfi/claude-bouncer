# A program file passed to awk -f or sed -f is never read

Q328 and Q334 read the program an awk or sed command is given on its command
line for the files it opens. A program given with `-f FILE` is not read: FILE is
judged as a read, and the README's Limitations say its contents "are not the
hook's to read". So the same program allows from a file:

| Command | Verdict |
|---|---|
| `awk -f p.awk in.txt`, p.awk holding `{print > "../x"}` | allow |
| `sed -f s.sed in.txt`, s.sed holding `w ../x` | allow |
| `awk '{print > "../x"}' in.txt` | ask |

Reviewer C measured two forms where the program text is in the command string
after all, so no file-time race applies: `awk -f - in.txt <<'EOF'` with a
`{ print > "L" }` body, and `awk -f /dev/stdin in.txt <<< '{ print > "L" }'`.
Both allow, and both wrote the file.

Verdicts measured 2026-11-17 by running the hook on the Q334 branch against a
scratch workspace. macOS awk run on such a `p.awk`, with a relative target,
created the file. Reviewer C counted 35 `awk -f` commands in local transcripts
with a crude match.

## The question first

This is a decision before it is a fix. The hook already exempts repo-resident
code: a script that resolves inside the workspace vouches for itself, so
`cat a && python3 x.py` allows (README, "Interpreter code"). An in-workspace
`p.awk` allowing is that rule applied to awk. Two ways it could change:

- **Read FILE when it is inside the workspace** and judge it like an inline
  program. Unlike Python, the hook can read both languages, so this would close
  the gap without new friction. The cost is reversing the documented "not the
  hook's to read", and a file read at hook time can differ from the one the
  command runs, when the same string writes it first; reviewer C proposes
  treating FILE as unread in that case. Reviewer C prefers this option.
- **Raise the interpreter signal** for `-f`, as reviewer C proposed. A FILE
  outside the root already asks as a read, as `cat in.txt && python3
  /x.py` does (measured), so the signal changes only the inside case, where it
  would make awk and sed stricter than every other interpreter.
