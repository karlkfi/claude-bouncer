# A program fed to awk -f on stdin is never read

Q328 and Q334 read the program an awk or sed command is given on its command line for the files it opens.
A program given with `-f FILE` is not read, and for a real file that is the documented contract: the README's Limitations say its contents "are not the hook's to read".
Karl kept that contract on 2026-11-17, so `awk -f p.awk in.txt` with p.awk holding `{print > "../x"}` goes on allowing, and this row does not change it.
His reason: reading every in-workspace script would still leave compiled and binary programs unread without decompilation, so closing that class belongs to a sandbox, and the guard stays a best-effort check against accidental misuse.

Two forms put the program text in the command string anyway, so reading them is the Q334 rule applied rather than a file read.
Reviewer C measured both on the Q334 branch against a scratch workspace, and both allow and wrote the file:

| Command | Verdict today | Should be |
|---|---|---|
| `awk -f - in.txt <<'EOF'` with a `{ print > "L" }` body | allow | judged as the inline program |
| `awk -f /dev/stdin in.txt <<< '{ print > "L" }'` | allow | judged as the inline program |

The fix reads the heredoc or here-string body as the program when `-f` names `-` or `/dev/stdin`, and judges it as the inline form `awk '{ print > "L" }' in.txt` is judged, which asks for an outside `L`.
`sed -f -` and `sed -f /dev/stdin` are unmeasured; check them first and fold them in if they allow the same way.
A program piped in from another command (`cmd | awk -f -`) stays unread, since its text is not in the string.
