# pipefail set in an implicit subshell still counts as on

Q148 scoped pipefail to the subshell that sets it, but only to a subshell
written with `(...)`
(`plugins/exit-status-guard/scripts/bash-exit-status-guard.py:599:def pipefail_walk(segs, initial=False):`).
bash also runs a command in a subshell when it is a stage of a pipeline or
backgrounded with `&`, and a function body does not run until the function is
called. In each of these the setting never reaches the pipe that follows, yet
the guard counts it as on and lets the piped gate through.

Found by the independent review of the Q148 pull request (#205). Driven
2026-10-04 under `env -i` bash 5.3.15, where `false | true` after each prefix
prints rc=0, and through the hook with `make check | tail -5`, which is silent
both on `main` and on the Q148 branch:

| prefix | pipefail on for the pipe (bash) | guard |
|---|---|---|
| `set -o pipefail \| true;` | no | silent |
| `set -o pipefail &` | no | silent |
| `f() { set -o pipefail; };` (never called) | no | silent |

## Which way it gets built

In `pipefail_walk`, apply a `set` only when its segment is neither a
pipeline stage nor backgrounded. A segment's own `post_ops` already show both
(`|`, `|&`, `&`), and the segment before it shows whether it is the right-hand
stage of a pipe. A function definition needs its body recognised as a
definition rather than a brace group that runs. If that cannot be done
reliably, leave it counting as on, since a missed deny is the direction this
guard takes when unsure.

## Who it is for, and what happens if it is never built

Nobody writes these on purpose to get a pipe through. Each is a way to append
pipefail that does not work. The cost of leaving it is that the token which
lifts the deny can still be added in a form that does nothing, which is the
same evasion surface Q148 closed for the after-the-pipe placement. The cost of
delay is flat.
