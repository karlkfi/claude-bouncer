# Re-drive every bash 5.3.15 claim under a named binary

Comments and docstrings across the tree say a shell behaviour was "measured on
bash 5.3.15", and some of them may have been taken on macOS's bash 3.2.57
instead. **The finding behind this row is unverified**: nobody has re-driven a
single one of the claims below, and how each was originally driven is unknown.

The mechanism is reported, not measured here. On this machine `env -i` clears
`PATH`, so a bare `env -i bash` resolves to `/bin/bash`, which is 3.2.57; the
Homebrew 5.3.15 is `/opt/homebrew/bin/bash`, and it is what the Bash tool runs.
Two bash claims in pull request #157 (Q214) flipped for exactly that reason,
and Q217 already records the trap for its own table:
`docs/queue/Q217.md:45:for the 3.2.57 column. Name the binary: `.

Who is worse off: a reader of the parser or a test who takes a recorded bash
answer as the shell that decides, and a worker who fixes a guard to match it. A
claim taken on 3.2 can encode the wrong behaviour into a test that then guards
it. If it is never done, each such claim stays wrong until someone happens to
re-drive it, and every row filed with the same wording adds to the set.

## The approach

Re-drive each claim with the binary named and its version printed in the same
call, so the output says which shell answered:

```
env -i /opt/homebrew/bin/bash --norc --noprofile -c 'echo "$BASH_VERSION"; <the claim>'
```

Where the 5.3 answer matches the recorded one, the claim holds and needs no
edit. Where it differs, the recorded answer came from 3.2 or from nowhere: fix
the comment, and where a test asserts the behaviour, fix the test and the guard
together, in their own PR, since that is a behaviour change rather than a doc
fix. A change under `lib/` reaches all five guards, so run `make sync` and say
which suites were re-run.
