# exit-status-guard reads git --git-completion-helper-all as a gate

`git checkout --git-completion-helper-all` prints the subcommand's option names
and exits. It has no result to lose. exit-status-guard still denies it as a
gate, both piped and sequenced. Re-driven 2026-11-02 against the hook on `main`
at `0608cb6b`:

- `git checkout --git-completion-helper-all | tr " " "\n"` is denied, because
  the gate is piped into a filter.
- `git switch --git-completion-helper-all | tr " " "\n"` is denied the same
  way.
- `git checkout --git-completion-helper-all; git commit -m x` is denied,
  because the gate is sequenced before a state change.

`git checkout` and `git switch` are in the `gates` registry
(`plugins/exit-status-guard/exit-status-guard.json:41:    "^git\\s+(pull|push|rebase|merge|cherry-pick|apply|am|commit|revert|add|stash|clone|fetch|checkout|switch|worktree|reset)(\\s|$)",`).
The structural escape for a command that only prints is `PROBE_FLAGS`
(`plugins/exit-status-guard/scripts/bash-exit-status-guard.py:402:PROBE_FLAGS = frozenset({'--version', '--help', '-V', '-h', 'version', '--usage'})`),
and git's completion helpers are not in it.

**Who is worse off.** A session building a git long-option table from git's own
output. The branch-guard work for Q285 and Q329 did exactly that: branch-guard's
`GIT_LONG_OPTS` table is taken from `git <sub> --git-completion-helper-all`. In
the 2026-11-01 batch the stream B worker was denied twice and rewrote the
command as separate calls with Python formatting. The cost is one rewrite per
occurrence, and occurrences are rare: they come only with git option work.
Flat urgency.

**Next step.** Add `--git-completion-helper` and `--git-completion-helper-all`
to `PROBE_FLAGS`. Pin the three commands above as allows, and pin
`git checkout main | tr` as still denied, so the new flags cannot exempt a real
checkout.
