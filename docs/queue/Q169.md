# A substitution body resolves relative paths against the wrong directory

workspace-guard tracks the cwd across a `cd` chain, so a relative operand is
checked against the directory bash would open it in. The command-substitution
recursion does not get that directory: it runs once over the whole string
*after* the group loop and starts from the string's entry cwd
(`plugins/workspace-guard/scripts/bash-workspace-guard.py:3898:_analyze_command(body, ctx, base_cwd,`),
so a relative path inside a substitution that follows a `cd` is judged against
a directory the command has already left. The verdict is then wrong in both
directions -- a read outside the root passes silently, and a read inside it
draws a prompt naming a path the command never touches.

Shell `-c` bodies two blocks below already do the right thing: each is carried
with the cwd of its own group
(`plugins/workspace-guard/scripts/bash-workspace-guard.py:3707:shell_bodies.extend((b, group_cwd) for b in shell_c_bodies(g))`)
and recursed into with it
(`plugins/workspace-guard/scripts/bash-workspace-guard.py:3918:for body, body_cwd in shell_bodies:`).
Substitution bodies cannot take the same route, because
`command_substitutions` scans the RAW string -- which is what reads quoting
correctly -- and the group loop walks post-shlex tokens, which carry no
position.

## Measured

2026-09-07, against the hook at 46ede93. Project root `/Users/karl/probe-proj`
with a `sub/` subdirectory; `/Users/karl/outside` is outside the root. Nothing
executed -- the hook resolves lexically, so the paths need not exist. Each row
is one Bash payload; the reason column is the path the decision names.

Row 3 was added later, from Q171's settling pass, and was taken against 17df02a
under a temporary root rather than `/Users/karl/probe-proj`. The two commits
carry a byte-identical `bash-workspace-guard.py` and `bouncer_parse.py`
(`git diff 46ede93 17df02a` touches only `docs/queue/`), and rows 1, 2 and 4
were re-run there and agreed, which is what lets the row sit in this table.

| command | verdict | path named | bash would open |
|---|---|---|---|
| `cd /Users/karl/outside && cat x` | ask | `/Users/karl/outside/x` | same |
| `cd /Users/karl/outside && echo $(cat x)` | ask | `/Users/karl/outside/x` | same |
| `cd /Users/karl/outside && echo "$(cat x)"` | **defer** | -- | `/Users/karl/outside/x` |
| `cd /Users/karl/outside && echo \`cat x\`` | **defer** | -- | `/Users/karl/outside/x` |
| `cd /Users/karl/outside && echo \`tee y\`` | **defer** | -- | `/Users/karl/outside/y` |
| `cd sub && cat ../x` | allow | -- | `<root>/x` |
| `cd sub && echo $(cat ../x)` | **ask** | `/Users/karl/x` | `<root>/x` |
| `cd sub && echo \`cat ../x\`` | **ask** | `/Users/karl/x` | `<root>/x` |
| `cd /Users/karl/outside && cat <<EOF`⏎`$(cat x)`⏎`EOF` | **allow** | -- | `/Users/karl/outside/x` |
| `cd /Users/karl/outside && cat <<EOF`⏎`` `cat x` ``⏎`EOF` | **allow** | -- | `/Users/karl/outside/x` |

Three readings come out of that table, and the third is the one that decides
the fix.

**The `$( )` form is covered by accident, at the top level and only unquoted.**
`(` is a punctuation char and `glue_dollar_paren` deliberately leaves it in the
token stream, so an unquoted top-level `$(…)` body's operands are also seen by
the group loop, with the tracked cwd. That is why row 2 is right. Quote the
same substitution and shlex returns the whole of it as one word -- `echo
"$(cat x)"` lexes to `['echo', '$(cat x)']` where the bare spelling lexes to
`['echo', '$', '(', 'cat', 'x', ')']` -- so nothing inside it is ever a command
the group loop walks, and row 3 is missed exactly as the backtick is. The
accident is a property of the *spelling*, not of the construct. The recursion
still re-checks the operands it did cover from `base_cwd`, which is where row
7's spurious `/Users/karl/x` comes from -- the group loop got it right and the
recursion added an offender beside it.

**A backtick body reaches the recursion and nothing else, and so does a quoted
`$( )`.** Rows 4 and 5 are missed offenders -- an out-of-root read and an
out-of-root write, no prompt at all, where the unquoted `$( )` twin asks -- and
row 3 is the same miss on the commoner spelling of the covered form, the one a
writer reaches for the moment a path might carry a space. All three resolve
against `base_cwd`, land back inside the root, and disappear.

**A heredoc body's substitutions reach the recursion and nothing else either,
whichever form they are written in.** Rows 9 and 10 are both missed, because
`strip_heredoc_bodies` removes the body before the group loop sees it, so the
"the flattened pass already had them" property that saves row 2 does not hold
there.

## Which way it gets built

**Carry a position, not a kind.** The alternative -- have
`command_substitutions`
(`lib/bouncer_parse.py:615:def command_substitutions(text, quotes=True):`)
say whether a body opened with `$(` or a backtick, and skip the `$(` bodies'
operands as already covered -- is refuted three times over. Rows 9 and 10: a
`$( )` inside a heredoc body was never covered, so skipping it on its kind
loses it. Row 3 is the cheaper refutation and needs no heredoc at all: a quoted
top-level `$( )` is not covered either, so the kind reading would take the
commonest spelling of the construct from missed-and-recoverable to
missed-by-design.

Row 3 also says what a kind could not fix. The fact that decides whether the
group loop saw a body is not `$(` against a backtick, it is whether the body
sat inside quotes -- and `command_substitutions` does not return that either,
so a kind reading would need a second out-parameter to answer a question a
position answers on its own. A position answers for the backtick, the heredoc,
and both spellings of `$( )` alike, because in every case the question is the
same one: which directory was tracked at the point in the string where this
body sat.

Matching `"$(" + body + ")"` back against the raw text to recover either fact
is not an option. It is a second parser over text the lexer already read, and
it disagrees with the lexer the first time one body appears in both forms. The
existing raw/stripped reconciliation is already keyed on body text
(`plugins/workspace-guard/scripts/bash-workspace-guard.py:3204:raw.setdefault(strip_heredoc_bodies(body), body)`),
where two identical bodies collapse into one -- a position would retire that
too.

So the shape is roughly:

1. `lib/bouncer_parse.py` -- `command_substitutions` grows an out-parameter
   carrying each body's offset in the string it scanned, additively, the way
   `strip_heredoc_bodies` grew `unterminated`. Every current caller passes
   nothing and is unaffected. `strip_heredoc_bodies` needs the same for its
   `expanded` bodies, or the heredoc rows above stay missed.
2. `bash-workspace-guard.py` -- the group loop records the tracked cwd against
   a position, so a body's offset resolves to the directory in force there.
   This is the part with no obvious shape today, because the loop is
   token-based and shlex reports no token positions. The recursion then takes
   that cwd in place of `base_cwd`.
3. The PowerShell frontend has the same line
   (`plugins/workspace-guard/scripts/bash-workspace-guard.py:5190:_ps_analyze_command(body, ctx, base_cwd,`)
   against its own location tracker, and should be fixed with it or the row
   split.

**The conservative fallback, if step 2 turns out too expensive.** The Q66
precedent is right beside this and names the same obstacle in its own comment
-- "so it has no position at which to snapshot the live map"
(`plugins/workspace-guard/scripts/bash-workspace-guard.py:3535:loop, so it has no position at which to snapshot the live map`)
-- and it solved it for variables by handing the recursion only the subset that
holds at every point in the string. The cwd analogue is: pass `base_cwd` only
when no `cd` ever moves it, and otherwise mark the cwd unknown. That closes the
missed offenders, which is the security half, and it is not free -- an unknown
cwd makes every relative operand `untracked`
(`plugins/workspace-guard/scripts/bash-workspace-guard.py:3389:relative path with an unknown cwd`),
which is a **deny**, so `cd sub && echo $(cat x)` would go from silent to
blocked. Take it only as a stopgap.

Fixture rows in both directions: each of the ten above, plus a nested backtick
inside a `$( )` after a `cd` (also missed today), an unresolvable `cd` before a
substitution, and an in-root relative operand after a `cd` that must stay
silent.

## Downstream

`karlkfi/claude-spill-guard` ported this segmentation and cwd tracker and found
the gap there first; its Q147 and Q92 are waiting on this, and that port stays
structurally identical rather than diverging, so the fix transfers by
inspection. Its release does not gate on this one. Downstream the lost
directory means *cannot resolve*, which fails closed into a coverage record;
here it decides a guard's verdict, which is why the row is filed at this
severity rather than that one.

How often the shape occurs there was measured downstream on 2026-09-06, over
one machine's transcripts: 137 coverage records on the relative-after-`cd` arm
carry a cd-family command, and 11 of those carry a `$(…)` or a backtick after
it. Those two figures are quoted from that measurement and were not re-taken
here; nothing in this row's own table re-derives them, and they size the
downstream arm rather than this guard's.

Q139 is the other row filed from the same downstream port and is a different
defect in the same layer -- a neighbour, not a blocker.

## If it is never built

A `cd` out of the root followed by a backtick substitution, or any heredoc body
substitution after a `cd`, reads and writes outside the workspace with no
prompt -- the boundary the guard exists to hold, absent on a construct the
`$( )` spelling of the same command does hold. The `$( )` false positives cost
less but are more visible: a prompt naming a path the command never touches,
which is the one claim a human at a prompt has to take on trust.
