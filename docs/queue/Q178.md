# A `nohup NAME=v cmd` denial names a command that never runs

`strip_head` peels an assignment run after `nohup`, `command` and `stdbuf`
the way it does after `env`. Those three are not `env`: they take no
assignment operands, so they try to execute a program literally called
`NAME=v` and exit non-zero. Nothing the guard then classifies ever runs.

So `nohup A=1 <a polling command>` denies, and the deny is about a command
bash will not reach. The user is asked to rewrite a line that was already
going to fail.

## Measured

2026-09-07, bash 5.3.15. Only `env` runs the command:

```
env      rc=0    ran, A=1
nohup    rc=127  nohup: A=1: No such file or directory
command  rc=127  bash: line 1: A=1: command not found
exec     rc=127  bash: line 1: exec: A=1: not found
stdbuf   rc=2    stdbuf: A=1: No such file or directory
setsid   rc=127  bash: line 1: setsid: command not found
```

The quoted spelling already behaves correctly and does so for the wrong
reason. After Q170, `nohup 'A=1' cmd` leaves the quoted word at `argv[0]`,
which is an unrecognised command, so the guard defers -- which is the right
answer, arrived at through command position's quoting rule rather than
through knowing what `nohup` does with an operand. The two spellings are
byte-identical to `nohup` itself, so they should reach the same verdict, and
today they do not.

## Who it is for, and what it is worth

Whoever writes `nohup VAR=x <long-running command>` and is told to restructure
it. Frequency is low -- the shape is uncommon and the deny is recoverable by
reading the message -- and the cost is one wasted rewrite each time. It ranks
at the tail because nothing is unsafe: the guard is over-denying a line that
fails anyway, which is the direction this repository's guards prefer to err.

## What happens if it is never built

The deny stays wrong and stays harmless, and the two spellings of the same
shell fact go on disagreeing. The more likely cost is a later reader taking
the peel after `nohup` as evidence that `nohup` consumes assignments, and
copying it somewhere it matters.

## Which way it gets built

Restrict the assignment-operand peel to the wrappers that actually take
operands. exit-status-guard already names that set -- `ASSIGN_WRAPPERS`,
`env` and `sudo`, with the reasoning in the comment above it -- so this is
making `strip_head` agree with a decision already recorded next door rather
than a new one. The `sudo` half of `strip_head` was fixed under Q170; this is
the rest of the same branch.

Check `exec` while there: it is in neither guard's wrapper handling today.

## Notes

Found during review of the Q170 pull request, which fixed the two wrappers
where the same peel was wrong in the unsafe direction. This one is wrong in
