# prod-guard expands a `$NAME` written inside single quotes

bash leaves `$C` inside single quotes as text, so `B='$C'` stores the four
characters `$C` and `$(echo '$C')` prints them. prod-guard resolves both against
`C`: `extract_env_prefix` expands every assignment value whatever its quoting,
at
`plugins/prod-guard/scripts/bash-prod-guard.py:919:            env[name] = expand_vars(value, {**base_env, **env})`,
and `expand_vars` matches a `$NAME` anywhere in a word, a substitution's
single-quoted body included, at
`plugins/prod-guard/scripts/bash-prod-guard.py:961:        return VAR_REF_RE.sub(repl, value)`.

It decides a verdict where the text reaches a shell that expands it again. A
double-quoted `bash -c` body is the measured case: the parent hands the child
`$C`, the child does not inherit the unexported `C`, and kubectl gets an empty
`--context=`, which is the current context.

Found by review-r2 on the Q348 pull request (#340), comment 6937793073, and
re-measured 2026-11-16 at `a3e072f` with the fixture `$HOME`, whose current
context is `gke_acme_prod-us`. The bash column ran `echo` in place of kubectl
under `env -i /opt/homebrew/bin/bash --norc --noprofile`, bash 5.3.15, with
`C=p`:

| command | guard | bash: what kubectl gets |
|---|---|---|
| `C=kind-ci; bash -c "kubectl --context=\$C delete pod x"` (control) | ask | `--context=` |
| `C=kind-ci; B='$C'; bash -c "kubectl --context=$B delete pod x"` | **defer** | `--context=` |
| `C=kind-ci; bash -c "kubectl --context=$(echo '$C') delete pod x"` | **defer** | `--context=` |
| `C=gke_acme_prod-us; B='$C'; bash -c "kubectl --context=$B delete pod x"` | deny | `--context=` |

The last row shows the same expansion resolving the other way, so the verdict
tracks whatever `C` holds rather than what the child runs. At top level, with no
child, bash hands kubectl the literal `--context=$C`, a context that does not
exist, so the wrong value there decides nothing measured.

Not Q279: these words are arguments, not command names, so a verdict for an
unresolvable command word does not reach them. Not Q348: that fix covers a `$`
the parent leaves as text through `\$` or `$"`, and here the `$` arrives through
the parent's own expansion of a quoted value.

## Which way it gets built

Keep a single-quoted assignment value literal, which the lexer's per-token
`quotes` record may already be enough to tell (unchecked), and skip single-quoted runs inside a
substitution body before matching `VAR_REF_RE`. A value that holds a literal
`$NAME` then reaches the child as `$NAME`, which the child evaluation already
treats as unresolved and asks on. Check that the top-level row still defers, and
that `export B='$C'` takes the same path. Not measured.

## If it is never built

A mutation whose target passes through a single-quoted `$NAME` into a
re-expanding child shell runs against the current context without a prompt
whenever the parent's value is nonprod. It takes a quoted indirection most
commands never write, so it is likely rare.
