# workspace-guard's branch-guard pairing names three outcomes, not four

`plugins/workspace-guard/README.md:1798:- **asks** before committing or pushing to`
opens a three-bullet summary of what branch-guard does — asks, allows, defers.
Q99 gave branch-guard a fourth: a clean-worktree `git reset --hard` onto a tip
proved unreachable is denied in every permission mode. A reader of that section
meets three verdicts and can hit a fourth.

The same bullet already reads `reset --hard` as a plain ask, which branch-guard
has not done for a while — a clean worktree on a recoverable feature branch has
allowed it since the ownership model landed. So this is a summary that drifted
before Q99 and drifted further with it, rather than a sentence Q99 broke.

Not [Q104](Q104.md), which is the neighbouring row and does not reach this. That
one gates the companion roster between `## Companion plugins` and
`They run side by side` for uniformity across the five READMEs. This text sits
under `### The pairing with branch-guard`, below that block and unique to
workspace-guard, so a roster check as Q104 specifies it passes over this
paragraph untouched. Worth naming when Q104 is worked: the extraction window is
what decides whether the gate reaches prose like this, and widening it would mean
finding a uniformity claim that holds for a section only one README carries.

Left out of Q99's diff deliberately: it lands in another plugin's tree, which
triggers that plugin's CI job for a change with no bearing on it, and a sibling
session was working workspace-guard at the time.

Smallest honest fix is to say the guard also denies, and to stop implying every
`reset --hard` asks. Whoever takes it should re-read the whole subsection rather
than the one bullet — it summarizes a plugin whose behaviour table is a hundred
rows, so the other two bullets deserve the same check.
