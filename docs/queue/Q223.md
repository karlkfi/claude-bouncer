# branch-guard peels no wrapper, so env git push reads as env

A `git push` behind any command wrapper is not recognised as a push.
`branch-guard.py` has no wrapper peel at all, so the wrapper takes the command
head.

Measured 2026-10-01 at `b27be8d` by driving the hook with a JSON payload, `cwd`
the repo root:

| command | guard |
|---|---|
| `git push --force origin main` | ask -- control |
| `env git push --force origin main` | **defer** |
| `command git push --force origin main` | **defer** |
| `nohup git push --force origin main` | **defer** |
| `timeout 60 git push --force origin main` | **defer** |
| `sudo git push origin main` | **defer** |

The same gap in workspace-guard is filed as Q219 (on the branch landing Q214).
That row counts the wrapper peels three other guards keep: prod-guard,
exit-status-guard and foreground-guard. branch-guard is the fifth guard and
has none, which this row records.

## Which way it gets built

Peel the wrappers bash runs a command through (`env` with its assignments and
options, `command`, `nohup`, `nice`, `timeout` with its duration, `stdbuf`,
`setsid`, `time`) before the `git` lookup. Decide each option's arity per
character, the shape Q200's fix uses in prod-guard. Q219's own question is
whether this is the moment a shared peel moves into `lib/`: a fourth and fifth
guard needing the same behaviour is what the repo's rule waits for. Answer
both rows together.

## If it is never built

`timeout 60 git push --force origin main`, a natural way to bound a slow push,
reaches the protected branch with no prompt.
