# Two of the three here-string spellings get the wrong answer

`split_groups` steps over a here-string's operand without collecting it. The
`<<<` case shares the `<<` branch, which advances past the operator and its
operand without appending either to the group's command tokens or to its
redirect targets
(`plugins/workspace-guard/scripts/bash-workspace-guard.py:3429:if t in ('<<', '<<<'):`).
That is deliberate and correct as far as it goes -- a here-string operand is
string *content*, not a path -- but the marker scan Q169 added reads the same
two lists
(`plugins/workspace-guard/scripts/bash-workspace-guard.py:3332:for tok in g + g_redir:`),
so a substitution written in that operand is never given a position. What
happens next depends on how it was spelled, and only one of three spellings
comes out right.

## Measured

2026-09-08, against `main` at c368aca -- the commit that closed Q169, so this
is the state after that fix. Project root is a fresh directory outside host
temp; `/etc` stands in for the outside directory, and `T` is the relative
operand. Paths are shown as the hook renders them, through macOS's `/etc`
symlink. Nothing executed by the hook -- it resolves lexically.

**The path column is the point.** A verdict-only table records rows 2 and 3 as
identical, and they are not: one of them names a path bash never forms.

| # | command | verdict | path named | bash opens |
|---|---|---|---|---|
| 1 | `cd /etc && cat <<<"$(cat T)"` | **allow** | -- | `/private/etc/T` |
| 2 | ``cd /etc && cat <<<`cat T` `` | ask | **``/private/etc/T` ``** | `/private/etc/T` |
| 3 | `cd /etc && cat <<<$(cat T)` | ask | `/private/etc/T` | `/private/etc/T` |
| 4 | `cd /etc && echo "$(cat T)"` | ask | `/private/etc/T` | `/private/etc/T` |
| 5 | `cd /etc && cat <<EOF`⏎`$(cat T)`⏎`EOF` | ask | `/private/etc/T` | `/private/etc/T` |

Rows 4 and 5 are the same read in two spellings Q169 closed, and they are what
makes rows 1 and 2 defects rather than a decision. Row 3 is genuinely correct,
for the reason Q169 catalogued: `(` is punctuation the tokenizer keeps, so the
bare spelling splits into ordinary tokens and the operand reaches the group
with the tracked cwd. That accident covers exactly one of the three.

### Row 1: an affirmative allow, reached with the recursion working

The verdict is `allow`, carrying `Guarded commands target workspace/pipe only`
(`plugins/workspace-guard/scripts/bash-workspace-guard.py:4109:decision, reason = "allow", "Guarded commands target workspace/pipe only"`).

**The body is recursed and its offenders do bubble up.** That is worth stating
because it is the obvious wrong guess:

| command | verdict | path named |
|---|---|---|
| `cd /etc && cat <<<"$(cat /etc/hosts)"` | ask | `/etc/hosts` |
| `cat <<<"$(cat ../../../../etc/hosts)"` | ask | `/private/etc/hosts` |

The second row is the defect in miniature: the operand's `../../../../` is
resolved against the string's *entry* cwd, because the marker scan never gave
the body a position. So in row 1 the body runs its `cat T` against the project
root, `T` resolves inside the workspace, the body yields **no offender at all**,
and the outer `cat` -- guarded, and now clean -- earns the allow on its own
account.

Q169 drops `guarded` for a recursed body so that a clean body cannot vouch for
the enclosing string. That safeguard ran. It governs `guarded` and not
offenders, so it cannot help when the body produces no offender to begin with.

**This is the same failure Q169 closed, in a spelling it did not reach** -- not
a stronger one. Measured across the fix, pre-Q169 at d846ce7 against c368aca:

| command | pre-Q169 | post-Q169 |
|---|---|---|
| `cd /etc && cat <<EOF`⏎`$(cat T)`⏎`EOF` | allow | ask |
| `cd /etc && echo "$(cat T)"` | defer | ask |
| `cd /etc && cat <<<"$(cat T)"` | allow | **allow** |

Q169 turned an allow into an ask on the heredoc spelling. The defer on the
`echo` spelling is only that `echo` is not a guarded command while `cat` is.

### Row 2: a false positive wearing a correct-looking verdict

The path named carries the trailing backtick inside the filename. Bash never
forms that path -- it opens `/private/etc/T` -- so the prompt is the Q169
false-positive shape on the one spelling a verdict-only reading records as
working. The mechanism is tokenization, not substitution handling:

```
lex('cat <<<`cat T`')     -> ['cat', '<<<', '`cat', 'T`']
lex('cat <<<"$(cat T)"')  -> ['cat', '<<<', '$(cat T)']
lex('cat <<<$(cat T)')    -> ['cat', '<<<', '$', '(', 'cat', 'T', ')']
```

``T` `` survives the backtick spelling as a bare word after the `<<<` operator.
`command_substitutions` finds `cat T` in all three strings, so the scanner is
not what differs.

## Which way it gets built

**Not by appending the operand to `cur_redir`.** That is the shape this row
recommended when first filed, and it does not work: the marker scan and the
outside-path check read the same list
(`plugins/workspace-guard/scripts/bash-workspace-guard.py:3759:for f in g_redir:`),
so feeding one feeds the other, and a here-string operand is content rather
than a path. Built and measured, base against patched:

| command | base | operand in `cur_redir` |
|---|---|---|
| `cd /etc && cat <<<"$(cat T)"` | allow | **deny** |
| `cd /etc && cat <<<$(cat T)` | ask | **deny** |
| ``cd /etc && cat <<<`cat T` `` | ask, 1 phantom | ask, 3 paths, 2 phantoms |
| `cat <<<"/etc/passwd"` | allow | ask naming `/etc/passwd` |
| `cat <<<"$FOO"` | allow | **deny** |
| `cat <<<"~/secrets"` | allow | ask naming `/Users/karl/secrets` |

The marker half does work -- row 1 starts naming the right path -- but the same
token reaches `check_file` as a redirect target, where an unparseable operand
is category `expand` and denies. The last three rows are ordinary here-strings
carrying string literals that bash never opens, and they are the Q169
false-positive shape this row condemns.

So it needs a channel the marker scan reads and the path check does not: a
third list, or an additive out-parameter on `split_groups`, which is the shape
`strip_heredoc_bodies` set as precedent when it grew `unterminated`.

Q169 left `split_groups` byte-for-byte equivalent to the block it was extracted
from, verified over 4,036 token lists. Any of these forfeits that, so this
wants its own differential run rather than a fixture or two.

## If it is never built

An out-of-root read the guard affirmatively vouches for, on one spelling; and
on another, a prompt naming a path bash never forms while the real target goes
unmentioned. The second is the more corrosive -- a human approving a path they
cannot check is the failure Q169 called its more visible half, and a phantom
path offers the reader nothing to catch it by.
