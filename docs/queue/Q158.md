# `sudo -h HOST` can run the command, and prod-guard defers it

Q152 gave each wrapper a set of flags that take a separate value, so the value
is skipped with the flag instead of becoming the tool. `sudo -h` was held out of
that set because sudo spells two options `-h`: `--help`, which takes no value,
and `--host`, which takes one. The row assumed that whichever arity the guard
picked, one shape would walk past the tool.

The answer is to follow sudo's own parse, and on the sudo releases that matter
the host form runs the command. So the guard's defer there is a false
negative, not a harmless guess.

## Measured

**What sudo does.** Sudo 1.8.8 through 1.9.17 accepted `-h host` when running a
command, not only when listing privileges, and ran the command locally under
whatever sudoers granted for that host. That is CVE-2025-32462, fixed in
1.9.17p1 (https://www.sudo.ws/security/advisories/host_any/). On 2026-10-04,
sudo 1.9.17p2 on macOS, every probe run with `-n` and `/usr/bin/true` as the
command:

| argv after `sudo -n` | sudo's answer | exit |
|---|---|---|
| `-h somehost /usr/bin/true` | `a remote host may only be specified when listing privileges.` | 1 |
| `-hsomehost /usr/bin/true` | the same refusal | 1 |
| `-h -n /usr/bin/true` | usage text | 1 |
| `-h` | usage text | 1 |

That refusal is the fix in 1.9.17p1 at work, not a property of the option. The
hook cannot see which sudo the command will run under, so it has to read the
host form as running the tool. Sudo's own parse is narrower than that, read from `parse_args.c` at v1.9.17
and at `SUDO_1_8_31` in review (read, not run). A value attached to the `-h`
(`-hmyhost`) is a host. A detached word is a host only when the token is
exactly `-h` and the word is neither an option nor a `VAR=value`, and
`--host` always takes one. Every other `-h` is help, including one that ends
a bundle (`-nh myhost`), and help runs nothing on every version.

**What the guard does.** 2026-10-04, prod-guard at `a3c9052`, with the
remedy below applied to a copy of the hook:

| command | today | with the remedy |
|---|---|---|
| `sudo -h myhost kubectl --context gke_acme_prod-us delete ns foo` | defer | deny |
| `sudo --host myhost kubectl …` (same tail) | defer | deny |
| `sudo -u bob -h myhost kubectl …` | defer | deny |
| `sudo -nh myhost kubectl …` | defer | deny |
| `sudo -hmyhost kubectl …` | deny | deny |
| `sudo --host=myhost kubectl …` | deny | deny |
| `sudo -h -n kubectl …` | deny | defer |
| `sudo -h kubectl --context gke_acme_prod-us delete ns foo` | deny | defer |
| `sudo -h` | defer | defer |
| control: `sudo kubectl …` | deny | deny |
| control: `sudo -l kubectl …` | defer | defer |

Three of the first four rows are the defect: `-h myhost`, `--host myhost`
and `-u bob -h myhost`. On a sudo before 1.9.17p1 each one runs `kubectl`
against a production context, and the guard says nothing. The fourth,
`-nh myhost`, is help by sudo's parse and runs nothing, so the remedy's deny
there is a false deny. `sudo -h FOO=bar kubectl …` is the same case. The two
rows that move to defer are the help form, and a command where `kubectl` is
the host and `--context` is then an option sudo rejects. Neither runs a tool.

## Which way it gets built

**Ask (answered):** the row asked whether this was worth closing at all,
between leaving it, a lookahead, and a break-out. Sudo's own parse settles it,
and it is a lookahead of one word on the token after `-h`, not tool-name
knowledge.

- Add `-h` and `--host` to sudo's entry in `WRAPPER_VALUE_FLAGS`
  (`plugins/prod-guard/scripts/bash-prod-guard.py:276:sudo's`), so a host's
  value is skipped and the walk reaches the tool.
- In `is_sudo_run_nothing`, return true for an `h` that ends its token when the
  next operand is missing or starts with `-`
  (`plugins/prod-guard/scripts/bash-prod-guard.py:712:if char in SUDO_RUN_NOTHING:`).
  That is the help form.
- Replace the comment that holds `-h` out
  (`plugins/prod-guard/scripts/bash-prod-guard.py:682:is left alone: it spells both`),
  and the matching note in `WRAPPER_VALUE_FLAGS`, with the CVE and the parse
  above.
- Pin every row of the table above as a test, both directions. `--help` stays
  with Q181, which owns every wrapper's own `--help` and `--version`.

That patch is the one the table was measured against.

**It keeps a deny stricter than sudo, on purpose.** It reads any `h` that
ends its token, followed by a plain word, as a host, so `-nh WORD` and
`-h VAR=value` deny where sudo would print help. Matching sudo exactly would
rest on a source reading of two versions that nobody has run against a
vulnerable sudo. The two errors also cost different amounts: a false deny here
costs one rewrite, while a false defer lets a command reach a production
cluster unprompted. A test pins the stricter reading and names this paragraph.

**Not measured:** any sudo other than 1.9.17p2 was not run here, and the CVE
behaviour is from sudo's advisory rather than a probe. `sudo-rs` may treat
`-h` as help only. The parse above denies more than that would, never less.

**Who it is for:** a host still on sudo 1.9.17 or older, where an agent writing
`sudo -h host kubectl …` reaches a production cluster with no prod-guard
prompt. Nobody writes the shape by accident, so it is rare. But the miss is on
the side the guard exists for, and the fix is three small edits.
