# `sudo -h` runs no command, so prod-guard can stop guessing its arity

Q152 gave each wrapper a set of flags that take a separate value, so the value
is skipped with the flag instead of becoming the tool. `sudo -h` was held out of
that set because sudo spells two options `-h`: `--help`, which takes no value,
and `--host`, which takes one. The row assumed that whichever arity the guard
picked, one shape would walk past the tool.

That premise is false: neither shape runs a tool at all. That changes the
answer.

## Measured

2026-09-04, prod-guard at `4a81387` with Q152's fix applied, fixture `$HOME`
with ambient context `gke_acme_prod-us`:

| command | verdict | if `-h` took a value |
|---|---|---|
| `sudo -h kubectl delete ns foo` | deny | would skip `kubectl`, defer |
| `sudo -h myhost kubectl delete ns foo` | defers | would deny |

2026-10-04, sudo 1.9.17p2 on macOS, every probe run with `-n` and
`/usr/bin/true` as the command:

| argv after `sudo -n` | sudo's answer | exit |
|---|---|---|
| `-h somehost /usr/bin/true` | `a remote host may only be specified when listing privileges.` | 1 |
| `-h /usr/bin/true` | the same refusal: the next word is taken as the host | 1 |
| `-hsomehost /usr/bin/true` | the same refusal | 1 |
| `-h -n /usr/bin/true` | usage text | 1 |
| `-h` | usage text | 1 |

So `-h` followed by a word that does not start with `-` is a host, and sudo
itself refuses to run a command once a host is named. A `-h` followed by an
option, or by nothing, is help. Either way sudo runs nothing. The refusal comes
from sudo's own argument parsing, which is stricter than the row's "sudoers
cannot execute it": it holds whatever policy is installed.

Read against the table above: the first shape (`sudo -h kubectl delete ns
foo`) makes `kubectl` the host and runs nothing. The guard's deny there is a
**false deny**. The second shape runs nothing either, so its defer was never a
false negative.

## Which way it gets built

**Ask (answered):** the row asked whether this was worth closing at all,
between leaving it, a lookahead, and a break-out. The measurement removes the
trade-off the three options were weighing. The break-out is now simply
correct: it answers "runs nothing" for both shapes, which is what sudo does.
The lookahead would have built tool-name knowledge into the flag walk to fix a
false negative that does not exist.

Add `h` to `SUDO_RUN_NOTHING`
(`plugins/prod-guard/scripts/bash-prod-guard.py:684:SUDO_RUN_NOTHING = frozenset('lveKU')`)
and `--host` to `SUDO_RUN_NOTHING_LONG`. Replace the comment that holds `-h`
out
(`plugins/prod-guard/scripts/bash-prod-guard.py:682:is left alone: it spells both`)
with the measurement above, and the matching "held out" note in
`WRAPPER_VALUE_FLAGS`. `--help` is not in this set; it belongs to Q181,
which owns every wrapper's own `--help` and `--version`. Pin both table shapes
as defers, plus a `-u bob -h host kubectl …` case, so the walk still skips a
value-taking flag before it reaches `h`.

**Not measured:** any sudo other than 1.9.17p2. In particular, `sudo-rs` may
treat `-h` as help only. That would still run nothing, but it is unmeasured,
and the test should record which binary it was driven against.

**Who it is for:** an agent that writes `sudo -h …` and receives a prod-guard
deny for a command sudo would have refused anyway. **If it is never built**,
that false deny lands about never, since nobody writes the shape on purpose.
Flat, and rare. The fix is one character and one long option, which is why it
is worth doing once it is reached, not why it should be reached sooner.

Rank: it keeps its place near the bottom of the ready rows.
