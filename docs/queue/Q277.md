# A gate's status is lost through `<(…)` or a `(…)` subshell, unflagged

exit-status-guard denies `make check | tail` and `make check; git push`,
because the gate's status is lost or ignored. Written inside a process
substitution, or in a `(…)` subshell before a `;`, the same gate gets no
decision, though its status is lost the same way.

Measured 2026-10-05 on `origin/main` at `d43db6e`, from a `git archive` of
that tree:

| command | exit-status-guard |
|---|---|
| `make check \| tail` (control) | deny |
| `make check; git push` (control) | deny |
| `{ make check; }; git push` (control) | deny |
| `tail <(make check)` | **none** |
| `cat <(make check); git push` | **none** |
| `(make check); git push` | **none** |

Under `env -i "$(command -v bash)" --norc --noprofile -c` (5.3.15),
`tail <(false)` returns 0, so a failing gate reads as a pass. The independent
review of #219 found both halves and drove more shapes, among them
`diff <(make check) x`, `cat <(make check)|tail` and
`( make check ); git push`. It also found that `(make check)| tail` and
`make check |& tail` already deny. Its table is in
https://github.com/karlkfi/claude-bouncer/pull/219#issuecomment-5989911630.

These are two causes, not one:

- **Process substitution.** lib's `command_substitutions` returns nothing for a
  `<(…)` body, so the gate inside is likely never seen. Q276 (workspace-guard)
  has the same lead, and one `lib/` change could serve both.
- **The subshell.** `{ make check; }; git push` denies and
  `(make check); git push` does not, so the sequencing rule stops at a `(…)`
  group where it reads through a `{…}` one. That half is not traced.

## Which way it gets built

Split this row if the two halves land in different places. Fixtures: each
shape above, with the denying control beside it.

## If it is never built

`tail <(make check)` reports a failing gate as success, which is the exact
mistake the guard exists to stop, written one way it does not read.
