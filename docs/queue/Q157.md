# `sudo`'s run-nothing modes are stripped as if they ran the command

`sudo -l`, `-v` and `-e` run no command: `-l` lists privileges, `-v` refreshes
the timestamp, `-e` edits the files named as operands. `strip_wrappers` drops
each as an ordinary flag, so the operands behind it read as a command and a
production target in them is denied for something that was never going to run.

Same shape as Q142, which is why `command -v` already breaks out of the wrapper
loop instead of being stripped — `is_command_lookup` is the fixture to match
against. `sudo` has three such modes and no equivalent check.

## Measured

2026-09-04, prod-guard at `4a81387`, fixture `$HOME` with ambient context
`gke_acme_prod-us`:

| command | what sudo does | verdict |
|---|---|---|
| `sudo kubectl delete ns foo` | runs kubectl | deny — correct |
| `sudo -l kubectl delete ns foo` | lists privileges | **deny** |
| `sudo -v kubectl delete ns foo` | refreshes the timestamp | **deny** |
| `sudo -e kubectl delete ns foo` | edits four files | **deny** |

Read off `sudo -h` on sudo 1.9.17p2, whose usage puts `-l`, `-v` and `-e` in
synopsis lines of their own.

## Which way it gets built

A `sudo`-side twin of `is_command_lookup`: break out of the wrapper loop, as
`command -v` does, leaving `sudo` in place so the segment is uncovered and
defers. Flags bundle (`sudo -kl`), and `--` ends them.

`-U`/`--other-user` is the reason to do this before extending the flag table
any further. It takes a separate value and so belongs in `WRAPPER_VALUE_FLAGS`
by Q152's rule, and it is valid only in list mode — adding it while `-l` is
still stripped would turn one wrong deny into another. It was held back from
Q152 for that reason and lands here.

## If it is never built

A deny where nothing was at stake, which runs the whole Bash call not at all —
so an edit bundled into the same call is silently skipped, the cost
[Q154](Q154.md) measures for the same class in a sibling guard. Rarer than
Q154's, since `sudo -l <command>` is not a shape a session emits often.
