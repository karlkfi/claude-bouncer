# Opt-in extra-roots for shared cross-worktree files

A session that works across checkouts is prompted on every guarded file
argument landing outside its own root, and answers yes every time. This row has
carried an opt-in extra-roots env var as the fix since it was filed.

The measurement below is why it should not be built as written.

**Ask:** whether a session may read another session's worktree without a prompt.
The maintainer's position, 2026-08-31, is unresolved and leans against — "I
don't really want sessions accessing the worktree of another session, in
general. But maybe there are some valid reasons why that's the appropriate
action and it's not really a secrecy/privacy violation." Nothing in the repo
settles it: it is a preference about isolation between concurrent sessions, not
a fact about the guard.

## Measured

Seven days to 2026-08-31, over 1,615 local transcript files. Of 180
workspace-guard asks, the cross-checkout path tokens split:

| target | tokens |
|---|---|
| another session's worktree, different repo | 54 |
| another session's worktree, same repo | 29 |
| main checkout of a different repo | 53 |
| main checkout of the same repo | 4 |

100 of 106 such asks were reads, by `grep`, `sed`, `cat`, `python3` and `ls`.
All were approved — see `Q139`, which owns the approval measurement.

**The two halves want opposite answers, which is what the original row missed.**
Reading a *main checkout* is reading canonical, committed repo state: comparing
a `.gitignore`, deduping a backlog row, reading `queue.py --help`. Reading
another session's *worktree* is reading a peer's uncommitted work in progress,
and it is the larger half at 83 tokens against 57.

The same-repo cases are the sharpest: one session's cwd had moved from its own
worktree into a sibling's and was reading that sibling's tree. The guard's
prompt is the only thing that surfaced it.

Some peer reads look deliberate rather than accidental — one target worktree is
named `pr1790-review-vb`, a checkout made to review a pull request, which is a
plausible thing for a second session to want. So the class is not uniformly
wrong, which is exactly why it needs a decision rather than a default.

## Which way it gets built, once the question is answered

Split the two halves rather than shipping one extra-roots var over both:

- **Main checkouts** are the tractable half. A session's own repo root is
  derivable from its worktree, so exempting reads of the checkout a worktree
  belongs to needs no configuration at all.
- **Peer worktrees** stay prompting unless the answer above says otherwise, and
  would then need the opt-in, empty-by-default var this row was filed for.

Read `Q139` before sizing either: a remembered per-shape approval meets much of
this demand with no configuration, leaving only the operator who wants the
exemption standing rather than re-granted each session.

`Q140` is the neighbouring case and is deliberately separate — it covers reads
of Claude's own home directory, where an exemption already exists and stops
short.

## If it is never built

83 approved prompts a week on peer-worktree reads, which is also the only
signal that they are happening at all.
