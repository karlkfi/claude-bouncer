# Opt-in extra-roots for shared cross-worktree files

**Demand:** a cross-checkout read that the object store genuinely cannot serve —
that is, a session with a real need for a peer's *uncommitted* working tree.
None has been seen. Until one is, the fleet change below removes the demand
without touching the boundary.

Deferred 2026-08-31. This row proposed an opt-in extra-roots env var so
cross-checkout reads stop prompting. It should not be built, because the reads
do not need the filesystem.

## The fleet change that removes the demand

Read the ref, not the worktree. Worktrees of a repo share one object store and
one ref namespace, so a peer's committed work is reachable from any checkout of
that repo without touching the peer's working tree at all.

Probed 2026-08-31 against workspace-guard 1.11.0:

| command | verdict |
|---|---|
| `cat <peer-worktree>/docs/x.md` | ask |
| `grep -n foo <peer-worktree>/docs/x.md` | ask |
| `sed -n '1,20p' <peer-worktree>/docs/x.md` | ask |
| `git -C <repo> show <branch>:docs/x.md` | allow |
| `git -C <repo> cat-file -p <branch>:docs/x.md` | allow |
| `git -C <repo> diff origin/main...<branch> -- docs/` | allow |

Verified end to end rather than by reading the table: `git -C` against this
repository's main checkout printed a file that exists only on a worktree branch,
with no filesystem access to that worktree.

Three reasons this is better than the exemption, not merely cheaper:

- **It is already allowed**, so the boundary does not move and no configuration
  is added.
- **A ref is a defined state; a live working tree is not.** A peer session may
  be mid-edit or mid-rebase, so a filesystem read races against it and can
  return a half-written file.
- **It survives worktree cleanup.** `claude-ground-truth`'s
  `vibrant-feistel-6b3523` worktree was read through the filesystem during the
  measured week and no longer exists on disk; its branch is still in the object
  store, local and on origin. A ref-based read of that same content still works
  today and a path-based one cannot.

The residual it does not cover is a peer's uncommitted work, which is the case
the maintainer does not want served: "I don't really want sessions accessing the
worktree of another session, in general."

## Where the change lands

Not in this repository. It is guidance for the session fleet — the
`session-worker` and `session-orchestrator` skills in `karlkfi/claude-skills` —
so the row here records why the guard-side fix was declined.

## Measured demand this was filed against

Seven days to 2026-08-31, of 180 workspace-guard asks, the cross-checkout path
tokens split 83 into another session's worktree against 57 into a main checkout.
100 of 106 such asks were reads. `Q139` owns the approval measurement.

## If nothing is done

83 prompts a week, all approved, on reads that a `git show` would have made
silently and more correctly.
