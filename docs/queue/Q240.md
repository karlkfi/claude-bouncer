# prod-guard peels no NAME=value operand behind sudo

`sudo` takes `VAR=value` operands before the command, and its usage line
documents them: `[-u user] [VAR=value] [-i | -s] [command [arg ...]]`.
The `sudo` branch of `strip_wrappers` peels only options, so the first
assignment becomes the command head, and the covered tool behind it is
never classified.

Found while measuring Q176. Driven 2026-10-04 through the hook (fixture
`$HOME`) against `origin/main` at `442c86e`:

| command | guard |
|---|---|
| `sudo kubectl --context gke_acme_prod-us delete ns x` | deny -- control |
| `sudo FOO=1 kubectl --context gke_acme_prod-us delete ns x` | **defer** |
| `sudo -u root FOO=1 kubectl --context gke_acme_prod-us delete ns x` | **defer** |
| `sudo env FOO=1 kubectl --context gke_acme_prod-us delete ns x` | deny -- control |

Whether sudo then runs the command was not driven: that needs a password.
The claim is from `man sudo` on macOS. A command-line variable is held to the
same restrictions as an inherited one, unless `setenv` is set, the command
carries the `SETENV` tag, or the command matched is `ALL`. The last case
should cover the common `ALL=(ALL) ALL` rule, though that is read from the
page rather than driven. What sudo does with a variable its policy refuses
was not checked.

exit-status-guard and foreground-guard already peel these operands behind
sudo, by sudo's own rule since Q218. prod-guard is the guard that peels
none.

## Which way it gets built

Peel sudo's `NAME=value` operands into the segment env the way the `env`
branch does, then carry on to the command. sudo's rule is not
env's: `is_envar` in its `src/parse_args.c` takes an operand holding `=`
that starts with neither `/` nor `=`, and runs any other as the command.
exit-status-guard and foreground-guard apply that rule, so reuse theirs,
but not their two-pass loop: sudo takes operands between its options, and
Q275 is that defect in those two guards. A
`PROD_GUARD_OVERRIDE` peeled here is Q176's question, not this row's.

## If it is never built

One harmless assignment after `sudo` hides any mutating command behind it,
and the guard stays silent.
