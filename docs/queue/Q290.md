# A command substitution's assignment reaches later segments

An assignment made inside a `$( … )` or backtick substitution dies with the
subshell that runs it, and prod-guard still carries it forward to the segments
after. So the guard resolves a variable bash leaves unset, and judges the
target by a value the command never uses.

The row first covered four more forks: a `( … )` subshell, a pipeline stage on
either side of `|`, and a backgrounded list. Q300 made those drop their
assignments, as part of scoping the brace groups it unhid. Only the
substitution is left.

## Measured

2026-10-05, prod-guard at the Q180 branch head (`72ff9cc`), with
`evaluate_command_string` and a fixture `$HOME` whose `~/.kube/config` has
`current-context: gke_acme_prod-us`. Nothing executed.

| command | guard | bash 5.3.15 `$C` at kubectl |
|---|---|---|
| `kubectl --context $C delete ns x` (control) | ask | unset |
| `(C=kind-ci); kubectl --context $C delete ns x` | defer, ask since Q300 | unset |
| `(export C=kind-ci); kubectl --context $C delete ns x` | defer, ask since Q300 | unset |
| `C=kind-ci \| true; kubectl --context $C delete ns x` | defer, ask since Q300 | unset |
| `C=kind-ci & kubectl --context $C delete ns x` | defer, ask since Q300 | unset |
| `x=$(C=kind-ci); kubectl --context $C delete ns x` | **defer** | unset |
| ``x=`C=kind-ci`; kubectl --context $C delete ns x`` | **defer** | unset |

The "since Q300" verdicts and the backtick row were taken 2026-10-07 on the
Q300 branch with the suite's `run_hook`.

The bash column was driven directly, e.g.
`/opt/homebrew/bin/bash -c '(export C=kind-ci); echo "[$C]"'` prints `[]`.

Each deferred row is a mutation the guard reads as non-production and lets
through silently. What it actually runs against is `--context ""`, which the
guard cannot pin. The control shows the verdict owed: an unresolved `$C` asks.
That kubectl reads `--context ""` as the current context, prod in this
fixture, is unverified here: no kubectl was run. It does not change
the answer, since an unresolvable target asks either way.

## Where it happens

`split_simple_commands` drops the operator that separated two segments
(`plugins/prod-guard/scripts/bash-prod-guard.py:532:def split_simple_commands(tokens):`),
and the segment loop folds every assignment-only segment into the one shell
env
(`plugins/prod-guard/scripts/bash-prod-guard.py:3065:_assign(seg_inline, defining, maybe, functions, shell_env,`).
`export` does the same through the `ASSIGN_BUILTINS` branch. So no segment
knows whether it ran in the invoking shell.

## Which way it gets built

Q300's `segment_layout` already drops an assignment inside parentheses, and a
`$(` reaches it as a word ending in `$` before a `(`. What still lets the
assignment through is that `tokenize` hoists a substitution's body into
segments of its own, which the outer walk then reads as running in the shell.
The fix is to mark the hoisted segments as running apart.

## Who it is for, and what it costs

Anyone running prod-guard. Each shape above is a production mutation that runs
with no prompt. Writing one by accident is unusual: a subshell assignment
followed by a use outside it is a mistake in the command itself. But the guard
is there for exactly the command that does not do what its author thought, and
a model composing a multi-step command can produce any of these shapes.

Found while working Q165, whose `eval` merge has to stay out of this hole. It
does so with `_runs_in_one_shell`, which refuses the merge for a whole command
string holding any `(`, `)`, backtick, `<`, or a lone `|` or `&`. That is
coarser than this row can afford, since bare assignments are the common case:
it would stop resolving `C=x 2>&1; kubectl --context $C …` too. This fix wants
a per-segment answer, which means telling the hoisted substitution and heredoc
segments `tokenize` inserts apart from the command's own.
