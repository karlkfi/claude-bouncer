# The suppression escalation's ask is structurally ungrantable

An operator who turns session grants on and approves a suppression escalation
buys nothing: the identical command asks again, every time. The grant is never
recorded and never matched, so the mechanism that stops a guard re-asking a
settled question does not reach this prompt, and nothing says so.

`plugins/workspace-guard/scripts/bash-workspace-guard.py:4961:finish(esc[0], esc[1], [], data)`
passes an empty offenders list, and
`plugins/workspace-guard/scripts/bash-workspace-guard.py:3251:def grant_shapes(offenders, cwd):`
returns None for one. So PostToolUse records nothing and the pre-check has
nothing to match. The PowerShell frontend does the same, in the `handle_*` body
that opens
`plugins/workspace-guard/scripts/bash-workspace-guard.py:6313:outside, guarded = ps_analyze_command(cmd, ctx, ctx.cwd,`.

## Which way it gets built

**Settles (answered):** it stays ungrantable, and the fix is a sentence in the
README saying so. No third grant shape.

A grant has to be keyed on something. Keying on the signal alone (`sh -c`,
`kill`) is far too broad: one approval would silence every such command in the
session. The other candidate was the normalized command string. The guard's
own grant design already rejects that key for offenders, because the string
"differs on every call and would remember nothing"
(`plugins/workspace-guard/scripts/bash-workspace-guard.py:3216:never the command string, which differs on`).
Measured here, that holds for escalations too.

Replayed 2026-10-04 at `442c86e`: every Bash command in this machine's
transcripts from the last 60 days that names `sh|bash|zsh|dash -c` or a kill
went through `analyze_command` and `escalate_suppression` as `auto`. That was
28,570 of 198,868 commands. **99 would escalate** (56 `kill`, 42 `sh -c`,
1 `pkill`). They made 98 distinct (session, command) pairs. **A grant keyed on
the exact command string would have spared one prompt in 60 days.** The replay
uses today's hook, after Q211, and treats each transcript's `cwd` as the
project root. Treat it as a population reading, not a per-session rate.

So a third grant shape (the semantics would sit in this guard, not in
`lib/bouncer_grants.py`) would buy nothing measurable. The README's grants
section should say that a suppression escalation is never remembered, because
it names no target to key on, and that `WORKSPACE_GUARD_ESCALATE` is the
setting that quiets it, set in the hook's environment. An inline
`WORKSPACE_GUARD_ESCALATE=off` prefix on the command does nothing, as
re-measured in review under `auto` and `bypassPermissions`, so the line must
not suggest it. Q210 settles the per-command escape on the same
reasoning: the escalation stays a per-command question.

**Who is worse off** without the line: an operator who enables grants
expecting every prompt to become one-time, and is asked again. That reader is
real only once `WORKSPACE_GUARD_SESSION_GRANTS=1` is set, and it was unset on
this machine when the row was filed. **If it is never built**, the cost is a
puzzled operator and one repeat prompt in roughly sixty days. That is flat, and
low.

Rank: it belongs near the bottom of the ready rows. It is a one-sentence docs
change with no decision moving, so it is not a reason to open a release.
