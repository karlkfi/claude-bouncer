# workspace-guard never reads a literal eval body

`eval 'P'` runs `P` in the current shell, and prod-guard and foreground-guard read a literal `eval` body the way they read a `bash -c` one. workspace-guard does not: it reads a `-c` body and asks on an outside read inside it, but an `eval` of the same text defers, so the read runs on the session's own permission rules.
In `auto` those pre-approve it.

Measured 2026-11-17 on `main` at `b17c7054`, through the hook's launcher from a linked worktree, with `/opt/q8-fake-target` as the outside path:

| command | verdict |
|---|---|
| `cat /opt/q8-fake-target/f` (control) | ask |
| `bash -c 'cat /opt/q8-fake-target/f'` (control) | ask |
| `eval 'cat /opt/q8-fake-target/f'` | **defer** |
| `bash -c 'eval "cat /opt/q8-fake-target/f"'` | **defer** |

A literal body only.
`eval "$X"` and `eval "$(…)"` run text the guard cannot read, which is Q279's and Q382's.
Next step: hand a literal `eval` operand to the path a `-c` body takes, keeping the cd-tracking loss `eval` already carries, and add the two defer rows above as fixtures.

How often it bites is not measured: `eval` appears in a few hundred of this machine's 30-day commands by regex, nearly all of them `eval "$(…)"`, and nobody has counted the literal-body subset.
