# No test pins that the release-note check fails closed

Q108 moved the Dependabot exemption into `scripts/release-note.py`, and
`TestWorkflowWiring` pins that the workflow passes the pull request author to
it. What nothing pins is that the step *fails* when the script does. The
wiring test is a substring `assertIn` on the call, so a workflow that keeps the
call and stops honouring its exit status still passes.

Found by the independent review of #174, which ran three workflow mutants
against the assertion (string checks only), at `6af2cdb`:

| mutant | `assertIn(call)` today | `assertIn(full if-line)` | full line anchored, `re.M` |
|---|---|---|---|
| `… --author "$AUTHOR" \|\| true; then` | survives | killed | killed |
| real call drops `--author`, old line kept as a `# ` comment | survives | survives | killed |
| `continue-on-error: true` on the step | survives | survives | survives |

Review thread:
https://github.com/karlkfi/claude-bouncer/pull/174#issuecomment-5985102839.

## Which way it gets built

Anchor the wiring assertion to the whole line, both ends, under `re.M`:

```python
self.assertRegex(wf, re.compile(
    r'^[ \t]*' + re.escape(LINE) + r'[ \t]*$', re.M))
```

where `LINE` is the workflow's `if ! printf '%s' "$BODY" | python3
scripts/release-note.py --author "$AUTHOR"; then`. Then add a second
assertion that the release-note step carries no `continue-on-error`, which the
anchored line cannot see. Drive each mutant above against the new test
and say which went red.

**Who is worse off:** the repo's pull-request gate. Without this, a workflow
edit that makes `release-note` always green passes every local and CI check,
and the check keeps reporting success on bodies it no longer judges. That
predates Q108: the old `run:` block had no test at all.
