# Drop the EXIT=$? capture from the foreground fix texts

Four of exit-status-guard's deny reasons hand back a rewrite ending in `; echo "EXIT=$?"`: `PIPED_REASON`, `PIPESTATUS_REASON`, `GH_API_PIPED_REASON` and `PROCSUB_REASON` (`plugins/exit-status-guard/scripts/bash-exit-status-guard.py:1591:    "<MKDIR>cmd > <LOG> 2>&1; echo \"EXIT=$?\"; "`).
Each of those calls runs in the foreground, where the Bash tool already reports a non-zero exit with the result, so the capture adds nothing the session does not get anyway.

What it does add is a second statement.
In acceptEdits and default, Claude Code's permission matcher sends a command it cannot analyse to a prompt, and `make backlog-lint; echo rc=$?` is a recorded `bashMiss:too-complex` prompt.
Measured 2026-11-27 over local transcripts for 2026-10-27 to 2026-11-26: 196 of the 358 Bash prompts in acceptEdits sessions carried a status capture, an `echo` or an `rc=` assignment reading the last exit, and 157 of them were `too-complex`.
The guard's text is one source of that habit, not the only one, and the measurement does not separate them.
Auto mode is unaffected, since it never prompts for a matcher miss.

`PIPED_REASON` also chains its `grep` onto the same call.
The rewrite becomes `cmd > <LOG> 2>&1`, with the log read in a separate call.

`LOST_STATUS_REASON` keeps `rc=$?; echo "EXIT=$rc"; exit $rc`: that call is backgrounded, its notification reports the last statement, and the capture is what carries the status out.
`SUBST_REASON` keeps its capture too, because the substitution's status is lost unless it is read on the next statement.

Pin the new texts with the suite's reason assertions, and check the friction report's `GATE_RE` still reads the gate from each one.
Found while measuring Q429.
