# GNU env -a hides the command from prod-guard

GNU `env` takes `-a NAME` (long form `--argv0`) to set the command's
`argv[0]`, and runs the command after it. prod-guard's `env` value-flag set
does not list it:
`plugins/prod-guard/scripts/bash-prod-guard.py:284:    'env': frozenset({'-u', '--unset', '-C', '--chdir', '-P'}),  # -P is BSD's`.
So `-a` drops one word instead of two, and its value is read as the tool.

Measured 2026-10-04 by calling `strip_wrappers` on this tree:

| argv | stripped to |
|---|---|
| `env -u F kubectl delete` | `kubectl delete` -- control |
| `env -a x kubectl delete` | `x kubectl delete` |
| `env --argv0 x kubectl delete` | `x kubectl delete` |
| `env -ia x kubectl delete` | `x kubectl delete` |

GNU env 9.11 runs the command after each form. That was driven under
`env -i bash --norc --noprofile -c` (bash 5.3.15) with `/bin/echo RAN_*` as
the command: `-a x`, `--argv0 x`, `-ia x` and `--arg x` all printed. BSD
`env` has no `-a`, so this reaches hosts with GNU coreutils as `env` (Linux,
and macOS with the coreutils `gnubin` on `PATH`).

Found while fixing foreground-guard's twin in Q221, which added `-a` and
`--argv0` to that guard's set.

## Which way it gets built

Add `-a` and `--argv0` to the `env` entry, with a hook-level test behind
`env -a x` and `env -ia x` in front of a prod-targeted mutation. The abbreviated
`--arg` is the prefix-matching work in Q228 (open as #189 when this was filed).
Once that lands, `--argv0` in the set covers `--arg` with no further change.

## If it is never built

A mutating command written behind `env -a`, an ordinary GNU flag, reaches
production with the guard silent. It is rare in hand-typed commands. It is
also a one-line bypass for anyone who knows about it.
