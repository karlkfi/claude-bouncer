# A config regex that overflows turns off all of Class A

`re.compile` raises `OverflowError`, not `re.error`, for a repetition count
past its limit, such as `a{99999999999}`. foreground-guard catches only
`re.error` where it compiles config patterns, so one such pattern escapes to
the hook's top-level handler, which fails open by design
(`plugins/foreground-guard/scripts/bash-foreground-guard.py:# noqa: BLE001 — fail-open on any infrastructure error`).
Every Class A check goes with it, the built-in watch patterns included.

Measured 2026-10-04 on Python 3.14.7, driving the hook without
`FOREGROUND_GUARD_DEBUG`. With `{"poll": {"extra_watch_patterns":
["a{99999999999}"]}}` in the project config, `tail -f x.log` produced no output
and exit 0, so it ran. With `{}` it was denied. In debug mode the traceback
ends `OverflowError: the repetition number is too large` from
`watch_matchers`. The same pattern under `exempt_watch_patterns` crashes
`exempt_matchers` the same way.

Found by the independent review of the Q87 pull request (#186). It is present
on `main` too, so it is not that change's.

The same narrow catch sits at three more sites. These were not driven, so
whether each one fails open, and what it takes down with it, is unmeasured:

- foreground-guard's Class B registry:
  `plugins/foreground-guard/scripts/bash-foreground-guard.py:            continue  # a broken pattern loses itself`
- prod-guard's config patterns:
  `plugins/prod-guard/scripts/bash-prod-guard.py:            continue  # a broken pattern loses itself, not the whole list`
- exit-status-guard's registry:
  `plugins/exit-status-guard/scripts/bash-exit-status-guard.py:                self.errors.append(p)`

## Which way it gets built

Catch `(re.error, OverflowError)` at each compile of a config pattern, so a
pattern that cannot compile loses itself, as the comments beside them already
promise. Add a test per site with an overflowing pattern beside a working one.
prod-guard is a security guard: drive its site before and after, because there
a fail-open means a production command goes through with no prompt.

## If it is never built

A pattern written with a large repetition count, by a person or a generator,
silently disables the guard for the whole repository. Nothing reports it,
because the fail-open is silent outside debug mode. It is rare, and nobody
notices while it lasts.
