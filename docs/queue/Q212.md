# A kill inside a readable `sh -c` body is masked by `interpreter`

Q211 stopped a readable `-c` body labelling its group `sh -c`, on the reasoning
that the `allow` is withheld either way because `interp_code_source` fires on
the same shell word. It does — but the label it leaves behind is `interpreter`,
which sits outside the default `scoped` escalation scope, and the merge that
folds the body's own findings back in keeps the first non-None signal. So a
`kill` the recursion finds inside the body never reaches
`escalate_suppression`.

Measured 2026-09-17 by running the v1.12.0 hook and the one at db357c9 as
subprocesses over the same throwaway project, macOS, `WORKSPACE_GUARD_ESCALATE`
unset:

```
cat in.txt; bash -c 'kill -9 -1'          auto               ask  -> defer
cat in.txt; bash -c 'kill -9 -1'          bypassPermissions  deny -> defer
cat in.txt; timeout 5 bash -c 'kill …'    auto               ask  -> defer
cat in.txt; xargs sh -c 'kill -9 -1'      auto               ask  -> defer
cat in.txt; kill -9 -1                    auto               ask  -> ask
```

A defer runs under `bypassPermissions`, so the last unexamined shape is the one
the kill rule exists for. The bare kill still asks, so wrapping it in a local
`bash -c` is now the way past the rule.

The v1.12.0 catch was incidental — the reason it printed named a body the hook
had in fact read — so this is a coverage loss the Q211 fix exposed rather than
one it invented.

## The fix

Prefer a nested body's signal over `interpreter` where the two disagree, at
both recursion merge sites (`sh -c` bodies and substitution bodies). Anything
else keeps first-non-None. `interpreter` is the label for code the hook cannot
read; a `kill` the recursion did read is the more specific fact, and the one
the default scope acts on.
