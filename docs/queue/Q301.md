# An assignment after && or || is read as made, though it may not run

prod-guard reads every assignment in a list as made, whatever joins it to the
command before. bash runs the right side of `&&` only when the left succeeds,
and the right side of `||` only when it fails. So `false && C=kind-ci` leaves
`C` alone, and the guard judges a later `$C` by a value the command never sees.

## Measured

2026-10-07, prod-guard at `main` `5a5552d` and on the Q300 branch, fixture
`$HOME` whose current context is `gke_acme_prod-us`. Both heads give the same
verdicts.

| command | guard | bash 5.3.15 `$C` at kubectl |
|---|---|---|
| `C=gke_acme_prod-us; false && C=kind-ci; kubectl --context $C delete pod x` | **defer** | `gke_acme_prod-us` |
| `C=gke_acme_prod-us; true \|\| C=kind-ci; kubectl --context $C delete pod x` | **defer** | `gke_acme_prod-us` |

The bash column was driven with `echo`: `C=prod; false && C=kind-ci; echo "[$C]"`
prints `[prod]`, and `false || C=kind-ci` prints `[kind-ci]`.

## Mechanism

Q300 made an assignment inside an `if`, a loop or a `case` arm leave the name
unknown, because bash may not run it. Those are found by their reserved words.
An `&&`/`||` list has none. Q300's `segment_layout` keeps the operators, but
only to find what runs apart, so the assignment still counts as made:

`plugins/prod-guard/scripts/bash-prod-guard.py:701:def _assign(values, defining, maybe, functions, *scopes, unknown=()):`

## Which way it gets built

Read the list operator before each segment from `segment_layout`, and treat an
assignment after `&&` or `||` the way Q300 treats one in a conditional body:
the name becomes unknown, so a target that reads it prompts. That covers a
`{ …; }` group after one too, which Q300 reads as running. A `;` or newline
ahead of it means the assignment runs. Q300 already drops it after `&` or `|`.

## If it is never built

`C=<prod>; <check> && C=<nonprod>; kubectl --context $C delete …` reaches the
production cluster without a prompt whenever the check fails.
