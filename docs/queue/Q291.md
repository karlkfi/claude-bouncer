# A gate's status is lost when its `$(…)` is an argument to a command

A command substitution's status reaches the caller only when it is the whole
command. In an assignment, `x=$(false)` returns 1. As an argument, the
enclosing command's status replaces it: `echo "$(false)"` and
`printf %s "$(false)"` both return 0. exit-status-guard has no rule for the
second case. Driven 2026-10-05 under
`env -i /opt/homebrew/bin/bash --norc --noprofile -c` (5.3.15), and through
the hook from a `git archive` of `origin/main` `ad9ff93`:

| command | bash rc (`false` for the gate) | guard |
|---|---|---|
| `echo "$(make check)"` | 0 | none |
| `set -o pipefail; echo "$(make check \| tail)"` | 0 | deny |
| `x=$(make check)` (control) | 1 | none |

The second row denies on `ad9ff93` only by way of the pipe rule. A `$(…)`
body was judged with pipefail off, so the pipe inside it denied. Once Q259's
change is in, the body inherits pipefail and the shape goes silent, though bash
still returns 0. So the gap predates Q259, and Q259 removes the one shape that
was covering for it by accident. The orchestrator's review of the Q259 pull
request found it.

## Which way it gets built

Deny a registered gate whose substitution is an operand of another command
rather than the value of an assignment. The body's spans already come from
`command_substitutions(cleaned, spans=…)`, so the question is whether the
segment holding the span has a command word of its own. Keep `x=$(gate)`
silent. Keep `if [ "$(gate)" ]` in mind: `[` discards the status too, but a
test of a gate's output may be deliberate, so measure how often it appears
before deciding.

## Who it is for, and what happens if it is never built

A session that writes `echo "$(make check)"` reads the output and takes the
call's exit 0 as a pass. That is the false green this guard exists to stop,
written one way it does not read. How often the shape appears has not been
measured. The cost of delay is flat.
