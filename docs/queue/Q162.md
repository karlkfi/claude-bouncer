# Five project-registry tests are not isolated from `CLAUDE_PROJECT_DIR`

`project_registry_path` resolves its root as
`plugins/exit-status-guard/scripts/bash-exit-status-guard.py:353:root = os.environ.get('CLAUDE_PROJECT_DIR') or cwd`,
so the environment variable outranks the `cwd` the caller passed. Five tests
pass a `tempfile.TemporaryDirectory` as that `cwd` and assert the file they
wrote inside it is the one read:

- `plugins/exit-status-guard/tests/test_exit_status_guard.py:626:def test_project_file_extends_the_defaults(self):`
- `plugins/exit-status-guard/tests/test_exit_status_guard.py:646:the shipped registry must not guess a project target`
- `plugins/exit-status-guard/tests/test_exit_status_guard.py:656:def test_project_file_can_replace_the_defaults(self):`
- `plugins/exit-status-guard/tests/test_exit_status_guard.py:680:def test_the_1x_project_filename_is_still_read(self):`
- `plugins/exit-status-guard/tests/test_exit_status_guard.py:686:def test_the_current_filename_wins_over_the_1x_one(self):`

With `CLAUDE_PROJECT_DIR` set to anything, the temporary directory is never
consulted and all five fail.

Measured 2026-09-04, from `plugins/exit-status-guard`:

| `CLAUDE_PROJECT_DIR` | result |
|---|---|
| unset | `OK`, 62 tests |
| a directory holding no `.claude/` at all | `FAILED (failures=5)` |
| this repository's root | `FAILED (failures=4)`, before Q154 added the fifth test |

The empty directory is the control, and it is what makes this pre-existing
rather than something Q154 introduced: where `CLAUDE_PROJECT_DIR` names a
directory with no registry file, `project_registry_path` returns `None` and the
temporary directory is still not read. The variable does not have to point
anywhere useful — it only has to be set.

## Who it is for, and what happens if it is never built

A developer running the suite from a shell that exports `CLAUDE_PROJECT_DIR`.
Claude Code sets it for hooks and not for the Bash tool, so an ordinary session
and every CI run have it unset — the bite rate today is close to zero, and the
failure is a false red, which is the safe direction.

What earns it a row is that the reading points away from its cause. Five
assertions about the project registry fail together, which reads as the loader
being broken, and nothing in the output names an environment variable. Never
building it leaves a trap whose only symptom is a wrong diagnosis.

## Which way it gets built

Clear the variable for the duration. `TestLegacyNames` already brackets
`PIPE_GUARD_REGISTRY` with `try`/`finally`
(`plugins/exit-status-guard/tests/test_exit_status_guard.py:700:os.environ['PIPE_GUARD_REGISTRY'] = path`),
so the pattern is in the file; `unittest.mock.patch.dict` is the shorter
spelling and covers `REGISTRY_ENV_VARS` in the same move, which is the other way
the environment outranks the caller.

Do not repair it by having `project_registry_path` prefer `cwd`. That precedence
is deliberate —
`plugins/exit-status-guard/scripts/bash-exit-status-guard.py:349:CLAUDE_PROJECT_DIR is the root Claude Code resolved; the payload's cwd is`
says why. This is a defect in the tests, not in the loader.
