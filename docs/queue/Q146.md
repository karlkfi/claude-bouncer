# A `cd` segment silently drops `BRANCH_GUARD_OVERRIDE`

The break-glass prefix is ignored whenever any `cd` sits in the command ahead of
the guarded git call — including a `cd` to the directory the shell is already
in, which changes nothing and still costs the override. The guard re-emits the
same denial it would have emitted with no prefix at all, so the reason names
`gh pr view` and the caller reads it as the override having been considered and
refused.

The only tell is a sentence going missing. A denial that could be lifted ends
with `Re-run it prefixed with BRANCH_GUARD_OVERRIDE=<reason> if you mean to
proceed anyway`; the same denial with a `cd` in front omits it. Nothing else in
the two messages differs, and nobody diffs a refusal they have just read.

`override_reason` is not where it goes wrong. It walks every segment and takes
the first leading assignment run
(`plugins/branch-guard/hooks/branch-guard.py:1849:def override_reason(segments):`),
so it finds the prefix perfectly well behind a `cd`. It is never called. The
gate is one line up:
`plugins/branch-guard/hooks/branch-guard.py:2301:override = override_reason(segments) if liftable else None`,
and `liftable` requires every segment's verdict to be one of a closed set
(`plugins/branch-guard/hooks/branch-guard.py:2296:liftable = (all(ovr for _, ovr, _ in asks)`).
A segment that is not a git or gh invocation classifies as `nongit`
(`plugins/branch-guard/hooks/branch-guard.py:1922:return ('nongit', None)`),
which is outside that set, so one `cd` makes the whole command unliftable.

`echo` survives the same position because it is on a list that `cd` never
joined:
`plugins/branch-guard/hooks/branch-guard.py:308:BENIGN_COMMANDS = frozenset({'echo', 'printf', 'true', 'false', ':'})`.
The string `cd` does not appear anywhere in the file.

**The defect is wider than `cd`, which the title understates.** Any command
outside `BENIGN_COMMANDS` in a leading segment does this: `pwd && OVR=… git
reset --hard` denies with the hint absent, exactly as the `cd` spelling does.
`cd` is what makes it *frequent* rather than what makes it happen, so a fix
listing `cd` alone closes the common case and leaves the class open.

## Measured

Re-measured 2026-09-04 against this tree at `7e143fc5`, by driving the hook on
synthetic stdin. Every row is a `git reset --hard` on a clean worktree whose
branch tip is genuinely unreachable, so each allowed row was safe to allow.

| command | verdict | hint shown |
|---|---|---|
| `git reset --hard origin/main` | deny | **yes** |
| `OVR=… git reset --hard origin/main` | allow | — |
| `OVR=… git reset --hard origin/main 2>&1` | allow | — |
| `echo hi; OVR=… git reset --hard origin/main` | allow | — |
| `OVR=… git reset --hard origin/main; echo done` | allow | — |
| `OVR=… git reset --hard origin/main > /dev/null` | allow | — |
| `cd <the cwd it is already in> && OVR=… git reset --hard` | **deny** | **no** |
| `cd . && OVR=… git reset --hard` | **deny** | **no** |
| `pwd && OVR=… git reset --hard` | **deny** | **no** |
| `OVR=… git reset --hard origin/main > log` | **deny** | **no** |

`OVR=` is `BRANCH_GUARD_OVERRIDE=` with a reason. The redirect rows separate two
things that read alike: a write to a **real file** costs the override, while
`> /dev/null` does not, because `redirect_writes_file` exempts the device
targets. The `pwd` row is what widens the finding past `cd`.

**The 2026-09-01 note that the installed hook is byte-identical to this tree no
longer holds.** The row recorded `sha256 fe6798df…` for both; #85 has landed 232
diff lines since, so the tree is `7e143fc5…` and only the installed 1.10.0 still
carries `fe6798df…`. Every verdict above is the tree's, which is where a fix
lands, and the citations here were re-checked against it.

An earlier attempt to measure this was invalid and is worth naming so nobody
repeats it. Aiming the variants at a throwaway repository with `git -C` is the
one form the guard refuses to reason about, so every variant comes back `ask`
for a reason that has nothing to do with the override, and the uniform result
reads as a finding. The working probe had to be a no-op in the session's own
repository.

## Who is worse off

A session that leads with `cd` by habit, which is most of them — the working
agreement that governs these repos tells agents to give `cd` a literal target
so workspace-guard can track it, so the two guards pull opposite ways on the
same token. The cost is not the refusal. It is that the documented escape hatch
appears broken, and the next thing a session reaches for is a wider one:
`BRANCH_GUARD_PUSH_OVERLAP_ENABLED=0` or its neighbours turn a control off for
everything that follows, which is the outcome the per-invocation prefix exists
to avoid.

**Measured across this machine's transcripts**, this session excluded: 47 real
branch-guard denials in 34 sessions. **11 of them, across 6 sessions, led with a
`cd`, and not one carried the hint** — the mechanism has no counterexample in
the corpus. Separately, 12.2% of all 132,842 distinct Bash commands ever run
here lead with a `cd` and contain a git call, which is the exposure rather than
the hit rate.

Counting real denials needs care: the guard's own reason text also appears in
test output and in probe logs that print a `permissionDecisionReason`, so
matching it anywhere in a tool result reports 217 denials across 89 sessions and
produces two apparent counterexamples to the mechanism above. Both turned out to
be fixtures rather than verdicts. Requiring the guard's line at position 0 of the
result — where a denial puts it, because the command never ran — gives the 47.

## The two shapes, and which one keeps the exclusion honest

The fix is either to resolve a literal `cd` and keep the exclusion, or to treat
`cd` as benign only when its target resolves inside the current repository. The
measurement settles it, and not in the way the phrasing suggests.

**"Inside the current repository" is the wrong test, and it re-admits
[Q135](Q135.md)'s defect.** Two worktrees of one repository return the *same*
`--git-common-dir` and *different* `--show-toplevel`. So a repository-identity
test calls a `cd` into a sibling worktree local, lifts the override there, and
hands the break-glass to exactly the case where the probe measured the wrong
tree. The honest test is **worktree** identity — `--show-toplevel` — which is
what `targets_other_repo`'s callers actually depend on even though its docstring
says "repository":
`plugins/branch-guard/hooks/branch-guard.py:1840:def targets_other_repo(globals_):`.

A control confirms the test discriminates rather than always answering yes: a
genuinely separate throwaway repository returns a different `--git-common-dir`
from both worktrees.

**One trap in implementing it.** `git rev-parse --git-common-dir` answers a
*relative* `.git` from a primary checkout and an absolute path from a worktree,
so a string comparison reports the primary checkout and its own worktree as
different repositories. `--path-format=absolute` returns the same path for both.

**Cost: one subprocess, or none.** Resolving a literal `cd` target is path work
and needs no git call at all if the comparison is made against the session's
already-known toplevel. Where a call is wanted to confirm the target is a git
worktree, it is free in practice. Medians of 21 runs, all in one pass on a quiet
machine (load average 5.5), against this repository and its 56 worktrees:

| call | cost | vs floor |
|---|---|---|
| `rev-parse --git-dir` (process-spawn floor) | 9.04 ms | 1.00× |
| `rev-parse --show-toplevel` | 8.72 ms | 0.96× |
| `rev-parse --path-format=absolute --git-common-dir` | 9.12 ms | 1.01× |
| `git worktree list` | 16.51 ms | 1.83× |
| `git log --stat` (costly control) | 198.00 ms | 21.89× |

Both identity reads are indistinguishable from the cost of starting a process at
all, so the honest test is also the cheapest one. The control is in the table
because without it a set of near-identical numbers cannot be told from an
instrument that has stopped discriminating.

So: **resolve a literal `cd`, compare worktree identity, keep the exclusion.**
A non-literal target — a `$VAR` or an unresolved `$( )` — stays unliftable, which
is correct: the hook cannot know where it lands.

## The boundary with Q135

Both rows turn on what `targets_other_repo` should see, and the earlier reading
that "whichever settles that one settles this" is **too strong**. They are
separable, and this row is not blocked:

- **This row owns whether the break-glass is reachable** — the `liftable` gate.
  Its fix is a classification change and touches no probe, so a `cd` whose
  literal target is the **same worktree** can be made liftable on its own. That
  is the case the corpus actually contains: every one of the 11 cd-led denials
  above is a `cd` to the session's own tree or to a path within it.
- **Q135 owns what the probe measures** — the cwd handed to `push_overlap` and
  `current_branch`. Only that row can make a `cd` into a *different* worktree
  liftable, because until the probe is aimed there is no correct verdict to lift.

A cross-worktree `cd` therefore stays denied under this row's fix alone, and that
is the right residual rather than a shortfall: the override should not lift a
verdict the guard measured in the wrong tree. The shared piece is the
worktree-identity test above, which whichever lands first should introduce.
