# A `cd` segment silently drops `BRANCH_GUARD_OVERRIDE`

The break-glass prefix is ignored whenever any `cd` sits in the command ahead of
the guarded git call — including a `cd` to the directory the shell is already
in, which changes nothing and still costs the override. The guard re-emits the
same denial it would have emitted with no prefix at all, so the reason names
`gh pr view` and the caller reads it as the override having been considered and
refused.

The only tell is a sentence going missing. A denial that could be lifted ends
with `Re-run it prefixed with BRANCH_GUARD_OVERRIDE=<reason> if you mean to
proceed anyway`; the same denial with a `cd` in front omits it. Nothing else in
the two messages differs, and nobody diffs a refusal they have just read.

`override_reason` is not where it goes wrong. It walks every segment and takes
the first leading assignment run
(`plugins/branch-guard/hooks/branch-guard.py:1757:def override_reason(segments):`),
so it finds the prefix perfectly well behind a `cd`. It is never called. The
gate is one line up:
`plugins/branch-guard/hooks/branch-guard.py:2202:override = override_reason(segments) if liftable else None`,
and `liftable` requires every segment's verdict to be one of a closed set
(`plugins/branch-guard/hooks/branch-guard.py:2197:liftable = (all(ovr for _, ovr, _ in asks)`).
A segment that is not a git or gh invocation classifies as `nongit`
(`plugins/branch-guard/hooks/branch-guard.py:1830:return ('nongit', None)`),
which is outside that set, so one `cd` makes the whole command unliftable.

`echo` survives the same position because it is on a list that `cd` never
joined:
`plugins/branch-guard/hooks/branch-guard.py:307:BENIGN_COMMANDS = frozenset({'echo', 'printf', 'true', 'false', ':'})`.
The string `cd` does not appear anywhere in the file.

## Measured

2026-09-01, branch-guard 1.10.0. The installed hook is byte-identical to this
tree — both `sha256
fe6798dfe7b65f130ea070630969e38ae5116192618ec28a8b33d80bae54e0d7`. Every row
below is `git reset --hard HEAD` run on a clean tree whose branch already
pointed at `HEAD`, so each allowed row was a no-op and the branch never moved.

| command | verdict |
|---|---|
| `git reset --hard HEAD` | deny, hint shown |
| `OVR=… git reset --hard HEAD` | allow |
| `OVR=… git reset --hard HEAD 2>&1` | allow |
| `OVR=… git reset --hard HEAD 2>&1` then `echo …; git rev-parse HEAD` | allow |
| `echo …` then `OVR=… git reset --hard HEAD` | allow |
| `cd <the cwd>` then `OVR=… git reset --hard HEAD` | **deny, hint absent** |

`OVR=` is `BRANCH_GUARD_OVERRIDE=` with a reason. The redirect and the trailing
segments are in the table because they were the first suspects and both are
innocent: what separates the last row from the one above it is only that the
leading segment is `cd` rather than `echo`.

An earlier attempt to measure this was invalid and is worth naming so nobody
repeats it. Aiming the variants at a throwaway repository with `git -C` is the
one form the guard refuses to reason about, so every variant comes back `ask`
for a reason that has nothing to do with the override, and the uniform result
reads as a finding. The working probe had to be a no-op in the session's own
repository.

## Who is worse off

A session that leads with `cd` by habit, which is most of them — the working
agreement that governs these repos tells agents to give `cd` a literal target
so workspace-guard can track it, so the two guards pull opposite ways on the
same token. The cost is not the refusal. It is that the documented escape hatch
appears broken, and the next thing a session reaches for is a wider one:
`BRANCH_GUARD_PUSH_OVERLAP_ENABLED=0` or its neighbours turn a control off for
everything that follows, which is the outcome the per-invocation prefix exists
to avoid.

## The one-line fix is not obviously safe

Adding `cd` to `BENIGN_COMMANDS` is the shape, and `cd` is not inert the way
`echo` is: it changes which repository the later segments act on. The exclusion
that keeps the break-glass honest is aimed at exactly that —
`plugins/branch-guard/hooks/branch-guard.py:1810:if set(inv['globals']) & GIT_ESCAPE_HATCHES or targets_other_repo(inv['globals']):`
refuses to lift anything pointed at another checkout, because the override's
whole claim is that the loss stops at this machine. But
`plugins/branch-guard/hooks/branch-guard.py:1748:def targets_other_repo(globals_):`
reads only `git -C`, `--git-dir` and `--work-tree`. A `cd` is invisible to it,
so calling `cd` benign would let an override lift a command that had walked
into a checkout this session does not own.

**Measure:** which of the two shapes keeps the exclusion honest, and what it
costs. The fix is either to resolve a literal `cd` and keep the exclusion, or to
treat `cd` as benign only when its target resolves inside the current
repository. Neither is endorsed here, and the measurement belongs with
[Q135](Q135.md)'s — both turn on what `targets_other_repo` should see, so
whichever settles that one settles this. Q135 records the same blindness on the push path and cites the same
function; whichever way that one is settled should settle this one, and a fix
landing there first may make this a two-line change.
