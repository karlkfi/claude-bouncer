# A command substitution inside double quotes is invisible to the guard

`tokenize` rewrites `` ` `` to `;` before lexing, so a substituted command splits
into its own simple command. When the substitution sits inside double quotes
the rewritten `;` lands inside a quoted word, shlex keeps the word whole, and
no segment is produced. The command is never classified and the segment
defers.

Bash runs it. Double quotes do not suppress command substitution -- they only
suppress word splitting and globbing -- so every shape below executes while the
guard is silent. This is the false-negative direction, which
[`plugins/prod-guard/CLAUDE.md`](../../plugins/prod-guard/CLAUDE.md) names as
the failure mode to fear.

`tokenize`'s own docstring asserts the opposite: *"Rewriting inside quotes only
ever creates extra segments to inspect, never hides one."* That sentence is
false, and the unit reading below is the counter-example.

## Measured

2026-09-09 at `80d19b3`, fixture `$HOME` with ambient context `gke_acme_prod-us`.
Identical verdicts on trunk and on the Q159 branch, so this predates both.

| command | guard | bash runs it? |
|---|---|---|
| `` `kubectl delete ns foo` `` bare | deny -- control | yes |
| `` echo "`kubectl delete ns foo`" `` | **DEFER** | **yes** |
| `` X="`kubectl delete ns foo`" `` | **DEFER** | **yes** |
| `echo "$(kubectl delete ns foo)"` | **DEFER** | **yes** |
| heredoc body, bare `` ` `` | deny -- control | yes |
| heredoc body, `` "`kubectl delete ns foo`" `` | **DEFER** | **yes** |
| heredoc body, `` '`kubectl delete ns foo`' `` | **DEFER** | **yes** |

That bash runs each was driven separately with a payload that exists nowhere on
`PATH`, so the invocation is proved by `command not found` rather than by
running a real tool. A quoted-delimiter heredoc is the negative control: it
suppresses all three forms, and nothing ran.

The root cause is one lexer reading, not a verdict:

```
body                                     tokens produced
`kubectl delete ns foo`                     -> [';', 'kubectl', 'delete', 'ns', 'foo', ';']   2 separators
x = "`kubectl delete ns foo`"               -> ['x', '=', ';kubectl delete ns foo;']          0 separators
```

The single-quote row is the sharper one. Inside a heredoc body quote characters
are literal text and suppress nothing, so applying POSIX quoting there is the
wrong model twice over.

## How it was found

A session writing a pull-request body used an unquoted heredoc whose text
contained backtick-delimited code spans. Bash substituted them and
`kubectl delete ns foo` ran against a live kind cluster. It returned
`namespaces "foo" not found` -- nothing was destroyed because that namespace
did not exist. The guard defers on that shape, so it never prompted.

Two guards were between that command and the cluster, and neither is at fault
for the typo: the point is that the shape is reachable by accident, from a
routine editing call, and the deny that should have caught it did not fire.

## Which way it gets built

Not by rewriting a backtick to `;` more aggressively -- inside single quotes
in ordinary shell text a backtick really is literal, so a blunter rewrite trades
this false negative for a false positive.

Extract substitutions structurally instead. `bouncer_parse` already exposes
`command_substitutions(text, quotes=True)`, whose `quotes` parameter is exactly
this decision, and the guard does not call it here. Two contexts need opposite
answers, which is why this is size M rather than S:

- **Ordinary shell text**: a substitution inside double quotes expands, inside
  single quotes does not. `quotes=True` is the right reading.
- **A heredoc body with an unquoted delimiter**: nothing in the body is a quote
  character, so every substitution expands regardless. The body needs scanning
  with quoting *disabled*.

`tokenize` already separates the two -- `strip_heredoc_bodies` hands expandable
bodies back through an out-list -- so the split exists and only the scan is
wrong. Fix the docstring in the same change: it currently asserts the invariant
this row disproves.

Check the sibling guards while here. The rewrite-then-lex shape is prod-guard's
own, but whether workspace-guard and foreground-guard read a double-quoted
substitution is worth one probe each rather than an assumption.

## If it is never built

Any mutating command a session writes inside double quotes reaches the cluster
unguarded -- and that includes the ordinary case of quoting a command into a
variable, not just the accident that surfaced it.
