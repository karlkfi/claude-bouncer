# prod-guard expands an escaped `\$X` in a `bash -c` body in the parent

In `X=kind-ci; bash -c "\$X kubectl --context=gke_acme_prod-us delete pod x"` the parent
leaves `$X` for the child, which does not inherit an unexported `X`, so the child runs the
delete. prod-guard expands any double-quoted body against the parent's variables
(`plugins/prod-guard/scripts/bash-prod-guard.py:3435:                    body = expand_vars(body, same_shell)`),
reads `kind-ci kubectl …`, and defers.

The expansion is right for a live `"$X"`, which the parent does expand. Since Q322 the lexer
drops the backslash from `\$X` as bash does, so the body token reads `$X` either way and
prod-guard cannot tell which `$X` the parent left alone.

Measured 2026-11-01 by the stream-A reviewer on #314 at `fcd44b0`, through each guard's hook
script: defer from all five guards on `main` at `1d0fe4e6` and on #314. Under bash 5.3.15 the
child runs the command.

## Which way it gets built

The reviewer proposes expanding a child body only against exported names and the segment's
prefix assignments. Expanding fewer names leaves more unresolved, and an unresolved
command-position word already reads both ways (Q298), so this direction only judges more. It
would also stop resolving a live `"$C"` that names a context from an unexported variable, which
then asks instead of denying. Neither effect is measured. Recording, per `$`, whether its
backslash was dropped would keep the live case; that is a lexer change reaching all five guards.

## If it is never built

A production mutation behind an escaped `\$X` in a double-quoted `bash -c` body goes unjudged
whenever the parent has an unexported `X` set to a plain word. The shape needs an unexported
assignment and an escaped reference to the same name, so it is likely rare.
