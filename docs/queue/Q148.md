# `set -o pipefail` after the pipeline suppresses the piped-gate deny

`sets_pipefail` asks whether *any* segment sets the option
(`plugins/exit-status-guard/scripts/bash-exit-status-guard.py:427:def sets_pipefail(segs)`),
so a segment that runs after the pipeline suppresses the deny for a pipeline it
could not have affected. Measured 2026-09-01 against the shipped registry, with
the same command minus the option as a control: `make check | tail; set -o
pipefail` is allowed, `make check | tail; echo hi` is denied.

No realistic command has this shape — the option is written first or not at all
— so this is an evasion surface rather than a live false green, and pruning it
is a defensible groom outcome. What argues for keeping it is that the token is
the only thing standing between a pipe and a deny, which makes appending it a
rewrite an agent could reach for once the deny is otherwise unavoidable.

Scoping to the segments that precede the pipeline is the fix. Q136 removes the
sibling `$pipestatus` suppression outright and so does not reach this one; the
options differ because `pipefail` is portable and genuinely does mitigate a
pipeline it precedes.
