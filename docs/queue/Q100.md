# `&&` breaks a mutation control, whose gate is required to fail

**The guard is right about this shape, and that is what makes the row worth
filing rather than shrugging at.** `sequenced_mutation` catches a real
fail-open, and in the same session it misfired in it also fired correctly
twice: once on `git add … ; git commit`, where `&&` is exactly the join the
caller wanted, and once on a piped `git push`, where the status would have been
the filter's. A report that reads as general complaint gets weighed against
that hit rate and loses. This is one shape, not a noise level.

The shape is a mutation control: mutate a file, run a gate that is **required
to fail** — the failure is the assertion — then restore. `&&` skips the restore
on the expected failure and leaves the mutated file in the tree, so a session
that follows the remedy verbatim breaks the thing it was building.

Measured 2026-08-22. Two instances in one session, from a worker building
mutation controls in `karlkfi/claude-spill-guard`; it cost two denied calls and
a wrapper script to work around. One milder instance in the coordinating
session, a `gh api … --jq` read whose exit status nobody needed.

Two directions, both priced here rather than one being picked:

- **Recognise the shape, and change what the remedy says for it.** The
  detection is
  `plugins/exit-status-guard/scripts/bash-exit-status-guard.py:566:def sequenced_mutation`,
  which asks only whether a gate is sequenced before a mutator. Telling a
  restore from a publish needs a third question — is this mutator undoing what
  an earlier segment did — and the remedy for a hit then becomes the capture
  form: `cmd > log 2>&1; rc=$?; restore; [ "$rc" -ne 0 ] || fail`.
- **Leave the detection alone, and widen the remedy text.**
  `plugins/exit-status-guard/scripts/bash-exit-status-guard.py:700:Join them with`
  names `&&` and nothing else; naming capture-then-restore beside it needs no
  new analysis. It is not one sentence, though. The sequencing reason is the
  one that names no log file —
  `plugins/exit-status-guard/tests/test_exit_status_guard.py:646:One denial per reason that names a log file`
  — so a capture form has to route through `with_log_path` and join the
  three-template placeholder fixture. The standing cost is a longer reason on
  every sequencing deny, most of which do want `&&`.

Either way the fixtures assert `is sequenced before` rather than the remedy
tail, so nothing existing inverts.

**Calibration, not a second complaint:** the same session took a
`workspace-guard` deny on a write to `/tmp` and a `foreground-guard` deny on a
45-second `sleep`. Both were correct, and both remedies — the session
scratchpad, and a bounded wait — were the right answers.
