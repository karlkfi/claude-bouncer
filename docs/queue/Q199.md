# Reconsider the cross-worktree break-glass exclusion

A verdict about a *different* worktree is unliftable, in both spellings. The
`git -C` half is `is_overridable`'s escape-hatch check
(`plugins/branch-guard/hooks/branch-guard.py:1995:if set(inv['globals']) & GIT_ESCAPE_HATCHES or targets_other_repo(inv['globals']):`),
and the `cd` half is the classification Q146 added, which admits a `cd` as
recognized-safe only when `same_worktree` places its target in the tree already
being judged
(`plugins/branch-guard/hooks/branch-guard.py:2408:else 'nongit', None, False))`).
Both keep the ask.

**The reason both were written no longer holds.** Each rests on the same
argument: until the guard's probes are aimed at the tree the command acts on,
there is no correct verdict there to lift, so the override must not reach it.
Q135 aimed them — `git_cwd` walks every `-C` and `cd_destination` follows a
literal `cd`, and the branch and overlap probes now read the tree the command
runs in rather than the session's own. So the premise is spent while the
exclusion it justified is still in place, in two separate mechanisms that
happen to agree.

That does not settle which way it should go. Refusing to lift a cross-worktree
verdict may be right on its own merits, since the reason a session gives is
about work it can see and the branch in the other tree belongs to a session it
cannot ask. The point is that nothing has argued that, and the code currently
asserts it by inheritance.

## Who is worse off

A session standing down from work it holds in two trees, which is the arrangement
a parallel run produces. It meets a deny it cannot lift, and the documented
next move — the prefix — is refused a second time. That is the shape Q146 shows
sessions respond to by reaching for a repo-wide `*_ENABLED=0` knob instead.

## What happens if it is never built

Unknown, and that is the finding rather than a reason to rank it low. The
frequency is unmeasured: Q146 counted 47 real denials and attributed 11 to a
leading `cd`, none of them cross-worktree, so the corpus that motivated Q146
says nothing about this cell either way.

## Which way it gets built

Undecided.

**Measure:** Count cross-worktree denials in this machine's transcripts the
way Q146 counted cd-led ones — the guard's line at position 0 of the tool
result, so fixtures and probe logs that merely quote a reason are excluded.
Split them by spelling (`-C` versus a followed `cd`) and by whether the target
was a worktree of the same repository or a separate one. A count near zero
settles it as written and the exclusion stays on its own merits; a non-trivial
count makes the design question real, and it should then be answered against
what the reason string can honestly claim about a tree the session does not
hold.

Both halves move together or neither does. Fixing one spelling and not the
other would leave the guard lifting `cd <sibling> && …` while refusing
`git -C <sibling> …`, which is the same command written two ways.

## Notes

Carried out of Q135, which introduced the aimed probe and left this as a stated
residual rather than a defect, and confirmed still open against Q146's fix by
driving the hook: with the override set, `git -C <sibling worktree> reset --hard`
and `cd <sibling worktree> && …` both deny, while the same command in the
session's own tree allows.
