# Reconsider the cross-worktree break-glass exclusion

**Event:** either of two things in this machine's transcripts or config:

- A cross-worktree branch-guard denial from a version carrying Q135 (2026-09-09
  or later), counted the way the table below was taken. One is enough to revive
  this, because the count since Q135 is zero.
- Worktree grants (Q144's `BRANCH_GUARD_WORKTREE_GRANTS`) turned on by default.
  That would let the guard tell "a worktree this session created" apart from
  "a peer's worktree", which is the distinction the exclusion's own argument
  turns on (see below).

Deferred 2026-10-04 after measuring. The exclusion stays as written. Nothing
in the corpus shows it costing anything under the current guard.

## What the exclusion is

A verdict about a *different* worktree is unliftable, in both spellings. The
`git -C` half is `is_overridable`'s repo-redirect check
(`plugins/branch-guard/hooks/branch-guard.py:if set(inv['globals']) & GIT_ESCAPE_HATCHES or targets_other_repo(inv['globals']):`).
The `cd` half is the classification Q146 added: a `cd` counts as
recognized-safe only when `same_worktree` places its target in the tree already
being judged
(`plugins/branch-guard/hooks/branch-guard.py:else 'nongit', None, False))`).
Both keep the ask.

Both were first written on one argument: until the probes measured the tree a
command acts on, there was no correct verdict there to lift. Q135 aimed the
probes, so that argument is spent. What remains is the argument on the merits:
the reason a session gives is about work it can see, and a branch in another
tree may belong to a session it cannot ask.

## Measured

Taken 2026-10-04 over every transcript under `~/.claude/projects/`,
subagents included and this session excluded. A denial counts only when the tool
result opens with `branch-guard: ` or `PreToolUse:Bash hook error: branch-guard: `
and is an error. That is Q146's rule: it drops fixtures, source reads and probe
logs that merely quote a reason. Each denial was joined to its Bash command by
tool-use ID. The corpus starts 2026-08-22, the day after the prefix shipped
(#101), and ends on the day of the walk.

| | denials | sessions |
|---|---|---|
| all real branch-guard denials | 90 | 72 |
| carrying `BRANCH_GUARD_OVERRIDE` | 7 | — |
| naming any directory other than the session's own | 9 | 8 |
| — of which a `cd "$(git rev-parse --show-toplevel)"`, the same tree | 5 | 5 |
| — of which a separate repository (another repo's worktree; a `git init` probe repo) | 2 | 2 |
| — of which a sibling worktree of the same repository | **2** | **1** |
| — of which a `git -C` spelling | 0 | 0 |
| denials after Q135 (2026-09-09) | 28 | — |
| — of which cross-worktree | **0** | **0** |

The `-C` zero is not an instrument that cannot fire. The same flagger reports
`git -C /x/y push origin main` as a hit, and none of the 90 commands contains
` -C ` at all. Neither separate-repository denial carried the override.

The one sibling-worktree session, on 2026-08-27, was a subagent rebasing a
peer's pull request in a scratchpad worktree, `wt31`, that it had created
with `git worktree add` three minutes earlier. Its push from there was denied for an
overlap. It retried with the override, giving the reason "false positive: guard
read the stale remote head", and was refused. Three minutes later it checked
the same commit out on a new branch in its own worktree and pushed from there.
The guard allowed that push, and the push landed.

Two things about that one case:

- **The guard behind it predated Q135.** The installed version was 1.9.0.
  `git_cwd` first appears at the `branch-guard/v1.11.0` tag, after Q135 merged
  on 2026-09-09, and is absent at `v1.10.0`. So that guard measured the
  overlap in the session's own tree rather than in `wt31`, which is the defect
  Q135 fixed and the "false positive" the session named in its reason. The
  current guard follows the `cd` into `wt31`, and might not have denied at all.
  That last part is inferred, not re-driven.
- **The refusal changed where the push came from, not what was pushed.** The
  worktree belonged to the session itself, not to a peer. The exclusion's
  argument on the merits had nothing to protect, and the route around it went
  through the session's own checkout.

## The answer

**Measure (answered):** keep the exclusion and build nothing. The row's own
rule decides it: a count near zero leaves the exclusion standing on its merits.
Under the current guard the count is zero.

The single case also shows where the merits argument is weak. It protects a
peer's worktree and cannot tell one from the session's own, so it refused a
session working its own scratch checkout. That is the shape the second revive
trigger names. Grants would let the guard lift for a worktree this session
created and keep refusing every other. Until grants are on by default, the
guard has no ownership fact to key that on.

Both halves still move together or neither does. Lifting `cd <sibling> && …`
while refusing `git -C <sibling> …` would treat one command written two ways
differently.

## If it is revived

Who it is for: a session standing down from work it holds in two trees, which
a parallel run produces. It meets a deny it cannot lift, and the override, the
documented next move, is refused a second time. The measured response is to
redo the push from a checkout the guard does accept. That loses nothing in the
one case on record, but it puts the session's own worktree on a branch it was
not on.
