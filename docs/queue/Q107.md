# Every gate-adding PR conflicts on the same `check:` list line

**Event:** two pull requests that each add a gate to `check:` conflict on that
list after both were pushed.

Deferred 2026-10-04 after measuring the rate this row asked the fix to be sized
against. I parsed `check:`'s prerequisites at every commit on `origin/main` that
touched the `Makefile`. Seven gates were added after the bootstrap commit
(`eef0568`). Four landed on 2026-08-22, the day the plugin repos were
consolidated (#4, #8, #15, #30). Since then there have been three in 38 days:
`install-ref-check` (#67, 08-27), `backlog-claims` (#118, 09-09) and
`gate-parity-check` (#220, Q183), and Q215's `launcher-check` lands in the PR
carrying this deferral. No other row in the store adds a gate. At
roughly one gate every two weeks, a registry file, a merge driver and a
`gate-parity-check` that reads the registry cost more than the conflict they
prevent.

**Not verified:** whether GitHub's mergeability check honours a `.gitattributes`
`merge=union` or a custom merge driver. If it does not, a registry only
automates the local rebase, and the CI re-run counted below as the cost remains.
Settle that before building this if the trigger fires.

**One instance so far, 2026-10-05.** Rebasing Q215 onto #220 conflicted on
`check:`, `.PHONY` and the `CLAUDE.md` Checks block. One stream had serialized
the two on purpose, the hand union took about a minute, and nothing re-ran in
CI, because Q215 had not been pushed. The trigger counts only a conflict after
both PRs were pushed. That is the case that costs the CI re-run this row is
about, and this one did not.

If it is built, `scripts/gate-parity-check.py` reads `check:`'s prerequisites
as written, so it has to learn to expand the registry in the same PR.

`make check` names its gates in one backslash-continued list in the
`Makefile`. Every pull request that adds a gate appends to the line that list
ends on, so any two of them conflict whatever order they merge in -- there is no unchanged line between the two
changes for git to anchor a three-way merge on, which is the same mechanism
that makes adjacent rows in a committed backlog table collide.

Measured 2026-08-22 while adding `action-pin-check`: the gate list went from
six entries to seven. The store already held rows that would each add another
-- the roster check (Q104) and the backlog index (Q93) were two of them, and
by 2026-08-23 the allocator gate (Q112) was a third. Any two landing in
sequence send the later one back for a rebase and a full CI re-run, and the
resolution is always the same trivial union of entries.

The shape that fixes it is a registry file every gate-adding change appends to,
routed by `.gitattributes` to a merge driver that merges entries as a set.
`github-actions-gateway` runs this as `mk/gate-lists.mk`, and the comment at
its head records why the lists left the Makefile. Worth taking the mechanism
rather than the file: at seven gates the registry is arguably heavier than the
problem, so size it against how often a gate actually gets added here.

The same argument reaches the `.PHONY` line and the `help` block, which every
gate-adding change also edits.
