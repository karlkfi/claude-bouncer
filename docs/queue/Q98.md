# The friction report cannot say which guard version produced a decision

A report over any window wide enough to be interesting spans releases, and
nothing in its output says so. Every decision is presented as the current
guard's, so friction a shipped fix already removed still ranks, and the shapes
worth acting on are buried under ones that no longer occur.

Measured 2026-08-22 on a 30-day run: 873 `expand` prompts, of which the top
offending path was `$f` with 228. Probed against the installed 1.10.0, every
`$f` shape in that count now allows — a glob loop, a literal-assigned variable,
a `$(basename)` beside a resolved token. The ranking was answering "what did
this guard used to prompt on", and reads as "what does it prompt on".

`--since` is the workaround and it is not a fix: it needs the release dates the
report does not carry, and a window chosen to exclude one fix silently excludes
everything else that shipped alongside it.

The blocker is that the installed version at decision time is not in the
transcript. `~/.claude/plugins/installed_plugins.json` holds only what is
installed *now*, and its `gitCommitSha` is written at first install and never
refreshed, so it cannot date anything. What is derivable: this repo's tags give
each version a date, and the decisions carry timestamps, so a release-dated
boundary is computable from the repo rather than from the transcript. That is
approximate at the edges — a machine that upgraded late sits on the old guard
after the tag — and approximate beats silent.

**Bucket the decisions by the release window their timestamp falls in**, and
show the boundary in the category and path tables, so a shape a fix removed
visibly stops rather than accumulating. Two alternatives were considered and
lose to it: a coverage note beside the two already at
`plugins/workspace-guard/scripts/friction-report.py:429:def coverage_note` is
cheap and honest but leaves the ranking exactly as misleading, and defaulting
`--since` to the current version's release date fixes the default reading by
throwing away the history that makes a trend visible.

Whichever lands, say in
`plugins/workspace-guard/docs/development/measuring-friction.md` that a ranking
over a multi-release window mixes them. prod-guard had the neighbouring problem
one guard over — categories drifting from the hook's live output, now pinned by
feeding the report what the hook actually prints — and this one is the same
class: the report describing a guard it no longer matches.
