# A Set-Location inside a PowerShell $(…) never moves the outer location

The PowerShell frontend follows a `Set-Location` written as a statement of its
own, but not one written inside a `$(…)`. The subexpression is masked out of
the text the segment walk reads, and the recursion that analyses its body keeps
its location to itself, so a relative operand after it is judged against the
directory the string was in before.

## Measured

2026-10-04, driving the hook with `tool_name: PowerShell` and `cwd` set to a
scratch workspace, on `main` at 9f90e5c. Rows 1 to 3 were also driven on the
Q172 branch and gave the same answers. `q172-x` is a synthetic name; nothing
was read.

| command | verdict |
|---|---|
| `Set-Location ..; Get-Content q172-x` -- control | ask |
| `Write-Output $(Set-Location ..); Get-Content q172-x` | **allow** |
| `$null = $(Set-Location ..); Get-Content q172-x` | **allow** |
| `Get-Content in.txt; Write-Output $(Set-Location ..)` | allow |
| `& { Set-Location .. }; Get-Content q172-x` | ask |

**Not measured: what PowerShell does.** No `pwsh` is installed where this was
filed. The row rests on PowerShell keeping the current location as session
state rather than per scope, and on `$(…)` running in the current scope, so a
`Set-Location` inside one moves every statement after it. If that holds, rows
2 and 3 are an `allow` for a read outside the workspace. Run them under `pwsh`
first: if the location does not persist, this row is closed by that
measurement and the guard is right.

Row 5 asks only because of how the script block happens to tokenize. Treat it
as an accident to check in the fix rather than evidence the frontend handles
script blocks.

Bash is the other way round. A `cd` in `$(…)` runs in a subshell and moves
nothing, and Q173 is the guard getting that wrong in the other direction. The
two frontends need opposite rules here.

## Which way it gets built

Q172 numbered the subexpression masks, so the segment walk now knows which
body sits in each token. The fix is for the recursion to also return the
location its body leaves behind. The walk then applies that location after the
segment that holds the body, in the order PowerShell evaluates the arguments.
A body whose final location the recursion cannot follow makes the location
unknown, which is what an untracked `Set-Location $d` already does.

## If it is never built

On the Windows frontend, a one-word wrapper around a `Set-Location` takes every
later relative read in the string outside the workspace with an `allow`. The
guard's `allow` short-circuits the user's own permission settings, so this is a
silent read with the hook vouching for it.
