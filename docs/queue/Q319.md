# Two guards read time options as bash does, not as POSIX sh runs them

`strip_sh_keywords` takes `time`'s options the way bash 5.3.15 reads the
keyword: one `-p`, then one `--`, and anything after that is the command. That
holds for the shell the Bash tool runs, and not for every shell a command
string can reach. Under `env -i <shell> -c`, measured 2026-11-01:

| command | bash | `bash --posix` | `/bin/dash` |
|---|---|---|---|
| `time -p -p cat f` | runs `-p` | runs `cat` | runs `cat` |
| `time "-p" cat f` | runs `-p` | runs `-p` | runs `cat` |
| `time -- -p cat f` | runs `-p` | `/usr/bin/time` runs `-p` | `/usr/bin/time` runs `-p` |

Under `--posix`, and in dash, which has no `time` keyword, a `time` followed by
an option is `/usr/bin/time`, and that program takes a repeated or quoted `-p`
as its own option.

prod-guard reads these as a wrapper and denies all three (Q241, #286).
workspace-guard and exit-status-guard take the shared strip's answer, so a
command behind `time -p -p` is unjudged when it reaches them inside
`sh -c '…'` on a system whose `sh` is dash, or inside `bash --posix -c '…'`.
Both guards deferred on these shapes before Q241 as well, so this is a gap
that predates the change, not a regression.

## Which way it gets built

Decide in each guard whether to judge the words after the run of `-p`/`--`
the way prod-guard does, by handing `time` to the guard's own wrapper peel.
Over-judging the `time -- -p` shape costs a prompt on a command that runs
nothing guarded. Keep the shared strip exact to bash. The guards that need the
POSIX reading can take it at their call sites, as prod-guard does.

## If it is never built

`sh -c 'time -p -p rm /etc/x'` passes workspace-guard where dash is `sh`. How
often sessions write a repeated `-p` is not measured, and it is likely rare.
