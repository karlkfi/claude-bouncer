# A function a sourced file defines can reassign a name the guard holds

Since Q299, `source` and `.` make every name the guard holds unknown. A name
assigned after the `source` is known again, and the guard reads a later call
to a name it never saw defined as a command that sets nothing. bash runs the
function the sourced file defined, which can set that name:

| command | guard | bash 5.3.15 `$C` at kubectl |
|---|---|---|
| `source x.sh; C=kind-ci; f; kubectl --context $C delete ns x` | defer | `from-file` |

Measured 2026-11-01 on the Q299 branch, fixture `$HOME` whose current context
is `gke_acme_prod-us`. The bash column ran `echo "[$C]"` in place of kubectl
under `env -i /opt/homebrew/bin/bash --norc --noprofile`, with `x.sh` holding
`f() { C=from-file; }`.

## Which way it gets built

After a `source`, treat a call to any command the guard does not know as a
function that may set every name, the way a call to a function defined in the
string already forgets what its body assigns. Not settled: whether that should
cover commands with an evaluator too, since a sourced file can define
`kubectl` itself.

## If it is never built

`source <file>; C=<nonprod>; <fn>; kubectl --context $C delete …` reaches
whatever cluster the function points `C` at without a prompt. It needs a
sourced file that defines a function reassigning the name, so it is unlikely
by accident.
