# gsed -i gets no note that its write never ran

When a guard refuses a whole Bash call, `note_discarded_writes` appends a sentence naming the writes in it that did not happen, so the model does not believe an edit landed.
Its `sed` case matches the bare name only (`lib/bouncer_parse.py:2330:    elif name == 'sed' and any(o.startswith('-i') or o.startswith('--in-place')`), so a `gsed -i` in a refused call is left out of that sentence.
Measured 2026-11-16 on `origin/main` at `36d05ed8`, calling `discarded_writes` directly:

| command | writes named |
|---|---|
| `sed -i 's/a/b/' f` | `` `sed -i` `` |
| `gsed -i 's/a/b/' f` | none |
| `gsed -i 's/a/b/' f; tee g` | `` `tee g` `` |

All five guards call `note_discarded_writes`, so the note is missing from each one's refusals.
Found while Q341 aliased `gsed` to `sed` in workspace-guard, where the boundary check itself now covers `gsed`.
This is the message, not the verdict: the refusal still lands, and nothing runs.

Q373 is the same note missing a write behind a wrapper.
Both fixes land in `_segment_writes`, so one worker should take the pair.

## Which way it gets built

Treat `gsed` as `sed` in `_segment_writes`, and pin the `gsed -i` row of the table in the shared parser's tests.
Then `make sync` to carry the change into all five vendored copies.

## If it is never built

A refused call holding `gsed -i` says nothing about that write.
A model that wrote the edit and the check in one call may then read the edit as done, which is the mistake the note exists to stop.
It is rare: it needs GNU sed under its Homebrew name, inside a call some guard refuses.
