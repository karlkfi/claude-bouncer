Minor release: the workspace boundary now covers the script an interpreter is told to run. `python3 /outside/script.py` reads that file, so the path is checked like any other read. A clean guarded command also stops earning a silent `allow` for interpreter code elsewhere in the same string. Plus a symlink fix, and a new page recording what each decision actually does per permission mode.

> [!IMPORTANT]
> **An interpreter's script argument is now checked against the workspace boundary.** `python3 /outside/script.py` prompts like any other outside-workspace read. Measured on 52,327 recorded commands against v1.9.0, 211 (0.4%) become blocking, and they are the interesting ones — scripts run out of another repo or worktree. Installed extension code under `~/.claude/plugins/` and `~/.claude/skills/` joins the default read-exempt prefixes, on the same trust boundary as the plugin itself. That exemption is load-bearing rather than a convenience: 82% of outside-root interpreter script arguments in that sample were plugin scripts a hook or skill launched, so without it the check would prompt on the extension ecosystem and be turned off. Reads only — a write into plugin code still prompts, and a skill symlinked out to another repo resolves to its real location and is deliberately not exempt.

Interpreters are still not guarded commands. Guarding their file arguments in general remains a documented non-goal, and a bare `python3 x.py` resolving inside the root defers to your normal permission rules. The second half of the change withdraws rather than adds: the hook no longer emits `allow` for code it cannot read, meaning an inline `-c`/`-e`, a heredoc, or a stdin body. `allow` speaks for the whole command string and short-circuits the permission settings underneath it. Nothing is newly allowed. See [Allowed read prefixes](https://github.com/karlkfi/claude-workspace-guard/blob/v1.10.0/README.md#allowed-read-prefixes) for the exemption list and [Limitations](https://github.com/karlkfi/claude-workspace-guard/blob/v1.10.0/README.md#limitations) for what an interpreter's own file access still hides.

**Symlinks**

* fix(guard): judge an unlink by the link, not by what it points at by @karlkfi in https://github.com/karlkfi/claude-workspace-guard/pull/159

Removing or renaming a symlink is now judged by the link itself rather than by its target. `rm` of a skill symlinked into a repo you happen to have a worktree of no longer denies as a cross-checkout write. Removing a whole sibling worktree now denies the way removing a file inside it already did. See [Worktree-aware sibling-checkout deny](https://github.com/karlkfi/claude-workspace-guard/blob/v1.10.0/README.md#worktree-aware-sibling-checkout-deny).

[Permission modes](https://github.com/karlkfi/claude-workspace-guard/blob/v1.10.0/docs/permission-modes.md) is new, and it is worth reading before relying on any suppression. Claude Code has six permission modes. `ask` and `deny` both stop a command running unattended, but a *deferred* command simply runs under `auto`, `acceptEdits`, and `bypassPermissions`. So every mechanism that works by declining to vouch — the signalling, shell `-c`, and interpreter suppressions — protects only `manual`, `dontAsk`, and `plan`. That is why the interpreter change checks the script path outright instead of merely withholding `allow`.
