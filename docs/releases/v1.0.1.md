A Claude Code hook that denies shell commands whose exit status is the answer and gets discarded — piped into a filter, backgrounded behind an `echo`, or sequenced before a state change with `;`.

> [!CAUTION]
> **On macOS and Linux, 1.0.0 never fired once.** The launcher `hooks/hooks.json` invokes shipped mode 644, The shell refused it, so the hook exited 126 having written nothing to stdout, and Claude Code reads a `PreToolUse` hook that produced no decision as no objection. Every Bash call proceeded unguarded. If you installed 1.0.0, you have been running without the guard, and the sessions since then were not checked. Windows is unaffected, because `cmd.exe` needs no execute bit.

> [!WARNING]
> **The upgrade does not deliver itself.** Marketplace `autoUpdate` is persisted and nothing consumes it ([anthropics/claude-code#73673](https://github.com/anthropics/claude-code/issues/73673)), so an install stays on the version it started with until you run the commands under **Upgrading** by hand.

This is the first tagged release. 1.0.0 was published to the marketplace but never tagged, so there is no compare link against it.

## Highlights

**The guard actually runs.** `scripts/run-python-hook.cmd` now ships executable, set in the git index rather than the working tree, so it survives packaging. This is the whole release. 1.0.0's logic was never wrong; one missing bit made all of it inert on POSIX. ([#4](https://github.com/karlkfi/claude-pipe-guard/pull/4), fixes [#3](https://github.com/karlkfi/claude-pipe-guard/issues/3))

**The suggested rewrites run when you paste them.** The three denial reasons named `tmp/out.log`. `tmp/` is a build-output name, commonly gitignored and so absent from a fresh checkout or a new worktree. The redirect failed before the gate ran, and the `EXIT=1` that came back could not be told apart from a gate that ran and failed. Reasons are templates now. `with_log_path` fills in this session's scratchpad when it is really on disk, and otherwise a self-contained `mkdir -p tmp && …` form. ([#5](https://github.com/karlkfi/claude-pipe-guard/pull/5), fixes [#2](https://github.com/karlkfi/claude-pipe-guard/issues/2))

**A packaging failure now goes red instead of quiet.** `tests/test_packaging.py` asserts the execute bit on every file the plugin invokes directly, read from the git index because that is what gets packaged. A `packaging-mutation-control` job ships the launcher non-executable and requires both the suite and the launcher check to fail. The 1.0.0 bug has the same shape the plugin exists to catch, a check that reports clean when it never ran, so it gets a check that can fail. ([#1](https://github.com/karlkfi/claude-pipe-guard/pull/1), [#4](https://github.com/karlkfi/claude-pipe-guard/pull/4))

**A multi-line `&&` chain is no longer denied as a `;` sequence.** A backslash-newline continuation was read as a statement separator, so a gate and a mutator joined by `&&` across two lines were denied with a reason telling you to join them with `&&`. Following the advice reproduced the denial, leaving `PIPE_GUARD_OVERRIDE` as the only exit. Continuations are now folded into one logical line before tokenizing, the way POSIX does it. A bare newline between two commands is still a sequence and still denies. ([#9](https://github.com/karlkfi/claude-pipe-guard/pull/9), fixes [#8](https://github.com/karlkfi/claude-pipe-guard/issues/8))

## Upgrading

No configuration changes, no migration. `pipe-guard.json`, `hooks/hooks.json`, and the `PIPE_GUARD_OVERRIDE` escape hatch are unchanged, so a customized registry carries over untouched. The only step is getting the new version onto the machine.

**Claude Code (CLI or IDE extension)** — refreshing the catalog alone does not upgrade an installed plugin, hence the explicit reinstall:

```
/plugin marketplace update pipe-guard
/plugin uninstall pipe-guard@pipe-guard
/plugin install pipe-guard@pipe-guard
```

**Claude Code for Claude Desktop, or headless** — Desktop does not expose the `/plugin` slash commands, but the `claude` CLI shares its plugin state:

```
claude plugin marketplace update pipe-guard
claude plugin update pipe-guard@pipe-guard
```

Then run `/reload-plugins`, or restart Claude Code. Confirm with **Verifying this release** below. On this upgrade in particular, checking is the point: the failure mode being fixed is one that looks exactly like everything working.

## Deprecations

None. Nothing is deprecated, nothing is scheduled for removal, and no rule that fired in 1.0.0 has stopped firing.

## API and surface changes

**Nothing added, nothing removed**, measured rather than assumed. `pipe-guard.json`, `hooks/hooks.json`, `.claude-plugin/plugin.json`, and `.claude-plugin/marketplace.json` are byte-identical to 1.0.0 apart from the version string itself. No gate pattern changed, and `PIPE_GUARD_OVERRIDE` is unchanged.

One verdict does change, in the permissive direction: a gate and a mutator joined by `&&` across a backslash-newline continuation was denied in 1.0.0 and is silent in 1.0.1. Nothing that ran in 1.0.0 is denied in 1.0.1. Since 1.0.0 never fired on POSIX, most installs will meet both behaviors for the first time on this upgrade.

The one behavior change a user will notice is the text of the denial reasons, which now name a writable log path instead of `tmp/`. `decide()` grew a `scratch` parameter, which is internal: the guard is a script invoked by a hook, not a library anything imports.

## Security

No advisory accompanies this release, and there are no dependencies to bump. The guard is stdlib only, by design, so that it cannot fail to run on a machine that skipped a `pip install`.

Worth stating plainly anyway, because it is the shape of the bug fixed here: **this hook fails open.** A `PreToolUse` hook that errors, times out, or writes nothing is read as no objection, and the Bash call proceeds. That is the right default for a guardrail, since a hook that hard-fails makes ordinary work fail, but it means a broken install is indistinguishable from a clean session at the point of use. Treat pipe-guard as a check against mistakes, never as a control against anything adversarial, and verify after every upgrade rather than assuming silence means enforcement.

## Verifying this release

Two checks, in order. The first confirms the file that 1.0.0 got wrong:

```
ls -l "$HOME/.claude/plugins/cache/pipe-guard/pipe-guard/1.0.1/scripts/run-python-hook.cmd"
```

It must report `-rwxr-xr-x`. If it reports `-rw-r--r--`, the guard is installed and inert.

The second confirms the guard decides. Ask Claude to run a piped gate:

```
make check | tail -5
```

That call must come back denied, with a reason naming the filter and, on 1.0.1, naming a log path that exists rather than `tmp/out.log`. If it simply runs, the guard is not enforcing. Then ask it to run the redirect form the denial suggests; that is the documented correct shape and should proceed without comment.
