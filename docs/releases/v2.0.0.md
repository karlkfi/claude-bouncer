**The plugin is renamed from `pipe-guard` to `exit-status-guard`, and two commands it used to deny wrongly now go through.** Your configuration carries over untouched: every 1.x override prefix, filename, and environment variable is still read. The upgrade is four commands and does not deliver itself.

> [!WARNING]
> **Uninstall `pipe-guard@pipe-guard` and its marketplace before installing the new plugin.** The four commands are under **Upgrading**. Claude Code keys an install on the plugin and marketplace names, and both changed, so the new name installs *alongside* the old one instead of replacing it. Leave both in place and two `PreToolUse` hooks run on every Bash call: the 1.x one is still 1.0.1, so it keeps denying the two things this release fixes, while the `/plugin` menu shows 2.0.0 installed.

> [!NOTE]
> **The repository moved too.** `karlkfi/claude-pipe-guard` is now `karlkfi/claude-exit-status-guard`. GitHub redirects the old slug, so an existing marketplace entry keeps resolving, but the upgrade steps register the new one and you should not need the redirect after that.

The guard itself is unchanged in what it looks for: a shell command whose exit status is the answer, discarded by piping it into a filter, backgrounding it behind an `echo`, or sequencing it before a state change with `;`.

[Full changelog](https://github.com/karlkfi/claude-exit-status-guard/compare/v1.0.1...v2.0.0)

## Highlights

**`pipe` named one check out of three, so the plugin is now `exit-status-guard`.** A gate backgrounded behind an `echo` and a gate sequenced with `;` before a state change are both exit-status losses with no pipe in them. The name covered the first check and got stretched over the other two. Every 1.x spelling still works, undocumented and not scheduled for removal. The table under **What still works** is the list. The rename reaches this repo's docs and nothing in your `.claude/` directory or your CLAUDE.md, which are what tell a session which prefix to type. ([#18](https://github.com/karlkfi/claude-exit-status-guard/pull/18), closes [#16](https://github.com/karlkfi/claude-pipe-guard/issues/16))

**Reading a tag is no longer denied as publishing one.** The registry lists commands whose exit status is the answer as `gates`, and state-changing commands as `mutators`. `git tag` was in both, because `git tag -a` publishes and `git tag -l` reads, and the sequencing rule picked the roles backwards: it read `git tag -a` as the gate and `git tag -l` as the state change. So `make check; git tag` was denied on the grounds that the tag would be published even if the check failed. Reading a tag changes nothing, so that denial had no correct rewrite. The rule's suggestion is to join the two with `&&` so the first gates the second, and here there was nothing to gate. Gate and mutator classification now runs the same two screens, so an entry in the registry's `exempt` list and a capability probe (`--version`, `--help`, `--dry-run`) both count in either role. That also fixed `make check; git push --help` and `make check; kubectl apply --dry-run=client`, which were denied for the same reason: the classifier that recognized a probe on the gate side did not run on the state-change side. ([#13](https://github.com/karlkfi/claude-exit-status-guard/pull/13), fixes [#11](https://github.com/karlkfi/claude-pipe-guard/issues/11))

**A read is recognized by its shape now, instead of by a list of flags.** The fix above named `git tag`'s listing flags one at a time, and that list was shorter than git's: `--sort`, `--column`, `-i`, `--omit-empty`, and `--format` were all missing, so `git tag --sort=-v:refname | head -5` was still denied as a piped gate. `git stash list` and `git worktree list` had no read entry at all. Two structural splits replace the enumeration. A read verb in the subcommand path (`list`, `ls`, `show`, `view`, `history`) is now recognized for every registered gate, the way `--version` and `--help` already were. Where no verb separates a read form from a write form, only the *write* forms are registered and everything else falls through as a read, on the reasoning that new listing flags are the side that keeps arriving. `kubectl rollout status` is deliberately not treated as a read: it waits for a condition and reports the answer as an exit code, so a pipe really does swallow it. ([#20](https://github.com/karlkfi/claude-exit-status-guard/pull/20), fixes [#19](https://github.com/karlkfi/claude-pipe-guard/issues/19))

## Upgrading

**Claude Code (CLI or IDE extension)** — four commands, in this order:

```
/plugin uninstall pipe-guard@pipe-guard
/plugin marketplace remove pipe-guard
/plugin marketplace add karlkfi/claude-exit-status-guard
/plugin install exit-status-guard@exit-status-guard
```

Then run `/reload-plugins`, or restart Claude Code.

**Claude Code for Claude Desktop, or headless** — Desktop does not expose the `/plugin` slash commands, but the `claude` CLI shares its plugin state:

```bash
claude plugin uninstall pipe-guard@pipe-guard
claude plugin marketplace remove pipe-guard
claude plugin marketplace add karlkfi/claude-exit-status-guard
claude plugin install exit-status-guard@exit-status-guard
```

Then restart Claude Code, since the hook is registered at startup.

**No configuration edits are needed, and renaming your own files is optional.** The one thing worth knowing: with both `.claude/pipe-guard.json` and `.claude/exit-status-guard.json` present, the 1.x file is ignored rather than combined, so delete it once you have moved its patterns across. The [friction report](https://github.com/karlkfi/claude-exit-status-guard#friction-report) reads both labels, so history from before the rename still shows up.

**The upgrade does not deliver itself.** Marketplace `autoUpdate` is persisted and nothing consumes it ([anthropics/claude-code#73673](https://github.com/anthropics/claude-code/issues/73673)), so an install stays on the version it started with until you run the commands above by hand.

### Reinstall even if you think you are current

A marketplace install is a clone of the default branch rather than a checkout of a tag: the local marketplace clone holds zero tags and sits on `main`, and the version directory takes its name from `plugin.json`. So an install picks up whatever was on `main` that day, under whatever version string `plugin.json` carried.

That matters once here. Two repo-state checks, a `git push` onto a base that has moved into this branch's own line ranges and a `gh pr create` overlapping an open PR, were added in [#15](https://github.com/karlkfi/claude-exit-status-guard/pull/15) and taken back out in [#17](https://github.com/karlkfi/claude-exit-status-guard/pull/17). Neither is about exit status, and no tagged release ever carried them, but an install taken while those commits were on `main` has them, filed under version `1.0.1`. Following the steps above replaces it. Both checks live in [claude-branch-guard](https://github.com/karlkfi/claude-branch-guard) and [claude-pr-sentinel](https://github.com/karlkfi/claude-pr-sentinel) now, which already parse those two commands to the depth the checks need.

## Security

No advisory accompanies this release, and there are no dependencies to bump. The guard is stdlib only, by design, so that it cannot fail to run on a machine that skipped a `pip install`.

Worth stating plainly, because a rename gives it a new way to bite: **this hook fails open.** A `PreToolUse` hook that errors, times out, or writes nothing is read as no objection, and the Bash call proceeds. That is the right default for a guardrail, since a hook that hard-fails makes ordinary work fail, but it means a broken install is indistinguishable from a clean session at the point of use. An upgrade that half-lands has two shapes, and only one of them is loud: leaving the old plugin installed keeps denying things and is hard to miss, while ending up with neither plugin enabled after the restart looks exactly like a quiet, well-behaved session. Treat exit-status-guard as a check against mistakes, never as a control against anything adversarial, and verify after every upgrade rather than assuming silence means enforcement.

## Verifying this release

Two checks in a session, then one on disk. Start with the session, because it is the only one that observes the hook actually deciding.

**1. The guard denies.** Ask Claude to run a piped gate:

```
make check | tail -5
```

That must come back denied, with a reason naming the filter and offering `EXIT_STATUS_GUARD_OVERRIDE=<reason>` as the escape hatch. Your project does not need a `make check` target for this: the guard classifies the command before anything runs it. If the call simply proceeds, no version of the guard is enforcing. Then ask for the redirect form the denial suggests, which should run without comment.

**2. It is the 2.0.0 guard deciding, not a leftover 1.x one.** Ask Claude to run:

```
git tag --sort=-v:refname | head -5
```

1.0.1 denied this and 2.0.0 lets it through, so a denial here means a `pipe-guard` hook is still registered and still running, whatever the `/plugin` menu says. Go back to **Upgrading** and remove it. A denial naming `PIPE_GUARD_OVERRIDE=` rather than `EXIT_STATUS_GUARD_OVERRIDE=` names the culprit outright.

**3. The launcher shipped executable.** This is the file 1.0.0 got wrong, and the mistake was silent:

```
ls -l "$HOME/.claude/plugins/cache/exit-status-guard/exit-status-guard/2.0.0/scripts/run-python-hook.cmd"
```

It must report `-rwxr-xr-x`. If it reports `-rw-r--r--`, the guard is installed and inert. If the path does not exist at all, the install did not land under 2.0.0 — check the version in the `/plugin` menu.
